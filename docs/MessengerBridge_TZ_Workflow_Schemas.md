# ТЗ: Механика схем Workflow — доработка bridge по образцу fbp-engine

Документ отвечает на issue [#236](https://github.com/rumaster/bridge/issues/236) и является
**техническим заданием**, а не изменением кода: в рамках issue #236 код и сам мастер-документ
[`docs/MessengerBridge_TZ.md`](./MessengerBridge_TZ.md) не редактируются. Здесь зафиксированы
(а) факты о первоисточнике и о текущем состоянии bridge, установленные прямым чтением кода,
(б) целевая модель и разрешение противоречий с действующим ТЗ, (в) пошаговый план реализации для
последующих issue/PR, (г) точечные предложения правок к `docs/MessengerBridge_TZ.md` и
`docs/plan/services/07-fbp-engine.md` / `11-saas-administration.md`, которые должны быть внесены
**отдельным** PR после согласования (по аналогии с тем, как `docs/MessengerBridge_TZ_Review.md`
предшествовал коммиту `f0b0c47 "docs: применены предложения ревью к ТЗ MessengerBridge"`).

Все находки снабжены уровнем важности, как в `MessengerBridge_TZ_Review.md`:

- 🔴 **Блокер** — активная брешь безопасности или прямое противоречие с требованием issue.
- 🟠 **Существенно** — расхождение с целевой механикой, которое нужно закрыть до реализации issue.
- 🟡 **Замечание** — уточнение/будущий этап, не блокирующий текущий MVP.

## 1. Контекст issue #236

Дословное требование (issue #236, без комментариев, без меток, состояние — open):

> Здесь должен был быть адаптированный fbp_engine. Рассмотри первоисточник (репозиторий
> fbp_engine или tg_games) который должен был быть адаптирован. Напиши детальное пошаговое ТЗ для
> исправления bridge. **Не исправляй код.** Сейчас как я понял надо произвольно добавлять схемы, но
> это не верно. Должны быть определённые в коде схемы для каждого определённого кейса, эти схемы
> добавляются сидом и их нельзя удалить или добавить другие, можно редактировать, должен быть
> драфт и рабочая версия. Драфт версия с автосохранением. Можно добавлять в БД субсхемы (при
> необходимости для разных контекстов), в схему можно добавлять узел со ссылкой на субсхему. узел
> субсхемы не имеет тела вместо него ссылка. узел transform не имеет bodyGraph, имеет произвольный
> js код. Узлы имеют порты и соединяются перетягиванием указателем мыши, есть импорт и экспорт
> схем. Все организации сейчас используют одну (дефолтную версию схемы), но позже должна быть
> возможность у организаций иметь свою версию (для каждой организации будет сделана их копия
> которую они смогут редактировать или сбросить до дефолтной). Все механики редактора схем должны
> быть реализованы в bridge по подобию fbp_engine.

Из текста выделяется 8 конкретных требований к целевой механике (пронумерованы для сквозной
трассируемости далее по документу):

| № | Требование |
|---|---|
| R1 | Схемы для типовых кейсов определены **в коде** и заводятся **сидом**; произвольное создание/удаление схемы запрещено, редактирование — разрешено. |
| R2 | Версия схемы существует в виде **драфта** (с автосохранением) и **рабочей** (опубликованной) версии. |
| R3 | В БД можно заводить **субсхемы** для разных контекстов. |
| R4 | Узел-ссылка на субсхему **не содержит тела** — только ссылку. |
| R5 | Узел `transform` не имеет `bodyGraph`, содержит **произвольный JS-код**. |
| R6 | Узлы имеют **порты** и соединяются **перетаскиванием мышью**. |
| R7 | Есть **импорт и экспорт** схем. |
| R8 | Сейчас одна дефолтная версия схемы на все организации; в будущем — **своя копия схемы на организацию** (редактируемая или сбрасываемая к дефолтной). |

## 2. Первоисточник: важная находка перед чтением остального документа

**`rumaster/fbp-engine` и `rumaster/tg-games` — не два разных проекта, а один и тот же код на двух
срезах времени.** Оба репозитория клонированы и сверены построчно:

- `package.json` в обоих — `"name": "tg-games"` (fbp-engine на версии `0.9.52`, tg-games —
  `0.9.53`, на один шаг новее).
- `README.md` в обоих репозиториях побайтово идентичен и начинается с `# tg-games — Telegram LLM
  RPG Bot`, а не с описания generic FBP-движка.
- История `rumaster/fbp-engine` — два коммита, первый называется дословно **«Initial commit:
  FBP-Engine, currently embedded in text adventure RPG project»** — само сообщение коммита
  признаёт, что это точечный срез (snapshot) кодовой базы `tg-games`, а не выделенная в отдельную
  библиотеку generic-система.
- Публичное описание репозитория (`gh repo view rumaster/fbp-engine`) — «Flow-based Programming
  Engine» — расходится с фактическим содержимым (Telegram RPG-бот с встроенным движком графов).

Следствие для этого ТЗ: bridge адаптирует не отдельную переиспользуемую FBP-библиотеку, а
**встроенный движок схем одного конкретного приложения** («Schema Engine» проекта tg-games),
изначально спроектированный для single-installation Telegram-бота с несколькими «играми», а не для
multi-tenant SaaS. Это объясняет, почему часть механик первоисточника (см. §2.1) переносится
дословно, а часть (в первую очередь — организации/tenants, §2.1 п.8, и предположение о единственном
администраторе) должна быть спроектирована для bridge заново, лишь по аналогии.

### 2.1 Механика первоисточника (факты, `packages/schema-contract`, `packages/core/src/engine/schemaEngine.ts`, `apps/admin-api`, `apps/admin-web`, здесь и далее — файлы `tg-games`, идентичные `fbp-engine`)

1. **Модель графа.** Источник истины типов — пакет `@tg-games/schema-contract`
   (`packages/schema-contract/index.d.ts`), общий для `core`/`admin-api`/`admin-web`:
   ```ts
   interface NodeDefinition { id: string; type: NodeType; position: {x:number;y:number}; config: Record<string, unknown>; label?: string }
   interface EdgeDefinition { id: string; from: string; fromPort: string; to: string; toPort: string }
   interface SchemaGraph { version: 1; schemaType?: SchemaType; subSchemaClass?: SubSchemaClass; slug: string; gameId?: string; nodes: NodeDefinition[]; edges: EdgeDefinition[]; variables: Record<string, unknown> }
   ```
   Граф хранится в Postgres целиком как `JSONB` (`schemas.graph_json`), а не разложен на
   реляционные таблицы узлов/рёбер.
2. **Субсхема — узел без тела, со ссылкой.** `resolveSubSchemaGraph()`
   (`schemaEngine.ts:1167-1195`) читает либо встроенный `node.config.graph`, либо
   `node.config.schemaSlug` (строковая ссылка) и в этом случае вызывает инжектированный колбэк
   `ctx.resolveSubSchema(slug)` → поиск активной схемы по `slug` в таблице `schemas`
   (`getActiveSchema`, `db/repositories/schemas.ts:136-152`). Исполнение создаёт изолированный
   дочерний контекст (свои `variables`/`nodeOutputs`), общий `state` пробрасывается обратно.
   Граничные порты узла берутся из `start`/`end` узлов выбранной субсхемы
   (`subSchemaNodePorts`, `schema-contract/index.mjs:474-484`). Субсхемы типизированы полем
   `subSchemaClass: 'game' | 'support' | 'common'`, ограничивающим совместимость.
3. **Transform — произвольный JS в песочнице `node:vm`, НЕ отдельный процесс/isolate.**
   `executeTransform()` (`schemaEngine.ts:1108-1131`) берёт `node.config.code` и исполняет через
   `runInSandbox()` (`schemaEngine.ts:1513-1540`):
   ```js
   function runInSandbox(source, sandbox) {
     if (FORBIDDEN_EXPRESSION_TOKENS.test(source)) throw new Error('Выражение содержит запрещённый доступ к окружению');
     const context = vm.createContext({ ...sandbox });
     const script = new vm.Script(source);
     return script.runInContext(context, { timeout: SANDBOX_TIMEOUT_MS }); // 1000 мс
   }
   ```
   Защита эшелонирована, но целиком внутри одного процесса Node.js: (1) regex
   `FORBIDDEN_EXPRESSION_TOKENS` блокирует токены `process|globalThis|global|window|document|
   Function|eval|require|import|constructor|prototype|__proto__|this`; (2) `vm.createContext`
   не даёт Node-глобалей; (3) `timeout: 1000` прерывает бесконечный цикл силами V8. Тот же
   `runInSandbox` используется и для `condition`-выражений, и для `loop.exitExpression` — то есть
   произвольный JS в источнике допускается не только в Transform.
4. **Порты — типизированы и явно поименованы в самом ребре.** `PortDefinition = {id, label, type,
   direction}`, `PortType = exec | string | number | boolean | object | string_array |
   object_array | expertise | memory | any`. `EdgeDefinition` хранит `fromPort`/`toPort` (не только
   `from`/`to` узла). Совместимость — `arePortTypesCompatible()` (`schema-contract/index.mjs:
   393-396`): `exec` соединяется только с `exec`, остальные — при равенстве типов либо через `any`.
5. **Drag-and-drop — React Flow (`@xyflow/react` v12), не самописный canvas.** Компонент
   `SchemasView.tsx` рендерит `<ReactFlow nodes edges onConnect={handleConnect}
   isValidConnection={isValidConnection} .../>`; `isValidConnection` вызывает
   `canConnectGraphPorts()`, которая проверяет типовую совместимость **прямо во время
   перетаскивания линии**, до отпускания мыши. Добавление узла из палитры — обычный HTML5 DnD
   (`dataTransfer`) поверх `screenToFlowPosition()` (штатный API React Flow) — своей DnD-механики
   поверх готовой библиотеки не изобретается.
6. **Импорт/экспорт — JSON через REST, с двойной валидацией.** `GET /api/schemas/export` отдаёт
   только активные схемы; `POST /api/schemas/import` валидирует вход дважды: (а) Zod-схема формы
   запроса, (б) структурная/семантическая проверка графа `normalizeSchemaGraph()` →
   `validateSchemaGraphContract()` из общего `schema-contract`. Импорт делает upsert по `slug` с
   diff-отчётом «создано/обновлено/без изменений» перед подтверждением пользователем.
7. **Draft/working — отдельная колонка в той же таблице, а не отдельная сущность.**
   `schemas.draft_graph_json JSONB NULL` рядом с рабочим `schemas.graph_json JSONB NOT NULL`.
   API: `GET/PATCH /api/schemas/:slug/draft`, `POST /api/schemas/:slug/promote` (черновик →
   рабочая, с архивацией предыдущей рабочей версии в `schema_history`), `DELETE
   /api/schemas/:slug/draft` (сброс черновика к рабочей). Автосохранение на фронтенде —
   **событийное**, не по таймеру: при размонтировании редактора, при переключении схемы/области и
   перед тест-прогоном (`autoSaveDraft()`, `SchemasView.tsx:1314-1331`). Тест-прогон схемы всегда
   идёт по черновику, если он есть.
8. **Мультиарендности НЕТ.** `grep -rni "tenant|organization"` по всему исходнику — ноль
   совпадений. Единственная ось кастомизации — `schemas.game_id` (nullable FK на
   `game_manifests`): `game_id IS NULL` — глобальная схема-дефолт, `game_id = 'X'` — override для
   конкретной игры; резолвинг всегда «игра → глобальный fallback» одним запросом
   (`ORDER BY CASE WHEN game_id = $2 THEN 0 ELSE 1 END`). Это архитектурно **ближайший аналог**
   будущей задачи R8 (организация вместо игры), но требование issue «своя копия на организацию,
   которую можно редактировать или сбросить к дефолтной» **шире**, чем просто fallback: нужен явный
   **fork** (copy-on-write) и явный **reset**, которых в источнике нет как отдельного действия —
   там per-game строка либо существует, либо резолвится в глобальную без явного «сброса».
9. **Общая архитектура.** TypeScript/Node.js ≥20, npm workspaces: `packages/core` (движок +
   Postgres-репозитории, синхронно встроен в `apps/bot` — исполнение графа происходит **в
   процессе бота**, не отдельным сервисом), `packages/schema-contract` (общий источник типов),
   `apps/admin-api` (NestJS 11 + сырой SQL + Zod), `apps/admin-web` (Vite + React 19 + React Flow).
   Связь слоёв — только REST, без WebSocket/реалтайм-синхронизации редакторов. Docker-образ бота
   явно не включает `admin-api`/`admin-web` — админка разворачивается отдельно.

### 2.2 Что из механики источника **не** переносится в bridge

Домен-специфичные типы узлов первоисточника (`llm_request, knowledge_query, graph_rag,
game_memory_read/write, manifest, game_state_read/write, support_history_read, game_history_read,
media_generate` и т.д. — итого 23 типа) — это узлы конкретно для Telegram RPG-игр и не
переносятся: действующий каталог bridge (`FBP_NODE_TYPES`, 6 kebab-case типов) уже сознательно
нейтрален от домена согласно §13.13 п.1 мастер-ТЗ, и это свойство нужно сохранить. Из источника
перенимаются **инфраструктурные механики** (R1–R8), а не конкретный список типов узлов.

## 3. Инвентаризация текущего состояния bridge

Установлено прямым чтением `services/fbp-engine/src/**`, `services/backend/src/modules/workflow/**`,
`apps/saas-admin/src/**`, `db/migrations/*.sql`, `db/seeds/000001_m0_seed.ts`,
`packages/contracts/**`.

### 3.1 🔴 Backend не валидирует схему при сохранении версии — источник «произвольного добавления схем»

`WorkflowService.createVersion()` (`services/backend/src/modules/workflow/workflow.service.ts:
65-122`) выполняет
```sql
INSERT INTO workflow_versions (id, organization_id, workflow_id, version_no, schema, created_by, created_at)
VALUES ($1, $2, $3, $4, $5::jsonb, $6, now())
```
без единого вызова `validateWorkflowSchema`/движка. Единственные проверки на всём пути —
`@IsObject()` в `CreateWorkflowVersionDto.schema` (DTO) и `CHECK (jsonb_typeof(schema)='object')` на
уровне БД (`db/migrations/20260703140000000_m3_schema.sql:40`). Реальная строгая валидация
(`services/fbp-engine/src/schema/validate-workflow.ts` — DAG, whitelist типов узлов, whitelist
Transform-операций) существует, но вызывается только (а) в in-memory reference-модели движка и
(б) **при старте инстанса**, никогда при сохранении версии в реальном коде. Ровно это и означает
фраза issue «надо произвольно добавлять схемы, но это не верно» — технически сегодня можно записать
в `workflow_versions.schema` любой JSON-объект.

### 3.2 🔴 Словарь типов узлов движка и словарь UI/Backend DTO почти не пересекаются

Движок (контракт C5, `packages/contracts/src/c5.ts:86-93`): `FBP_NODE_TYPES = ["backend-api",
"llm", "knowledge-base-search", "branch", "transform", "wait-event"]` — 6 типов, kebab-case,
зафиксировано тестом `tests/contract/c5-fbp-node-catalog.test.ts`. UI/Backend DTO
(`apps/saas-admin/src/api/client/types.ts:215-222`, `shared/workflow.ts:16-24`):
`"backend_api_call" | "llm_call" | "kb_search" | "branch" | "transform" | "wait_event" |
"sub_schema"` — 7 типов, snake_case. Совпадают только `branch` и `transform`. Транслирующего слоя
между словарями нигде нет. Практическое следствие: схема, собранная реальным UI, при старте
инстанса на реальном движке была бы отвергнута с «Неизвестный тип узла» почти для каждого узла —
только это уже сегодня *не* проверяется (см. §3.1), поэтому расхождение молча копится в БД.

### 3.3 🔴 Нет seed / code-defined схем — ни одного пути появления Workflow в реальном окружении

`db/seeds/000001_m0_seed.ts` сидирует только `roles/organizations/users/user_roles`. Ни одной
строки `workflows`/`workflow_versions` не сидируется нигде (`grep "INSERT INTO workflow"` по всем
`db/migrations/*.sql` — ноль совпадений). При этом создать Workflow через API тоже нельзя: маршруты
`workflow.controller.ts` — `listWorkflows, listVersions, createVersion, updateWorkflow,
listInstances, getInstance` — ни одного `POST /workflows` (создание) или `DELETE`. То есть
сегодня Workflow не может появиться в реальном окружении вообще никаким штатным путём — не «можно
создать произвольно», а «нельзя создать вовсе, и нет декларативного механизма тоже». Это
частично соответствует духу R1 («нельзя произвольно создать»), но полностью противоречит второй
половине R1 («схемы для кейсов определены в коде и добавляются сидом»).

### 3.4 🟠 `sub_schema` хранит собственную копию тела, а не ссылку — прямо противоположно R4

`createWorkflowNode("sub_schema", …)` (`apps/saas-admin/src/shared/workflow.ts:107-131`) кладёт в
`config` одновременно `schema_id: ""` (свободная строка без связи с БД — таблицы субсхем нет
вообще) **и** сразу полноценный вложенный `bodyGraph` (`createWorkflowBodyGraph`, строки 133-146).
Мок-фикстура `wfv-support-2` (`apps/saas-admin/src/api/mocks/fixtures.ts:281-347`) подтверждает то
же на уровне тестовых данных. В БД нет `sub_schemas`/аналога (`grep "sub_schema|subschema"` по
`db/migrations/*.sql` — ноль совпадений).

### 3.5 🟠 Transform — безопасный декларативный evaluator, не произвольный JS (прямое противоречие с R5 и текущим ТЗ)

`services/fbp-engine/src/transform/evaluator.ts` + `operations.ts` + `validate-expression.ts`
реализуют whitelist AST-выражений (`lit/input/var/get/if/map/filter/reduce` + ~50 чистых функций),
без `eval`/`Function`/сети/ФС «по построению». Это ровно то, что требуют действующие §13.4, §13.12
и §13.13 п.5 мастер-ТЗ («Transform не должен исполнять произвольный код … явно запрещены `eval`,
`new Function`, `node:vm`, `isolated-vm`, WASM»). Issue R5 требует обратного — это единственное
**прямое архитектурное противоречие** между issue и действующим ТЗ, разрешение — в §5.1.

### 3.6 🟠 Draft — только React-состояние в браузере, ничего не персистится (частично противоречит R2)

UI-текст `«Черновик сохранён локально.»` (`apps/saas-admin/test/m3-workflow.test.tsx:146`)
подтверждает буквально: черновик существует только в памяти вкладки браузера и теряется при
обновлении страницы. Бэкенд не имеет понятия «черновик» — есть только неизменяемые опубликованные
`workflow_versions`. Автосохранение (R2) технически невозможно без серверного хранения.

### 3.7 🟡 Нет модели портов — связи описаны парой `{from, to}` на уровне узла

Явной сущности «порт» (именованный вход/выход со своим типом данных) в коде bridge нет — ни в

drag-and-drop узлов **уже реализованы** в `WorkflowPage.tsx` (нативный HTML5 DnD + сырой SVG для
линий), но без типизации портов и без проверки совместимости в момент перетаскивания — то есть R6
выполнено частично (drag-and-drop есть), типизированные порты (R6, по аналогии с источником) — нет.

### 3.8 🟡 Импорт/экспорт схем не реализован

В `WorkflowPage.tsx` (1486 строк, прочитан полностью) нет функций сохранения/загрузки JSON-файла —
только внутреннее клонирование состояния. R7 не реализовано.

### 3.9 🟡 Мультиорганизационность схем — не реализована, но БД уже готова

уже сегодня — не хватает (а) механизма клонирования дефолтной схемы на организацию и (б) UI/API

## 5. Разрешение архитектурных противоречий с действующим мастер-ТЗ

### 5.1 Transform Node: произвольный JS (R5) против запрета произвольного кода (§13.4, §13.12, §13.13 п.5)

Действующий текст мастер-ТЗ (§13.12): узел не должен исполнять произвольный код; явно запрещены
`eval`, `new Function`, `node:vm`, `isolated-vm`, WASM. Issue прямо требует обратного: «узел
transform... имеет произвольный js код». Источник (`tg-games`/`fbp-engine`) решает это через
`node:vm` с таймаутом 1000 мс и regex-блокировкой опасных токенов.

**Это решение источника нельзя копировать дословно для bridge.** Официальная документация Node.js
прямо предупреждает: *«The vm module is not a security mechanism. Do not use it to run untrusted
code»* — `vm.createContext` не изолирует память процесса, не защищает от side-channel/DoS через
разделяемый event loop и не ограничивает CPU/память на уровне ОС. Источник — single-installation
Telegram-бот с одним оператором и доверенным контентом одной команды; bridge — multi-tenant SaaS,
где Transform-код потенциально пишут разные организации, и утечка/DoS одной организации не должны
задевать другие. Разница контекста требует **более сильной**, а не аналогичной изоляции.

**Предлагаемое решение для bridge** (реализует R5, снимает противоречие с §13.12):

- Исполнение произвольного кода Transform выносится в **отдельный процесс-исполнитель**
  (worker pool на `isolated-vm`, а не `node:vm`): каждый вызов — новый V8 Isolate с собственной
  кучей, жёстким лимитом памяти (например 16 МБ) и CPU-time (например 200 мс), без доступа к
  Node-глобалям (`process`, `require`, сеть, ФС) — они просто не прокидываются в контекст.
- Дополнительный барьер — запуск воркер-пула в отдельном OS-процессе/контейнере без сетевого
  namespace и без переменных окружения организации (secrets), с per-organization квотой на число
  параллельных/за период вызовов (защита от DoS через параллельный спам).
- Явно фиксируется остаточный риск (side-channel атаки уровня V8/CPU — не решается полностью ни
  `isolated-vm`, ни `node:vm`) и приемлемость этого риска для MVP указывается отдельным решением
  на CP (согласование), а не тихо принимается по умолчанию.
- Безопасный декларативный evaluator (`transform/evaluator.ts`) **не удаляется** — становится
  вторым, более дешёвым режимом Transform-узла («safe expression» vs «custom code»), либо
  сохраняется как исполнитель для `condition`/`branch`-выражений, где полный JS избыточен.
- Требуется точечная правка §13.4/§13.12/§13.13 п.5 мастер-ТЗ (см. §8) — это единственное место
  во всём документе, где нужно менять именно запрет, а не дополнять его.

### 5.2 Draft-версия (R2) против «версии неизменяемы, публикуются сразу» (§13.10)

§13.10 описывает только immutable опубликованные версии с version pinning запущенных инстансов —
подходящая и обязательная модель для *исполнения*, но не описывает состояние *редактирования до
публикации*. Issue требует явного черновика с автосохранением. Противоречия по сути нет — черновик
логически предшествует версии и не участвует в pinning инстансов; требуется **дополнение**, а не
изменение §13.10:

- Черновик хранится как отдельное поле состояния Workflow (например `workflows.draft_schema
  JSONB NULL`, по аналогии с `schemas.draft_graph_json` источника), не как `workflow_versions`-
  строка — черновики не версионируются и не участвуют в pinning.
- «Публикация» черновика создаёт новую immutable `workflow_versions`-строку с `version_no + 1`
  (используя уже существующий механизм bridge) и обнуляет `draft_schema`.
- Автосохранение — событийное (как в источнике: при уходе из редактора/переключении
  Workflow/перед тест-прогоном), не периодическое по таймеру — проще и меньше нагрузки на API.

### 5.3 Импорт/экспорт (R7) против «после MVP» (§13.11, §16.7)

§13.11 и §16.7 сегодня относят импорт/экспорт и «библиотеку пользовательских узлов» к пост-MVP.
Issue включает импорт/экспорт в список обязательных механик прямо сейчас. Противоречия по духу
нет — §13.11 лишь откладывал приоритет, не запрещал функциональность. Требуется **снять
пометку «после MVP»** для импорта/экспорта конкретно (см. §8), сохранив её для прочих пунктов
раздела (совместное редактирование, произвольная библиотека пользовательских узлов — этого issue
не просит).

### 5.4 Мультиарендность схем (R8) — новый раздел, не значился в мастер-ТЗ

§16.7 сегодня описывает только «выбор активной версии» без per-organization копий. Issue явно
относит эту часть к будущему («позже»). Требуется не изменение, а **добавление** нового пункта в
§16.7 мастер-ТЗ, помечающего этот функционал как отдельный этап после базового MVP-исправления
(Этап 7 в §7 ниже) — без изменения текущего MVP-объёма остальных разделов.

## 6. Термины: соответствие первоисточник ↔ bridge

| Первоисточник (`schema-contract`) | bridge (мастер-ТЗ §4.16-4.17) | Комментарий |
|---|---|---|
| `SchemaGraph` | Workflow (схема, `workflow_versions.schema`) | В bridge уже версионируется отдельной immutable-таблицей — сильнее источника. |
| `NodeDefinition` | Node | Тип, конфиг, позиция — совпадает по духу. |
| `EdgeDefinition {from, fromPort, to, toPort}` | Connection `{from, to}` | В bridge нет портов — целевая модель добавляет `fromPort/toPort`. |
| `PortDefinition {id, label, type, direction}` | — (отсутствует) | Вводится заново по образцу источника (§4 п.7). |
| узел `sub_schema` + `schemaSlug` | узел `sub_schema` + `schema_id` (сейчас — embedded `bodyGraph`) | Целевая модель: убрать `bodyGraph`, оставить только ссылку. |
| `schemas.draft_graph_json` | — (черновик только в React-состоянии) | Вводится `workflows.draft_schema` по аналогии (§5.2). |
| `schemas.game_id` (per-game override) | `workflows.organization_id` (уже NOT NULL) | Аналогичный по духу, но требует явного fork/reset, а не только fallback (§5.4). |
| `node:vm` в `runInSandbox` | безопасный AST-evaluator (`transform/evaluator.ts`) | Целевая модель — `isolated-vm`/выделенный процесс, не прямое копирование (§5.1). |

  `POST /workflows/{id}/import` (только как **новая версия/черновик** существующего Workflow —
  не создание нового Workflow, что сохраняет ограничение Этапа 2).
- Двойная валидация на импорт: (а) форма JSON (аналог Zod-проверки источника — здесь
  class-validator DTO), (б) `validateWorkflowSchema` из Этапа 0.
- Frontend: кнопки «Экспортировать» / «Импортировать» в `WorkflowPage.tsx`, с предварительным
  diff-подтверждением (что изменится) перед сохранением импортированной версии/черновика.

### Этап 7 — Per-organization копии схемы (закрывает §3.9, реализует R8; отдельный этап «после MVP-исправления»)

- Механизм fork: при первом обращении организации к дефолтному Workflow — копирование текущей
  активной версии в новую строку `workflows`/`workflow_versions` с `organization_id` этой
  организации (используя уже готовую RLS-модель, ничего не меняя в структуре БД).
- Механизм reset: явное действие `POST /workflows/{id}:reset-to-default`, которое **не удаляет**
  историю версий организации, а публикует новую версию с содержимым текущего дефолта (сохраняя
  append-only принцип, уже принятый в §13.10 мастер-ТЗ).
- Обновить §16.7 мастер-ТЗ новым пунктом об административном действии «Сбросить к дефолтной схеме»
  (см. §8 ниже).

## 11. Риски и открытые вопросы

- 🟡 **Выбор технологии песочницы Transform (Этап 5)** — `isolated-vm` добавляет нативную
  зависимость (компиляция под платформу деплоя); альтернатива — вынести исполнение в отдельный
  под/сервис-исполнитель (ещё сильнее изолирует ценой сетевой задержки и сложности деплоя). Требует
  решения на согласовании (CP), а не в рамках этого ТЗ.
  - **Обновление на 2026-07-07 (что изменилось с версии 1.0 этого документа).** Технологический
    ландшафт с момента первичного анализа не даёт оснований менять рекомендацию: `isolated-vm`
    остаётся поддерживаемым (последний релиз в реестре пакетов — начало 2025 года, совместим с
    актуальными LTS-версиями Node.js 20/22), а описанный в §5.1 подход «V8 isolate + жёсткие
    лимиты CPU/памяти + отдельный worker-пул без сети/ФС» по-прежнему соответствует практике
    изоляции недоверенного кода в Node.js-экосистеме. Отдельный под/контейнер-исполнитель
    (gVisor/Firecracker-класс) остаётся более сильной, но существенно более дорогой по
    инфраструктуре альтернативой. Открытый вопрос — что именно из двух вариантов согласовать на
    CP — не закрывается этим обновлением и осознанно оставлен архитектурному согласованию, а не
    предрешается задним числом в документе-ТЗ.
- 🟡 **Регистр типов узлов (Этап 1)** — переход UI/DTO на kebab-case (или движка на snake_case)
  — это breaking change контракта C5, затрагивает существующие тесты `c5-fbp-node-catalog.test.ts`
  и моковые фикстуры; нужно явно выбрать направление миграции и период сосуществования (если
  нужна обратная совместимость с уже опубликованными схемами).
- 🟡 **Формат хранения субсхем (Этап 4)** — отдельная таблица `workflow_subschemas` vs. переиспользование
  `workflows` с флагом-классификатором; выбор влияет на то, есть ли у субсхемы собственные
  инстансы/логи исполнения (по факту не нужны — субсхема исполняется только как часть родительского
  инстанса).
- 🟡 **Период сосуществования двух режимов Transform** (`expression` vs `code`, Этап 5) — не
  определено, нужно ли ограничивать режим `code` какой-то ролью/флагом организации на переходный
  период, или он доступен всем сразу.
- 🟡 Данное ТЗ **не пересматривает** остальные результаты `docs/MessengerBridge_TZ_Review.md` —
  оно сфокусировано исключительно на механике Workflow-схем (issue #236) и не затрагивает
  найденные там противоречия по другим подсистемам.
