# Четвёртая серия промптов для параллельного выполнения этапа M3

Документ отвечает на issue #91: анализирует план, фиксирует порядок выполнения и
даёт четвёртую серию промптов для параллельного прохождения четвёртого этапа. Он
продолжает первую серию
[`parallel-stage-1-prompts.md`](./parallel-stage-1-prompts.md) (этап M0), вторую
серию [`parallel-stage-2-prompts.md`](./parallel-stage-2-prompts.md) (этап M1) и
третью серию [`parallel-stage-3-prompts.md`](./parallel-stage-3-prompts.md)
(этап M2).

Под «четвёртым этапом» здесь понимается **M3 — Программируемость** из
[`docs/plan/README.md`](./README.md): администратор описывает автоматизацию как
**Workflow** в визуальном редакторе, Workflow меняет данные **только** через узел
вызова Backend API, а конфигурацию платформы можно задать на естественном языке
через **AI Onboarding**. Этап замыкается на **двух** точках согласования: **CP-4**
— «Workflow вызывает Backend API» (SVC-API(fbp-integration) + SVC-FBP +
SVC-DATA(`workflow_*`), заморозка **C5**, e2e «Workflow вызывает Backend API») и
**CP-5** — визуальный редактор Workflow + AI Onboarding (SVC-ADMIN + SVC-FBP +
SVC-AI + SVC-API, совместная стабилизация **C3 + C4 + C5**, e2e «Admin правит
Workflow» и «AI Onboarding применяет конфиг»). M3 опирается на результаты M2:
контракты **C2/C6** заморожены на CP-2, **C4** — на CP-3, живые срезы
омниканальности и AI Assistant работают, поэтому команды продолжают работать
независимо и сходятся только на CP-4 и CP-5.

---

# 1. Итоговая последовательность выполнения

## 1.1 Общая последовательность вех

1. **M0 — Контракты и каркас.** *(выполнено первой серией.)* Структура репозитория,
   CI-скелет, контракты v1, моки и базовые приложения/сервисы.
2. **M1 — Вертикальный срез «приём и ответ».** *(выполнено второй серией.)* Web Chat
   → Core → Manager Workspace → ответ клиенту; точка согласования **CP-1**.
3. **M2 — Омниканальность + realtime + AI Assistant.** *(выполнено третьей серией.)*
   Внешние адаптеры, WebSocket realtime, AI Assistant из Knowledge Base; **CP-2**,
   **CP-3**.
4. **M3 — Программируемость.** *(текущий этап.)* Форк FBP Engine, узел Backend API,
   безопасный Transform Node, визуальный редактор Workflow, AI Onboarding; **CP-4**,
   **CP-5**.
5. **M4 — Broadcast + Edge/ПДн + Notification + Mobile/Telegram Console.** Массовые
   коммуникации, RF Edge, буферизация, уведомления, Mobile API, Telegram Console;
   **CP-6**, **CP-7**, **CP-8**.
6. **M5 — Стабилизация и приёмка.** Полный e2e-набор, нагрузка, безопасность,
   RPO/RTO, документация; **CP-9**.

Критический путь четвёртого этапа (§ 10.1 мастер-плана, две ветки к CP-4 и CP-5):

```text
M2 contracts C2/C6 (CP-2) + C4 (CP-3) заморожены
  -> SVC-DATA M3 schema (workflow_* + outbox_events как coordination-patch)
  -> ветка CP-4: SVC-API(fbp-integration + узел Backend API) + SVC-FBP(форк + узлы)
  -> ветка CP-5: SVC-ADMIN(редактор Workflow + Onboarding UI) + SVC-AI(Onboarding)
  -> инфраструктура ядра: SVC-CORE(outbox доменных событий) + SVC-IDN(аудит доступа)
```

## 1.2 Внутренний порядок M3

M3 лучше выполнять в три шага:

1. **M3-01, короткий обязательный предшественник.** SVC-DATA создаёт схему M3
   (§ 4.8/M3 мастер-плана, раздел 5.4 плана SVC-DATA): `workflows`,
   `workflow_versions` (`UNIQUE(workflow_id, version_no)` — неизменяемые версии),
   `workflow_instances` (version pinning), `workflow_instance_state` (состояние вне
   исполнителя), `workflow_execution_logs` (журнал), с RLS по `organization_id` и
   изоляцией логов исполнения. Дополнительно SVC-DATA поставляет `outbox_events`
   (**C-OUT**) как **coordination-patch** для SVC-CORE M3 (см. § 1.4). Без реальной
   схемы integration-тесты FBP/API/CORE (запуск Workflow, узел Backend API, outbox)
   не проходят — это единственный жёсткий предшественник M3.
2. **M3-02...M3-10, параллельная волна.** Владельцы сервисов реализуют
   M3-функциональность в своих зонах, потребляя схему SVC-DATA и **замороженные на
   CP-2/CP-3** контракты C2/C6/C4 и стабильный C3. Волна распадается на две
   сходящиеся ветки:
   - **CP-4 (Workflow вызывает Backend API):** SVC-API (фасады `ai-integration` C4
     и `fbp-integration` C5 с timeout/circuit breaker/bulkhead + узел Backend API)
     и SVC-FBP (форк fbp-engine, нейтральный набор узлов, узел Backend API,
     безопасный Transform Node, мультиарендность).
   - **CP-5 (редактор Workflow + AI Onboarding):** SVC-ADMIN (визуальный редактор
     Workflow + диалог AI Onboarding) и SVC-AI (структурированные команды
     Onboarding §12.6).
   - **Инфраструктура ядра и безопасности:** SVC-CORE (транзакционный outbox
     доменных событий для Workflow) и SVC-IDN (полный аудит действий
     аутентификации/управления доступом). Бэкенд-модули (CORE, API, IDN) работают
     против реальной схемы SVC-DATA; SVC-FBP — против **мока Backend API**;
     SVC-ADMIN — против моков C5/C4, пока живые срезы не собраны на gate.
3. **M3-99, интеграционный gate CP-4 + CP-5.** Проверка, что оба среза замыкаются
   сквозными сценариями: e2e «Workflow вызывает Backend API» (CP-4), «Admin правит
   Workflow» и «AI Onboarding применяет конфиг» (CP-5); заморозка **C5** на CP-4 и
   совместная стабилизация **C3 + C4 + C5** на CP-5; добавление contract-тестов
   API↔FBP; подтверждение сквозных инвариантов M3 (узел Backend API — единственный
   способ менять данные из Workflow, безопасность Transform Node на этапе сохранения
   схемы, мультиарендная изоляция, аудит `actor_type = ai|workflow`).

## 1.3 Сервисы без задач на M3

По точкам согласования мастер-плана (§ 6, § 11) M3 замыкается **только** на **CP-4**
и **CP-5** (Программируемость), поэтому четвёртая серия ведёт работы по семи
активным сервисам: **SVC-DATA (01)**, **SVC-CORE (02)**, **SVC-IDN (03)**, **SVC-API
(04)**, **SVC-ADMIN (08)**, **SVC-AI (09)** и **SVC-FBP (10)**. Их моки/каркасы из
предыдущих вех переиспользуются; отдельных промптов в четвёртой серии для остальных
сервисов нет. Нумерация задач сохраняет **сквозное соответствие сервису из первой
серии** (01 = SVC-DATA, 02 = SVC-CORE, 03 = SVC-IDN, 04 = SVC-API, 08 = SVC-ADMIN,
09 = SVC-AI, 10 = SVC-FBP); номера **05, 06, 07, 11, 12, 13, 14, 15** (SVC-INT,
SVC-CHAT, SVC-MWS, SVC-BCAST, SVC-NOTIF, SVC-EDGE, SVC-MOB, SVC-TGC) в этой серии не
используются.

**Отложены на M4 (их точки согласования — CP-6/CP-7/CP-8):** SVC-BCAST (CP-6),
SVC-EDGE(Edge-контур РФ/буфер, CP-7), SVC-NOTIF (CP-8), SVC-TGC(Telegram Console,
CP-8), SVC-MOB (CP-7). SVC-INT/SVC-CHAT/SVC-MWS на M3 крупных работ не ведут и
остаются под регрессией CI.

> **Замечание о расхождении в плане (для сопровождающих).** Матрица § 5.1 и таблица
> e2e → веха § 8.2 мастер-плана относят подготовку Notification/Broadcast/Telegram
> Console («приходят уведомления») к M3, тогда как их **точки согласования** CP-6 и
> **CP-8** и поддерживающая схема (`broadcast_*`, `notifications`,
> `notification_settings` — SVC-DATA § 5.5) запланированы на **M4** (мастер § 5, § 6,
> § 11). Чтобы серия оставалась связной и исполняемой (без незакрытых зависимостей по
> схеме), уведомления/рассылки/Telegram Console вынесены в серию M4 к своим CP; здесь
> они остаются на моках M0/M2 под регрессией. Расхождение стоит устранить в
> мастер-плане, приведя § 5.1/§ 8.2 в соответствие с CP-таблицей § 6.

## 1.4 Coordination-patch: `outbox_events` из M4 в M3

SVC-CORE M3 (план `03-communication-core.md`, § «Доменные события для Workflow»)
публикует доменные события ядра для интеграции с SVC-FBP через **транзакционный
outbox** (`outbox_events`, C-OUT, мастер § 4.10). При этом план SVC-DATA относит
создание таблицы `outbox_events` к M4 (§ 5.5). Поскольку миграции — **исключительная
зона SVC-DATA**, таблицу нельзя создать в модуле ядра. Поэтому `outbox_events`
переносится в M3-01 как **минимальный coordination-patch**: без него integration-
тесты outbox в SVC-CORE M3 не проходят. Остальные таблицы M4
(`broadcast_*`/`notifications`/`edge_message_buffer`) в M3 **не** создаются.

# 2. Правила для исполнителей четвёртой серии

- Каждый исполнитель берёт **ровно один** промпт из раздела 4.
- Формулировка задачи должна звучать как: «Выполнить этап **M3** плана
  `docs/plan/services/XX-...md`».
- Реализуется **только** объём M3 своего сервиса; нельзя забегать в вехи M4+
  (неизменяемость версий/version pinning как инварианты и stateless-масштабирование
  FBP; сквозная идемпотентность через Edge-буфер; Broadcast; Edge-контур РФ;
  Notification; фасады broadcast/notification; bootstrap организаций и приглашения)
  сверх того, что нужно для прохождения CP-4 и CP-5.
- Между CP разработка идёт против **моков** соседних контрактов: SVC-FBP — против
  **мока Backend API**; SVC-ADMIN — против моков C5/C4; SVC-API/SVC-AI сходятся по
  C4/C5 через моки контрактов до gate. Бэкенд-модули ядра (CORE, API, IDN) для своих
  integration-тестов используют **реальную схему** SVC-DATA (результат M3-01).
- Контрактные артефакты и их обновления кладутся в `packages/contracts`; код
  сервиса — только в его директорию из мастер-плана § 3.
- Соблюдаются сквозные инварианты: узел Backend API — **единственный санкционированный
  способ** менять данные из Workflow (ТЗ §13.5, §13.13); прямого доступа AI/Workflow
  к БД **нет**; безопасность Transform Node проверяется **на этапе сохранения схемы**,
  а не при исполнении (ТЗ §13.4, §13.13); изоляция арендаторов по `organization_id`
  (RLS, ТЗ §22.6); авторитетная авторизация на Backend (RBAC, ТЗ §9.8); действия
  AI/Workflow пишутся в аудит с `actor_type = ai|workflow` (ТЗ §22.9).
- Для каждого промпта результатом должны быть код/миграции/документация, тесты
  (unit + integration, а на CP-4/CP-5 — contract + e2e) и короткий отчёт: что
  сделано, какие команды проверки запущены, какие контракты затронуты.

# 3. Критерии готовности M3

M3 считается завершённой, когда:

- SVC-DATA создал схему M3 (`workflows`, `workflow_versions` с
  `UNIQUE(workflow_id, version_no)`, `workflow_instances`, `workflow_instance_state`,
  `workflow_execution_logs`) плюс `outbox_events` (C-OUT) как coordination-patch;
  миграции обратимы (`up`/`down`), неизменяемость `version_no` и изоляция логов
  исполнения по арендатору подтверждены тестами;
- SVC-CORE публикует доменные события (новое сообщение, смена статуса, создание
  диалога) в `outbox_events` в **одной транзакции** с изменением агрегата и
  доставляет их идемпотентно (повтор публикации не создаёт дублей);
- SVC-IDN пишет `append-only` `audit_events` по всем действиям входа/сессий/отзыва
  сессий/смены ролей/изменения прав/административным действиям, записи защищены от
  изменения;
- SVC-API предоставляет фасады `ai-integration` (C4) и `fbp-integration` (C5) с
  **timeout + circuit breaker + bulkhead**, узел Backend API как единственный
  санкционированный способ менять данные из Workflow (проверка полномочий +
  применение бизнес-логики), применяет структурированную команду AI Onboarding после
  валидации §12.6 и проверки прав, пишет аудит `actor_type = ai|workflow`;
- SVC-AI реализует AI Onboarding (`POST /ai/onboarding:command`): NL-запрос → JSON-
  команда по схеме §12.6 без прямого доступа к данным; строгая валидация команды по
  JSON-схеме как первый барьер; окончательная проверка/применение — на Backend;
- SVC-FBP форкнул fbp-engine и переработал его под платформу: нейтральный набор
  узлов (вызов Backend API, LLM, KB-поиск, ветвление, Transform, ожидание события),
  узел Backend API как единственный способ менять данные, удалён прямой доступ к БД,
  мультиарендная изоляция по `organization_id`, безопасный Transform Node
  (декларативный evaluator над whitelist, валидация на сохранении схемы), базовый
  журнал исполнения, интеграция с редактором Workflow;
- SVC-ADMIN даёт визуальный редактор Workflow (список с включением/версией, редактор
  схемы в безопасном наборе узлов, сохранение как новой версии, просмотр истории
  исполнения) и диалог AI Onboarding (подтверждение → команда → Backend применяет);
- на CP-4 заморожен **C5** и добавлен contract API↔FBP + e2e «Workflow вызывает
  Backend API»; на CP-5 совместно стабилизированы **C3 + C4 + C5**, добавлены e2e
  «Admin правит Workflow» и «AI Onboarding применяет конфиг»;
- CI зелёный: lint → unit → integration → contract → e2e затронутых сценариев
  (§ 9.4 мастер-плана).

# 4. Четвёртая серия промптов

## M3-01 — SVC-DATA: схема Workflow (`workflow_*`) и транзакционный outbox (C-OUT)

```text
Выполни этап M3 плана docs/plan/services/01-data-platform.md.

Цель: дать движку Workflow, ядру и Backend полную схему M3 — неизменяемые версии
Workflow, экземпляры с version pinning, состояние вне исполнителя и журнал
исполнения; дополнительно поставить транзакционный outbox для доменных событий ядра
(coordination-patch для SVC-CORE M3), с изоляцией по арендатору.

Исходные документы:
- docs/plan/README.md, разделы 4.8 M3, 5, 6 CP-4, 9, 10.1;
- docs/plan/services/01-data-platform.md, раздел 5.4 M3 (и 5.5 — по outbox_events);
- docs/plan/services/03-communication-core.md, раздел M3 (потребитель outbox_events).

Зона ответственности:
- db/migrations;
- db/seeds;
- тестовые фикстуры БД в packages/testing или сервисной test-директории.

Сделай:
1. Создай workflows, workflow_versions (UNIQUE(workflow_id, version_no) —
   неизменяемые версии, ТЗ §13.10), workflow_instances (version_id FK — version
   pinning), workflow_instance_state (состояние вне исполнителя, stateless executor),
   workflow_execution_logs (журнал исполнения, ТЗ §13.9, §24.6). RLS по
   organization_id; изоляция логов исполнения по арендатору.
2. Создай outbox_events (C-OUT, мастер §4.10) с индексом по status и инвариантом
   «запись в одной транзакции с агрегатом», с выборкой pending для доставки. Это
   coordination-patch: таблица нужна SVC-CORE M3, миграции — только у SVC-DATA.
3. Проверь миграции по циклу up -> down -> up на реальной БД.

Проверка:
- unit: фабрики версий/инстансов/логов и outbox-событий; валидатор монотонности
  version_no;
- integration: миграции up/down; неизменяемость версии (повторная запись той же
  version_no отклоняется); изоляция логов исполнения по арендатору; атомарность
  outbox (событие и изменение агрегата коммитятся/откатываются вместе), выборка
  pending.

Не делай:
- не создавай остальные таблицы M4 (broadcast_*, notifications,
  notification_settings, edge_message_buffer) сверх пустых forward-compatible
  заглушек — это M4;
- не переноси в БД бизнес-логику Workflow/RAG/identity — она в SVC-FBP/SVC-AI/ядре.
```

## M3-02 — SVC-CORE: доменные события для Workflow (транзакционный outbox)

```text
Выполни этап M3 плана docs/plan/services/03-communication-core.md.

Цель: надёжно уведомлять вынесенные сервисы (прежде всего SVC-FBP) о доменных
событиях ядра через транзакционный outbox — фундамент интеграции с Workflow.
Разработка ведётся против мока фасада FBP.

Исходные документы:
- docs/plan/README.md, разделы 4.10 (outbox/C-OUT), 7.1, 8.2, 6 CP-4;
- docs/plan/services/03-communication-core.md, раздел M3.

Зона ответственности:
- services/backend/src/modules/communication-core;
- потребление таблицы outbox_events (результат M3-01) через backend;
- фасад к SVC-FBP через мок; tests/contract при необходимости.

Сделай:
1. Публикуй доменные события (новое сообщение, смена статуса, создание диалога) в
   outbox_events в ОДНОЙ транзакции с изменением агрегата (ТЗ §11.12, мастер §4.10).
2. Реализуй идемпотентную доставку/replay событий из outbox: повтор публикации не
   создаёт дублей.
3. Сформируй payload события по мастер §4.10 (aggregate_id, event_type, payload,
   status).

Проверка:
- unit: формирование payload события, атомарность «message+outbox»;
- integration: Backend<->PostgreSQL (outbox publish/replay), фасад к SVC-FBP через
  мок;
- e2e: участие ядра в сценарии «Workflow (запуск->Node->завершение)» (CP-4).

Не делай:
- не реализуй сквозную идемпотентность через Edge-буфер, интеграцию Broadcast и
  приём от SVC-EDGE(C9) — это M4;
- исполнение Workflow держит SVC-FBP; ядро только публикует события;
- фасады устойчивости (circuit breaker/bulkhead) к вынесенным сервисам — зона
  SVC-API (M3-04).
```

## M3-03 — SVC-IDN: аудит действий аутентификации и управления доступом

```text
Выполни этап M3 плана docs/plan/services/02-identity-platform.md.

Цель: полный аудит безопасности идентичности — append-only записи audit_events по
```

# 5. Что запускать первым

Минимальный практичный запуск M3:

1. Выполнить **M3-01** (SVC-DATA) — обязательный предшественник: без реальной схемы
   M3 (`workflow_*` + `outbox_events`) integration-тесты FBP/API/CORE не проходят.
2. Как только схема готова, параллельно запустить две сходящиеся ветки и
   инфраструктуру ядра:
   - **CP-4 (Workflow вызывает Backend API):** **M3-04** (API: фасады + узел Backend
     API) и **M3-10** (FBP: форк + узлы + Transform).
   - **CP-5 (редактор Workflow + AI Onboarding):** **M3-09** (AI: Onboarding) и
     **M3-08** (ADMIN: редактор Workflow + Onboarding UI).
   - **Инфраструктура ядра и безопасности:** **M3-02** (CORE: outbox доменных
     событий) и **M3-03** (IDN: аудит доступа). Бэкенд-модули (CORE/API/IDN) идут
     против реальной схемы SVC-DATA; SVC-FBP — против мока Backend API; SVC-ADMIN —
     против моков C5/C4 до сборки живых срезов.
3. Сервисы без задач на M3 (SVC-INT, SVC-CHAT, SVC-MWS, SVC-BCAST, SVC-NOTIF,
   SVC-EDGE, SVC-MOB, SVC-TGC) в этой серии не запускать: их артефакты сохраняются
   под регрессией и подключаются на M4 (CP-6/CP-7/CP-8).
4. После слияния результатов выполнить **M3-99** (gate CP-4 + CP-5) и только затем
   открывать серию M4-промптов для CP-6/CP-7/CP-8.
