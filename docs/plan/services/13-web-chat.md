# План разработки сервиса Web Chat (SVC-CHAT)

Настоящий документ детализирует участок работ сервиса **Web Chat** и подчиняется
мастер-плану [`docs/plan/README.md`](../README.md) — единому источнику истины по
сквозным решениям: вехам M0–M5 (§ 5), точкам согласования CP-1…CP-9 (§ 6),
каталогу контрактов C1…C10 (§ 7), модели данных (§ 4), структуре проекта (§ 3),
Definition of Done (§ 9.4) и стратегии тестирования (§ 8). Здесь эти решения **не
переопределяются** — документ ссылается на них и раскрывает специфику Web Chat.

SVC-CHAT — это **встраиваемый веб-виджет чата для конечных клиентов** (React +
Vite + TS, ТЗ §21) и связанный **Web Chat Endpoint** как **первый канал**
платформы. Виджет — клиентское приложение: он **потребляет** публичный чат-API/WS
и не содержит бизнес-логики (ТЗ §18.8, §5.8). Со стороны платформы Web Chat — это
**канал**: серверный Web Chat Endpoint в связке с адаптером Web Chat в SVC-INT
публикует входящие в ядро через **C2 Ingress** (мастер § 7, § 7.1). Именно
SVC-CHAT первым **замыкает вертикальный срез «приём и ответ»** (M1). Участвует в
двух точках согласования: **CP-1** (M1, первый канал) и **CP-7** (M4, подключение
клиентов РФ через Edge Cluster).

> Ссылки «ТЗ §X.Y» — на техническое задание; «§ N» — на мастер-план; «CP-N» —
> точки согласования (§ 6); «M0…M5» — общие вехи (§ 5); «C1…C10» — контракты (§ 7).

## 1. Назначение и границы

SVC-CHAT — **эталонный клиент** платформы (Reference Client, ТЗ §18.3). С точки
зрения ядра Web Chat не отличается от Telegram/WhatsApp/MAX — это один из
Communication Endpoint (ТЗ §18.2).

**Владеет** (в границах SVC-CHAT):

- **встраиваемым виджетом чата** (ТЗ §18.4): инициализация сессии посетителя,
  подключение клиента, отправка/получение сообщений, вложения, отображение
  истории, статуса соединения и статуса доставки, работа в реальном времени;
- **инициализацией/восстановлением анонимной сессии посетителя** и её привязкой к
  Communication Endpoint (`channel=web_chat`) — до идентификации ведётся отдельная
  Conversation на сессию (ТЗ §18.6, §8.13);
- **клиентским представлением AI-ответов** в общей ленте (ТЗ §18.5) — без
  специального режима «чат с AI»;
- серверным **Web Chat Endpoint** (совместно с SVC-INT): приём входящих от виджета
  и публикация в ядро через **C2 Ingress**.

**НЕ входит** (принадлежит ядру — SVC-CORE/API):

- **хранение диалогов и сообщений** — это ядро (ТЗ §8, §18.8); виджет держит лишь
  локальную ленту/кэш и не является владельцем истории;
- **бизнес-логика, маршрутизация, принятие решений, проверки полномочий** —
  выполняются Backend/Communication Core (ТЗ §18.8, §5.8);
- **определение C1 и контракта C2** — владелец **SVC-CORE** (§ 7.1); нормализация
  Web Chat ⇄ C1 и публикация Ingress — **адаптер Web Chat в SVC-INT** (тесно
  связанный контрагент, § 8);
- **прямой доступ к БД** — его нет ни у кого, кроме Backend (ТЗ §22.3); виджет
  работает только через публичный чат-API/WS.

Таким образом, SVC-CHAT — **пользовательский интерфейс + точка входа канала Web
Chat**, а вся обработка сообщений остаётся за ядром (ТЗ §18.8).

## 3. Интерфейсы и контракты

### 3.1 Экспортирует

| Что | Форма | Направление / потребитель | Веха |
|---|---|---|---|
| **Встраиваемый виджет чата** | JS-бандл для сайта организации: лента, ввод, вложения, статусы | клиент (браузер) | **M0**→M1→M2 |
| Публикация входящих (**C2 Ingress**, совместно с SVC-INT) | входящее Web Chat → **C1** → `POST /internal/ingress/messages` | Web Chat Endpoint → CORE | **M1** |

**Web Chat Endpoint (совместно с SVC-INT).** Виджет отправляет сообщение на
серверный Web Chat Endpoint; **адаптер Web Chat в SVC-INT** нормализует его в **C1**
и публикует через **C2 Ingress** (владелец C1/C2 — SVC-CORE, § 7.1). SVC-CHAT
отвечает за клиентскую часть и передачу полезной нагрузки/идемпотентного ключа;
сам контракт C2 SVC-CHAT **не определяет**.

### 3.2 Потребляет

| Что | Владелец | Использование в SVC-CHAT |
|---|---|---|
| **Публичный чат-API** (**C3.messages** / **C1**) | SVC-CORE/API | `POST /messages` (идемпотентно, §11.12) — отправка; `GET /conversations/{id}/messages` — история/подгрузка |
| **C7 WS Events** (ТЗ §11.7) | SVC-CORE/API (совладение с SVC-EDGE) | realtime: `message.created`, `message.status_changed`, `typing.*`; авто-reconnect |
| **C1 Message Model** (ТЗ §8.4) | SVC-CORE | формат сообщения для рендеринга ленты и локального кэша |
| **C9 / Edge (Edge↔App Tunnel)** | SVC-EDGE | при подключении клиентов РФ соединение виджета идёт через Edge, прозрачно (ТЗ §18.7, §7.9–§7.10) |

**Итого потребляемых контрактов: 4** — публичный чат-API (C3.messages/C1), C7 (WS
realtime), C1 (модель сообщения) и C9/Edge (подключение РФ). SVC-CHAT контрактами
**не владеет**: C1/C2/C7 замораживает SVC-CORE на CP-1, C9 — SVC-EDGE на CP-7
(§ 6). До заморозки разработка идёт против **моков** публичного API/WS (MSW).

## 4. Модель данных

SVC-CHAT **не владеет таблицами** и не имеет прямого доступа к БД (ТЗ §22.3):
диалоги и сообщения хранит ядро (§ 4.3–§ 4.4 мастер-плана, владелец схемы —
SVC-DATA/SVC-CORE). Раздел описывает **клиентское состояние/сессию посетителя** и
её связь с серверными сущностями, а не владение таблицами.

**Клиентская сессия посетителя.**

- **Токен анонимной сессии** — в браузере (`localStorage`/cookie встраивающего
  домена); восстанавливает сессию после перезагрузки. Для анонимных сессий — «одна
  Conversation на сессию» до идентификации (ТЗ §18.6, §8.13).
- **Привязка к серверным сущностям.** Сессия соответствует **Communication
  Endpoint** с `channel=web_chat` (§ 4.3): `external_id` = идентификатор сессии
  виджета; Endpoint связывается с `clients`/`conversations` **ядром** (identity
  resolution, ТЗ §8.13). Виджет оперирует идентификаторами Conversation/Message от
  Backend — не создаёт их сам.
- **Идентификация/слияние.** Присоединение анонимной сессии к существующему Client
  — только после подтверждённой идентификации (авторизация, верификация
  телефона/почты, явная привязка); решение принимает Backend (ТЗ §8.13, §18.6).

**Локальная история/кэш сообщений.**

- Виджет держит **локальную ленту** текущей Conversation (кэш для отображения и
  подгрузки), сопоставляя серверные `message_id` с клиентскими; источник истины —
  ядро (`GET /conversations/{id}/messages`).
- **Идемпотентный ключ.** Для каждой исходящей реплики — клиентский
  `idempotency_key` (= будущий `message_id`, ТЗ §11.12), хранимый до подтверждения,
  чтобы **переотправка при reconnect** не создала дубль (§7.10, §7.9).
  Восстановление порядка — по серверному порядку/`sequence_number`.

Серверная схема `communication_endpoints`/`conversations`/`messages` — § 4.3–§ 4.4
мастер-плана; здесь **не переопределяется**.

## 5. Поэтапный план (по вехам M0…M5)

Разбивка привязана к вехам (§ 5 мастер-плана). Тесты каждого этапа: **unit**
(компоненты виджета, логика сессии, обработка WS/reconnect, идемпотентность),
**integration** (против мок-Backend/WS через **MSW** или dev-стенда; публикация
Ingress через Web Chat Endpoint), **e2e** («Web Chat» M1 §26.6, «Потеря соединения»
M4 §26.6).

### 5.1 M0 — каркас виджета + согласование первого канала

- **Цель.** Каркас виджета (Vite, встраивание, дизайн) и согласование, что Web
  Chat — первый канал для среза M1.
- **Задачи.** (1) инициализировать `apps/web-chat` (React+Vite+TS, ТЗ §21.1),
  настроить **встраиваемый бандл**: точка монтирования на сторонней странице,
  ленивая загрузка, базовый дизайн ленты/ввода (ТЗ §18.4, §21.7); (2) подключить
  `packages/ui-kit`, `packages/api-client`; поднять **мок API/WS** (MSW);
  (3) согласовать с SVC-INT/SVC-CORE/SVC-MWS роль Web Chat как первого канала
  среза (вход в CP-1).
- **Тесты.** *unit* — монтирование виджета, рендер пустой ленты, ввод;
  *integration* — виджет ↔ MSW по мок-контракту C3.messages/C1; *e2e* — участие в
  поднятии скелета (зелёный CI, § 9.1).
- **DoD.** § 9.4; каркас встраивается и проходит CI; роль первого канала
  зафиксирована с участниками CP-1.

### 5.2 M1 — обмен сообщениями через ядро (первый канал, CP-1)

- **Цель.** Замкнуть срез **«приём и ответ»**: посетитель пишет в Web Chat → через
  ядро → менеджер видит и отвечает → клиент получает ответ (CP-1, совместно с
  SVC-INT/CORE/MWS).
- **Задачи.** (1) **инициализация сессии** и создание/получение **Conversation**
  через ядро (анонимный режим, ТЗ §18.6, §8.13); (2) **отправка** —
  `POST /messages` (идемпотентно, клиентский `idempotency_key`, §11.12) через
  публичный чат-API; **приём** ответа менеджера; отображение **статуса доставки**;
  (3) **базовая история** (`GET /conversations/{id}/messages`); публикация входящих
  в ядро через **Web Chat Endpoint** (C2 Ingress, совместно с SVC-INT).
- **Тесты.** *unit* — создание/восстановление сессии, формирование исходящего с
  `idempotency_key`, рендер статусов; *integration* — против мок-Backend/WS или
  dev-стенда: отправка → Ingress через Web Chat Endpoint → сохранение; базовая
  история; *e2e* — **CP-1** «Web Chat: приём и ответ» (§26.6, § 8.2).
- **DoD.** § 9.4 + contract-тест (потребление API/WS) и e2e CP-1 (§ 6); заморожены
  C1/C2/C7 (владелец — SVC-CORE).

**Статус реализации CP-1.** M1 Web Chat завершён для первого канала: клиентские
API/MSW проверки живут в `apps/web-chat/test/**`, а сквозной gate
`tests/e2e/web-chat-cp1.test.mjs` поднимает Web Chat adapter и настоящий
Communication Core, принимает inbound через C2 Ingress, создаёт manager reply
через C3 `POST /messages` и доставляет outbound обратно в Web Chat session.

### 5.3 M2 — AI-ответы, полная история/подгрузка, realtime по WS (C7)

- **Цель.** **AI-ответы** в ленте (§12), **полная история** с подгрузкой,
  **realtime** через WebSocket (C7).
- **Задачи.** (1) **AI-ответы** (ТЗ §18.5, §12.3): при разрешённом AI Assistant
  ответы приходят **стандартным механизмом** ядра и отображаются в общей ленте —
  без специального режима (ТЗ §18.5, §12.5); (2) **полная история**:
  пагинация/бесконечная прокрутка, корректный порядок; (3) **realtime по WS (C7)**:
  подписка на `message.created`, `message.status_changed`, `typing.*` (§11.7),
  **авто-reconnect**, обновление ленты без перезагрузки (§21.6).
- **Тесты.** *unit* — обработка событий WS и обновление ленты, логика **reconnect**
  (восстановление подписки без потери событий), рендер AI-ответа; *integration* —
  против мок-WS (MSW): приём событий, постраничная подгрузка, AI-ответ из ядра;
  *e2e* — обмен с realtime-обновлением; AI-ответ виден клиенту (в связке с CP-3).
- **DoD.** § 9.4 + realtime с авто-reconnect (§11.7); история в правильном порядке.

**Статус реализации M2.** M2 Web Chat завершён как участник CP-3: клиентская
история, realtime-подгрузка и AI-ответы через стандартный message flow
покрываются unit/MSW тестами `apps/web-chat/test/**`, а сквозной AI-срез
зафиксирован `tests/e2e/ai-assistant-kb.test.mjs` через общий C4/C7 контракт без
специального режима доставки AI-сообщений.

### 5.4 M3 — без крупных задач у SVC-CHAT

- **Цель.** Веха **M3** (программируемость: Workflow-редактор, AI Onboarding,
  Notification) **не содержит крупных задач для SVC-CHAT** (§ 5.1 мастер-плана,
  строка SVC-CHAT: «—»).
- **Задачи.** Поддерживать стабильность потребляемых контрактов (API/WS); при
  необходимости — мелкие правки виджета вслед за событиями ядра (без изменения
  контрактов). Крупные интеграционные работы отсутствуют.
- **Тесты.** Регрессия unit/integration виджета M2 на каждом PR (§ 8.3); e2e M3
  SVC-CHAT не ведёт.
- **DoD.** § 9.4 (для мелких правок); контракты не изменены.

### 5.5 M4 — подключение клиентов РФ через Edge Cluster (CP-7)

- **Цель.** Работа виджета для **клиентов РФ через Edge Cluster** (ТЗ §7, §18.7):
  **буферизация/переотправка** при разрыве, **идемпотентность**, **порядок** (CP-7,
  совместно с SVC-EDGE/CORE).
- **Задачи.** (1) **подключение через Edge**: соединение виджета (REST/WS) проходит
  через Edge **прозрачно** (ТЗ §18.7, §7.6, §5.2); (2) **устойчивость при разрыве**:
  очередь неотправленных реплик на стороне виджета и **переотправка** после
  восстановления; серверная сторона — **буфер Edge** (§7.9); **дедупликация** по
  сквозному `idempotency_key` (= `message_id`, §11.12); (3) **порядок** в рамках
  Conversation/Endpoint (§7.10); лента без пропусков после переподключения.
- **Тесты.** *unit* — поведение при разрыве (очередь, переотправка), отсутствие
  дублей при повторе того же `idempotency_key`, сохранение порядка; *integration* —
  против мок-Backend/WS с эмуляцией разрыва: переотправка **без дублей**,
  корректный порядок; *e2e* — **CP-7** «Потеря соединения» (§26.6) — буфер/
  восстановление без потерь/дублей, порядок (совместно с SVC-EDGE/CORE).
- **DoD.** § 9.4 + подтверждены «переотправка без дубля» и порядок после разрыва;
  CP-7 зелёный; учтено сопряжение с C9 (владелец — SVC-EDGE).

### 5.6 M5 — приёмка: доступность виджета и устойчивость соединения

- **Цель.** **Стабилизация и приёмка** (CP-9): доступность (accessibility)
  виджета, устойчивость соединения, участие в полном наборе e2e (§26.6).
- **Задачи.** (1) **доступность**: клавиатурная навигация, ARIA-роли ленты/ввода,
  контраст, корректная работа во встраивающем окружении (§ 8); (2) **устойчивость
  соединения**: деградация при нестабильной сети (частые reconnect, длительный
  разрыв → буфер Edge §7.9), отсутствие потерь/дублей и порядок; (3) участие в
  полном наборе e2e (§26.6): «Web Chat» (M1) и «Потеря соединения» (M4);
  производительность виджета (ленивая загрузка, размер бандла, §21.7).
- **Тесты.** *unit* — accessibility-инварианты (роли/фокус), граничные reconnect;
  *integration* — устойчивость к серии разрывов (MSW/dev-стенд), консистентность
  ленты; *e2e* — «Web Chat» и «Потеря соединения» (§26.6) в полном наборе;
  регрессия.
- **DoD.** § 9.4 + подтверждены доступность и устойчивость соединения; приёмочные
  сценарии (§29) с участием Web Chat зелёные.

## 6. Точки согласования (ЯВНО)

Между CP SVC-CHAT разрабатывается автономно против **моков** публичного API/WS
(MSW) (§ 1.2 мастер-плана). Ниже — ожидания, замораживаемый контракт и добавляемые
межсервисные тесты (§ 6, § 11: SVC-CHAT → CP-1, CP-7).

| CP | Веха | Участники | Что готово у SVC-CHAT | Замораживаемый контракт | Межсервисные тесты |
|---|---|---|---|---|---|
| **CP-1** | M1 | SVC-CHAT, SVC-INT(адаптер Web Chat), SVC-CORE, SVC-API, SVC-IDN, SVC-MWS | виджет: сессия, отправка/приём, базовая история; Web Chat Endpoint публикует Ingress | **C1**, **C2**, **C7** (заморозка на примере Web Chat) | e2e «Web Chat: приём и ответ»; contract INT↔CORE |
| **CP-7** | M4 | SVC-EDGE, SVC-CORE, SVC-CHAT | подключение через Edge; переотправка/дедупликация/порядок при разрыве | **C9** (Edge↔App tunnel), **C1** | e2e «Потеря соединения»; contract EDGE↔CORE |

**CP-1 (M1) — с SVC-INT(адаптер Web Chat)/SVC-CORE/SVC-MWS.**
- *Ожидания.* Web Chat как **первый канал замыкает срез**: виджет создаёт сессию и
  Conversation, шлёт сообщение через публичный API; **адаптер Web Chat SVC-INT**
  публикует Ingress (C2); SVC-MWS показывает сообщение менеджеру и отвечает; ответ
  доходит до виджета.
- *Контракт.* Здесь **замораживаются C1/C2/C7** (владелец — SVC-CORE): модель
  сообщения, Ingress/Egress, WS-события. SVC-CHAT фиксирует своё **потребление**
  публичного API/WS.
- *Тесты.* e2e **«Web Chat: приём и ответ»** (§26.6, § 8.2); consumer-driven
  contract на потребление API/WS (§ 8.4); contract **INT↔CORE** (Ingress) — со
  стороны Web Chat Endpoint.

**CP-7 (M4) — с SVC-EDGE/CORE.**
- *Ожидания.* Клиенты РФ подключаются **через Edge Cluster** прозрачно (ТЗ §18.7);
  при разрыве Edge буферизует входящие (§7.9), виджет переотправляет накопленное;
  **дедупликация** по `idempotency_key` (§11.12) и **порядок** по
  `sequence_number`/Endpoint (§7.9–§7.10) исключают потери, дубли и перестановки.
- *Контракт.* Замораживается **C9** (Edge↔App tunnel, владелец — SVC-EDGE) в части
  сопряжения с **C1**; SVC-CHAT — потребитель соединения через Edge.
- *Тесты.* e2e **«Потеря соединения»** (§26.6) — буфер/восстановление без
  потерь/дублей, порядок; contract **EDGE↔CORE** (§ 8.4) в части клиентского
  подключения.

## 7. Стратегия тестирования

Соответствует § 8 мастер-плана (ТЗ §26). Специфика SVC-CHAT — **Vitest + Testing
Library** (unit/компоненты) и **мок публичного API/WS через MSW** во всех
integration-тестах (реальный Backend в CI виджета не поднимается; сквозная связка —
e2e, § 3.1).

- **Создание/восстановление сессии посетителя.** Инициализация анонимной сессии,
  сохранение/восстановление токена после перезагрузки; одна Conversation на сессию
  до идентификации (ТЗ §18.6, §8.13).
- **Отправка без дублей при reconnect (идемпотентность).** Клиентский
  `idempotency_key` (= `message_id`) хранится до подтверждения; переотправка после
  разрыва не создаёт второе сообщение (§11.12; §7.10) — тест «повтор без дубля».
- **Корректный порядок и подгрузка истории.** Пагинация/бесконечная прокрутка
  `GET /conversations/{id}/messages`; восстановление порядка ленты по серверному
  порядку/`sequence_number`; отсутствие пропусков после переподключения.
- **Поведение при разрыве через Edge.** Эмуляция разрыва (MSW): очередь и
  переотправка на стороне виджета, дедупликация; согласованность с буфером Edge
  (§7.9) и порядком по Endpoint (§7.10).
- **AI-ответы.** Ответ AI Assistant, пришедший **стандартным механизмом** ядра
  (ТЗ §18.5, §12.5), корректно рендерится в общей ленте; без режима «чат с AI».
- **Обработка WS/reconnect.** Приём событий C7 (`message.created`,
  `message.status_changed`, `typing.*`), восстановление подписки после разрыва без
  потери событий (§11.7).

Целевые показатели — § 8.3 мастер-плана: ключевая клиентская логика (сессия,
идемпотентная отправка, WS/reconnect) покрыта unit-тестами; каждая CP (CP-1/CP-7) —
минимум один contract- и один e2e-тест. Общая стратегия — § 8.

## 8. Риски и зависимости

| Риск | Влияние | Митигирование |
|---|---|---|
| **Встраивание в чужие сайты** (конфликт стилей, CSP хоста) | сломанный/небезопасный виджет | **изоляция стилей** (изолированный контейнер монтирования), совместимость с CSP, ленивая загрузка (ТЗ §18.1, §21.7); проверки во встраивающем окружении (M5) |
| **Анонимная идентификация и последующее слияние клиента** (ТЗ §8.13) | ошибочное слияние сессии с чужой историей | одна Conversation на анонимную сессию до идентификации; присоединение — только по подтверждённой идентификации, решает Backend (ТЗ §18.6, §8.13) |
| **Консистентность при Edge-разрыве** (ТЗ §7.9) | потеря/дубли/перестановки сообщений | **идемпотентность** по `idempotency_key` (§11.12) + порядок по `sequence_number`/Endpoint (§7.10) + буфер Edge (§7.9); e2e «Потеря соединения» (CP-7) |
| **Зависимость от адаптера Web Chat SVC-INT** | без адаптера входящие не попадают в ядро | Web Chat Endpoint ведётся совместно с SVC-INT (§ 1, § 3.1); до готовности — мок API/WS (MSW); заморозка C2 на CP-1 |
| **Дрейф потребляемых контрактов** (API/WS, C9) | ломает интеграцию на CP | contract-first (M0), consumer-driven тесты (§ 8.4), заморозка C1/C2/C7 на CP-1 и C9 на CP-7 (§ 6) |
| **Недоступность AI** | нет AI-ответов клиенту | AI — вспомогательная подсистема (ТЗ §5.4): обмен сообщениями и работа виджета продолжаются (§12.1) |

**Зависимости.** SVC-CHAT зависит от: **SVC-CORE/API** — публичного чат-API,
C1/C2/C7 (заморозка на CP-1); **SVC-INT** — адаптера Web Chat / серверного Web Chat
Endpoint (публикация Ingress); **SVC-EDGE** — подключения клиентов РФ и C9/буфера
(CP-7, §7.9); **SVC-MWS** — стороны менеджера в сценарии CP-1; `packages/ui-kit` и
`packages/api-client` (§ 3). Как фронтенд/клиентский интерфейс, SVC-CHAT первым
**замыкает** срез M1 (CP-1), но сам не на критическом пути ядра M0/M1 (§ 10.1): до
готовности ядра и адаптера виджет разрабатывается против моков API/WS.
