# План разработки сервиса Broadcast Platform (SVC-BCAST)

Broadcast Platform — **вынесенный (деградируемый) сервис** массовых коммуникаций
(мастер §2, ТЗ §14): создание и планирование **кампаний**, **сегментация**
получателей по фильтрам, **шаблоны** и персонализация, **расписание** запуска,
**rate limiting** и **статистика** выполнения. Ключевой архитектурный принцип
(ТЗ §14.3, §6.9): SVC-BCAST **не содержит собственной системы доставки** —
сформированные сообщения проходят через **единый механизм ядра** (SVC-CORE) по
контрактам **C1** (Message Model) и **C2** (Egress), а доставку во внешние каналы
выполняют адаптеры SVC-INT (ТЗ §14.10). SVC-BCAST — **владелец контракта C8**
(Broadcast, мастер §7). Как деградируемый сервис (ТЗ §11.2, §5.4): его
недоступность **не влияет на диалоги** — приём, хранение и доставка обычной
переписки продолжаются. SVC-BCAST участвует в точке согласования **CP-6** (мастер §6).

## 1. Назначение и границы

**Входит в SVC-BCAST:**

- **создание и планирование кампаний** (черновик → расписание → запуск → контроль),
  жизненный цикл `draft|scheduled|running|done|failed` (ТЗ §14.2, мастер §4.6);
- **сегментация/фильтры получателей** — по организации, тегам, каналам связи,
  пользовательским сегментам, произвольным условиям (ТЗ §14.4); отбор клиентов и
  их Endpoint через Backend (C3.clients);
- **шаблоны и персонализация** сообщения по данным клиента/организации до передачи
  в ядро (ТЗ §14.5);
- **расписание** запуска: немедленно / по расписанию / по событию / из Workflow
  (ТЗ §14.7);
- **rate limiting** — управление скоростью отправки с учётом возможностей канала,
  политик организации и инфраструктурных ограничений (ТЗ §14.6);
- **ретраи и обработка ошибок** массовой доставки (повторная отправка при
  временных ошибках, ТЗ §14.9), согласованные со сквозной идемпотентностью
  ядра (ТЗ §11.12);
- **сбор и отдача статистики**: подготовлено / отправлено / доставлено / ошибки /
  время выполнения (ТЗ §14.8, `broadcast_stats` мастер §4.6).

**НЕ входит в SVC-BCAST (границы):**

- **прямая доставка в каналы** и обращения к внешним API — это SVC-CORE (единый
  механизм, C2) и SVC-INT (адаптеры); SVC-BCAST работает только с внутренней
  моделью сообщений (ТЗ §14.3, §14.10);
- **дублирование истории диалогов** — сообщения кампании создаются и хранятся в
  ядре (`messages`), а не в отдельной истории; SVC-BCAST хранит лишь **связь**
  `broadcast_messages ↔ messages` (мастер §4.6);
- **прямой доступ к БД** — доступ к схеме только через Backend, схему и миграции
  поставляет SVC-DATA (мастер §4, §22.3);
- собственный конечный автомат статуса сообщения — он ведётся ядром (C1
  `status`); SVC-BCAST агрегирует его в `broadcast_stats`.

Каноническое определение схемы БД — мастер §4.6 (владелец — SVC-DATA);
каноническое определение контрактов — `packages/contracts` (мастер §7). Настоящий
план **не переопределяет** их, а детализирует участок SVC-BCAST.

## 2. Технологии

| Область | Решение |
|---|---|
| Язык/фреймворк | TypeScript, сервис `services/broadcast-platform` (мастер §3); публичный API — модуль-фасад `broadcast-facade` в ядре (мастер §3). |
| Доступ к данным | Только через слой Data Platform (SVC-DATA); PostgreSQL 16; никаких прямых обращений к внешним каналам. |
| Планировщик/очередь заданий | Планировщик расписаний (ТЗ §14.7) + очередь заданий рассылки; батчинг получателей и **rate limiting** (ТЗ §14.6) — токен-бакет/лимитер на канал/организацию. |
| Идемпотентная генерация | Генерация сообщений с предсказуемым/сквозным `idempotency_key = message_id` (ТЗ §11.12): повторный запуск кампании не создаёт дублей. |
| Интеграция с ядром | Через **Backend/outbox** (мастер §4.10, C-OUT) и публичный `POST /messages` (C1/C2): постановка сообщений в единый механизм доставки; результат доставки читается из ядра (`messages.status`, `message_delivery_attempts`). |
| Деградируемость | Таймауты, circuit breaker, bulkhead и ретраи на вызовах к ядру/адаптерам (ТЗ §11.2); недоступность SVC-BCAST не влияет на диалоги (ТЗ §5.4). |
| Тестирование | Jest (unit, `*.spec.ts`), Testcontainers (integration Backend↔Broadcast, ТЗ §26.4), contract- и e2e-тесты на CP (мастер §8). |

## 3. Интерфейсы и контракты

SVC-BCAST — **владелец** контракта **C8** (Broadcast, мастер §7). Ниже —
детализация операций; **каноническое определение хранится в `packages/contracts`**
(`openapi/`), semver и заморозка — по мастер §7.4/§9.3.

### 3.1 Экспортируемые контракты

**C8 — Broadcast (публичный REST, группа `C8.broadcasts`, мастер §7.2, префикс
`/api/v1`).**

- `GET /broadcasts` — список кампаний организации (со `status`);
- `POST /broadcasts` — создание кампании: `template`, `filter`, `schedule`,
  `rate_limit` (ТЗ §14.2, §14.4–§14.7); **NFR создания ≤ 3 с** (ТЗ §25.2);
- `GET /broadcasts/{id}` — карточка кампании;
- `POST /broadcasts/{id}:start` — запуск кампании (немедленно/по расписанию,
  ТЗ §14.7); идемпотентен по кампании (повторный вызов не дублирует доставку);
- `GET /broadcasts/{id}/stats` — статистика выполнения (ТЗ §14.8);
- управление **получателями** (пересчёт/просмотр сегмента), **шаблоном** и
  **расписанием** кампании (в пределах статуса `draft|scheduled`).

**Событие C7 (мастер §7.3).** SVC-BCAST инициирует `broadcast.state_changed`
(смена состояния кампании) — публикуется через ядро/фасад для realtime в UI.

### 3.2 Потребляемые контракты

| Контракт | От кого | Назначение |
|---|---|---|
| **C1** (Message Model) | SVC-CORE | каноническая форма сообщения кампании (ТЗ §8.4, поля мастер §4.4); `sender_type = broadcast`. |
| **C2** (Egress) | SVC-CORE / SVC-INT | **доставка через единый механизм ядра** и адаптеры (ТЗ §14.3, §14.10); перенос `idempotency_key`; результат — в `messages.status`/`message_delivery_attempts`. |
| **C3.clients** | SVC-CORE/API (Backend) | список клиентов и их Endpoint для сегментации/фильтров (ТЗ §14.4); теги (`client_tags`). |
| **C6** (Capability Descriptor) | SVC-INT | учёт **возможностей каналов** при формировании сообщения и лимитов (ТЗ §10.6, §14.6). |
| Схема БД + миграции | SVC-DATA | таблицы §4.6, RLS по `organization_id`; чтение `clients`/`endpoints`/`messages`. |

## 4. Модель данных

Таблицы — по мастер §4.6 (владелец схемы SVC-DATA, потребители SVC-ADMIN,
SVC-MWS). SVC-BCAST использует их так:

| Таблица | Ключевые поля (акцент SVC-BCAST) | Появляется |
|---|---|---|
| `broadcasts` | `id`, `organization_id`, `name`, **`status`** (`draft\|scheduled\|running\|done\|failed`), **`template`** (jsonb), **`filter`** (jsonb — сегментация, ТЗ §14.4), **`schedule`** (jsonb, ТЗ §14.7), **`rate_limit`** (jsonb, ТЗ §14.6), `created_by`. | M3 |
| `broadcast_recipients` | `broadcast_id`, **`client_id`**, **`endpoint_id`**, **`status`** — материализованный сегмент получателей (ТЗ §14.4). | M3 (сегмент) / M4 (статусы доставки) |
| `broadcast_messages` | `broadcast_id`, **`message_id`** (FK на `messages` ядра), `status` — **связь с сообщениями ядра**, без дублирования истории (мастер §4.6). | M4 |
| `broadcast_stats` | `broadcast_id` (PK), **`prepared`**, **`sent`**, **`delivered`**, **`failed`**, `updated_at` — агрегаты контроля выполнения (ТЗ §14.8). | M4 |

**Инварианты SVC-BCAST:** (1) один получатель кампании (`client_id`+`endpoint_id`) —
не более одного доставленного сообщения при повторном запуске (идемпотентность,
ТЗ §11.12); (2) `broadcast_stats` согласованы с фактическими `messages.status`
через `broadcast_messages`; (3) изменение `template`/`filter`/`schedule` допустимо
только в статусах `draft|scheduled`.

## 5. Поэтапный план

Каждый этап привязан к вехе (мастер §5) и даёт вертикальный срез. Для каждого:
Цель · Задачи · Тесты (unit / integration / e2e) · DoD (единый — мастер §9.4).

### M0 — Контракты и каркас

- **Цель.** Заморозить контракт **C8** и поднять мок для параллельной разработки
  UI (SVC-ADMIN) и ядра.
- **Задачи.** Определить и зафиксировать в `packages/contracts` **C8** (эндпоинты
  §3.1, DTO `template`/`filter`/`schedule`/`rate_limit`, `stats`); поднять **мок
  C8**; каркас сервиса `broadcast-platform` и фасада `broadcast-facade`.
- **Тесты.** unit — валидация DTO C8 (create/start/stats); contract-заготовки
  BCAST↔CORE (доставка через C1/C2).
- **DoD.** Контракт C8 v1 заморожен (semver), мок в CI зелёный (мастер §9.4).

### M1 — без крупных задач (зависит от готовности ядра)

- **Цель.** Нет самостоятельного среза; SVC-BCAST **ожидает готовности ядра M1**
  (приём/хранение/маршрут, C1/C2) и разрабатывается против моков C8.
- **Задачи.** Только поддержка мока C8 в актуальном состоянии; уточнение контракта
  сопряжения с C1/C2 по мере стабилизации ядра (мастер §5.1).
- **Тесты.** Регресс на мок C8 (контракт не «дрейфует»).
- **DoD.** Мок C8 зелёный; изменения контракта согласованы (мастер §9.3).

### M2 — без крупных задач (зависит от готовности адаптеров)

- **Цель.** Нет самостоятельного среза; SVC-BCAST **ожидает готовности адаптеров
  M2** (SVC-INT: каналы + Capability C6) — они потребуются для реальной доставки на
  M4.
- **Задачи.** Согласовать учёт Capability (C6) и лимитов каналов в модели
  `rate_limit` (подготовка к M4); поддержка мока C8.
- **Тесты.** unit — интерпретация Capability/лимитов канала (на моках C6).
- **DoD.** Модель `rate_limit` учитывает C6; мок C8 зелёный.

### M3 — Создание и планирование кампаний

- **Цель.** Кампанию можно создать, сегментировать получателей, задать шаблон и
  расписание (ТЗ §14.2, §14.4–§14.7).
- **Задачи.** Реализовать **создание/редактирование кампаний** (`broadcasts`,
  статусы `draft|scheduled`); **сегментацию/фильтры** получателей по организации,
  тегам, каналам, сегментам, произвольным условиям (ТЗ §14.4) с материализацией в
  `broadcast_recipients` (через C3.clients); **шаблоны/персонализацию** (рендер по
  данным клиента/организации, ТЗ §14.5); **расписание** (немедленно/по расписанию/
  по событию/из Workflow, ТЗ §14.7) и планировщик; соблюсти **NFR: создание
  Broadcast ≤ 3 с** (ТЗ §25.2).
- **Тесты.** unit — **фильтрация/сегментация** получателей, **рендер шаблона**,
  **планировщик** (вычисление времени запуска); integration — **Backend↔Broadcast**
  (создание кампании, материализация сегмента, изоляция арендатора, ТЗ §26.4);
  проверка NFR ≤ 3 с на создание.
- **DoD.** Кампании создаются/планируются; NFR ≤ 3 с соблюдён; изоляция арендатора
  и серверная валидация (мастер §9.4).

### M4 — Запуск кампаний через единый механизм ядра

- **Цель.** Кампания доставлена **через ядро**: сообщения созданы в `messages`,
  доставка — через C2/адаптеры; собрана статистика (ТЗ §14.3, §14.8) — точка
  согласования **CP-6**.
- **Задачи.** **Запуск кампании** (`:start`): **идемпотентная генерация сообщений**
  в ядре (C1, `sender_type = broadcast`, `idempotency_key = message_id`, ТЗ §11.12)
  и доставка **через единый механизм ядра/адаптеров** (C2), связь
  `broadcast_messages ↔ messages`; **rate limiting** (ТЗ §14.6) — батчинг и лимитер
  на канал/организацию с учётом Capability (C6); **ретраи и обработка ошибок**
  (ТЗ §14.9) — повторная отправка при временных ошибках, согласованная со сквозной
  идемпотентностью (без дублей, ТЗ §11.12); **сбор статистики** (`broadcast_stats`:
  prepared/sent/delivered/failed) из статусов ядра; событие
  `broadcast.state_changed` (C7).
- **Тесты.** unit — **логика rate limiting/бэкоффа** (не превышает лимиты),
  **подсчёт статистики** (в т. ч. при частичных сбоях), формирование сообщения из
  шаблона; integration — **генерация сообщений в ядре через мок** (C1/C2),
  **идемпотентность повторного запуска** (без дублей), contract **BCAST↔CORE**;
  e2e — **«Broadcast: доставка кампании»** (CP-6, ТЗ §26.6).
- **DoD.** Кампания идёт через единый механизм ядра; повторный запуск не создаёт
  дублей; статистика корректна; добавлены contract- и e2e-тесты (мастер §9.4, CP-6).

**Статус реализации M4 (M4-99).** M4 Broadcast завершён для CP-6: запуск кампании
генерирует канонические C8-черновики (`C8.BroadcastCoreDeliveryDraft`) и доставляет
их **строго через C1/C2 ядра** (`sender_type = broadcast`, `idempotency_key =
message_id`), не обходя SVC-CORE; связь `broadcast_messages ↔ messages`
фиксируется на каждой доставке, повторный запуск дедуплицируется. Контракт **C8**
заморожен как `stable_for_m5` в `packages/contracts/cp6-cp7-freeze.v1.json`
(скреплено `tests/contract/m4-gate-freeze.test.mjs`). Покрытие: contract
`tests/contract/m4-core-cp6-cp7.contract.test.mjs`,
`tests/contract/c8-broadcast-contract.test.mjs`,
`tests/contract/int-delivery-attempts-cp6.test.mjs`; e2e
`tests/e2e/broadcast-cp6.test.mjs`, `tests/e2e/broadcast-delivery-cp6.test.mjs`.

### M5 — Нагрузка и устойчивость

- **Цель.** Крупные кампании под нагрузкой, устойчивость к отказам адаптеров,
  гарантия отсутствия дублей при массовой доставке.
- **Задачи.** Нагрузочные пробники на **крупные кампании** (ориентиры ТЗ §25.11):
  батчинг/rate limiting держат лимиты каналов; **устойчивость к отказам адаптеров**
  (таймауты/ретраи/бэкофф, деградация без блокировки ядра, ТЗ §11.2, §25.4);
  **дедупликация/идемпотентность массовой доставки** — согласованно со сквозным
  `idempotency_key` (ТЗ §11.12); поведение при частичных сбоях (частичная
  доставка, корректная статистика).
- **Тесты.** unit — стабильность лимитера под нагрузкой, идемпотентность генерации
  ключей; integration — деградация при недоступном адаптере (кампания не теряет
  сообщения, статистика отражает ошибки), повторный запуск после сбоя без дублей;
  e2e — участие в полном наборе ТЗ §26.6 (регрессия, CP-9).
- **DoD.** Пройдены нагрузка/устойчивость; нет дублей при массовой доставке;
  критерии приёмки (мастер §9.4, CP-9).

**Статус реализации M5 (M5-99).** На интеграционном gate CP-9 SVC-BCAST принят:
крупные кампании доставляются строго через C1/C2 ядра без дублей под нагрузкой,
регрессия §26.6 зелёная (`tests/e2e/broadcast-delivery-cp6.test.mjs`). Контракт
**C8** финально заморожен как `released_v1` в
`packages/contracts/cp9-freeze.v1.json` (скреплено `tests/contract/m5-gate-freeze.test.mjs`).

## 6. Точки согласования

Формулируются явно: ожидания от смежных сервисов · замораживаемый контракт ·
добавляемые межсервисные тесты (мастер §6).

### CP-6 (M4) — Broadcast через единый механизм ядра с SVC-CORE / SVC-INT

- **Ожидания.**
  - **готово ядро (M1)** — приём/хранение/маршрутизация и публичный `POST /messages`
    (C1/C2): SVC-BCAST ставит сгенерированные сообщения на доставку **через ядро**,
    не в обход SVC-CORE (ТЗ §14.3);
  - **готовы адаптеры (M2)** — SVC-INT доставляет во внешние каналы, публикует
    **Capability (C6)**, обеспечивает **rate limit/ретраи** на уровне канала
    (ТЗ §10.8, §14.9);
  - SVC-BCAST формирует получателей (сегмент), применяет rate limiting и передаёт
    кампанию на доставку.
- **Замораживаем.** **C8** (Broadcast) + **переиспользование C1/C2** (сопряжение
  генерации/доставки сообщений кампании).
- **Тесты.** e2e **«Broadcast: доставка кампании»** (кампания → получатели →
  доставка через единый механизм ядра, ТЗ §26.6); **contract BCAST↔CORE**
  (генерация сообщений/идемпотентность через C1/C2).

## 7. Стратегия тестирования

Соответствует мастер §8 (пирамида unit/integration/contract/e2e). Специфические
проверки SVC-BCAST:

- **корректность сегментации** и учёт **Capability каналов** (C6): в сегмент
  попадают ровно подходящие клиенты/Endpoint; несовместимые с каналом сообщения не
  формируются (ТЗ §14.4, §14.6, §10.6);
- **идемпотентность повторного запуска** кампании — повторный `:start`/ретраи **не
  создают дублей** сообщений (сквозной `idempotency_key`, ТЗ §11.12);
- **корректность статистики при частичных сбоях** — `broadcast_stats`
  (prepared/sent/delivered/failed) согласована с фактическими `messages.status`,
  включая частичную доставку и ошибки (ТЗ §14.8);
- **rate limiting не превышает лимиты каналов** — лимитер/бэкофф держат допустимую
  скорость с учётом возможностей канала и политик организации (ТЗ §14.6);
- **NFR: создание Broadcast ≤ 3 с** (ТЗ §25.2) — проверяется на M3.

Общие требования, пирамида и покрытие — мастер §8; обязательный e2e-сценарий
«Broadcast (кампания→получатели→доставка)» на M4 — мастер §8.2.

## 8. Риски и зависимости

| Риск / зависимость | Влияние | Митигирование (где в плане) |
|---|---|---|
| **Массовая нагрузка на ядро/адаптеры** при крупных кампаниях | Перегрузка доставки, влияние на диалоги | **rate limiting/батчинг** (ТЗ §14.6), очередь заданий, деградация без блокировки ядра (M4/M5, §2, §5) |
| **Дубли при ретраях** массовой доставки | Клиент получает сообщение повторно | **идемпотентность** по сквозному `idempotency_key = message_id` (ТЗ §11.12), связь `broadcast_messages ↔ messages` (M4/M5) |
| **NFR ≤ 3 с на создание** Broadcast (ТЗ §25.2) | Нарушение производительности | материализация сегмента и валидация оптимизированы; проверка NFR на M3 (§5) |
| **Сегментация по устаревшим данным клиентов** | Отбор «не тех» получателей | пересчёт сегмента на момент запуска из C3.clients; фиксация `broadcast_recipients` при `:start` (M3/M4) |
| **Зависимость от готовности ядра (M1) и адаптеров (M2)** | Блокировка реальной доставки до M4 | разработка против моков C8/C1/C2/C6 до CP-6; крупные задачи — только на M3/M4 (§5) |
| **Недоступность SVC-BCAST** (деградируемый сервис) | — (по требованию не влияет на диалоги) | вынос из ядра, таймауты/circuit breaker/bulkhead в фасаде (ТЗ §11.2, §5.4, §2) |

Зависимости по данным и владению — мастер §4.6 и §4.11 (владелец схемы SVC-DATA);
контрактам — мастер §7 (владелец C8 — SVC-BCAST; C1/C2 — SVC-CORE; C6 — SVC-INT).
