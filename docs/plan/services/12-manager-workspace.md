# План разработки сервиса Manager Workspace (SVC-MWS)

Документ детализирует работы по сервису **Manager Workspace** (SVC-MWS) —
**фронтенд-приложению** (React + Vite + TypeScript, ТЗ §21.1), веб-рабочему месту
менеджера: **очередь диалогов**, **переписка в реальном времени**, **карточка
клиента**, **отправка ответов**, **AI-подсказки** и **уведомления** (ТЗ §4.23,
§17.1). SVC-MWS — **эталонный** интерфейс менеджера (ТЗ §17.8): прочие клиентские
интерфейсы (SVC-TGC, SVC-MOB) используют те же Backend API. SVC-MWS **не содержит
бизнес-логики** (ТЗ §5.8, §21.5): он **потребляет** Backend API и WebSocket, все
проверки полномочий и решения — на сервере. Приложение **ссылается** на мастер-план
[`docs/plan/README.md`](../README.md) как на источник истины по контрактам (§7),
вехам (§5), точкам согласования (§6), структуре фронтендов (§3, `apps/manager-workspace`)
и DoD (§9.4). При расхождении приоритет имеет ТЗ
([`docs/MessengerBridge_TZ.md`](../../MessengerBridge_TZ.md)).

**Точки согласования этого сервиса:** **CP-1** (M1 — базовый цикл «очередь → ответ»),
**CP-3** (M2 — панель AI-подсказок из Knowledge Base), **CP-8** (M3 — отображение
уведомлений в web). SVC-MWS — **потребитель** контрактов C3.* (Backend REST), **C7**
(WS-события realtime), **C4** (AI Assistant) и **C10** (Notification); он **не владеет**
ни таблицами, ни контрактами (мастер-план §7, §4.11).

## 1. Назначение и границы

SVC-MWS реализует **веб-рабочее место менеджера** — представление данных Backend
(ТЗ §17.1, §21.1). Всё состояние производно от Backend; собственных бизнес-сущностей
SVC-MWS не хранит (ТЗ §5.12).

**В границах сервиса (UI-слой):**

- **Очередь / список диалогов** — очередь обращений и поиск клиентов (ТЗ §17.2):
  список Conversation с последним сообщением и статусом;
- **Единая история коммуникаций** — переписка по клиенту, объединяющая все каналы в
  одну Conversation (ТЗ §17.3, §8.5); менеджер не переключается между интерфейсами;
- **Отправка ответов** — ввод/отправка сообщений, вложения, шаблоны (ТЗ §17.5);
  отправка **идемпотентна** (`idempotency_key`, ТЗ §11.12);
- **Карточка клиента** — сведения, Communication Endpoint, активные обращения,
  заметки, теги, история изменений (ТЗ §17.4);
- **Работа в реальном времени** — через WebSocket без перезагрузки: новые сообщения,
  изменения статусов, «печатает», статус клиента и очередь (ТЗ §17.7, §11.7);
- **AI-подсказки** — панель вариантов ответа, резюме переписки, перевода/исправления,
  поиска в KB (ТЗ §17.6, §12.3); менеджер сам решает применять;
- **Уведомления** — индикатор и список уведомлений, отметка прочтения, realtime через
  WS (ТЗ §17.2, §15.3, §11.7).

**Вне границ сервиса (жёсткие ограничения):**

- **Нет бизнес-логики, БД, SQL, решений о правах** (ТЗ §5.8, §21.5) — данные только
  через Backend API/WS; проверки полномочий выполняет Backend (ТЗ §9.8), UI **не
  определяет** доступность операций.
- **Не владеет таблицами и контрактами** — Conversation/Message/Client/Notification
  принадлежат SVC-CORE/SVC-NOTIF (мастер-план §4.11); SVC-MWS их **потребляет**.
- **Не обращается к внешним каналам** и **не выполняет доставку** — отправленное
  сообщение передаётся Communication Core (ТЗ §17.5, §6.3).
- **AI — вспомогательный** (ТЗ §5.4): отсутствие SVC-AI **не блокирует** менеджера;
  панель AI **деградирует** без остановки очереди/переписки.
- **Аутентификация/авторизация** — за SVC-IDN; SVC-MWS ведёт по сценарию входа
  (Telegram-код, ТЗ §9.5) и работает в рамках сессии.

**Адаптивность:** минимально Desktop и Tablet (ТЗ §21.8); мобильные браузеры —
архитектурно расширяемо.

## 3. Интерфейсы и контракты

SVC-MWS **экспортирует** UI и **потребляет** контракты платформы; полные схемы
ведут сервисы-владельцы (мастер-план §7).

### 3.1 Экспортирует

**UI менеджера** (SPA): экраны очереди диалогов, переписки, карточки клиента, центра
уведомлений. Внешних программных интерфейсов нет — это конечный клиент Backend API/WS.

### 3.2 Потребляет

| Контракт (владелец) | Что используется | Назначение в SVC-MWS |
|---|---|---|
| **C3.auth** (SVC-IDN) | `POST /auth/login/telegram/start`, `.../verify`, `GET /auth/session`, `POST /auth/logout` | Вход менеджера (Telegram-код, ТЗ §9.5), контекст сессии |
| **C3.conversations** (SVC-CORE) | `GET /conversations`, `GET /conversations/{id}`, `GET /conversations/{id}/messages` | Очередь/список диалогов и история переписки (ТЗ §17.2, §17.3) |
| **C3.messages** (SVC-CORE) | `POST /messages` (**идемпотентно**, ТЗ §11.12), `GET /messages/{id}` | Отправка ответа клиенту; статус сообщения |
| **C3.clients** (SVC-CORE/API) | `GET /clients`, `GET /clients/{id}`, заметки/теги/endpoints | Поиск клиентов, карточка клиента (ТЗ §17.4) |
| **C4 / C3.ai** (SVC-AI) | `POST /ai/assistant:suggest` | AI-подсказки/варианты ответа, резюме, перевод, поиск в KB (ТЗ §12.3, §17.6) |
| **C10.notifications** (SVC-NOTIF) | `GET /notifications`, `POST /notifications/{id}:read` | Список и отметка прочтения уведомлений (ТЗ §15.6) |
| **C7 WS-события** (SVC-CORE/EDGE) | `GET /ws` (upgrade) + события §7.3 | Realtime-обновления без перезагрузки (ТЗ §11.7, §17.7) |

**Потребляемые WS-события C7** (мастер-план §7.3, ТЗ §11.7): `message.created`,
`message.status_changed`, `typing.started`/`typing.stopped`,
`client.status_changed`, `notification.created`. Соединение **восстанавливается
автоматически** (ТЗ §11.7).

### 3.3 Соответствие «экран/виджет → эндпоинт/событие»

| Экран / виджет | REST (C3.*/C4/C10) | WS-событие (C7) |
|---|---|---|
| Экран входа | `POST /auth/login/telegram/{start,verify}`, `GET /auth/session` | — |
| Очередь / список диалогов | `GET /conversations` | `message.created`, `message.status_changed`, `client.status_changed` |
| Переписка (история) | `GET /conversations/{id}/messages` | `message.created`, `message.status_changed`, `typing.*` |
| Поле ввода / отправка | `POST /messages` (идемпотентно) | `message.status_changed` (received→sent→delivered) |
| Карточка клиента | `GET /clients/{id}` (+ заметки/теги/endpoints) | `client.status_changed` |
| Панель AI-подсказок | `POST /ai/assistant:suggest` | — |
| Центр уведомлений (индикатор/список) | `GET /notifications`, `POST /notifications/{id}:read` | `notification.created` |

## 4. Модель данных

SVC-MWS **не владеет таблицами** (мастер-план §4.11); раздел описывает **потребляемые
ресурсы** и **клиентское состояние** (кэш/UI), производное от Backend. Авторитетные
схемы — мастер-план §4.3–§4.4, §4.7.

### 4.1 Потребляемые ресурсы (read-only проекции Backend)

| Ресурс | Ключевые поля (мастер-план) | Использование в UI |
|---|---|---|
| **Conversation** | `id`, `client_id`, `status` (open/closed/pending), `last_message_at` (§4.4) | Строка очереди/списка; заголовок переписки |
| **Message** | `id`, `conversation_id`, `channel`, `direction` (inbound/outbound), `sender_type`, `content`, `status` (received/routed/sent/delivered/failed), `created_at` (§4.4) | Пузырь сообщения; индикатор статуса доставки/прочтения |
| **Client** | `id`, `display_name`, endpoints, заметки, теги (§4.3) | Карточка клиента (ТЗ §17.4) |
| **Notification** | `id`, `category` (info/warning/error/critical/admin), `title`, `body`, `status` (new/read), `created_at` (§4.7) | Индикатор и список уведомлений |
| **AI-подсказка** (C4, не таблица) | предложенный ответ/подсказка + источники KB | Панель AI (только отображение; менеджер решает применять) |

### 4.2 Клиентское состояние (только UI)

- **Активный диалог** — выбранная Conversation и её история (пагинация/виртуализация
  длинных историй, §25.2);
- **Черновики ответов** — локально по Conversation до отправки; при отправке —
  `POST /messages` с клиентским `idempotency_key` (ТЗ §11.12);
- **Статус WS-соединения** — `connected`/`reconnecting`/`offline` (влияет на догрузку
  пропущенного);
- **Кэш server-state** — списки/история/уведомления с инвалидацией по WS-событиям
  (слияние realtime без дублей и пропусков, см. §7);
- **Непрочитанные уведомления** — счётчик индикатора.

ПДн в UI-состоянии — минимально необходимые; бизнес-логика и решения о правах в
клиенте запрещены (ТЗ §21.5).

## 5. Поэтапный план

Этапы привязаны к общим вехам M0…M5 (мастер-план §5). Каждый даёт вертикальный срез
(ТЗ §26.5). DoD этапа — единый (мастер-план §9.4).

### M0 — Каркас приложения

**Цель.** Работающий скелет `apps/manager-workspace` в общем CI (мастер-план §5, M0).

**Задачи.**
- Инициализация Vite + React + TS; слои Presentation/API Client/State/Routing/Shared
  (ТЗ §21.4); подключение `packages/ui-kit` (ТЗ §21.3).
- Роутинг с ленивой загрузкой (ТЗ §21.7): маршруты очереди/диалога/уведомлений
  (заглушки); `packages/api-client` (из OpenAPI) и заготовка WS-клиента (мок).
- **Auth-заглушка**: экран входа против мока C3.auth (реальная интеграция — M1/CP-1);
  каркас MSW для моков C3.*/C7.

**Тесты.** unit (Vitest+TL): рендер каркаса, роутинг, smoke ui-kit. Integration:
поднятие MSW-моков.

**DoD.** Зелёный CI (lint→unit→build); скелет собирается; моки контрактов подняты.

**Статус реализации.** Каркас `apps/manager-workspace` добавлен: React + Vite +
TypeScript, слои Presentation/API Client/State/Routing/Shared, ленивые маршруты
`login`/`queue`/`dialog`/`notifications`, временные типизированные заглушки
ui-kit/api-client, auth-заглушка C3.auth, MSW-моки C3.auth/C3.conversations/
C3.messages/C3.clients/C10.notifications и mock C7. Проверки этапа покрывают shell,
routing, smoke ui-kit, старт MSW-моков и frontend build.

### M1 — Очередь диалогов + история + отправка ответа (CP-1)

**Цель.** Базовый цикл менеджера «очередь → выбор диалога → история → ответ» против
C3 (мастер-план §5, M1; CP-1). Итог — e2e **«Работа менеджера»**.

**Задачи.**
- **Реальная auth** через C3.auth (Telegram-код, ТЗ §9.5), работа в рамках сессии.
- **Очередь/список диалогов** — `GET /conversations` (ТЗ §17.2): строки с последним
  сообщением и статусом, поиск клиентов.
- **История переписки** — `GET /conversations/{id}/messages` (ТЗ §17.3): единая
  Conversation, пузыри по `direction`/`sender_type`, вложения (просмотр).
- **Отправка ответа** — `POST /messages` **идемпотентно** (`idempotency_key`,
  ТЗ §11.12, §17.5); оптимистичное отображение + примирение статуса.
- **Карточка клиента (базовая)** — `GET /clients/{id}` (ТЗ §17.4).

**Тесты.** unit: компоненты списка/переписки/ввода; повтор `POST /messages` не
создаёт дубль (идемпотентность). Integration: против MSW-моков C3. **E2E
(Playwright): «Работа менеджера»** (очередь → история → ответ), а также участие в
e2e «Авторизация» (мастер-план §8.2).

**DoD.** DoD §9.4 + **CP-1**: contract-тесты потребителя C3.*, зелёный e2e «Работа
менеджера»; UI работает **без realtime** (polling/refetch допустим до M2).

### M2 — Realtime по WebSocket + панель AI-подсказок (CP-3)

**Цель.** Живой интерфейс (ТЗ §17.7) на C7 и панель AI-подсказок на C4 (мастер-план
§5, M2; CP-3). Итог — e2e **«AI Assistant из KB»** (web-часть).

**Задачи.**
- **WS-клиент с авто-reconnect** (`GET /ws`, ТЗ §11.7): подписка на события C7.
- **Live-сообщения** — `message.created` дописывает историю/поднимает диалог без
  перезагрузки; **статусы** — `message.status_changed` в пузырях,
  `client.status_changed` в карточке; **«печатает»** — `typing.started`/`stopped`.
- **Reconnection без дублей/пропусков** — при восстановлении (ТЗ §11.7) догрузка
  пропущенного (по `sequence_number`) и **дедупликация** по `message.id`
  (согласовано с SVC-EDGE/CORE, §7.10, §11.12); индикатор статуса соединения.
- **Панель AI-подсказок** — `POST /ai/assistant:suggest` (C4, ТЗ §12.3, §17.6):
  варианты ответа, резюме, перевод/исправление, поиск в KB; **graceful degradation**
  при недоступности SVC-AI (ТЗ §5.4).

**Тесты.** unit: обработчики WS-событий; слияние без дублей/пропусков после reconnect;
рендер и деградация панели AI. Integration: против мок-WS/Backend (MSW) или dev-стенда.
**E2E (Playwright): «AI Assistant из KB»** (web-часть: запрос подсказки → ответ из KB).

**DoD.** DoD §9.4 + **CP-3**: contract-тесты потребителя C4 и C7; зелёный e2e «AI
Assistant из KB»; проверено, что отключение AI **не ломает** очередь/переписку.

### M3 — Интерфейс уведомлений (CP-8)

**Цель.** Отображение внутренних уведомлений менеджера в web на C10 (мастер-план §5,
M3; CP-8). Итог — web-часть e2e **«Notification в Web + Telegram»**.

**Задачи.**
- **Индикатор уведомлений** — счётчик непрочитанных; realtime через
  `notification.created` (ТЗ §11.7).
- **Список уведомлений** — `GET /notifications` с категориями (info/warning/error/
  critical/admin, ТЗ §15.5).
- **Отметка прочтения** — `POST /notifications/{id}:read` (ТЗ §15.6); синхронизация
  счётчика.

**Тесты.** unit: индикатор/список/отметка прочтения; обработка `notification.created`.
Integration: против мок-C10/WS (MSW). **E2E (Playwright): «Notification в Web»**
(web-часть сценария «Notification в Web + Telegram», мастер-план §8.2).

**DoD.** DoD §9.4 + **CP-8**: contract-тест потребителя C10; зелёная web-часть e2e
«Notification в Web + Telegram».

### M4 — без крупных задач

Крупных функциональных задач для SVC-MWS на M4 **нет** (мастер-план §5.1: строка
SVC-MWS для M4 пуста). Возможны мелкие правки UI под нужды смежных сервисов (BCAST/
EDGE) и стабилизация; отдельного сквозного результата этап не даёт.

### M5 — Приёмка, производительность, полировка

**Цель.** Приёмочная готовность рабочего места (мастер-план §5, M5; CP-9).

**Задачи.**
- **Производительность (NFR ТЗ §25.2)**: список диалогов **≤ 1 с**, история **≤ 2 с**,
  отправка **≤ 1 с** (клиентский бюджет: рендер/виртуализация длинных историй,
  минимизация числа запросов — ТЗ §21.7).
- **Полировка UX**, адаптивность Desktop/Tablet (ТЗ §21.8), доступность.

**Тесты.** Полный прогон unit/integration/e2e; замеры соответствия §25.2; визуальная
регрессия ключевых экранов.

**DoD.** DoD §9.4 + участие в **CP-9**: приёмочные сценарии зелёные, NFR §25.2
подтверждены на клиентской части.

## 6. Точки согласования

Ниже — CP, в которых участвует SVC-MWS (мастер-план §6). Между CP разработка идёт
против моков (MSW).

### CP-1 (M1) — базовый цикл «очередь → ответ»

- **Участники:** SVC-INT (Web Chat), SVC-CORE, SVC-API, SVC-IDN, **SVC-MWS**.
- **Ожидания от SVC-MWS:** менеджер видит очередь, открывает историю и отвечает;
  вход через C3.auth; отправка идемпотентна.
- **Потребляемые контракты:** **C3.auth**, **C3.conversations**, **C3.messages**,
  **C3.clients** (мастер-план §7.2).
- **Межсервисные тесты:** contract-тесты потребителя C3.*; **e2e «Работа менеджера»**
  (очередь, история, ответ) и участие в e2e «Авторизация» (мастер-план §8.2).

### CP-3 (M2) — панель AI-подсказок

- **Участники:** SVC-API (AI-Integration), SVC-AI, SVC-DATA (KB), **SVC-MWS**/SVC-CHAT.
- **Ожидания от SVC-MWS:** панель отображает подсказку/вариант ответа из Knowledge
  Base; корректная **деградация** без AI (ТЗ §5.4).
- **Потребляемый контракт:** **C4** (`POST /ai/assistant:suggest`, мастер-план §7.1).
- **Межсервисные тесты:** contract-тест потребителя C4; **e2e «AI Assistant из KB»**
  (web-часть).

### CP-8 (M3) — отображение уведомлений в web

- **Участники:** SVC-NOTIF, продюсеры (CORE/BCAST/AI/FBP), **SVC-MWS**, SVC-TGC.
- **Ожидания от SVC-MWS:** уведомление, сгенерированное платформой, отображается в
  web (индикатор/список) и отмечается прочитанным; realtime через `notification.created`.
- **Потребляемый контракт:** **C10** (`GET /notifications`, `POST /notifications/{id}:read`,
  мастер-план §7.1, §7.2).
- **Межсервисные тесты:** contract-тест потребителя C10; **e2e «Notification в Web +
  Telegram»** (web-часть).

## 7. Стратегия тестирования

Соответствует мастер-плану §8 и ТЗ §26 (без автотестов разработка не допускается,
ТЗ §26.1). Специфика SVC-MWS:

- **Unit (Vitest+TL)**: рендер очереди/переписки (проекция Conversation/Message в
  список и пузыри по `direction`/`sender_type`/`status`, пустые/длинные истории);
  обработка каждого WS-события C7 (`message.created`, `message.status_changed`,
  `typing.*`, `client.status_changed`, `notification.created`); идемпотентная
  отправка (повтор `POST /messages` не создаёт дубликат, ТЗ §11.12); рендер и
  деградация панели AI и списка уведомлений.
- **Reconnection без дублей/пропусков** (unit/integration): после авто-reconnect
  (ТЗ §11.7) история восстанавливается **без дублей** (дедуп по `message.id`) и
  **без пропусков** (догрузка по `sequence_number`); согласовано с SVC-EDGE/CORE
  (§7.10, §11.12).
- **Integration**: против контрактных моков C3.*/C7/C4/C10 (**MSW**) или dev-стенда.
- **E2E (Playwright)**: «Работа менеджера» (M1), «AI Assistant из KB» (M2),
  «Notification в Web» (M3) — мастер-план §8.2.
- **NFR §25.2** (M5): клиентские замеры (список ≤ 1 с, история ≤ 2 с, отправка
  ≤ 1 с) и **визуальная регрессия** ключевых экранов.

Целевые показатели — по мастер-плану §8.3 (каждый CP — минимум один contract- и один
e2e-тест).

## 8. Риски и зависимости

| Риск / зависимость | Влияние | Митигирование |
|---|---|---|
| **Realtime-консистентность при reconnect** (ТЗ §11.7) | Дубли/пропуски/перестановки сообщений в UI после разрыва | Дедупликация по `message.id`, восстановление порядка по `sequence_number` (§7.10, §11.12); **согласовано с SVC-EDGE/CORE**; unit/integration и e2e «Потеря соединения» (веб-наблюдаемая часть) |
| **Производительность длинных историй** (ТЗ §25.2) | Просадка рендера, превышение бюджетов ≤ 1 с / ≤ 2 с | **Виртуализация** списка/истории, пагинация, ленивая загрузка (ТЗ §21.7), минимизация числа запросов; замеры на M5 |
| **Зависимость AI-подсказок от SVC-AI** (ТЗ §5.4) | Недоступность AI не должна ломать рабочее место | **Graceful degradation** панели AI: очередь/переписка/отправка работают без AI (ТЗ §5.4, §5.1); проверка, что отключение AI не ломает e2e ядра |
| **Дрейф контрактов C3/C4/C7/C10** | Ломает интеграцию на CP-1/CP-3/CP-8 | Contract-first (M0), **потребительские** contract-тесты, заморозка на CP (мастер-план §6, §8.4); разработка против MSW между CP |
| **Готовность Backend/WS-стенда** (SVC-CORE/API/EDGE/NOTIF/AI) | Блокировка интеграции UI | До готовности — **MSW-моки** C3.*/C7/C4/C10; переход на dev-стенд по мере готовности смежных сервисов |
| **UI-логика прав вместо серверной** (ТЗ §9.8, §21.5) | Ложное разрешение/запрет операций | Все проверки — на Backend; UI **не** решает о правах; действия сверяются с ответами Backend (401/403) |
| **Единая ui-kit / без дублей** (ТЗ §21.3) | Расхождение компонентов между фронтендами | Переиспользование `packages/ui-kit`; запрет дублирования компонентов (ТЗ §21.3) |
