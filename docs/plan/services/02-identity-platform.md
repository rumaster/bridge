# План разработки сервиса Identity Platform (SVC-IDN)

Документ детализирует работы по сервису **Identity Platform** (SVC-IDN) — модулю
синхронного ядра, отвечающему за аутентификацию пользователей платформы, сессии,
RBAC, инициализацию (bootstrap) организаций и приглашения. Он **ссылается** на
мастер-план [`docs/plan/README.md`](../README.md) как на источник истины по модели
данных (§4.2), контрактам (§7), вехам (§5), точкам согласования (§6) и DoD (§9.4);
здесь детализируется только участок Identity. При расхождении приоритет имеет ТЗ
([`docs/MessengerBridge_TZ.md`](../../MessengerBridge_TZ.md)).

**Точки согласования этого сервиса:** **CP-1** (M1 — Telegram-логин и сессии,
необходимые для e2e «Авторизация» и «Работа менеджера»); косвенно **CP-8** (M4 —
поставка событий аудита действий доступа продюсерам/потребителям уведомлений).

---

## 1. Назначение и границы

SVC-IDN — единственная подсистема, отвечающая за аутентификацию и проверку
полномочий (ТЗ §9.1). Ни один другой модуль не реализует проверку прав
самостоятельно (ТЗ §9.1, §5.8): все проверки выполняются серверным guard'ом
Identity.

**В границах сервиса:**

- аутентификация пользователей платформы — MVP через одноразовый код Telegram-бота
  (ТЗ §9.5);
- управление серверными сессиями: выпуск, проверка, истечение по `expires_at`,
  отзыв (ТЗ §9.2, §9.7, §16.4);
- RBAC по ролям MVP: **Platform Operator**, **Administrator**, **Manager**
  (ТЗ §9.3), с расширяемостью набора ролей через конфигурацию (ТЗ §9.4);
- bootstrap организаций Platform Operator'ом и поток приглашений (ТЗ §9.10);
- аудит действий аутентификации и управления доступом (ТЗ §9.9, §23.8).

**Вне границ сервиса:** бизнес-данные клиентов (clients, endpoints, conversations,
messages — владелец SVC-CORE, мастер-план §4.3–§4.4); конечные клиенты **не**
являются пользователями админ-части и проходят идентификацию в каналах связи
(ТЗ §9.2). Профиль организации и её конфигурация — домен SVC-API; SVC-IDN даёт им
лишь провижининг Tenant в рамках bootstrap и guard.

**Резервный вход по email — архитектурно предусмотрен, но ВНЕ MVP (ТЗ §9.6).**
Вход в MVP выполняется только через Telegram-бот — это зависимость от единственного
мессенджера. Для роли Administrator резервный не-Telegram способ входа (email +
одноразовый код) должен быть **архитектурно предусмотрен**: провайдер входа
моделируется как подключаемый компонент (pluggable auth provider), а
`login_codes.purpose` и `invitations.contact_type` заранее допускают канал `email`.
**Реализация в MVP не выполняется** — закладываются только точки расширения
(см. §5, M5).

## 2. Технологии

- **NestJS-модуль** `identity` в составе backend-монолита (мастер-план §3,
  `services/backend/src/modules/identity/`); отдельного процесса не образует
  (ТЗ §11.2), масштабируется вместе с ядром (stateless-обработка, состояние — в
  общей БД).
- **Хранение сессий** — серверные сессии в PostgreSQL (`auth_sessions`,
  мастер-план §4.2); идентификатор сессии передаётся клиенту как непрозрачный
  токен (httpOnly-cookie/Bearer). Опциональный кэш для быстрой проверки — вне
  MVP.
- **Хеширование одноразовых кодов и токенов приглашений** — в БД хранится только
  `code_hash` / `token_hash` (не сам секрет), стойкий алгоритм с солью; сравнение
  в постоянном времени. Управление любыми внешними секретами (токен Telegram-бота)
  — через централизованный менеджер секретов, не в коде (ТЗ §23.7).
- **Guard'ы и декораторы ролей** — NestJS `AuthGuard` (наличие активной сессии +
  принадлежность организации) и `RolesGuard` + декоратор `@Roles(...)` для
  проверки полномочий (ТЗ §9.8, §23.4). Guard экспортируется остальным модулям
  ядра как единая точка авторизации.
- Защита эндпоинтов входа: rate limiting и защита от перебора кода (ТЗ §23.5).

## 3. Интерфейсы и контракты

Схемы контрактов ведутся в `packages/contracts` (мастер-план §7). SVC-IDN —
владелец группы **C3.auth** и совладелец **C3.platform** / **C3.users**
(мастер-план §7.2).

### 3.1 Экспортирует

**C3.auth** (аутентификация и сессии, ТЗ §9.5, §9.2):

| Метод и путь (`/api/v1`) | Назначение |
|---|---|
| `POST /auth/login/telegram/start` | Приём Telegram-имени, проверка пользователя, инициирование отправки одноразового кода (ТЗ §9.5, шаги 1–3). |
| `POST /auth/login/telegram/verify` | Проверка кода, выпуск сессии (ТЗ §9.5, шаги 4–5). |
| `POST /auth/logout` | Завершение текущей сессии (отзыв). |
| `GET /auth/session` | Текущая сессия: пользователь, организация, роли (ТЗ §9.7). |

**C3.platform** (операции уровня платформы, роль Platform Operator, ТЗ §9.3, §9.10):

| Метод и путь | Назначение |
|---|---|
| `POST /platform/organizations` | Провижининг организации (Tenant); создаёт изолированную область данных. |
| `POST /platform/organizations/{id}/administrators` | Создание первого Administrator и инициирование приглашения. |
| `POST /platform/organizations/{id}/block` | Блокировка/разблокировка организации (`status`). |

**C3.users** (управление пользователями организации, ТЗ §16.4, §9.10):

| Метод и путь | Назначение |
|---|---|
| `GET/POST /organizations/{id}/users` | Список и создание пользователей организации. |
| `PATCH /users/{id}` | Изменение пользователя (статус, роли). |
| `POST /users/{id}/sessions:revoke` | Отзыв активных сессий пользователя (ТЗ §16.4, §9.2). |
| `POST /invitations` | Создание приглашения (Administrator приглашает Manager и др.). |

> Разграничение владения с SVC-API: SVC-IDN владеет логикой идентичности,
> сессий, ролей и приглашений; профиль организации и её конфигурация — за SVC-API
> (мастер-план §7.2, C3.org). `POST /platform/organizations` создаёт запись
> `organizations` через доменный сервис SVC-API, а Identity добавляет владельца и
> первого администратора.

**Guard авторизации** — внутренний контракт для всех модулей ядра: единый
`AuthGuard`/`RolesGuard`, применяемый к каждому защищённому эндпоинту Backend API
(ТЗ §9.1, §9.8). Форматы ошибок — единые для платформы (мастер-план §7,
ТЗ §11.11).

### 3.2 Потребляет

- **Доставка одноразового кода в Telegram** — SVC-IDN не обращается к внешним API
  напрямую (ТЗ §10.7). Отправка кода выполняется через **Backend →
  Integration Platform (SVC-INT)** по контракту **C2 (egress)** / внутреннему
  интерфейсу Telegram-адаптера (мастер-план §7.1). До готовности адаптера
  (CP-1/CP-2) используется **мок** канала доставки.
- **Провижининг Tenant** — доменный сервис организаций SVC-API (см. §3.1).
- **Запись событий аудита** — модуль `audit` (SVC-API, таблица `audit_events`,
  мастер-план §4.1), append-only (ТЗ §23.8).

## 4. Модель данных

Таблицы — из мастер-плана **§4.2** (владелец схемы — SVC-IDN, физическая модель —
SVC-DATA). Ниже — ключевые поля и этап появления; **схема здесь не
переопределяется**.

| Таблица | Ключевые поля | Появляется |
|---|---|---|
| `users` | `organization_id **NULL** для Platform Operator` (ТЗ §9.3), `telegram_username`, `email`, `status` (active/blocked) | M1 |
| `roles` | `code UNIQUE` (`platform_operator`/`administrator`/`manager`), `scope` | M1 (seed), полномочия — M2 |
| `user_roles` | `PK(user_id, role_id, organization_id)` | M1/M2 |
| `auth_sessions` | `issued_at`, **`expires_at`**, **`revoked_at`**, `ip`, `user_agent` (ТЗ §9.2, §16.4) | M1 |
| `login_codes` | **`code_hash`** (не код), `purpose`, `expires_at`, `consumed_at` (одноразовость, ТЗ §9.5) | M1 |
| `invitations` | `contact_type`/`contact_value`, `role_id`, **`token_hash`**, `expires_at`, `accepted_at` (ТЗ §9.10) | M4 |

Примечания к изоляции: все арендо-зависимые записи несут `organization_id` и
подпадают под RLS (мастер-план §4, ТЗ §22.6); исключение — Platform Operator
(`users.organization_id = NULL`) как субъект вне организации. Ссылки в аудите —
суррогатные (обезличивание вместо удаления, ТЗ §22.11).

## 5. Поэтапный план

Этапы привязаны к общим вехам **M0…M5** (мастер-план §5). DoD каждого этапа —
единый (мастер-план §9.4). Тесты размещаются по соглашению мастер-плана §3.1.

### M0 — Контракт C3.auth + мок guard

- **Цель.** Заморозить контракт аутентификации и предоставить моки, чтобы
  SVC-ADMIN/MWS и другие модули разрабатывались независимо.
- **Задачи.** Описать OpenAPI/DTO для C3.auth (start/verify/logout/session) в
  `packages/contracts`; заглушки эндпоинтов; **мок `AuthGuard`** (пропускает с
  сидированным пользователем/ролью) для остальных модулей ядра; каркас модуля
  `identity` в backend.
- **Тесты.** unit — валидация DTO входа; contract — схема C3.auth опубликована и
  верифицируема.
- **DoD.** Контракт C3.auth v1 заморожен; мок guard подключаем; зелёный CI на
  скелете (мастер-план §9.4).

### M1 — Telegram-логин, сессии, базовый guard (CP-1)

- **Цель.** Рабочий вход по одноразовому коду Telegram и серверные сессии —
  фундамент для e2e «Авторизация» и «Работа менеджера» (мастер-план §8.2).
- **Задачи.**
  - `POST /auth/login/telegram/start`: поиск пользователя по `telegram_username`,
    генерация одноразового кода, сохранение **`code_hash`** с TTL, запрос
    доставки в Telegram через Backend/SVC-INT (в M1 — мок адаптера) (ТЗ §9.5).
  - `POST /auth/login/telegram/verify`: проверка кода (не истёк, не использован),
    пометка `consumed_at`, выпуск `auth_sessions` с `expires_at` (ТЗ §9.2, §9.7).
  - `POST /auth/logout` и отзыв сессии (`revoked_at`); `GET /auth/session`.
  - Базовый `AuthGuard` (наличие активной, не истёкшей и не отозванной сессии +
    принадлежность организации, ТЗ §9.8).
  - **Seeded-организация и seeded-admin** для e2e (полноценный self-service
    bootstrap отложен на M4); сид ролей (`roles`).
  - Защита от перебора: лимит попыток/локаут, rate limit на `start`/`verify`
    (ТЗ §23.5).
- **Тесты.**
  - **unit** — генерация/проверка/**истечение** кода, одноразовость
    (`consumed_at`), TTL сессии, отказ по истёкшей/отозванной сессии.
  - **integration** — Backend↔PostgreSQL для `login_codes`/`auth_sessions`;
    проверка изоляции арендаторов (сессия одной организации не видит данные
    другой).
  - **e2e** — **«Авторизация»** (Telegram-вход) через SVC-ADMIN/MWS (мастер-план
    §8.2, CP-1); участие во входе в сценарий «Работа менеджера».
  - **contract** — верификация C3.auth (CP-1).
- **DoD.** Пользователь входит по коду и получает сессию; e2e «Авторизация»
  зелёный; C3.auth заморожен; аудит входов/ошибок аутентификации пишется
  (ТЗ §9.9) — базовый минимум, полный аудит управления доступом — M3.

**Статус реализации CP-1.** M1 Identity реализован в исполняемом
NestJS/TypeScript-коде (компилируется в `dist/main.js`, issue #189): маршруты
`POST /api/v1/auth/login/telegram/start`, `/verify` и `GET /api/v1/auth/session`
— `src/modules/identity/telegram-auth.controller.ts` +
`telegram-auth.service.ts`; доставка кода — `telegram-bot.service.ts` (реальный
Telegram Bot API `sendMessage` при заданном `TELEGRAM_BOT_TOKEN`, иначе
задокументированная деградация). C3.auth опубликован в
`packages/contracts/openapi/auth/c3.auth.openapi.json`, e2e «Авторизация» —
`apps/saas-admin/test/e2e/saas-admin.auth.spec.ts`. Rate-limiting 429 на
start/verify портирован в production через `telegram-login-rate-limiter.ts` и
покрыт `services/backend/test/unit/telegram-login-rate-limiter.spec.ts`,
`services/backend/test/integration/telegram-auth.spec.ts` и
`tests/e2e/backend-dist-communication-core.test.ts`. Старые `.mjs`-наборы
удалены как изолированный backend-прототип; см.
`docs/audit/backend-mjs-production-audit.md` (пункты 6, 10, 12).

### M2 — Полноценный RBAC по ролям §9.3

- **Цель.** Ввести проверку полномочий по ролям Platform Operator/Administrator/
  Manager во всех guard'ах ядра.
- **Задачи.** `RolesGuard` + `@Roles(...)`; матрица прав ролей (ТЗ §9.3):
  Manager — работа с обращениями без доступа к админ-конфигурации; Administrator —
  управление организацией; Platform Operator — операции уровня платформы вне
  организации; замена мок-guard на реальный во всех модулях; расширяемость набора
  ролей через конфигурацию/сиды (ТЗ §9.4).
- **Тесты.** unit — проверка ролей (разрешение/запрет по каждой роли, отказ
  Manager к админ-операциям); integration — эндпоинт под guard возвращает 403 при
  недостатке прав и учитывает изоляцию арендатора.
- **DoD.** Каждый защищённый эндпоинт проходит серверную проверку роли; мок-guard
  удалён из ядра.

**Статус реализации M2.** M2 RBAC завершён: `RolesGuard` и `@Roles(...)`
подключены к доменным endpoint'ам ядра, unit-проверки живут в
`services/backend/test/unit/roles.guard.spec.ts`, а интеграционный сценарий
`services/backend/test/integration/m2-rbac.spec.ts` подтверждает 401 без сессии,
403 для Manager на административном endpoint'е, tenant-scope enforcement и
доступ Administrator к конфигурации.

### M3 — Аудит действий аутентификации и управления доступом

- **Цель.** Полный аудит безопасности идентичности (ТЗ §9.9, §22.9, §23.8).
- **Задачи.** Писать `audit_events` для: успешных/неуспешных входов, завершения и
  **отзыва** сессий, смены ролей, изменения прав, административных действий
  (create/block организации, создание пользователей). Записи append-only,
  защищены от изменения; ссылки суррогатные (ТЗ §23.8, §22.11).
- **Тесты.** unit — формирование записи аудита по каждому типу действия;
  integration — Backend↔PostgreSQL: событие пишется в `audit_events` при
  входе/отзыве/смене роли и не перезаписывается.
- **DoD.** Все действия аутентификации и управления доступом фиксируются
  (мастер-план §9.4, п.6); косвенно питает CP-8 (аудит как источник событий).

**Статус реализации M3.** M3 Identity завершён для аудита доступа: login
failure/success, logout и tenant-isolated audit path покрыты
`services/backend/test/unit/identity-audit.spec.ts` и
`services/backend/test/integration/telegram-auth.spec.ts`. Для CP-4/CP-5
роль SVC-IDN — поставлять реального принципала и роли, по которым Backend
проверяет AI/Workflow изменения; самодекларированные роли из Workflow-контекста
не являются источником прав. Готовность M4: audit_events остаются стабильной
append-only базой для bootstrap/приглашений и будущих Notification-событий.

### M4 — Bootstrap организаций Platform Operator'ом + приглашения

- **Цель.** Заменить seeded-bootstrap M1 на полноценный self-service провижининг
  и поток приглашений (ТЗ §9.10).
- **Задачи.**
  - `POST /platform/organizations` — провижининг Tenant (изолированная область
    данных, §22.6) через доменный сервис SVC-API.
  - `POST /platform/organizations/{id}/administrators` — создание первого
    Administrator; `invitations` с **`token_hash`**, TTL, одноразовость.
  - `POST /invitations` и приём приглашения: первый вход по приглашению (личность
    устанавливается по токену, а не по «существованию пользователя», ТЗ §9.10,
    шаг 3); канал приглашения не завязан на единственный мессенджер (ТЗ §9.6,
    §9.10) — `contact_type` допускает telegram/email.
  - `POST /platform/organizations/{id}/block` — блокировка организации.
- **Тесты.** unit — генерация/проверка/истечение/одноразовость токена приглашения;
  integration — Backend↔PostgreSQL: bootstrap создаёт Tenant + первого admin,
  приглашение активируется однократно; проверка изоляции (приглашение видно
  только своей организации). e2e «Авторизация» дополняется путём первичной
  активации через приглашение.
- **DoD.** Организация и первый администратор создаются self-service; приглашения
  одноразовы и ограничены по времени; все шаги пишут аудит (ТЗ §9.10, §23.8).

### M5 — Точки расширения email-входа, UX отзыва сессий, харденинг

- **Цель.** Стабилизация и подготовка к резервному входу без его реализации.
- **Задачи.**
  - **Точки расширения резервного email-входа (ТЗ §9.6, БЕЗ реализации):**
    выделить абстракцию провайдера входа (pluggable auth provider); убедиться, что
    `login_codes.purpose` и `invitations.contact_type` поддерживают `email`;
    задокументировать точку подключения. Реализацию email-входа не выполнять.
  - **UX/операции отзыва сессий:** список активных сессий пользователя, массовый
    отзыв (`/users/{id}/sessions:revoke`), самоотзыв (ТЗ §16.4).
  - **Харденинг безопасности:** усиление лимитов/локаута перебора, ротация
    секретов бота через менеджер секретов (ТЗ §23.7), проверка защиты аудита от
    изменения.
- **Тесты.** unit — выбор провайдера входа возвращает Telegram-провайдер (email
  недоступен в MVP); проверка лимитов локаута. integration — сценарии отзыва
  сессий; участие в полном e2e-наборе приёмки (CP-9, мастер-план §8.2).
- **DoD.** Модель аутентификации расширяема под email-вход без изменения
  интерфейсов (ТЗ §9.6); отзыв сессий доступен из UI; критерии приёмки по
  безопасности пройдены.

> **Статус в продакшн-сборке (issue #192).** Backend `.mjs`-прототип удалён.
> Telegram start/verify rate-limiting 429 работает в исполняемом
> `telegram-auth.service.ts` через `telegram-login-rate-limiter.ts`. Лимиты
> настраиваются переменными `TELEGRAM_LOGIN_START_RATE_LIMIT`,
> `TELEGRAM_LOGIN_VERIFY_RATE_LIMIT`,
> `TELEGRAM_LOGIN_RATE_LIMIT_WINDOW_SECONDS`; значения по умолчанию — 10 попыток
> на 60 секунд.

**Статус реализации M5.** Telegram остаётся единственным включённым
MVP-провайдером входа; `login_codes.purpose` допускает
`telegram_login`/`email_login`, `invitations.contact_type` — `telegram`/`email`,
что оставляет точку расширения для будущего email-входа без публикации нового
endpoint-а в C3.auth v1. Для UX/операций сессий добавлены список активных
сессий пользователя, массовый отзыв и самоотзыв через существующий
logout-контракт. Харденинг закреплён production-тестами лимитов/локаута,
append-only аудита и отсутствия хранения сырого кода/токена.

## 6. Точки согласования

### CP-1 (M1) — Telegram-логин для e2e «Авторизация» и «Работа менеджера»

Участники (мастер-план §6): SVC-INT(Web Chat), SVC-CORE, SVC-API, **SVC-IDN**,
SVC-MWS. Роль SVC-IDN — аутентификация и сессии, без которых менеджер не может
войти и обрабатывать обращения.

**Ожидания от смежных сервисов:**

- **SVC-INT** — Telegram-адаптер для **доставки одноразового кода** (контракт
  C2/egress). До готовности адаптера SVC-IDN работает против **мока** доставки.
- **SVC-CORE** — контекст пользователя/организации для последующей работы
  менеджера (сценарий «Работа менеджера»).
- **SVC-ADMIN / SVC-MWS** — **экран входа** (ввод Telegram-имени и кода),
  вызывающий C3.auth; UI без бизнес-логики (ТЗ §5.8).

**Замораживаемый контракт:** **C3.auth** (мастер-план §6, §7.2). Ломающие
изменения — только новой версией (ТЗ §11.8).

**Добавляемые межсервисные тесты:** **contract** — верификация C3.auth
(потребители SVC-ADMIN/MWS); **e2e** — **«Авторизация»** (Telegram-вход) и
участие входа в сценарий «Работа менеджера» (мастер-план §8.2).

### CP-8 (M4, косвенно) — аудит как источник событий

На M3–M4 SVC-IDN пишет `audit_events` о действиях доступа; эти события могут
служить источником уведомлений безопасности для продюсеров/потребителей CP-8
(SVC-NOTIF и др., мастер-план §6). Прямого контракта Identity в CP-8 нет —
взаимодействие через общий журнал аудита (ТЗ §23.8).

## 7. Стратегия тестирования

Соответствует мастер-плану §8 (пирамида: unit → integration → contract → e2e),
покрытие критической логики ядра ≥ 80 % (мастер-план §8.3).

- **Unit.** Генерация/проверка/**истечение** одноразового кода; **одноразовость**
  (повторная проверка использованного кода отклоняется); TTL и истечение сессии;
  отказ по отозванной сессии; проверка ролей (allow/deny по каждой роли);
  генерация/истечение/одноразовость токена приглашения.
- **Integration.** Backend↔PostgreSQL для `login_codes`, `auth_sessions`,
  `invitations` (Testcontainers, мастер-план §8.1); каждый публичный эндпоинт —
  счастливый путь + **проверка изоляции арендатора** + ошибка валидации
  (мастер-план §8.3); guard возвращает 401/403 корректно.
- **Contract.** C3.auth (CP-1) — consumer-driven со стороны SVC-ADMIN/MWS
  (мастер-план §8.4).
- **E2E.** «Авторизация» (Telegram-вход) — M1; участие во входе для «Работа
  менеджера» — M1; полный e2e-набор приёмки — M5/CP-9 (мастер-план §8.2).
- **Безопасность (обязательно).** Перебор кода — **лимиты/локаут** и rate limiting
  (ТЗ §23.5); **одноразовость** и **истечение** кодов и приглашений; хранение
  только хешей (`code_hash`/`token_hash`), сравнение в постоянном времени;
  проверка защиты `audit_events` от изменения (ТЗ §23.8).
