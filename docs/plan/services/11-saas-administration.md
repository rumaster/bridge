# План разработки сервиса SaaS Administration (SVC-ADMIN)

**SVC-ADMIN** — веб-приложение администратора организации (React + Vite +
TypeScript, ТЗ §21): настройка организации и её конфигурации, управление
пользователями/ролями, каналами связи (ТЗ §16.5), Knowledge Base (ТЗ §16.6),
**визуальный редактор Workflow** (ТЗ §16.7 — входит в объём MVP), интерфейс
**AI Onboarding** (ТЗ §16.8), управление Broadcast и настройками уведомлений.
Это **UI-слой без бизнес-логики** (ТЗ §16.9, §21.5): все проверки полномочий,
обработка данных и принятие решений выполняются серверной частью, а приложение
**потребляет Backend API** — сервис является потребителем контрактов, а не их
владельцем.

Документ подчиняется мастер-плану [`docs/plan/README.md`](../README.md) — единому
источнику истины по вехам M0–M5 (§ 5), точкам согласования CP-1…CP-9 (§ 6),
каталогу контрактов C3.*/C4/C5/C8/C10 (§ 7), структуре проекта (§ 3,
`apps/saas-admin`), Definition of Done (§ 9.4) и стратегии тестирования (§ 8).
Здесь эти решения **не переопределяются**. Ключевая веха сервиса — **M3** (точка
согласования **CP-5**). При расхождении приоритет имеет ТЗ
([`docs/MessengerBridge_TZ.md`](../../MessengerBridge_TZ.md)).

## 1. Назначение и границы

SVC-ADMIN реализует административные экраны уровня организации (ТЗ §16, роль
Administrator) — единственный интерфейс управления конфигурацией организации
(ТЗ §16.1). В границы сервиса входят:

- **управление организацией и конфигурацией** — название, описание, часовой
  пояс, язык, параметры AI, ограничения, настройки (ТЗ §16.3);
- **пользователи, роли, приглашения** — создание, блокировка, смена ролей, отзыв
  сессий, приглашения при bootstrap организации (ТЗ §16.4, §9.10);
- **каналы связи** (ТЗ §16.5) — состояние подключения, дата последней проверки,
  используемые Capabilities, журнал ошибок, параметры подключения;
- **Knowledge Base** (ТЗ §16.6) — загрузка/обновление/удаление документов,
  переиндексация, отображение состояния индексации;
- **визуальный редактор Workflow** (ТЗ §16.7 — **в MVP**) — включение/отключение,
  выбор активной версии, создание/редактирование схем в безопасном наборе узлов,
  сохранение новой версии, просмотр истории исполнения и диагностики;
- **AI Onboarding** (ТЗ §16.8) — диалоговый помощник настройки, применяющий
  изменения через Backend API после подтверждения администратором;
- **Broadcast** и **настройки Notification** — управление кампаниями и каналами
  доставки внутренних уведомлений.

**Вне границ.** Сервис не владеет таблицами БД и контрактами, не содержит
бизнес-логики, не выполняет прямых SQL-запросов и не принимает решений о правах
доступа (ТЗ §21.5) — вся логика и данные доступны только через Backend API.
Панель уровня платформы (Platform Operator, ТЗ §9.3) в объём этого плана MVP не
входит; предусматривается архитектурно как отдельный набор полномочий того же
интерфейса.

## 2. Технологии

- **React + Vite + TypeScript** (ТЗ §21.1) — приложение `apps/saas-admin`
  (мастер §3); модульная структура со слоями Presentation / API Client /
  State Management / Routing / Shared Components (ТЗ §21.4).
- **Общая ui-kit** (`packages/ui-kit`, ТЗ §21.3) — формы, таблицы, карточки,
  модальные окна, навигация, уведомления, компоненты работы с файлами;
  дублирование компонентов между приложениями не допускается.
- **api-client** (`packages/api-client`, мастер §3) — TS-клиент,
  **сгенерированный из OpenAPI** Backend API (`packages/contracts/openapi`);
  контрактная совместимость с сервером обеспечивается автогенерацией.
- **State-management** — управление клиентским состоянием и серверным кэшем
  (загрузка/инвалидация ресурсов, оптимистичные обновления форм).
- **WebSocket-клиент** (C7, ТЗ §21.6) — realtime-обновления состояний
  (`channel`/`workflow`/`broadcast`/`notification`), автоматическое обновление UI.
- **Тесты**: **Vitest + Testing Library** (unit/компонентные, мастер §3.1),
  **MSW** (integration против мок-Backend), **Playwright** (e2e, мастер §8).

## 3. Интерфейсы и контракты

Каталог контрактов ведёт мастер-план (§ 7); ниже — только роль SVC-ADMIN как
потребителя. Все REST-вызовы идут под префиксом `/api/v1` (ТЗ §11.8).

### 3.1 Экспортирует

SVC-ADMIN **не предоставляет программного API**. Его «интерфейс» —
пользовательский UI администратора организации (набор экранов). Наружу сервис не
публикует контрактов и не является поставщиком ни в одной точке согласования.

### 3.2 Потребляет (мастер §7.2)

| Контракт | Назначение | Владелец |
|---|---|---|
| **C3.auth** | Вход (Telegram-код), сессия, выход | SVC-IDN |
| **C3.org** | Организация, чтение/изменение конфигурации | SVC-API |
| **C3.users** | Пользователи, роли, отзыв сессий, приглашения (§9.10) | SVC-IDN/API |
| **C3.channels** | Каналы связи, тест подключения, Capabilities (§16.5) | SVC-INT/API |
| **C3.kb** | Knowledge Base: документы, переиндексация (§16.6) | SVC-API |
| **C5** (+ редактор) | Workflow: версии, экземпляры, визуальный редактор (§16.7) | SVC-FBP |
| **C4** (C3.ai) | AI Onboarding: структурированная команда (§16.8) | SVC-AI |
| **C8** | Broadcast: кампании, запуск, статистика | SVC-BCAST |
| **C10** | Notification: список, прочтение, настройки | SVC-NOTIF |
| **C7 (WS)** | События realtime (состояния каналов/Workflow/кампаний/уведомлений) | SVC-CORE/API |

### 3.3 Экран → потребляемые эндпоинты

| Экран | Основные эндпоинты (мастер §7.2) | Контракт |

## 4. Модель данных

SVC-ADMIN **не владеет таблицами БД** и не имеет прямого доступа к PostgreSQL
(ТЗ §21.5). «Модель данных» фронтенда — это **потребляемые через Backend API
ресурсы** и их представление в клиентском состоянии/кэше. Авторитетная схема БД —
в мастер-плане (§ 4); типы DTO приходят из `api-client` (сгенерированы из
OpenAPI).

| Ресурс (отображается/редактируется) | Источник (контракт) | Роль во фронтенде |
|---|---|---|
| Organization, Configuration | C3.org (мастер §4.1) | форма настроек организации |
| User, Role, Invitation | C3.users (мастер §4.2) | таблицы/формы, приглашения |
| Channel, Capabilities | C3.channels (мастер §4.5) | карточки каналов, статусы |
| Knowledge Document | C3.kb (мастер §4.9) | список, загрузка, статус индексации |
| Workflow, WorkflowVersion, WorkflowInstance | C5 (мастер §4.8) | схема в редакторе, история исполнения |
| Broadcast, BroadcastStats | C8 (мастер §4.6) | список кампаний, статистика |
| Notification, NotificationSettings | C10 (мастер §4.7) | лента и настройки уведомлений |

**Клиентское состояние/кэш:** текущая сессия и роли (для условного рендеринга
UI, не для авторизации, ТЗ §9.8), кэш ресурсов с инвалидацией по WS-событиям
(C7), черновик схемы Workflow в редакторе (граф узлов/связей до сохранения новой
версии), состояние диалога AI Onboarding. Персистентного хранилища нет.

## 5. Поэтапный план

Этапы привязаны к общим вехам мастер-плана (§ 5). DoD каждого этапа —
по мастер §9.4. Тесты: **unit** — компоненты/формы/валидация (Vitest + Testing
Library); **integration** — против мок-Backend (**MSW**) или dev-стенда; **e2e** —
Playwright (мастер §8.2). До готовности смежных сервисов разработка идёт против
моков контрактов (§ 3.2).

### M0 — Каркас приложения

- **Цель.** Работающий «скелет» `apps/saas-admin` в общем CI (мастер §9.1).
- **Задачи.** Инициализация Vite + React + TS; роутинг и лейаут; подключение
  `ui-kit` (ТЗ §21.3); интеграция `api-client` из OpenAPI; заглушка
  аутентификации и защищённые маршруты; настройка MSW и Playwright; ленивая
  загрузка модулей (ТЗ §21.7).
- **Тесты.** Unit: рендер каркаса, роутинг, guard защищённого маршрута.
- **DoD.** Зелёный CI на скелете; `api-client` собран из контрактов v1; моки
  MSW подняты.

### M1 — Вход, организация и конфигурация

- **Цель.** Администратор входит в систему и управляет организацией.
- **Задачи.** Экран **входа** (C3.auth: ввод Telegram-имени → одноразовый код →
  сессия, ТЗ §9.5); хранение/продление сессии, выход; экран **организации** и
  редактор **конфигурации** (C3.org, ТЗ §16.3) с серверной валидацией ошибок;
  каркас навигации по разделам; условный рендеринг по роли (ТЗ §9.8).
- **Тесты.** Unit: форма входа, форма конфигурации, отображение ошибок
  валидации. Integration (MSW): сценарий входа и сохранения конфигурации против
  мок-Backend. **e2e «Авторизация»** (Playwright, мастер §8.2) — совместно с
  SVC-IDN на CP-1.
- **DoD.** Мастер §9.4; e2e «Авторизация» зелёный.

**Статус реализации CP-1.** M1 SaaS Administration завершён: вход через C3.auth,
экран организации/конфигурации, logout и обработка ошибок покрыты unit/MSW
тестами `apps/saas-admin/test/**`, e2e «Авторизация»
`apps/saas-admin/test/e2e/saas-admin.auth.spec.ts` и consumer contract
`packages/contracts/consumer/saas-admin-c3.consumer.v1.json`.

### M2 — Каналы связи и Knowledge Base

- **Цель.** Администратор подключает каналы и наполняет базу знаний.
- **Задачи.** Раздел **каналов** (C3.channels, ТЗ §16.5): карточки со статусом
  подключения, датой последней проверки, Capabilities, журналом ошибок; действие
  «проверить подключение»; realtime-статус по WS (C7). Раздел **Knowledge Base**
  (C3.kb, ТЗ §16.6): загрузка/обновление/удаление документов (компонент файлов из
  ui-kit), переиндексация, индикатор состояния индексации.
- **Тесты.** Unit: карточка канала, форма загрузки документа, индикатор
  индексации. Integration (MSW): подключение канала, загрузка и переиндексация;
  проверка ролевого доступа в UI.
- **DoD.** Мастер §9.4.

### M3 — Визуальный редактор Workflow и AI Onboarding (CP-5) — ключевой этап

- **Цель.** Администратор редактирует Workflow в визуальном редакторе и
  применяет конфигурацию через AI Onboarding. Это ключевая ценность платформы
  (ТЗ §3.4, §5.5) и центральный этап SVC-ADMIN.
- **Задачи.**
  - **Визуальный редактор Workflow** (ТЗ §16.7, интеграция с SVC-FBP через C5):
    список Workflow с включением/отключением и выбором активной версии; редактор
    схемы (граф узлов/связей) в **безопасном наборе узлов** (ТЗ §13.13), где
    изменения данных возможны только через узел вызова Backend API (ТЗ §13.5);
    сохранение изменений **как новой версии** (ТЗ §13.10), не влияющей на
    выполняющиеся экземпляры; просмотр истории исполнения и диагностики.
  - **AI Onboarding** (ТЗ §16.8, C4): диалоговый помощник; после подтверждения
    администратором формируется структурированная команда (`POST
    /ai/onboarding:command`), Backend проверяет полномочия и применяет изменения;
    UI отражает результат (обновлённая конфигурация/каналы).
- **Тесты.** Unit: компоненты редактора (палитра узлов, связи, панель свойств),
  валидация схемы, диалог Onboarding. Integration (MSW/dev-стенд): сохранение
  версии Workflow, применение команды Onboarding. **e2e «Admin правит Workflow»**
  и **e2e «AI Onboarding применяет конфиг»** (Playwright, мастер §8.2) — на CP-5
  совместно с SVC-FBP, SVC-AI, SVC-API.
- **DoD.** Мастер §9.4; оба e2e зелёные; контракты C3/C4/C5 стабилизированы на
  CP-5.

### M4 — Broadcast и настройки уведомлений

- **Цель.** Администратор управляет массовыми коммуникациями и уведомлениями.
- **Задачи.** Раздел **Broadcast** (C8): список кампаний, черновик (шаблон,
  фильтр получателей, расписание, ограничение скорости), запуск, статистика и
  realtime-статус по WS. **Настройки Notification** (C10): лента уведомлений,
  отметка «прочитано», управление категориями и каналами доставки
  (web/telegram/email/push, ТЗ §15.4).
- **Тесты.** Unit: форма кампании, таблица статистики, форма настроек
  уведомлений. Integration (MSW): создание и запуск кампании, изменение
  настроек уведомлений.
- **DoD.** Мастер §9.4.

### M5 — Приёмка, доступность и полировка

- **Цель.** Готовность к приёмке (мастер §5, ТЗ §29).
- **Задачи.** Прогон приёмочных админ-сценариев; **доступность** и
  **адаптивность** (Desktop/Tablet, ТЗ §21.8); визуальная регрессия ключевых
  экранов; полировка UX, состояний ошибок/загрузки, локализации; оптимизация
  размеров сборки (ТЗ §21.7).
- **Тесты.** Полный набор e2e админ-сценариев в общем прогоне (мастер §8.2);
  визуальная регрессия; проверка адаптивности.
- **DoD.** Мастер §9.4; участие в CP-9 (полный e2e-набор зелёный).

## 6. Точки согласования

Мастер-план (§ 6) — источник истины по CP. Для SVC-ADMIN релевантны:

- **CP-5 (M3) — ключевая для сервиса.** Участники: **SVC-ADMIN**, **SVC-FBP**
  (визуальный редактор Workflow, ТЗ §16.7), **SVC-AI** (AI Onboarding),
  **SVC-API**. Замораживаются/стабилизируются контракты **C3 + C4 + C5**.
  Добавляемые межсервисные тесты: **e2e «Admin правит Workflow»** и **e2e
  «AI Onboarding применяет конфиг»** (мастер §6, §8.2).
  **Ожидания к смежным сервисам:** к M3 готовы **FBP-движок** с безопасным
  набором узлов и редактором (SVC-FBP, CP-4→CP-5) и **AI Onboarding** (SVC-AI);
  Backend API предоставляет стабильные C3.* для применения изменений.
- **Зависимость от CP-1 (M1).** Экран входа зависит от контракта **C3.auth**
  (SVC-IDN); e2e «Авторизация» (мастер §8.2) выполняется совместно с SVC-IDN.
  До CP-1 вход разрабатывается против мока C3.auth.

Между точками согласования SVC-ADMIN разрабатывается автономно против моков
потребляемых контрактов (§ 3.2) и `api-client`, сгенерированного из OpenAPI.

## 7. Стратегия тестирования

Соответствует мастер §8; специфика фронтенда:

- **Компонентные тесты** форм и редактора (Vitest + Testing Library): валидация
  полей, отображение серверных ошибок, поведение палитры узлов/связей редактора
  Workflow, диалог AI Onboarding.
- **Контрактная совместимость с OpenAPI**: `api-client` генерируется из
  `packages/contracts/openapi`; несовместимость DTO ловится на сборке/типизации
  (автоген), integration-тесты идут против MSW-моков, отражающих контракты.
- **E2E ключевых админ-сценариев** (Playwright): «Авторизация» (M1),
  «Admin правит Workflow» и «AI Onboarding применяет конфиг» (M3), а также
  сценарии каналов/KB/Broadcast/уведомлений в общем прогоне (M5).
- **Проверка ролевого доступа в UI**: условный рендеринг элементов по роли
  (Administrator) — как UX-подсказка; авторитетная авторизация остаётся на
  Backend (ТЗ §9.8), негативные проверки идут против ответов 403 от мок-Backend.
- **Визуальная регрессия** ключевых экранов (организация, каналы, KB, редактор
  Workflow, Broadcast) на M5.
