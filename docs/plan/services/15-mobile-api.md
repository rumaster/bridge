# План разработки сервиса Mobile API (SVC-MOB)

Mobile API — **BFF (Backend-for-Frontend)** для мобильных приложений менеджера
(ТЗ §19): **специализированное представление Backend API** (ТЗ §19.2), которое
**агрегирует** вызовы ядра под мобильные экраны, обеспечивает **оффлайн-синхронизацию**
(дельты/курсоры), доставку **push-уведомлений** (ТЗ §19.4, §15.4), **эффективную
передачу** данных и **независимое версионирование** API (ТЗ §19.6). SVC-MOB **не
реализует бизнес-логику** — отдельная серверная логика для мобильных не допускается
(ТЗ §19.1): вся логика общая и живёт в ядре (SVC-CORE/SVC-API/SVC-IDN), а BFF лишь
**проксирует и переупаковывает** данные. Realtime — через WebSocket (C7), для РФ —
через Edge Cluster (SVC-EDGE, ТЗ §19.5, §7.6). SVC-MOB участвует в **CP-7** (мастер §6).

> Ссылки «ТЗ §…» — на техническое задание; «§…» — на мастер-план
> [`docs/plan/README.md`](../README.md); «M0…M5» — вехи (мастер §5); «CP-7» — точка
> согласования (мастер §6); «C3.\*/C7/C9/C10», «SVC-…» — контракты и сервисы (мастер §7, §2).

## 1. Назначение и границы

**Входит в SVC-MOB (адаптация Backend API под мобильные клиенты):**

- **агрегация запросов и эффективная передача** — сборка «экранных» ответов (список
  Conversation с превью и счётчиками и т. п.) из нескольких вызовов Backend в один;
  компактные DTO, курсорная постраничность, отдача только дельт (экономия трафика);
- **дельта-синхронизация для оффлайн** (ТЗ §19.3 «синхронизация данных») — выдача
  изменений с последнего курсора (диалоги/сообщения/статусы/уведомления), устойчивость
  «оффлайн → онлайн» без потерь и дублей;
- **push-уведомления** (ТЗ §19.4, §15.4) — регистрация устройства/push-токена и
  ретрансляция уведомлений (C10) во внешние провайдеры (FCM/APNs) при недоступности
  WebSocket, с последующей синхронизацией;
- **независимое версионирование** мобильного API (ТЗ §19.6) — изменения не нарушают
  работу ранее опубликованных версий приложений.

**НЕ входит в SVC-MOB (границы):**

- **бизнес-логика** приёма/хранения/маршрутизации, идентификации клиентов, прав — это
  ядро (SVC-CORE/SVC-API/SVC-IDN); отдельная серверная логика для мобильных **запрещена**
  (ТЗ §19.1); SVC-MOB **не владеет доменными таблицами**;
- **прямой доступ к доменной БД** — только **через Backend API** (мастер §4, §22.3);
- **транспорт realtime и переподключение** — WebSocket и авто-reconnect обеспечивают
  SVC-EDGE/SVC-API (мастер §7.3, ТЗ §11.7); SVC-MOB потребляет события C7;
- **буферизация/порядок/дедупликация при разрыве** в РФ-контуре — это SVC-EDGE (буфер
  §7.9, `sequence_number` §7.10, дедуп §11.12); клиент РФ подключается через Edge (§19.5, §7.6);
- **генерация уведомлений** — их формирует SVC-NOTIF (C10); SVC-MOB доставляет их как push.

Доменная модель — мастер §4 (владелец — SVC-DATA); потребляемые контракты (C3.\*, C7,
C9, C10) — `packages/contracts` (мастер §7). План их **не переопределяет**, а
детализирует участок SVC-MOB.

## 2. Технологии

| Область | Решение |
|---|---|
| Язык/фреймворк | TypeScript, **NestJS** (BFF); сервис `services/mobile-api` — отдельный сервис **или** модуль backend (мастер §3). |
| Стиль / вызовы ядра | **BFF-агрегация**: HTTP-клиент к Backend API (`/api/v1`, C3.\*), композиция в «экранные» ответы, без собственной бизнес-логики (ТЗ §19.1–§19.2); таймауты и деградация при недоступности ядра (ТЗ §11.2). |
| Протокол синхронизации | **Курсоры/дельты**: клиент передаёт курсор последней синхронизации, сервис отдаёт изменения после него; идемпотентность по сквозному `idempotency_key` = `message_id` (ТЗ §11.12) при отправке. |
| Push-провайдеры | **FCM** (Android) и **APNs** (iOS); маппинг уведомления C10 → push-payload; хранение push-токенов per user/device (см. §4). |
| Realtime | **WebSocket** (C7, `GET /ws`, авто-reconnect, ТЗ §11.7); при невозможности постоянного соединения — **Push + последующая синхронизация** (ТЗ §19.4). |
| Работа в РФ | Подключение мобильного клиента к **Edge Cluster** (C9/SVC-EDGE), далее — через VPN Tunnel и Communication Core (ТЗ §19.5, §7.6). |
| Версионирование | **Собственная версия** мобильного API в URL, **независимая** от Backend (ТЗ §19.6, §11.8); ломающие изменения — только новая версия. |
| Тестирование | Jest (unit, `*.spec.ts`), Testcontainers/моки (integration против мок-Backend/мок-WS, ТЗ §26.4), contract- и e2e-тесты на CP-7 (мастер §8). |

## 3. Интерфейсы и контракты

SVC-MOB **экспортирует** собственный мобильный API (независимая версия, ТЗ §19.6) и
**потребляет** контракты ядра/сервисов (C3.\*, C7, C10, при РФ — C9). Потребляемые
контракты — в `packages/contracts`; свой мобильный контракт SVC-MOB ведёт отдельно с
независимым semver (ТЗ §19.6, мастер §7.4).

### 3.1 Экспортируемые контракты (мобильный API, собственная версия §19.6)

Мобильный API — тонкий агрегирующий фасад над Backend API. Эндпоинты (под префиксом
**собственной версии**, напр. `/mobile/v1`, независимой от `/api/v1`):

- **`POST /mobile/v1/auth/login/telegram/{start,verify}`**, **`POST .../auth/logout`**,
  **`GET .../auth/session`** — аутентификация (проксирование C3.auth, ТЗ §19.3);
- **`GET /mobile/v1/conversations`** — агрегированный список диалогов с превью и
  счётчиками (сборка из C3.conversations + C3.messages; ≤ 1 с, ТЗ §25.2);
- **`GET /mobile/v1/conversations/{id}/messages`** — история диалога (курсорная
  постраничность; ≤ 2 с, ТЗ §25.2);
- **`POST /mobile/v1/messages`** — отправка **идемпотентно** (сквозной
  `idempotency_key` = `message_id`, ТЗ §11.12; ≤ 1 с) с проксированием в C3.messages;
- **`GET /mobile/v1/notifications`** — агрегированные уведомления (C10; ≤ 1 с, ТЗ §25.2);
- **`GET /mobile/v1/sync`** — **дельта-синхронизация**: по курсору возвращает
  изменившиеся диалоги/сообщения/статусы/уведомления и **новый курсор**;
- **`POST /mobile/v1/devices`** / **`DELETE /mobile/v1/devices/{id}`** — **регистрация**
  устройства/push-токена (per user, FCM/APNs) и отзыв токена.

Все эндпоинты — JSON/UUID/ISO-8601 (ТЗ §11.9), единый формат ошибок (ТЗ §11.11);
валидация, проверка организации и прав — **в ядре** (ТЗ §11.10, §22.6); BFF передаёт
контекст пользователя и не ослабляет проверки.

### 3.2 Потребляемые контракты

| Контракт / источник | От кого | Назначение |
|---|---|---|
| **C3.auth** (аутентификация/сессии) | SVC-IDN | вход, сессия, выход мобильного клиента (ТЗ §19.3). |
| **C3.conversations** (`GET /conversations`, `.../messages`) | SVC-CORE | список диалогов и история для агрегации/синхронизации. |
| **C3.messages** (`POST /messages` идемпотентно, `GET /messages/{id}`) | SVC-CORE | отправка сообщения и статусы (ТЗ §11.12). |
| **C3.clients** (`GET /clients/{id}` и пр.) | SVC-CORE/API | карточка клиента для мобильных экранов (ТЗ §19.3). |
| **C7 — WS Events** (`message.created`, `message.status_changed`, `notification.created`, `typing.*`, …) | SVC-CORE/SVC-API | realtime-события для мобильного клиента (ТЗ §11.7). |
| **C10 — Notification** | SVC-NOTIF | уведомления пользователя → ретрансляция в **push** (FCM/APNs, ТЗ §15.4). |
| **C9 — Edge↔App Tunnel** (при подключении РФ) | SVC-EDGE | мобильный клиент РФ подключается через Edge Cluster/VPN Tunnel (ТЗ §19.5, §7.6). |
| Внешние **push-провайдеры** (FCM/APNs) | внешние сервисы | фактическая доставка push на устройство. |

SVC-MOB — **чистый потребитель** доменных контрактов; своих доменных таблиц не имеет (§4).

## 4. Модель данных

SVC-MOB **не владеет доменными таблицами** и не имеет прямого доступа к доменной БД —
диалоги/сообщения/клиенты/уведомления берутся **через Backend API** (мастер §4, §22.3).
Собственное состояние BFF ограничено **синхронизацией и устройствами**, домен не дублирует:

| Данные (акцент SVC-MOB) | Назначение | Появляется |
|---|---|---|
| **Устройства / push-токены** (`per user`: `user_id`, `organization_id`, `platform` = fcm/apns, `push_token`, `device_id`, `created_at`, `last_seen_at`, `revoked_at`) | адресация push (ТЗ §19.4, §15.4); один пользователь — несколько устройств; отзыв токена при выходе/недоставке. | M4 |
| **Курсоры / состояние синхронизации** (`user_id`/`device_id`, `sync_cursor`, `last_synced_at`) | точка отсчёта дельта-синхронизации «оффлайн → онлайн» (ТЗ §19.3). | M4 |
| **Кэш дельт** (эфемерный, опционально) | временная упаковка изменений для эффективной отдачи мобильному клиенту; не источник истины. | M4 |

**Потребляемые доменные ресурсы** (диалоги, сообщения, клиенты, уведомления) — только
через Backend (C3.\*, C10); каноническая схема — мастер §4.3–§4.4, §4.7 (владелец —
SVC-DATA/SVC-CORE/SVC-NOTIF). Токены/курсоры (если в БД) — схема/миграции у **SVC-DATA**
(мастер §4, §22.3), изоляция по `organization_id` (ТЗ §22.6).

**Инварианты SVC-MOB:** (1) push-токен привязан к пользователю своей организации,
недоставляемый — деактивируется; (2) дельта по курсору **не теряет и не дублирует**
изменения (монотонность); (3) BFF — не источник истины домена (приоритет за ядром).

## 5. Поэтапный план

Каждый этап привязан к вехе (мастер §5): Цель · Задачи · Тесты (unit / integration /
e2e) · DoD (единый — мастер §9.4). Основная работа SVC-MOB — на **M4** (мастер §5.1).

### M0 — Мобильный контракт (собственная версия §19.6) + мок

- **Цель.** Заморозить **собственный мобильный контракт** (независимая версия,
  ТЗ §19.6) для параллельной разработки мобильного приложения против мока.
- **Задачи.** Зафиксировать мобильный API (агрегированные эндпоинты диалогов/сообщений/
  уведомлений, `GET /mobile/v1/sync`, `POST /mobile/v1/devices`, auth-проксирование) с
  **независимым semver** (ТЗ §19.6); поднять **мок мобильного API**; каркас сервиса
  `mobile-api` (потребляемые C3.\*/C7/C10/C9 не изменяются — см. §3.2).
- **Тесты.** unit — валидация DTO, формат курсора синхронизации, маппинг уведомления →
  push-payload (заготовка); contract-заготовки «приложение ↔ SVC-MOB» и потребления C3.\*/C7/C10.
- **DoD.** Мобильный контракт v1 заморожен (**независимый** semver, ТЗ §19.6), мок в CI
  зелёный (мастер §9.4).

### M1 / M2 / M3 — без крупных задач (зависят от готовности ядра/WS/уведомлений)

- SVC-MOB в вехах **M1–M3** крупных задач **не имеет** (мастер §5.1): он агрегирует уже
  существующие возможности, поэтому **зависит от готовности** ядра и C3.\* (**M1**),
  realtime C7 и Edge WS Gateway (**M2**), уведомлений C10 (**M3/CP-8**). До M4 разработка
  идёт **против моков**; по мере готовности C3.\* (M1) и C7 (M2) моки заменяются реальными.

### M4 — ОСНОВНАЯ работа: агрегация, оффлайн-синхронизация, push, realtime, Edge

- **Цель.** Работающий мобильный BFF: агрегированные экраны, устойчивая
  оффлайн-синхронизация, push и realtime; клиенты РФ работают через Edge (срез CP-7).
- **Задачи.**
  - **агрегированные эндпоинты** — сборка «экранных» ответов (диалоги с превью/счётчиками,
    история, уведомления) из вызовов C3.conversations/messages/clients/C10 (ТЗ §19.2–§19.3);
  - **оффлайн-синхронизация** — `GET /mobile/v1/sync` на **дельтах/курсорах**: изменения
    после курсора + новый курсор; устойчивость «оффлайн → онлайн» без потерь/дублей (ТЗ §19.3);
  - **идемпотентная отправка** — `POST /mobile/v1/messages` со сквозным
    `idempotency_key` = `message_id` (ТЗ §11.12), проксирование в C3.messages;
  - **push-уведомления** — регистрация устройства/токена (`POST /mobile/v1/devices`),
    ретрансляция C10 → **FCM/APNs**, fallback «нет WS → push + sync» (ТЗ §19.4, §15.4);
  - **realtime через WS** — потребление C7-событий (`message.created`,
    `message.status_changed`, `notification.created`, `typing.*`);
  - **подключение клиентов РФ через Edge** — маршрутизация на **Edge Cluster/VPN Tunnel**
    (C9/SVC-EDGE, ТЗ §19.5, §7.6); консистентность при разрыве даёт Edge-буфер/порядок/
    дедуп (§7.9, §7.10, §11.12), SVC-MOB её потребляет.
- **Тесты.**
  - **unit** — **агрегаторы** (композиция C3.\* → «экранный» DTO), **логика
    дельта-синхронизации/курсоров** (монотонность, нет потерь/дублей), **маппинг push**
    (C10 → FCM/APNs), идемпотентный ключ отправки;
  - **integration** — против **мок-Backend/мок-WS** (ТЗ §26.4): **оффлайн → онлайн**
    синхронизация (накопление → выдача по курсору), **доставка push** через мок-провайдер,
    проксирование `POST /messages` с дедупликацией; бюджеты (диалоги ≤ 1 с, история ≤ 2 с,
    уведомления ≤ 1 с, ТЗ §25.2);
  - **e2e** — **«Потеря соединения»** (мобильная часть) и **мобильный realtime** на M4
    (CP-7, ТЗ §26.6): клиент РФ через Edge, разрыв → восстановление → синхронизация без
    потерь/дублей и без нарушения порядка в рамках Endpoint.
- **DoD.** Агрегированные эндпоинты, sync (дельты/курсоры), push и realtime работают;
  клиент РФ ходит через Edge; e2e «Потеря соединения» зелёный; идемпотентность/изоляция
  арендатора соблюдены (мастер §9.4).

### M5 — Независимое версионирование §19.6, приёмка, производительность, устойчивость

- **Цель.** Совместимость версий мобильного API, целевая производительность и
  устойчивость синхронизации; приёмка.
- **Задачи.** **Независимое версионирование** (ТЗ §19.6) — изменения API не ломают ранее
  опубликованные версии приложений (поддержка предыдущей версии, тесты совместимости);
  **производительность** (ТЗ §25.2) — подтверждение бюджетов агрегированных вызовов;
  **устойчивость синхронизации** — повторные/частичные sync, восстановление после долгого
  оффлайна, доставляемость push (ретраи/деактивация мёртвых токенов); приёмка (CP-9).
- **Тесты.** unit — **совместимость версий** мобильного API (старый клиент → новая
  версия сервиса), устойчивость курсорной синхронизации к повторам; integration —
  нагрузочные пробники агрегированных эндпоинтов (бюджеты §25.2), доставляемость push
  через мок-провайдер (ретраи); e2e — участие в полном наборе ТЗ §26.6 (регрессия, CP-9).
- **DoD.** Независимое версионирование подтверждено (старые клиенты не сломаны, ТЗ
  §19.6); NFR §25.2 соблюдены; синхронизация устойчива; приёмка (мастер §9.4, CP-9).

## 6. Точки согласования

Явно: ожидания смежных сервисов · замораживаемый контракт · межсервисные тесты (мастер §6).

### CP-7 (M4) — Подключение мобильных клиентов РФ через Edge и консистентная синхронизация

- **Участники.** SVC-MOB (мобильная часть); **SVC-EDGE** (Edge/VPN/буфер) и
  **SVC-CORE** (порядок/идемпотентность); совместно с SVC-CHAT в общем сценарии CP-7.
- **Ожидания.**
  - **SVC-CORE** (**M1**) отдаёт/принимает данные по **C3.\*** и события по **C7**,
    поддерживает сквозной `idempotency_key`/`sequence_number` (порядок в Endpoint, дедуп
    после выгрузки буфера, ТЗ §7.10, §11.12);
  - **SVC-EDGE** готов: **WS Gateway** в App-контуре (**M2**) и полный **Edge + VPN +
    буфер + порядок** (**M4**) — клиент РФ подключается через Edge (ТЗ §19.5, §7.6),
    буферизация при разрыве и восстановление — на Edge (§7.9);
  - для мобильной части — **консистентная синхронизация при разрыве**: буфер/порядок/
    идемпотентность (§7.9/§11.12) без потерь, дублей и перестановок в Endpoint, а
    `GET /mobile/v1/sync` корректно доотдаёт накопленное.
- **Замораживаем.** Сопряжение потребляемых **C9** (Edge↔App tunnel) и **C7**
  (WS-события) с мобильной частью; **собственный мобильный контракт** SVC-MOB — **независимо**
  (ТЗ §19.6). Заморозка — мастер §6, §9.3.
- **Тесты.** межсервисные e2e — **«Потеря соединения»** (мобильная часть) и мобильный
  realtime (ТЗ §26.6); **contract** потребления C9/C7 и мобильного контракта. Ссылка —
  мастер §6, §8.4.

## 7. Стратегия тестирования

Соответствует мастер §8 (пирамида unit/integration/contract/e2e). Специфические проверки SVC-MOB:

- **Корректность дельта-синхронизации.** По курсору изменения выдаются ровно один раз
  (**нет потерь/дублей**, монотонность); повторный `sync` идемпотентен (ТЗ §19.3).
- **Идемпотентная отправка.** Повтор отправки с тем же сквозным `idempotency_key` =
  `message_id` не создаёт дубль (ТЗ §11.12).
- **Доставка push.** C10 маппится в FCM/APNs-payload и доставляется через мок-провайдер;
  недоставляемый токен деактивируется; fallback «нет WS → push + sync» (ТЗ §19.4, §15.4).
- **Оффлайн → онлайн через Edge.** Клиент РФ через Edge; при разрыве/восстановлении
  данные догоняются без потерь/дублей и порядка в Endpoint (§7.9/§7.10/§11.12).
- **Совместимость версий API (§19.6).** Изменение API не ломает опубликованные версии;
  старый клиент работает с новой версией сервиса.

Обязательные integration-связки (ТЗ §26.4) — против **мок-Backend/мок-WS**; e2e-участие —
**«Потеря соединения»** (мобильная часть, M4, мастер §8.2). Общая стратегия — мастер §8.

## 8. Риски и зависимости

| Риск / зависимость | Влияние | Митигирование |
|---|---|---|
| **Сложность оффлайн-синхронизации и консистентности** (ТЗ §11.12) | Потери/дубли/перестановки при «оффлайн → онлайн» | Дельты/курсоры с монотонностью и идемпотентностью; сквозной `idempotency_key`; опора на порядок/дедуп Edge/ядра (§7.9/§7.10/§11.12); e2e «Потеря соединения» на CP-7. |
| **Фрагментация версий мобильных клиентов** (ТЗ §19.6) | Старые приложения ломаются при изменениях API | **Независимое версионирование** мобильного API; поддержка предыдущей версии; тесты обратной совместимости (M5). |
| **Доставляемость push** (FCM/APNs) | Пропущенные уведомления, «мёртвые» токены | Ретраи, деактивация недоставляемых токенов, fallback «нет WS → push + синхронизация» (ТЗ §19.4); маппинг под оба провайдера. |

| Зависимость от **готовности ядра/WS/уведомлений** (C3.\* — M1, C7/Edge — M2/M4, C10/SVC-NOTIF — M3) и схемы **SVC-DATA** | Блокировка основной работы M4 | Работа против замороженных контрактов и их моков; замена моков реальными вызовами по мере готовности (M1→M2→M4); схема токенов/курсоров у SVC-DATA (мастер §4, §22.3); заморозка на CP (мастер §6, §9.3). |
| **Соблазн бизнес-логики в BFF** (нарушение ТЗ §19.1) | Дублирование логики, расхождение поведения | Строго агрегация/проксирование; бизнес-логика и валидация — только в ядре (ТЗ §11.10, §19.2). |
