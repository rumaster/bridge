# План разработки сервиса Integration Platform (SVC-INT)

Настоящий документ детализирует участок работ сервиса **Integration Platform
(Adapters)** и подчиняется мастер-плану [`docs/plan/README.md`](../README.md) —
единому источнику истины по сквозным решениям (вехи M0–M5 § 5, точки согласования
§ 6, контракты § 7, модель данных § 4, DoD § 9.4, тесты § 8). Эти решения здесь
**не переопределяются** — раскрывается только специфика Integration Platform.

SVC-INT — **набор адаптеров каналов**. Каждый Adapter преобразует внешний
протокол канала (Telegram, MAX, VK, WhatsApp Business, Email, SMS, Web Chat) в
**каноническую модель сообщения C1** (ТЗ §8.4) и обратно и **публикует возможности
канала** (Capability Model, ТЗ §10.6). По § 2 мастер-плана это **вынесенный
(деградируемый)** сервис (ТЗ §11.2): недоступность внешнего канала не должна ронять
ядро (§5.1, §5.4). SVC-INT — **потребитель** C1 (Message Model) и C2
(Ingress/Egress), но **владелец** C6 (Capability Descriptor, § 7.1 мастер-плана).
Участвует в **CP-1** (M1, Web Chat), **CP-2** (M2, Capability) и **CP-6** (M4,
массовая доставка).

> Ссылки «ТЗ §X.Y» — на техническое задание; «§ N» — на мастер-план; «CP-N» —
> точки согласования (§ 6 мастер-плана); «M0…M5» — общие вехи (§ 5); «C1…C10» —
> контракты (§ 7 мастер-плана).

---

## 1. Назначение и границы

**Владеет** (в границах SVC-INT):

- реализациями **Adapter** каналов MVP: Telegram, MAX, VK, WhatsApp Business,
  Email, SMS, Web Chat (ТЗ §10.4);
- **нормализацией вход/исход** — внешний формат ⇄ C1 (ТЗ §10.5) через **C2**;
- **Capability Model** (ТЗ §10.6) — публикацией возможностей канала как **C6**;
- **ретраями и обработкой ошибок доставки** на стороне адаптера (ТЗ §10.8):
  регистрация ошибки, оценка повторяемости, повтор с бэкоффом, уведомление ядра;
- контролем соединения с внешним API (вебхуки/long-poll, лимиты, деградация).

**НЕ входит** в границы SVC-INT (принадлежит ядру — SVC-CORE/API):

- **бизнес-логика диалогов, маршрутизация, принятие решений** (ТЗ §4.8, §10.10);
- **определение C1 и контракт C2** — **владелец SVC-CORE** (§ 7.1); SVC-INT их
  только **потребляет**;
- **прямой доступ к БД** — его нет ни у кого, кроме Backend (ТЗ §22.3): каналы,
  возможности и сообщения SVC-INT читает/пишет **только через Backend/ядро**;
- **хранение секретов** — хранится ссылка `credentials_ref`, не сам секрет (ТЗ
  §23.7, § 4.5).

SVC-INT — исключительно **транспортно-преобразующий** слой (ТЗ §10.1, §10.10):
инкапсулирует особенности каждого канала, чтобы ядро оставалось независимым от
транспорта (ТЗ §5.6, §8.8).

## 2. Технологии

| Область | Решение | Обоснование / ссылка |
|---|---|---|
| Уровень исполнения | **вынесенный сервис**, отдельные процессы адаптеров | ТЗ §11.2 (деградируемый); независимое масштабирование каждого канала (ТЗ §10.9) |
| Приём входящих | по каналу: **вебхуки** (Telegram/WhatsApp/VK/MAX/Web Chat) или **long-poll**; для Email — IMAP/приём почты; для SMS — вебхук провайдера | ТЗ §10.2, §10.3; способ инкапсулирован в Adapter |
| Публикация в ядро | HTTP-вызов **C2 Ingress** → `POST /internal/ingress/messages` | § 7.1 мастер-плана (владелец контракта — SVC-CORE) |
| Исходящие (Egress) | приём delivery-запроса от ядра (**C2 Egress**) + внутренняя **очередь исходящих** с ретраями и бэкоффом | ТЗ §10.8; §11.2 (асинхронная постановка задач с ретраями) |
| Идемпотентность доставки | сквозной `idempotency_key` (= `message_id`) сохраняется до внешнего канала; повтор с обработанным ключом отбрасывается | ТЗ §11.12; согласовано с §7.10 |
| Конфигурация и секреты канала | конфигурация (`channels`, `adapter_capabilities`) — **через Backend API**, без прямого доступа к БД (ТЗ §22.3); секреты — в менеджере секретов, в конфигурации хранится `credentials_ref` (ссылка), не сам секрет | § 4.5 мастер-плана; ТЗ §23.7 |
| Размещение (ПДн) | первичная фиксация входящих ПДн субъектов РФ — в RF-контуре; исходящий вызов к внешнему API может идти из доступного кластера | ТЗ §7.13, §7.14 (параметр инфраструктуры) |
| Тесты | Jest; integration — **мок внешнего API канала** + реальная связка Backend↔Integration (Testcontainers) | § 3.1, § 8.1 мастер-плана; ТЗ §26.4 |
| Health/metrics | `GET /health`, `GET /metrics` на сервисе | § 7.2 мастер-плана; ТЗ §24.4 |

Код адаптеров — в `services/integration-platform/src/adapters/{telegram,max,vk,
whatsapp,web-chat,email,sms}/`, Capability Model — в `.../src/capability/` (§ 3).

## 3. Интерфейсы и контракты

### 3.1 Экспортирует (владелец / совместно)

| Что | Форма | Направление / потребитель | Веха готовности |
|---|---|---|---|
| **C6 Capability Descriptor** (владелец SVC-INT) | набор возможностей канала: текст, изображения, файлы, голос, видео, кнопки, реакции, индикатор набора, подтверждение прочтения, удаление, редактирование (ТЗ §10.6) | INT → CORE | **M0** (определение) → **M2** (наполнение по каналам) |
| Публикация входящих (**C2 Ingress**, потребление) | `POST /internal/ingress/messages` — нормализованное C1 сообщение | Adapter → CORE | M1 (Web Chat) → M2 (остальные) |
| Эндпоинты управления каналами (**C3.channels**, совместно с SVC-API) | `GET/POST /channels`, `POST /channels/{id}:test`, `GET /channels/{id}/capabilities` | Backend → Frontend (SVC-ADMIN) | M1 (каркас) → M2 (полно) |

**C6 (Capability Descriptor).** Владелец — SVC-INT: каждый Adapter публикует
описание возможностей (ТЗ §10.6), а Communication Core решает по **возможностям**,
а не по названию канала. Набор MVP из ТЗ §10.6 (`text`, `image`, `file`, `voice`,
`video`, `buttons`, `reactions`, `typing_indicator`, `read_receipt`, `delete`,
`edit`) материализуется в `adapter_capabilities` (§ 4) и отдаётся через `GET
/channels/{id}/capabilities`; ядро им ограничивает исход (не слать кнопки в канал
без `buttons`).

**C3.channels (совместно с SVC-API).** Эндпоинты управления каналами — часть
публичного Backend API (§ 7.2, ТЗ §16.5): `GET/POST /channels`, `POST
/channels/{id}:test`, `GET /channels/{id}/capabilities`. Публичный REST и проверки
полномочий — на стороне SVC-API/ядра (ТЗ §11.1, §5.8); SVC-INT поставляет логику
подключения/проверки и наполняет Capability Model.

### 3.2 Потребляет

| Что | Владелец | Использование в SVC-INT |
|---|---|---|
| **C1 Message Model** (ТЗ §8.4) | SVC-CORE | целевой формат нормализации: результат приёма — C1, вход доставки — C1 |
| **C2 Egress** (Core → Adapter, доставка) | SVC-CORE | ядро передаёт сформированный ответ адаптеру для доставки в канал |
| Схема каналов/возможностей (`channels`, `adapter_capabilities`) | SVC-DATA | читается/пишется **через Backend** (ТЗ §22.3), не напрямую |
| Секреты каналов (по `credentials_ref`) | менеджер секретов (ТЗ §23.7) | разрешение ссылки в реальный токен при обращении к внешнему API |

Контракты C1/C2 SVC-INT **не определяет** — они замораживаются SVC-CORE на CP-1
(§ 6); до заморозки SVC-INT работает против **моков** C1/C2 (§ 1.2).

## 4. Модель данных

Схема авторитетна в мастер-плане **§ 4.5** (владелец — SVC-DATA, § 4.11); ниже она
**не переопределяется** — показан смысл таблиц для SVC-INT и этап появления.

```sql
channels(                                   -- подключённые каналы организации (ТЗ §16.5)
  id uuid PK, organization_id uuid, channel_type text, name text,
  status text,                              -- connected|error|disabled
  credentials_ref text,                     -- ССЫЛКА на секрет (ТЗ §23.7), НЕ сам секрет
  config jsonb, last_check_at timestamptz, created_at timestamptz)

adapter_capabilities(                       -- Capability Model (ТЗ §10.6), материализация C6
  id uuid PK, channel_id uuid FK, capability text, supported boolean)
```

- `channels` — арендо-зависимая (`organization_id NOT NULL`, RLS § 4, ТЗ §22.6);
  `credentials_ref` — **ссылка** на секрет (токен в БД не хранится, ТЗ §23.7);
  `status`/`last_check_at` наполняются при `:test` (ТЗ §16.5).
- `adapter_capabilities` — материализация **C6**: пара (`capability`, `supported`),
  отдаётся через `GET /channels/{id}/capabilities`.

**Этап появления.** Обе таблицы создаёт SVC-DATA к **M2** (§ 4.2, § 6, CP-2). На
**M1** для среза Web Chat достаточно минимального представления канала; полное
наполнение Capability Model — на M2.

## 5. Поэтапный план (по вехам M0…M5)

Разбивка привязана к общим вехам (§ 5 мастер-плана). Тесты каждого этапа: **unit**
(нормализация вход/исход канала, маппинг возможностей, ретраи/бэкофф),
**integration** (Backend↔Integration через **мок внешнего API**, ТЗ §26.4),
**e2e** (сквозной сценарий вехи).

### 5.1 M0 — контракт потребления C2 и определение C6 + мок адаптера

- **Цель.** Согласовать потребление **C2** (Ingress/Egress) и **определить C6**
  (Capability Descriptor); дать ядру и Frontend работающий **мок адаптера**.
- **Задачи.**
  1. Зафиксировать (с SVC-CORE) потребление **C2**: вызов Ingress `POST
     /internal/ingress/messages` и приём Egress (Core→Adapter); мок C1/C2 в
     `packages/contracts` (§ 1.2).
  2. **Определить контракт C6** (владелец SVC-INT): перечень возможностей (ТЗ
     §10.6), схема дескриптора, публикация в `packages/contracts`.
  3. **Мок-адаптер** (принимает C2 Egress, эмулирует приём → Ingress), каркас
     сервиса, `GET /health`, `GET /metrics` (ТЗ §24.4).
- **Тесты.** *unit:* валидатор схемы C6, сериализация C1 на моке. *integration:*
  мок-адаптер ↔ мок ядра (входящее → Ingress; Egress → «канал»-заглушка). *e2e:*
  участие как зависимость в поднятии скелета (зелёный CI, § 9.1).
- **DoD.** § 9.4; **C6 v1 заморожен**, мок C2 согласован с SVC-CORE.

### 5.2 M1 — адаптер Web Chat (первый канал вертикального среза)

- **Цель.** Дать **первый реальный канал** для сквозного сценария «Web Chat: приём
  и ответ» (CP-1) в связке с SVC-CHAT и SVC-CORE.
- **Задачи.**
  1. Реализовать **Web Chat Adapter**: нормализация входящего в **C1** и публикация
     через **C2 Ingress**; доставка ответа (**C2 Egress**) в Web Chat.
  2. Опубликовать **C6** Web Chat (базовые возможности `text`, `image`, `file`,
     `typing_indicator`, `read_receipt` — по факту поддержки, ТЗ §10.6).
  3. Каркас **C3.channels**: подключение/отдача возможностей для Web Chat.
- **Тесты.** *unit:* нормализация вход/исход Web Chat (текст/вложения) в C1 и
  маппинг возможностей. *integration:* Backend↔Integration (ТЗ §26.4) — приём →
  Ingress → ядро; ответ → Egress → доставка (мок канала). *e2e:* **CP-1** «Web
  Chat: приём и ответ» (ТЗ §26.6, § 8.2).
- **DoD.** § 9.4 + добавлены contract-тест **INT↔CORE** и e2e CP-1 (§ 6).

### 5.3 M2 — адаптеры Telegram/Email/SMS/VK/MAX/WhatsApp + наполнение Capability Model

- **Цель.** **Омниканальность**: сообщение из внешнего мессенджера доходит до
  менеджера и обратно; наполнить **Capability Model** для каждого канала (CP-2).
- **Задачи.**
  1. Адаптеры **Telegram**, **Email**, **SMS**, **VK**, **MAX**, **WhatsApp
     Business**: нормализация вход/исход в C1 (ТЗ §10.5), приём по вебхукам/
     long-poll/IMAP по каналу, инкапсуляция особенностей внешнего API (ТЗ §10.7).
  2. Наполнить **C6** каждого канала (`adapter_capabilities`): текст/медиа/кнопки/
     реакции/индикатор/прочтение/удаление/редактирование — по факту (ТЗ §10.6).
  3. Полный **C3.channels**: `POST /channels/{id}:test`, `GET
     /channels/{id}/capabilities`; секреты — по `credentials_ref` (ТЗ §23.7).
- **Тесты.** *unit:* нормализация вход/исход **каждого канала** в C1 и корректность
  Capability-маппинга адаптера. *integration:* Backend↔Integration **через мок
  внешнего API** каждого канала — Ingress и Egress; проверка `:test` и отдачи
  возможностей. *e2e:* **CP-2** «Telegram: приём и ответ» (ТЗ §26.6); per-adapter
  contract-тесты.
- **DoD.** § 9.4 + **C2+C6 заморожены** на CP-2; per-adapter contract-тесты зелёные.

### 5.4 M3 — без крупных задач у SVC-INT

- **Цель.** Веха **M3** (программируемость: Workflow-редактор, AI Onboarding,
  Notification) **не содержит крупных задач для SVC-INT** (§ 5.1, строка «—»).
- **Задачи.** Держать стабильными контракты C2/C6; при необходимости — мелкие
  правки адаптеров под события ядра для Workflow (без изменения публичных
  контрактов). Крупные интеграционные работы отсутствуют.
- **Тесты.** Регрессия unit/integration адаптеров M2 на каждом PR (§ 8.3); e2e M3
  SVC-INT не ведёт.
- **DoD.** § 9.4 (для мелких правок, если появятся); контракты не изменены.

### 5.5 M4 — ретраи, rate limiting, идемпотентная доставка

- **Цель.** Надёжная и **массовая доставка через адаптеры** (CP-6): ретраи и
  обработка ошибок (ТЗ §10.8), rate limiting на канал, **идемпотентность** (без
  дублей).
- **Задачи.**
  1. **Ретраи и обработка ошибок доставки** (ТЗ §10.8): регистрация ошибки, оценка
     повторяемости, повтор с **экспоненциальным бэкоффом**, уведомление ядра;
     фиксация попыток в `message_delivery_attempts` (§ 4.4) через Backend.
  2. **Rate limiting на канал** — лимиты внешних API, изоляция нагрузки между
     каналами (ТЗ §10.9), backpressure при исчерпании.
  3. **Идемпотентная доставка**: сквозной `idempotency_key` (= `message_id`) идёт
     до внешнего канала; повтор с обработанным ключом отбрасывается (ТЗ §11.12;
     согласовано с §7.10) — совместимость at-least-once ретраев и отсутствия дублей.
- **Тесты.** *unit:* логика **ретраев/бэкоффа** (расписание, предел, классификация
  повторяемых/неповторяемых ошибок), маппинг лимитов канала. *integration:*
  Backend↔Integration через мок внешнего API — **ретрай без дублей** (повтор того
  же `idempotency_key` не создаёт второе внешнее сообщение), rate limit, запись
  `message_delivery_attempts`. *e2e:* **CP-6** «Broadcast: доставка кампании» (ТЗ
  §26.6) с ретраями/лимитами.
- **DoD.** § 9.4 + доставка идемпотентна (тест «повтор без дубля»); CP-6 зелёный.

### 5.6 M5 — отказоустойчивость всех каналов и деградация

- **Цель.** **Стабилизация и приёмка** (CP-9): отказоустойчивость всех каналов,
  корректная деградация при недоступности внешнего API.
- **Задачи.**
  1. **Деградация при недоступности канала**: внешний API недоступен → ядро **не
     блокируется** (ТЗ §11.2, §5.1, §5.4); приём/доставка по другим каналам идут,
     недоставленное — в очередь/повтор.
  2. Отказоустойчивость адаптеров: таймауты, ограничение параллелизма (bulkhead),
     circuit breaker на «падающий» канал (ТЗ §11.2).
  3. Участие в полном наборе e2e (ТЗ §26.6) и проверке нагрузки/деградации (§25.11).
- **Тесты.** *unit:* поведение при таймауте/ошибке внешнего API (переход в
  деградацию, без исключения наружу). *integration:* мок внешнего API «падает» —
  ядро продолжает работу, другие каналы доставляются, недоставленное повторяется.
  *e2e:* участие в наборе § 26.6 как канал-транспорт; проба деградации
  «недоступность внешнего API».
- **DoD.** § 9.4 + подтверждена деградация «канал недоступен → ядро работает».

## 6. Точки согласования (ЯВНО)

Между CP SVC-INT разрабатывается автономно против **моков C1/C2** (§ 1.2). Ниже —
ожидания, замораживаемый контракт и добавляемые межсервисные тесты для каждой
относящейся к SVC-INT точки (§ 6, § 11: SVC-INT → CP-1, CP-2, CP-6).

**CP-1 (M1) — с SVC-CORE/CHAT** (участники: SVC-INT(Web Chat), SVC-CORE, SVC-API,
SVC-IDN, SVC-MWS).
- *Ожидания.* Готов Web Chat Adapter (вход/исход, Ingress, Egress); менеджер видит
  сообщение и отвечает.
- *Контракт.* На примере Web Chat **замораживаются C1 и C2** (владелец SVC-CORE);
  SVC-INT фиксирует потребление и публикует C6 Web Chat.
- *Тесты.* e2e «Web Chat: приём и ответ» (ТЗ §26.6); **consumer-driven contract
  INT↔CORE** (§ 8.4): SVC-INT как потребитель C2 публикует ожидания.

**CP-2 (M2) — с SVC-CORE** (участники: SVC-INT(Telegram…), SVC-CORE).
- *Ожидания.* Работают адаптеры Telegram/Email/SMS/VK/MAX/WhatsApp, для каждого
  наполнена **Capability Model**; входящее из внешнего мессенджера доходит до
  менеджера и обратно.
- *Контракт.* Замораживаются **C2 + C6**: ядро решает по возможностям канала (ТЗ
  §10.6), а не по названию.
- *Тесты.* e2e «Telegram: приём и ответ» (ТЗ §26.6); **per-adapter contract-тесты**
  (каждый Adapter — потребитель C2 и поставщик C6).

**CP-6 (M4) — с SVC-BCAST/CORE** (участники: SVC-BCAST, SVC-CORE, SVC-INT).
- *Ожидания.* Кампания превращается в сообщения и доставляется **через единый
  механизм ядра** и адаптеры; соблюдаются лимиты каналов, ретраи без дублей.
- *Контракт.* C8 (Broadcast, владелец SVC-BCAST) + C1/C2; SVC-INT — исполнитель
  доставки (rate limit/ретраи/идемпотентность, ТЗ §10.8, §11.12).
- *Тесты.* e2e «Broadcast: доставка кампании» (ТЗ §26.6); контроль отсутствия
  дублей по `idempotency_key` и соблюдения rate limit на канал.

## 7. Стратегия тестирования

Соответствует § 8 мастер-плана (ТЗ §26). Специфика SVC-INT — **мок внешнего API
канала** во всех integration-тестах (реальные внешние сервисы в CI не вызываются,
ТЗ §26.3), реальная связка Backend↔Integration через Testcontainers (ТЗ §26.4).

- **Нормализация каждого канала в C1.** Для **каждого** адаптера (Web Chat,
  Telegram, MAX, VK, WhatsApp, Email, SMS) — unit-тесты преобразования внешний
  формат ⇄ C1 (ТЗ §10.5); краевые случаи вложений и типов сообщений.
- **Корректность Capability на приём/исход.** Дескриптор C6 соответствует реально
  поддерживаемым возможностям (ТЗ §10.6); ядро не формирует неподдерживаемый исход
  (например, кнопки в канал без `buttons`).
- **Ретраи без дублей (идемпотентность).** Повтор того же `idempotency_key`
  (= `message_id`) не создаёт второе внешнее сообщение (ТЗ §11.12); бэкофф и предел
  попыток (`message_delivery_attempts`, § 4.4).
- **Недоступность внешнего API.** Таймаут/ошибка → адаптер в деградацию, **ядро не
  падает** (ТЗ §11.2, §5.4); circuit breaker/bulkhead изолируют «падающий» канал
  (ТЗ §10.9).
- **Contract-тесты per-adapter.** Пара **INT↔CORE** — consumer-driven contracts
  (§ 8.4): каждый Adapter как потребитель C2 и поставщик C6, артефакты в
  `packages/contracts`; предотвращают дрейф C2/C6 до e2e.

Целевые показатели (§ 8.3): каждый канал покрыт unit-тестом нормализации; каждый
эндпоинт `C3.channels` — минимум одним integration-тестом (включая изоляцию
арендатора); каждая CP (CP-1/CP-2/CP-6) — минимум один contract- и один e2e-тест.

## 8. Риски и зависимости

| Риск | Влияние | Митигирование |
|---|---|---|
| **Различие возможностей каналов** (текст-only vs кнопки/реакции/редактирование) | некорректный исход, потеря функций | **Capability Model / C6** (ТЗ §10.6): ядро решает по возможностям, а не по названию канала; неподдерживаемое не отправляется (§ 3.1, § 7) |
| **Лимиты внешних API** (rate limit, квоты) | троттлинг, потеря доставки | **rate limiting на канал** и бэкофф (M4, ТЗ §10.8, §10.9); backpressure; изоляция нагрузки между каналами |
| **Хранение секретов каналов** (токены/ключи) | компрометация арендатора | секреты — только в менеджере секретов; в схеме — `credentials_ref`, не сам секрет (ТЗ §23.7, § 4.5) |
| **Недоступность канала не должна блокировать ядро** | нарушение «Communication First» | **деградация** (M5): вынесенный сервис, таймауты/circuit breaker/bulkhead (ТЗ §11.2, §5.4); недоставленное — в очередь/повтор, ядро продолжает работу |
| **Дубли при at-least-once ретраях** (ТЗ §10.8, §11.12) | двойная доставка клиенту | **идемпотентная доставка** по сквозному `idempotency_key` до внешнего канала (M4); тест «повтор без дубля» (§ 7) |
| **Дрейф контрактов C2/C6** при параллельной разработке | ломает интеграцию на CP | contract-first (M0), **per-adapter contract-тесты** (§ 8.4 мастер-плана), заморозка на CP-1/CP-2 (§ 6) |
| **Размещение Adapter и ПДн РФ** (ТЗ §7.13, §7.14) | юридический риск | первичная фиксация входящих ПДн субъектов РФ — в RF-контуре; исходящий вызов к API — из доступного кластера; согласуется с SVC-DATA/SVC-EDGE |

**Зависимости.** SVC-INT зависит от **SVC-CORE** (владелец C1/C2, заморозка на
CP-1), **SVC-API** (публичный REST `C3.channels` и единый доступ к БД, ТЗ §22.3),
**SVC-DATA** (схемы `channels`/`adapter_capabilities` к M2, § 6) и менеджера
секретов (ТЗ §23.7). От SVC-INT зависят **SVC-CORE** (доставка через адаптеры),
**SVC-BCAST** (доставка кампаний, CP-6), **SVC-ADMIN** (управление каналами, ТЗ
§16.5). Как вынесенный сервис, SVC-INT не на критическом пути M0/M1 ядра (§ 10.1):
ядро разрабатывается против мока адаптера до CP-1.
