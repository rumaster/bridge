# План разработки сервиса Notification Platform (SVC-NOTIF)

Notification Platform — **вынесенный деградируемый сервис** (мастер §2, ТЗ §11.2)
внутренних уведомлений **сотрудникам платформы** (Administrator, Manager, ТЗ §15.3):
приём событий от продюсеров, **генерация** и **категоризация** уведомлений по
категориям (ТЗ §15.5), **доставка по каналам** — Web Interface, Telegram Console,
электронная почта, Push (ТЗ §15.4), **пользовательские настройки подписок**
(индивидуально на пользователя, ТЗ §15.6) и статус прочтения. Сервис **не содержит
бизнес-логики коммуникации** (ТЗ §15.7) и **не доставляет сообщения клиентам** —
это Broadcast (SVC-BCAST) и ядро (SVC-CORE); уведомления адресованы исключительно
сотрудникам (ТЗ §15.1, §4.13). SVC-NOTIF — **владелец контракта C10** (Notification,
мастер §7) и участвует в точке согласования **CP-8** (мастер §6).

> Ссылки «ТЗ §…» — на техническое задание; «§…» — на мастер-план
> [`docs/plan/README.md`](../README.md); «M0…M5» — вехи (мастер §5); «CP-8» —
> точка согласования (мастер §6); «C10/C7», «SVC-…» — контракты и сервисы
> (мастер §7, §2).

## 1. Назначение и границы

**Входит в SVC-NOTIF:**

- **приём событий от продюсеров** уведомлений (ТЗ §15.2): SVC-CORE (новое
  обращение/сообщение), SVC-BCAST (состояние кампании, ошибка Broadcast), SVC-AI,
  SVC-FBP (состояние/завершение Workflow), система безопасности, административные
  сервисы;
- **формирование уведомлений по категориям** (ТЗ §15.5): информационные,
  предупреждения, ошибки, критические события, административные сообщения;
- **доставка по каналам** (ТЗ §15.4): Web Interface (через WS-событие
  `notification.created`, C7), Telegram Console (SVC-TGC), электронная почта, Push;
- **пользовательские настройки подписок** — какие категории по каким каналам
  получает конкретный пользователь; настройки индивидуальны (ТЗ §15.6);
- **статус прочтения** уведомления (`new|read`, `read_at`) и его изменение;
- **идемпотентность/дедупликация** доставки одного логического события.

**НЕ входит в SVC-NOTIF (границы):**

- **доставка сообщений клиентам** — это SVC-CORE (переписка) и SVC-BCAST (массовые
  коммуникации); Notification предназначено только сотрудникам (ТЗ §15.1, §15.3);
- **бизнес-логика коммуникации** и маршрутизация клиентских сообщений (ТЗ §15.7);
- **прямой доступ к БД** — доступ к схеме только через Backend, схему и миграции
  поставляет SVC-DATA (мастер §4, §22.3);
- **транспорт WebSocket** до клиента и переподключение — это SVC-EDGE/SVC-API
  (мастер §7.3); SVC-NOTIF только публикует событие C7;
- **отправка через внешние каналы напрямую** — Telegram идёт через
  SVC-INT/SVC-TGC, email/push — через внешних провайдеров (см. §3.2).

Каноническое определение схемы БД — мастер §4.7 (владелец — SVC-DATA);
каноническое определение контракта C10 — `packages/contracts` (мастер §7).
Настоящий план **не переопределяет** их, а детализирует участок SVC-NOTIF.

## 3. Интерфейсы и контракты

SVC-NOTIF — **владелец** контракта **C10** (Notification) и **потребитель C7**
для доставки в web (совладение WS-транспортом — SVC-EDGE/SVC-API). Ниже —
детализация; **каноническое определение хранится в `packages/contracts`**
(`openapi/`, `events/`), semver и заморозка — по мастер §7.4/§9.3.

### 3.1 Экспортируемые контракты

**C10 — Notification (публичный REST, группа `C10.notifications`, мастер §7.2,
префикс `/api/v1`).** Эндпоинты:

- `GET /notifications` — список уведомлений текущего пользователя (фильтр по
  `status`/`category`, постранично; целевое время ≤ 1 с, ТЗ §25.2);
- `POST /notifications/{id}:read` — отметить уведомление прочитанным
  (`status=read`, `read_at`);
- `GET /notifications/settings` — текущие настройки подписок пользователя
  (категория × канал × `enabled`, ТЗ §15.6);
- `PUT /notifications/settings` — обновить настройки подписок пользователя.

**C7 — WS-событие `notification.created` (мастер §7.3, ТЗ §11.7).** SVC-NOTIF
публикует событие о новом уведомлении для web-клиента (SVC-MWS/SVC-ADMIN);
транспорт и переподключение — SVC-EDGE (мастер §7.3).

Все эндпоинты — под `/api/v1`, JSON/UUID/ISO-8601 (ТЗ §11.9), единый формат
ошибок (ТЗ §11.11), серверная валидация и проверка принадлежности организации
и прав пользователя (ТЗ §11.10, §22.6).

### 3.2 Потребляемые контракты

| Контракт / источник | От кого | Назначение |
|---|---|---|
| **События продюсеров** (через `outbox_events`/внутренний контракт, C-OUT) | SVC-CORE, SVC-BCAST, SVC-AI, SVC-FBP, безопасность, админ-сервисы | приём событий-триггеров уведомлений (ТЗ §15.2). |
| **Канал web** (C7, WS-транспорт) | SVC-EDGE / SVC-API | доставка `notification.created` в Web Interface. |
| **Канал telegram** | SVC-INT / **SVC-TGC** | доставка уведомления менеджеру в Telegram Console (ТЗ §20.3). |
| **Каналы email/push** | внешние провайдеры (SMTP/Push) | доставка по электронной почте и Push (ТЗ §15.4). |
| Схема БД + миграции | SVC-DATA | таблицы §4.7, RLS по `organization_id`. |

## 4. Модель данных

Таблицы — по мастер §4.7 (владелец схемы SVC-DATA, потребители SVC-MWS, SVC-TGC).
SVC-NOTIF использует их так:

| Таблица | Ключевые поля (акцент SVC-NOTIF) | Появляется |
|---|---|---|
| `notifications` | `organization_id`, **`recipient_user_id`** (адресат-сотрудник, ТЗ §15.3), **`category`** (`info\|warning\|error\|critical\|admin`, ТЗ §15.5), `title`, `body`, `payload` (jsonb), **`status`** (`new\|read`), `created_at`, **`read_at`**. | M3 |
| `notification_settings` | `organization_id`, **`user_id`**, **`category`**, **`channel`** (`web\|telegram\|email\|push`, ТЗ §15.4), **`enabled`** — подписка пользователя (ТЗ §15.6). | M3 (web/telegram) / M4 (email/push) |

**Инварианты SVC-NOTIF:** (1) уведомление всегда адресовано пользователю
(`recipient_user_id`) внутри своей организации (изоляция, ТЗ §22.6); (2) доставка
в канал выполняется только при `enabled=true` для пары (категория, канал); (3)
повторная обработка одного логического события не создаёт дубль уведомления
(идемпотентность).

## 5. Поэтапный план

Каждый этап привязан к вехе (мастер §5) и даёт вертикальный срез. Для каждого:
Цель · Задачи · Тесты (unit / integration / e2e) · DoD (единый — мастер §9.4).

### M0 — Контракты и каркас

- **Цель.** Заморозить контракт C10 для параллельной разработки продюсеров и
  потребителей (SVC-MWS, SVC-TGC).
- **Задачи.** Определить и зафиксировать в `packages/contracts` **C10**
  (эндпоинты `C10.notifications`: `GET /notifications`, `POST /notifications/{id}:read`,
  `GET/PUT /notifications/settings`) и схему **WS-события `notification.created`**
  (C7); поднять **мок C10** и мок события; каркас сервиса `notification-platform`
  и фасада `notification-facade`.
- **Тесты.** unit — валидация DTO C10, схема события `notification.created`;
  contract-заготовки «продюсеры↔NOTIF» и NOTIF↔MWS/TGC.
- **DoD.** Контракт C10 (+ схема C7-события) v1 заморожен (semver), моки в CI
  зелёные (мастер §9.4).

### M1 и M2 — без крупных задач

- SVC-NOTIF в вехах M1 и M2 крупных задач **не имеет** (мастер §5.1): критический
  путь этих вех — «приём и ответ» ядра, омниканальность и AI Assistant. Разработка
  ведётся против замороженного C10 и его мока; продюсеры и потребители (SVC-MWS)
  используют мок до старта реализации на M3.

### M3 — Генерация, категории, доставка в Web и Telegram

- **Цель.** Уведомление сгенерировано из события продюсера и доставлено сотруднику
  в **два канала** — Web и Telegram Console (вертикальный срез CP-8).
- **Задачи.** **Приём событий от продюсеров** (SVC-CORE/BCAST/AI/FBP) через
  `outbox_events`/внутренний контракт (ТЗ §15.2); **формирование уведомлений по
  категориям** (ТЗ §15.5) — маппинг «событие → категория/адресат», запись
  `notifications`; **доставка в web** — публикация WS-события `notification.created`
  (C7, ТЗ §11.7); **доставка в Telegram Console** через SVC-INT/SVC-TGC (ТЗ §20.3);
  реализация `GET /notifications`, `POST /notifications/{id}:read`; **базовые
  настройки подписок** (`GET/PUT /notifications/settings`) для каналов web/telegram.
- **Тесты.**
  - unit — **маршрутизация по категориям/каналам** (событие → категория →
    целевые каналы), формирование записи `notifications`, применение базовых
    настроек подписок;
  - integration — **Backend↔Notification** (приём события, запись, ТЗ §26.4),
    доставка в **WS (C7)** и в **Telegram (мок)**, **изоляция арендатора**
    (уведомление не пересекает `organization_id`);
  - e2e — **«Notification в Web + Telegram»** (мастер §8.2): событие продюсера →
    уведомление → отображение в SVC-MWS (web) и в SVC-TGC (telegram).
- **DoD.** Срез CP-8 проходит e2e в двух каналах; изоляция арендатора и серверная
  валидация (мастер §9.4).

### M4 — Дополнительные каналы, настройки, идемпотентность, NFR

- **Цель.** Полный набор каналов, уважение подписок, отсутствие дублей, целевое
  время ≤ 1 с.
- **Задачи.** **Дополнительные каналы** (ТЗ §15.4): электронная почта и Push через
  внешних провайдеров; **уважение пользовательских настроек подписок** —
  фактическая доставка только по включённым (категория × канал) для каждого
  пользователя (ТЗ §15.6); **идемпотентность/дедупликация** — один ключ логического
  события не порождает дубль уведомления и повторную доставку; **NFR** — «Получение
  уведомлений ≤ 1 с» (ТЗ §25.2) для `GET /notifications` (индексация, постраничная
  выдача).
- **Тесты.**
  - unit — применение настроек (отключённая подписка → нет доставки в канал),
    **дедупликация** повторного события, выбор каналов по настройкам;
  - integration — Backend↔Notification для email/push (моки провайдеров),
    Backend↔PostgreSQL (идемпотентность/индексы), проверка бюджета ≤ 1 с на
    `GET /notifications`;
  - e2e — расширение «Notification в Web + Telegram» доставкой при разных
    настройках подписок; регрессия дедупликации.
- **DoD.** Все каналы §15.4 подключены; отключённые подписки не доставляются;
  дублей нет; NFR ≤ 1 с соблюдён (мастер §9.4).

**Статус реализации M4 (M4-99).** M4 Notification завершён для CP-8: продюсеры
(`SVC-CORE/SVC-BCAST/SVC-AI/SVC-FBP/SVC-API/SVC-IDN/SVC-DATA`) публикуют
`notification.triggered`, а SVC-NOTIF — **единственный владелец**
`notification.created` (C7) — формирует уведомление, дедуплицирует повторные
триггеры по `dedupe_key` и доставляет только по включённым подпискам
(категория × канал), одинаковый C10-payload идёт в Web (SVC-MWS) и Telegram
Console (SVC-TGC). Контракты **C10** и схема **`notification.created`** заморожены
как `stable_for_m5` в `packages/contracts/cp8-freeze.v1.json` (скреплено
`tests/contract/m4-gate-freeze.test.mjs`). Покрытие: contract
`tests/contract/c10-notification-contract.test.mjs`,
`tests/contract/manager-workspace-c10-consumer.test.mjs`,
`tests/contract/telegram-console-cp8-consumer.test.mjs`; e2e
`tests/e2e/notification-subscriptions-cp8.test.mjs`,
`tests/e2e/telegram-console-cp8.test.mjs`; unit/integration
`services/notification-platform/test/**`.

### M5 — Тонкие настройки, устойчивость, приоритеты категорий

- **Цель.** Стабильная доставка и точные пользовательские настройки.
- **Задачи.** **Тонкие настройки** уведомлений (гранулярность категория/канал,
  ТЗ §15.6); **устойчивость доставки** при недоступности канала — ретраи,
  предсказуемая деградация, доставка через доступные каналы без блокировки
  остальных; **приоритеты/категории** — гарантированная доставка `critical` и
  `admin` (административные сообщения, ТЗ §15.5, §20.3) даже при частичном отказе
  каналов.
- **Тесты.** unit — приоритизация `critical`/`admin`, поведение при отказе канала;
  integration — деградация при недоступном канале (доставка через оставшиеся);
  e2e — участие в полном наборе ТЗ §26.6 (регрессия, CP-9).
- **DoD.** Пройдены устойчивость и тонкие настройки; критические уведомления
  доставляются; критерии приёмки (мастер §9.4, CP-9).

## 6. Точки согласования

Формулируются явно: ожидания от смежных сервисов · замораживаемый контракт ·
добавляемые межсервисные тесты (мастер §6).

### CP-8 (M3/M4) — Генерация и доставка уведомления в двух каналах

- **Участники.** SVC-NOTIF; **продюсеры** SVC-CORE (новое сообщение/обращение),
  SVC-BCAST (состояние кампании, ошибка Broadcast), SVC-AI, SVC-FBP (состояние
  Workflow); **потребители** SVC-MWS (web) и SVC-TGC (telegram).
- **Ожидания.**
  - продюсеры **публикуют события** об изменениях (через `outbox_events`/внутренний
    контракт, ТЗ §15.2), из которых SVC-NOTIF формирует уведомления по категориям
    (ТЗ §15.5);
  - SVC-MWS **отображает** уведомление в web по событию `notification.created` (C7);
  - SVC-TGC **отображает** уведомление менеджеру в Telegram Console (ТЗ §20.3).
- **Замораживаем.** **C10** (Notification) и схему **C7-события
  `notification.created`** — в версии v1 (мастер §7.4).
- **Реализация.** Генерация и доставка на **M3** (e2e в двух каналах), расширение
  каналов/настроек/идемпотентности и NFR — на **M4**.
- **Тесты.** e2e **«Notification в Web + Telegram»** (мастер §8.2); **contract
  «продюсеры↔NOTIF»** (мастер §8.4) и NOTIF↔MWS/TGC.

## 7. Стратегия тестирования

Соответствует мастер §8 (пирамида unit/integration/contract/e2e). Специфические
проверки SVC-NOTIF:

- **Доставка в правильные каналы согласно настройкам.** По событию уведомление
  уходит только в те каналы, что включены (`enabled=true`) для пары
  (категория, канал) конкретного пользователя (ТЗ §15.4, §15.6).
- **Дедупликация повторных событий.** Повторная генерация из того же логического
  события (тот же ключ) не создаёт второе уведомление и не дублирует доставку.
- **Уважение отключённых подписок.** Отключённая подписка (категория/канал) →
  уведомление в этот канал не доставляется; при этом остальные каналы работают.
- **Изоляция арендатора.** Уведомление адресуется только пользователю своей
  организации; чужой `organization_id` недоступен (ТЗ §22.6).
- **Деградация при недоступности канала.** Отказ одного канала (telegram/email/
  push) не блокирует доставку в остальные; критические (`critical`/`admin`)
  доставляются через доступные каналы.

Обязательные integration-связки (ТЗ §26.4): **Backend↔Notification**, доставка в
**WS (C7)** и Telegram (мок), Backend↔PostgreSQL (запись/идемпотентность/бюджет
≤ 1 с). E2e-участие — сценарий вехи (мастер §8.2): **«Notification в Web +
Telegram»** (M3, расширение на M4). Ссылка на общую стратегию — мастер §8.

## 8. Риски и зависимости

| Риск / зависимость | Влияние | Митигирование |
|---|---|---|
| **Шум / переуведомление** сотрудников | Снижение полезности, усталость от уведомлений | Категории (ТЗ §15.5) и индивидуальные **настройки подписок** (ТЗ §15.6); доставка только по включённым парам (категория, канал). |
