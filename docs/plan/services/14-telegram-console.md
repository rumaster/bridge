# План разработки сервиса Telegram Console (SVC-TGC)

Telegram Console — **интерфейс менеджера в Telegram** (ТЗ §20): получение
уведомлений о новых сообщениях, просмотр активного диалога и ответ клиенту, а
также AI-подсказки. Это **облегчённая мобильная альтернатива** Manager Workspace
(SVC-MWS) для оперативной работы вне Web-интерфейса (ТЗ §20.1). SVC-TGC — тонкий
**клиентский интерфейс поверх Telegram-бота**: он **не содержит собственной
бизнес-логики** (ТЗ §20.8) и работает исключительно через **Backend API** теми же
контрактами, что и остальные приложения платформы. Сервис **потребляет** уведомления
(**C10**), просмотр диалогов и истории (**C3.conversations**), отправку ответа
клиенту (**C3.messages**) и AI-подсказки (**C4**) — все контракты по мастер §7.
SVC-TGC участвует в точке согласования **CP-8** (мастер §6) как **потребитель**
уведомлений в канале `telegram` (совместно с SVC-NOTIF и Backend).

> Ссылки «ТЗ §…» — на техническое задание; «§…» — на мастер-план
> [`docs/plan/README.md`](../README.md); «M0…M5» — вехи (мастер §5); «CP-8» —
> точка согласования (мастер §6); «C3/C4/C10/C7», «SVC-…» — контракты и сервисы
> (мастер §7, §2).

## 1. Назначение и границы

**Входит в SVC-TGC:**

- **получение уведомлений о новых сообщениях/обращениях** менеджеру через
  Telegram-бот (ТЗ §20.3, §15.4) — канал доставки `telegram` для SVC-NOTIF;
- **просмотр активных диалогов** и краткой истории/сведений о клиенте (имя, канал,
  статус, число непрочитанных, ТЗ §20.5) через Backend (**C3.conversations**);
- **ответ клиенту** из бота — через Backend (**C3.messages**, `POST /messages`,
  идемпотентно, ТЗ §20.4, §11.12);
- **AI-подсказки** по запросу менеджера (резюме, рекомендуемый ответ, поиск по KB,
  перевод, **C4**, ТЗ §20.6, §12.3) — применяются **вручную** менеджером;
- **ссылки на разделы Manager Workspace** для перехода к полной карточке/переписке
  (ТЗ §20.2, §20.5);
- **переиспользование Telegram-бота**, уже применяемого для входа (ТЗ §9.5) — тот
  же бот выступает интерфейсом сотрудника.

**НЕ входит в SVC-TGC (границы):**

- **адаптер клиентского Telegram-канала** — приём/доставку сообщений *клиентов*
  через Telegram делает **SVC-INT** (ТЗ §10.4); здесь Telegram — **интерфейс
  СОТРУДНИКА** (менеджера), а не клиентский транспорт (принципиальное разграничение,
  см. §8);
- **прямой доступ к БД и к внешним каналам** — всё только через Backend API
  (ТЗ §20.4, §20.8, §11.1); доставка ответа до клиента — обязанность SVC-CORE и Adapter;
- **административные операции** (пользователи, настройки организации, Workflow,
  безопасность, каналы связи) **запрещены** (ТЗ §20.7) — только в SVC-ADMIN;
- **полная карточка клиента** и расширенная история — только в Manager Workspace
  (ТЗ §20.5); SVC-TGC даёт краткую сводку и ссылку;
- **собственная бизнес-логика/маршрутизация** — отсутствует (ТЗ §20.8), все решения
  принимает Backend.

Каноническое определение контрактов (**C3**, **C4**, **C10**, **C7**) —
`packages/contracts` (мастер §7). Настоящий план **не переопределяет** контракты
и схему БД, а детализирует участок SVC-TGC как их потребителя.

## 2. Технологии

| Область | Решение |
|---|---|
| Язык/платформа | TypeScript; клиент `clients/telegram-console` (мастер §3) — отдельное приложение-бот, а не модуль ядра. |
| Telegram Bot API | Обработка входящих обновлений (сообщения, команды), **inline-кнопки** (callback-запросы), меню; тот же бот, что используется для входа (ТЗ §9.5). |
| Привязка аккаунта | Сопоставление Telegram-аккаунта менеджера пользователю платформы (`users.telegram_username`, мастер §4.2); повторное использование механизма Telegram-входа (ТЗ §9.5) для установления личности. |
| Подписка на уведомления | Приём уведомлений канала **`telegram`** от SVC-NOTIF (**C10**, ТЗ §15.4, §20.3) и рендеринг их в бот. |
| Вызовы Backend | Только через **Backend API** (`/api/v1`): **C3.conversations** (просмотр), **C3.messages** (ответ, идемпотентно), **C4** через `C3.ai` (AI-подсказки). Аутентификация — серверная сессия менеджера (ТЗ §9.7). |
| Состояние сессии бота | Лёгкое состояние «активный диалог менеджера» (какую Conversation менеджер сейчас ведёт в боте) — вне БД платформы (локальное состояние клиента); все данные — из Backend. |
| Идемпотентность ответа | Проброс сквозного `idempotency_key`/`message_id` в `POST /messages` (ТЗ §11.12) — защита от дублей при ретраях/повторных нажатиях кнопок. |
| Ограничения Telegram | Учёт rate limits Bot API (ограничение частоты отправки), ретраи с backoff, устойчивость к таймаутам. |
| Тестирование | Jest (unit, `*.spec.ts`); integration против **мок-Backend** и **мок-Telegram API**; e2e-участие в «Notification в Web + Telegram» (telegram-часть) на M3 (мастер §8). |

## 3. Интерфейсы и контракты

SVC-TGC — **потребитель** контрактов ядра и вынесенных сервисов; собственных
публичных REST-контрактов платформы он **не экспортирует** (наружу «экспортируется»
только сам бот-интерфейс для менеджера). Каноническое определение потребляемых
контрактов — `packages/contracts` (мастер §7); заморозка/semver — по мастер
§7.4/§9.3.

### 3.1 Экспортирует

**Бот-интерфейс менеджера** — команды и inline-кнопки Telegram-бота (не платформенный
REST-контракт, а UX-поверхность):

- команды: `/start` (привязка/старт), `/dialogs` (активные диалоги), `/help`;
- inline-кнопки: «Открыть диалог», «Ответить», «AI: резюме», «AI: подсказать
  ответ», «AI: перевести», «Открыть в Manager Workspace»;
- push-сообщения: карточки уведомлений о новом обращении/сообщении с кнопками
  быстрых действий.

Бот-интерфейс не содержит бизнес-логики (ТЗ §20.8) — каждое действие
транслируется в вызов Backend API.

### 3.2 Потребляет

| Контракт (мастер §7) | Владелец | Что потребляет SVC-TGC |
|---|---|---|
| **C10** — Notification (группа `C10.notifications`) | SVC-NOTIF | приём уведомлений канала `telegram` (новое обращение/сообщение, критические, ошибка Broadcast, завершение Workflow, админ-сообщения, ТЗ §20.3); `GET /notifications`, `POST /notifications/{id}:read`. |
| **C3.conversations** | SVC-CORE | `GET /conversations` (активные диалоги менеджера), `GET /conversations/{id}` (сведения/статус), `GET /conversations/{id}/messages` (краткая история, ТЗ §20.5). |
| **C3.messages** | SVC-CORE | `POST /messages` — ответ клиенту (**идемпотентно**, сквозной `idempotency_key`, ТЗ §20.4, §11.12); `GET /messages/{id}` — статус. |
| **C4** — AI Contract (через `C3.ai`) | SVC-AI | `POST /ai/assistant:suggest` — AI-подсказки: резюме, рекомендуемый ответ, поиск по KB, перевод (ТЗ §20.6, §12.3). |
| **C7** — WS-событие `notification.created` (опц.) | SVC-CORE/API | альтернативный сигнал о новом уведомлении; в MVP доставка в бот — через C10/SVC-NOTIF (мастер §7.3). |
| Механизм Telegram-входа (`C3.auth`) | SVC-IDN | установление личности менеджера/привязка аккаунта (ТЗ §9.5). |

**Таблица «действие в боте → эндпоинт/контракт»:**

| Действие менеджера в боте | Backend-эндпоинт | Контракт |
|---|---|---|
| Привязать/войти (`/start`) | `POST /auth/login/telegram/start`, `POST /auth/login/telegram/verify` | C3.auth (SVC-IDN) |
| Показать активные диалоги (`/dialogs`) | `GET /conversations` | C3.conversations |
| Открыть диалог (кнопка) | `GET /conversations/{id}`, `GET /conversations/{id}/messages` | C3.conversations |
| Ответить клиенту | `POST /messages` (идемпотентно) | C3.messages |
| Проверить статус ответа | `GET /messages/{id}` | C3.messages |
| AI: резюме / подсказка / перевод | `POST /ai/assistant:suggest` | C4 (C3.ai) |
| Получить уведомление в бот | приём канала `telegram` / `GET /notifications` | C10 |
| Отметить уведомление прочитанным | `POST /notifications/{id}:read` | C10 |

Все вызовы — под `/api/v1`, JSON/UUID/ISO-8601 (ТЗ §11.9), единый формат ошибок
(ТЗ §11.11); авторизация и изоляция арендатора проверяются **на стороне Backend**
(ТЗ §9.8, §11.10, §22.6) — SVC-TGC полномочия сам не определяет (ТЗ §5.8).

## 4. Модель данных

SVC-TGC **не владеет таблицами** и **не имеет прямого доступа к БД** (ТЗ §11.1,
§20.8); он потребляет ресурсы через Backend API. Раздел описывает **привязку
менеджера к Telegram-аккаунту**, **состояние сессии бота** и **потребляемый канал
доставки** уведомлений.

| Ресурс / сущность | Где хранится (владелец) | Как использует SVC-TGC |
|---|---|---|
| **Привязка Telegram-аккаунта к пользователю** | `users.telegram_username` (SVC-IDN, мастер §4.2) | сопоставление Telegram-аккаунта менеджера пользователю платформы; установление личности — через Telegram-вход (ТЗ §9.5). |
| **Серверная сессия менеджера** | `auth_sessions` (SVC-IDN, мастер §4.2) | контекст авторизации для вызовов Backend (роль Manager, организация, срок действия, ТЗ §9.7). |
| **Канал доставки `telegram`** | `notification_settings.channel='telegram'` (SVC-NOTIF, мастер §4.7) | подписка пользователя на уведомления в Telegram Console (ТЗ §15.4, §20.3). |
| **Состояние сессии бота** (активный диалог менеджера) | локальное состояние клиента `telegram-console` (не БД платформы) | какой Conversation менеджер ведёт в боте сейчас; эфемерно, восстанавливается из Backend. |

**Инварианты SVC-TGC:** (1) все данные диалогов/сообщений/клиента получаются
**только** из Backend (ТЗ §20.8) — локально бизнес-данные не дублируются; (2)
действия менеджера в боте выполняются **под его сессией** и проходят проверки прав
на Backend (ТЗ §9.8); (3) уведомления в `telegram` доставляются только при
включённой подписке (`enabled=true`) у SVC-NOTIF (ТЗ §15.6); (4) ответ клиенту
идемпотентен по сквозному ключу (ТЗ §11.12).

## 5. Поэтапный план

Каждый этап привязан к вехе (мастер §5) и даёт вертикальный срез. Для каждого:
Цель · Задачи · Тесты (unit / integration / e2e) · DoD (единый — мастер §9.4).
SVC-TGC входит в дорожную карту начиная с **M3** (мастер §5.1): его работа зависит
от готовности уведомлений (SVC-NOTIF) и диалогов (SVC-CORE/API).

### M0 / M1 / M2 — без крупных задач (зависит от готовности уведомлений и диалогов)

- SVC-TGC в вехах **M0–M2 крупных задач не имеет** (мастер §5.1). Критический путь
  этих вех — «приём и ответ» ядра, омниканальность и AI Assistant в Web; Telegram
  как **интерфейс менеджера** подключается после того, как готовы **уведомления**
  (SVC-NOTIF, M3) и **диалоги/история** (SVC-CORE/API). До этого разработка ведётся
  **против замороженных контрактов** C3/C4/C10 и их **моков**.
- Допустимая подготовительная работа (не блокирующая): каркас клиента
  `telegram-console`, скелет обработчиков команд/кнопок против мок-Telegram API,
  черновая привязка аккаунта поверх Telegram-входа (ТЗ §9.5).

### M3 — ОСНОВНАЯ работа: уведомления в Telegram, просмотр диалога и ответ клиенту

- **Цель.** Менеджер получает уведомление о новом сообщении в Telegram-боте,
  открывает диалог, просматривает историю и **отвечает клиенту** — вертикальный
  срез, замыкающий telegram-часть **CP-8**.
- **Задачи.**
  - **Привязка Telegram-аккаунта менеджера** к пользователю платформы поверх
    Telegram-входа (ТЗ §9.5) и серверная сессия для вызовов Backend;
  - **доставка уведомлений в Telegram** — приём канала `telegram` от SVC-NOTIF
    (**C10**, ТЗ §15.4, §20.3), рендеринг карточек с inline-кнопками (ТЗ §20.3);
  - **просмотр активных диалогов и истории** через **C3.conversations**
    (`GET /conversations`, `.../{id}`, `.../{id}/messages`) — краткая сводка по
    клиенту (ТЗ §20.5);
  - **ответ клиенту через Backend** — `POST /messages` (**C3.messages**,
    идемпотентно, ТЗ §20.4, §11.12); доставка до клиента — SVC-CORE + Adapter;
  - **inline-кнопки** быстрых действий: «Открыть диалог», «Ответить», «Открыть в
    Manager Workspace» (ссылка, ТЗ §20.2);
  - **интеграция с CP-8** — согласование с SVC-NOTIF (публикация в `telegram`) и
    Backend (отдача диалогов/приём ответа).
- **Тесты.**
  - **unit** — обработчики команд/кнопок (роутинг callback → действие), **привязка
    аккаунта** менеджера, **формирование ответа** (сборка `POST /messages` с
    `idempotency_key`), рендер карточки уведомления;
  - **integration** — против **мок-Backend** и **мок-Telegram API**: **доставка
    уведомления** (C10 `telegram` → сообщение в боте) и **отправка ответа**
    (кнопка «Ответить» → `POST /messages`, идемпотентность), просмотр диалога
    (C3.conversations);
  - **e2e** — участие в **«Notification в Web + Telegram»** (**telegram-часть**,
    мастер §8.2, ТЗ §26.6): уведомление доставлено менеджеру в бот и отображено.
- **DoD.** Telegram-часть CP-8 проходит e2e; ответ клиенту идемпотентен; данные —
  только через Backend; проверки прав — на Backend (мастер §9.4).

### M4 — AI-подсказки в боте и быстрые ответы

- **Цель.** Менеджер получает AI-подсказки прямо в боте и отвечает быстрее.
- **Задачи.**
  - **AI-подсказки** (**C4** через `POST /ai/assistant:suggest`, ТЗ §20.6, §12.3):
    резюме, рекомендуемый ответ, поиск по KB, перевод — кнопки «AI: резюме»,
    «AI: подсказать ответ», «AI: перевести»; применяются **вручную** менеджером;
  - **быстрые ответы/шаблоны** — предзаготовленные варианты и вставка
    AI-рекомендации в поле ответа (нажатие → правка → `POST /messages`);
  - **деградация AI** — при недоступности SVC-AI бот работоспособен для уведомлений
    и ответов, подсказки временно недоступны без блокировки (ТЗ §5.4, §12.1).
- **Тесты.** unit — сборка запроса `assistant:suggest`, обработка ответа AI,
  поведение при недоступном AI (graceful); integration — против **мок-Backend/AI**:
  получение подсказки и её вставка в ответ, быстрый ответ → `POST /messages`
  (идемпотентность); e2e — менеджер запрашивает AI-подсказку в боте и отвечает клиенту.
- **DoD.** AI-подсказки доступны в боте; недоступность AI не ломает уведомления/
  ответы; ответ остаётся идемпотентным (мастер §9.4).

### M5 — Приёмка, устойчивость, ограничения Telegram

- **Цель.** Стабильная работа бота под ограничениями Telegram и приёмка.
- **Задачи.**
  - **ограничения Telegram Bot API** (**rate limits**) — контроль частоты отправки,
    очередь/троттлинг, ретраи с backoff, устойчивость к таймаутам;
  - **устойчивость** — корректная обработка сбоев Backend/Telegram (повтор без
    дублей по идемпотентному ключу), восстановление состояния активного диалога из
    Backend;
  - **безопасность привязки** — верификация принадлежности Telegram-аккаунта
    менеджеру (ТЗ §9.5), отзыв доступа при завершении сессии (ТЗ §9.7);
  - **приёмка** — участие в полном наборе ТЗ §26.6 (CP-9), регрессия telegram-части
    «Notification в Web + Telegram».
- **Тесты.** unit — троттлинг/backoff, поведение при rate limit; integration —
  устойчивость к таймаутам Backend/Telegram (повтор без дублей), восстановление
  сессии; e2e — регрессия telegram-части и приёмочные сценарии (CP-9).
- **DoD.** Ограничения Telegram соблюдены (без блокировки бота), дублей нет,
  привязка безопасна; критерии приёмки (мастер §9.4, CP-9).

## 6. Точки согласования

Формулируются явно: участники · ожидания от смежных сервисов · замораживаемый
контракт · добавляемые межсервисные тесты (мастер §6).

### CP-8 (M3) — Доставка уведомления в Telegram и ответ клиенту

- **Участники.** SVC-TGC (потребитель, telegram-часть); **SVC-NOTIF** (доставка
  уведомлений в канал `telegram`); **SVC-CORE/API** (Backend: просмотр диалогов и
  приём ответа); наряду с SVC-MWS (web-часть того же CP-8).
- **Ожидания.**
  - **SVC-NOTIF (M3)** — **публикует уведомления в канал `telegram`** (**C10**,
    ТЗ §15.4, §20.3), из которых бот формирует карточки менеджеру;
  - **Backend (SVC-CORE/API)** — **отдаёт диалоги/историю** (**C3.conversations**)
    и **принимает ответ клиенту** (**C3.messages**, `POST /messages`, идемпотентно);
  - при необходимости — сигнал `notification.created` (**C7**) как дополнительный
    триггер (мастер §7.3).
- **Замораживаем.** Для CP-8 используются уже фиксируемые владельцами контракты:
  **C10** (Notification, владелец SVC-NOTIF) и **C3** (conversations/messages,
  владелец SVC-CORE) — в версии v1 (мастер §7.4). SVC-TGC — их **потребитель**.
- **Реализация.** Доставка уведомлений + просмотр/ответ — на **M3**; AI-подсказки —
  на **M4** (C4).
- **Тесты.** **Межсервисные e2e**: **«Notification в Web + Telegram»**
  (**telegram-часть**, мастер §8.2, ТЗ §26.6); **contract-тесты** потребителя:
  SVC-TGC↔SVC-NOTIF (C10) и SVC-TGC↔Backend (C3.conversations/C3.messages)
  (мастер §8.4).

## 7. Стратегия тестирования

Соответствует мастер §8 (пирамида unit/integration/contract/e2e). Специфические
проверки SVC-TGC:

- **Корректная привязка аккаунта менеджера.** Telegram-аккаунт сопоставляется
  нужному пользователю платформы (ТЗ §9.5); чужой/неизвестный аккаунт не получает
  доступ к диалогам; действия идут под сессией менеджера (ТЗ §9.7, §9.8).
- **Доставка уведомлений в Telegram.** Уведомление канала `telegram` от SVC-NOTIF
  (C10) доставляется менеджеру в бот и корректно рендерится с кнопками (ТЗ §20.3).
- **Ответ клиенту без дублей (идемпотентность).** Повторное нажатие «Ответить» /
  ретрай не создаёт второе сообщение — сквозной `idempotency_key`/`message_id`
  (ТЗ §11.12); доставка до клиента — через Backend/SVC-CORE.
- **AI-подсказки.** Запрос `assistant:suggest` возвращает резюме/вариант/перевод;
  подсказка применяется **вручную** менеджером; недоступность AI не блокирует
  уведомления и ответы (ТЗ §5.4, §20.6).
- **Обработка ограничений Telegram.** При rate limit — троттлинг/очередь и ретраи с
  backoff без потери сообщений и без блокировки бота.

Обязательные integration-связки: **SVC-TGC↔мок-Backend** (C3.conversations,
C3.messages, C4) и **SVC-TGC↔мок-Telegram API** (доставка уведомления и отправка
ответа). E2e-участие — сценарий вехи (мастер §8.2): **«Notification в Web +
Telegram»** (telegram-часть, M3). Ссылка на общую стратегию — мастер §8.

## 8. Риски и зависимости

| Риск / зависимость | Влияние | Митигирование |
|---|---|---|
| **Лимиты Telegram Bot API** (rate limits, таймауты) | Задержки/потеря уведомлений и ответов, блокировка бота | Троттлинг и очередь отправки, ретраи с backoff, идемпотентность ответа (ТЗ §11.12); проверка на M5. |
| **Безопасность привязки аккаунта менеджера** | Несанкционированный доступ к диалогам организации | Привязка через проверенный Telegram-вход (ТЗ §9.5); действия под серверной сессией с проверкой прав на Backend (ТЗ §9.8); отзыв доступа при завершении сессии (ТЗ §9.7); изоляция арендатора (ТЗ §22.6). |
| **Разграничение с клиентским Telegram-адаптером (SVC-INT)** | Смешение «Telegram как интерфейс сотрудника» и «Telegram как канал клиента» → дублирование логики/ошибки маршрутизации | Чёткая граница (§1): приём/доставка сообщений клиентов — только SVC-INT; SVC-TGC — интерфейс менеджера без клиентского транспорта; данные — только через Backend. |
| **Зависимость от SVC-NOTIF** (публикация в канал `telegram`, C10) | Без уведомлений теряется ключевой сценарий (ТЗ §20.3) | Разработка против мока C10 до CP-8; заморозка контракта на CP (мастер §6, §9.3); деградация — при отсутствии уведомлений доступен просмотр/ответ по диалогам. |
| **Зависимость от Backend** (SVC-CORE/API: C3.conversations/C3.messages) | Без диалогов/отправки бот бесполезен | Работа против мок-Backend и замороженных C3; вся бизнес-логика и проверки — на Backend (ТЗ §20.8, §5.8). |
| **Зависимость от SVC-AI** (C4) | Недоступность AI-подсказок | AI — вспомогательный (ТЗ §5.4, §12.1): при недоступности подсказки скрываются, уведомления/ответы работают; разработка против мока C4. |
| **Дубли ответов** при ретраях/повторных нажатиях | Двойные сообщения клиенту | Сквозной `idempotency_key`/`message_id` (ТЗ §11.12), дедупликация на стороне ядра (мастер §4.4). |
| **Границы возможностей** (ТЗ §20.7) | Попытка админ-операций через бот | Явный запрет админ-действий в боте; такие операции — только в SVC-ADMIN; полная карточка/история — в SVC-MWS (ТЗ §20.5, §20.7). |
