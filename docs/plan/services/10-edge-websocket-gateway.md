# План разработки сервиса Edge & WebSocket Gateway (SVC-EDGE)

SVC-EDGE — **приграничный контур в РФ** (Edge Cluster, ТЗ §7.3), **WebSocket
Gateway** для событий реального времени (ТЗ §11.7) и **VPN Tunnel Service**
защищённого обмена между Edge Cluster и Application Cluster (ТЗ §7.8). Сервис
обеспечивает **буферизацию сообщений при разрыве** связи (ТЗ §7.9), **гарантию
порядка** в рамках Endpoint (ТЗ §7.10), **сквозную идемпотентность / дедупликацию**
по `idempotency_key` (ТЗ §11.12) и **локализацию персональных данных** субъектов
РФ по модели RF-first (ТЗ §7.14, 152-ФЗ). SVC-EDGE — вынесенный деградируемый
сервис (мастер §2, ТЗ §11.2): его недоступность не должна приводить к потере
сообщений. **Бизнес-логику диалогов сервис не реализует** — это SVC-CORE (ТЗ §7.3,
§8); Edge лишь принимает, буферизует и передаёт сообщения в ядро. SVC-EDGE
участвует в точке согласования **CP-7** (мастер §6).

> Ссылки «ТЗ §…» — на техническое задание; «§…» — на мастер-план
> [`docs/plan/README.md`](../README.md); «M0…M5» — вехи (мастер §5); «CP-…» —
> точки согласования (мастер §6); «C1/C7/C9», «SVC-…» — контракты и сервисы
> (мастер §7, §2).

## 1. Назначение и границы

**Входит в SVC-EDGE:**

- **WebSocket Gateway** — приём и удержание клиентских и операторских подключений,
  доставка событий реального времени (C7, ТЗ §11.7); автоматическое восстановление
  соединения после разрыва (ТЗ §11.7); горизонтальное масштабирование WS
  (ТЗ §25.3);
- **Edge Cluster в РФ** — региональная точка входа для пользователей РФ (ТЗ §7.3,
  §7.6): приём подключений, первичная фиксация трафика РФ в RF-контуре
  (**RF-first**, ТЗ §7.14), передача сообщений в Communication Core через туннель;
- **буферизация при разрыве** — при недоступности канала до Application Cluster
  Edge продолжает приём и складывает сообщения во временное защищённое хранилище
  `edge_message_buffer` (ТЗ §7.9), а после восстановления автоматически передаёт их
  в ядро без потерь;
- **VPN Tunnel Service** — защищённый канал Edge↔App (взаимная аутентификация,
  шифрование, контроль соединения, авто-восстановление, ТЗ §7.8);
- **сохранение порядка** в рамках Endpoint через `sequence_number`, присваиваемый на
  входе Edge (ТЗ §7.10), и **дедупликация** повторно переданных сообщений по
  сквозному `idempotency_key` (ТЗ §11.12).

**НЕ входит в SVC-EDGE (границы):**

- **бизнес-логика диалогов**, маршрутизация, Conversation, identity resolution,
  хранение истории — это SVC-CORE (ТЗ §7.3, §8); Edge только доставляет сообщения в
  ядро;
- **адаптеры внешних каналов** (Telegram/VK/WhatsApp/…) и обращения к внешним
  API — это SVC-INT (ТЗ §10.7);
- **AI Platform, FBP Engine, административная панель** — их в Edge Cluster нет
  (ТЗ §7.3);
- **каноническая схема БД и миграции** — поставляет SVC-DATA (мастер §4, §22.3);
  Edge не переопределяет модель сообщения.

Каноническое определение схемы `edge_message_buffer` — мастер §4.10 (владелец —
SVC-DATA/SVC-EDGE); каноническое определение контрактов — `packages/contracts`
(мастер §7). Настоящий план **не переопределяет** их, а детализирует участок
SVC-EDGE.

## 3. Интерфейсы и контракты

SVC-EDGE — **владелец** контракта **C9** (Edge↔App Tunnel, мастер §7.1) и
**совладелец C7** (WS events, вместе с SVC-CORE/SVC-API). Ниже — детализация
операций; **каноническое определение хранится в `packages/contracts`**
(`events/`, `openapi/`), semver и заморозка — по мастер §7.4/§9.3.

### 3.1 Экспортируемые контракты

**C7 — WS-события (Backend → клиенты, ТЗ §11.7, совладение с SVC-CORE/SVC-API).**

- `GET /ws` — WebSocket upgrade (мастер §7.2); удержание соединения клиента/менеджера;
- доставка событий реального времени (ТЗ §11.7): `message.created`,
  `message.status_changed`, `typing.started`/`typing.stopped`,
  `client.status_changed`, `notification.created`, `broadcast.state_changed`,
  `workflow.state_changed`;
- общий envelope C7 v1: `event_id`, `organization_id`, `sequence_number`,
  `payload`, `occurred_at`; `sequence_number` монотонен внутри одной WS-подписки;
- **автоматическое восстановление соединения** после временной потери связи
  (ТЗ §11.7): клиент переподключается с `last_event_id`, сервер досылает события
  после этого cursor, клиент отбрасывает уже виденные `event_id`;
- фактическое содержимое событий формирует Backend (SVC-CORE/SVC-API); SVC-EDGE
  отвечает за транспорт и переподключение (мастер §7.3).

**C9 — Edge↔App Tunnel (EDGE ↔ CORE, мастер §7.1).**

- передача сообщений **Edge → Application Cluster** (Communication Core) через VPN
  Tunnel Service (ТЗ §7.8);
- каждое tunnel-сообщение C9 v1 переносит **`sequence_number`** (порядок в рамках
  Endpoint, ТЗ §7.10), сквозной **`idempotency_key`** (= `message_id`, ТЗ §11.12),
  **`endpoint_id`**, C1 **`payload`** и timestamps `received_at`, `buffered_at`,
  `forwarded_at`;
- семантика **at-least-once** с дедупликацией на приёмнике: повторная передача из
  буфера (ТЗ §7.9) с уже обработанным `idempotency_key` отбрасывается ядром;
- восстановление порядка ядром по `sequence_number` в рамках `endpoint_id`.

### 3.2 Потребляемые контракты

| Контракт | От кого | Назначение |
|---|---|---|
| **C1** (Message Model) | SVC-CORE | каноническая модель сообщения (ТЗ §8.4, поля §4.4); Edge переносит её через туннель, не изменяя. |
| Приём/доставка (C9-приёмник) | SVC-CORE | ядро принимает сообщения с `sequence_number`/`idempotency_key`, восстанавливает порядок и дедуплицирует (ТЗ §7.10, §11.12). |
| События для WS | Backend (SVC-CORE/SVC-API) | доменные события (`message.*`, `typing.*`, `notification.created`, …) для доставки клиентам по C7 (ТЗ §11.7). |
| Схема БД + миграции | SVC-DATA | таблица `edge_message_buffer` в RF-контуре (мастер §4.10). |

## 4. Модель данных

Таблица — по мастер §4.10 (владелец схемы SVC-DATA/SVC-EDGE). Ключевая
особенность — **отдельная БД в RF-контуре** и **RF-first** локализация ПДн
(ТЗ §7.14): первичная фиксация принятых от субъектов РФ данных выполняется в РФ,
за рубеж данные передаются только после этого.

| Таблица | Ключевые поля (акцент SVC-EDGE) | Появляется |
|---|---|---|
| `edge_message_buffer` | `endpoint_id`, **`sequence_number`** (порядок, ТЗ §7.10), **`idempotency_key`** (дедуп, ТЗ §11.12), **`payload_encrypted`** (шифрованный payload), `received_at`, **`ttl`** (просрочка буфера), `forwarded_at` (факт передачи в ядро). | M4 |

> **RF-first (ТЗ §7.14).** `edge_message_buffer` и первичная фиксация принятого
> трафика РФ размещаются в **первичной БД в РФ**; зарубежный Application Cluster
> получает данные только **после** первичной записи и работает со вторичной
> репликой. Разделение контуров размещения — на уровне инфраструктуры, а не
> различием структуры таблиц (мастер §4.10).

**Инварианты SVC-EDGE:** (1) сообщение считается принятым (и подтверждается
клиенту) только после надёжной фиксации в RF-контуре (ТЗ §7.9, §25.11);
(2) `sequence_number` монотонен в пределах `endpoint_id`; (3) запись из буфера не
удаляется до подтверждения передачи в ядро (`forwarded_at`); (4) просроченные по
`ttl` записи обрабатываются по стратегии дренажа/оповещения (ТЗ §7.9).

## 5. Поэтапный план

Каждый этап привязан к вехе (мастер §5). Для каждого: Цель · Задачи · Тесты
(unit / integration / e2e) · DoD (единый — мастер §9.4). Основной объём работ
SVC-EDGE приходится на **M4**.

### M0 — Контракты и каркас

- **Цель.** Заморозить основу для параллельной разработки со стороны ядра и
  клиентов.
- **Задачи.** Определить и зафиксировать в `packages/contracts` контракт **C9**
  (Edge↔App Tunnel: передача сообщения с `sequence_number` + `idempotency_key`,
  ТЗ §7.10, §11.12) и **уточнить C7** (WS-события, `GET /ws`, авто-reconnect,
  ТЗ §11.7) совместно с SVC-CORE/SVC-API; поднять **мок туннеля** (C9) и мок
  WS-канала; каркас сервиса `edge-gateway` в NestJS.
- **Тесты.** unit — валидация DTO C9 (поля `sequence_number`/`idempotency_key`),
  схема WS-события; contract-заготовки EDGE↔CORE.
- **DoD.** Контракт C9 v1 заморожен (semver), C7 уточнён; моки в CI зелёные
  (мастер §9.4).

### M1 — без крупных задач

- SVC-EDGE в вехе M1 **не имеет крупных задач** (мастер §5.1): критический путь
  M1 — вертикальный срез «приём и ответ» через ядро (SVC-CORE/SVC-INT/SVC-MWS).
  Ожидание к M1 — ядро готово принимать сообщения с `sequence_number` /
  `idempotency_key` (см. §6, CP-7). Разработка Edge идёт против замороженного C9.

### M2 — WebSocket Gateway на стороне Application Cluster

- **Цель.** Обеспечить **realtime** для вехи M2: доставку событий клиентам и
  менеджерам по WebSocket (ТЗ §11.7) — без Edge-контура РФ (он появляется в M4).
- **Задачи.** WebSocket Gateway на стороне Application Cluster: `GET /ws`
  (upgrade), удержание соединений, **доставка событий C7** (`message.created`,
  `message.status_changed`, `typing.*`, `client.status_changed`, `notification.*`
  и др., ТЗ §11.7); **горизонтальное масштабирование WS** (ТЗ §25.3);
  **авто-reconnect** соединения после разрыва без дублирующей доставки (ТЗ §11.7).
- **Тесты.** unit — маршрутизация события в нужное соединение, логика
  переподключения без дублей; integration — **Backend↔WebSocket** (ТЗ §26.4);
  e2e — участие в realtime-сценариях M2 (омниканальность/AI Assistant — доставка
  обновлений в UI менеджера).
- **DoD.** События идут в realtime; WS масштабируется горизонтально; reconnect не
  дублирует доставку (мастер §9.4).

**Статус реализации M2.** M2 Application WS Gateway завершён для gate CP-2/CP-3:
контракт C7 и reconnect-семантика закреплены в
`packages/contracts/openapi/edge/c7.websocket.openapi.json`,
`packages/contracts/events/c7-websocket-event.schema.json` и consumer contract
SVC-MWS; дедупликация по `event_id`/`message.id` и gap detection по
`sequence_number` проверяются `apps/manager-workspace/test/realtime-merge.test.ts`
и `tests/contract/manager-workspace-c4-c7-consumer.test.mjs`.

### M3 — без крупных задач

- SVC-EDGE в вехе M3 **не имеет крупных задач** (мастер §5.1): M3 — программируемость
  (FBP/редактор/Onboarding/Notification). Edge продолжает разработку против моков
  и готовит Edge-контур к M4.

### M4 — Edge Cluster в РФ, VPN Tunnel, буфер, порядок, дедуп (ОСНОВНАЯ работа)

- **Цель.** Замкнуть сквозной сценарий: трафик РФ идёт через Edge + VPN Tunnel с
  **буферизацией при разрыве, восстановлением порядка и дедупликацией**, при
  соблюдении RF-first (ТЗ §7.9–§7.10, §7.14, §11.12; мастер §5, M4).
- **Задачи.**
  - **Edge Cluster в РФ** — региональная точка входа (ТЗ §7.3, §7.6): приём
    подключений и **первичная фиксация ПДн субъектов РФ в RF-контуре** (RF-first,
    ТЗ §7.14);
  - **VPN Tunnel Service** — защищённый канал Edge↔App (взаимная аутентификация,
    шифрование, контроль соединения, авто-восстановление, backpressure, ТЗ §7.8);
  - **буферизация при разрыве** (ТЗ §7.9): при недоступности канала — приём
    продолжается, сообщения складываются в `edge_message_buffer`
    (`payload_encrypted`, `ttl`); после восстановления — **автоматический дренаж**
    буфера в Communication Core (C9), без потерь;
  - **восстановление порядка** (ТЗ §7.10): присвоение `sequence_number` на входе
    Edge (ключ партиционирования — `endpoint_id`), передача его через туннель для
    восстановления порядка ядром;
  - **дедупликация по сквозному `idempotency_key`** (ТЗ §11.12) — **совместно с
    SVC-CORE**: повторно переданные из буфера сообщения отбрасываются на приёмнике;
  - интеграция с SVC-CHAT/SVC-MOB — их клиентские подключения РФ идут через Edge.
- **Тесты.** unit — присвоение/проверка `sequence_number`, дедупликация по
  `idempotency_key`, логика буфера (запись/`ttl`/дренаж), шифрование `payload`;
  integration — **Backend↔WebSocket** (ТЗ §26.4), пересылка через туннель с
  восстановлением порядка **на моке разрыва** канала; e2e — **«Edge Cluster»**
  (РФ→VPN Tunnel→обработка) и **«Потеря соединения»** (буфер→восстановление→без
  потерь/дублей, порядок) — оба на M4 (CP-7, ТЗ §26.6).
- **DoD.** e2e «Edge Cluster» и «Потеря соединения» зелёные; нет потерь/дублей и
  перестановок в рамках Endpoint; RF-first соблюдён; C9 заморожен (мастер §9.4).

**Статус реализации M4.** SVC-EDGE замкнут для gate CP-7. RF-first-конвейер Edge
реализован модулями `services/edge-gateway/src`: `rf-payload-cipher.mjs`
(AES-256-GCM для `payload_encrypted`), `edge-sequencer.mjs` (`sequence_number` по
ключу партиционирования `endpoint_id`), `edge-message-buffer.mjs` (in-memory и
Postgres-стор `edge_message_buffer` с `ttl` и дренажом), `vpn-tunnel.mjs` (VPN
Tunnel Service: mTLS, шифрование канала AES-256-GCM, контроль соединения,
авто-восстановление, backpressure) и `edge-cluster.mjs` (RF-first-оркестратор:
первичная фиксация в РФ → пересылка через туннель → авто-дренаж после разрыва).
Приёмная сторона (восстановление порядка по `sequence_number` и дедуп по сквозному
`idempotency_key`) — `createEdgeIntakeCoordinator` ядра (SVC-CORE), совместная зона
CP-7. Клиенты РФ SVC-CHAT/SVC-MOB подключаются через Edge
(`services/mobile-api/src/edge-connection.mjs`, переменная `EDGE_BASE_URL`). Тесты:
unit (`services/edge-gateway/test/unit/*`: шифр, секвенсор, буфер, VPN-туннель,
оркестратор; `services/mobile-api/test/unit/edge-connection.test.mjs`), integration
(`services/edge-gateway/test/integration/mock-edge-gateway.test.mjs` —
транспортный ack без backend-прототипа; `tests/integration/edge-message-buffer-store.test.mjs`
— Postgres-стор RF-буфера; Backend↔WebSocket ТЗ §26.4), contract
(`tests/contract/edge-core-c9-c7.contract.test.mjs` — EDGE↔CORE C9 с полезной
нагрузкой C1) и e2e (`tests/e2e/backend-dist-communication-core.test.mjs` для
production C9 intake, `tests/e2e/mobile-connection-loss-cp7.test.mjs` для
клиентского сценария потери соединения).
Секреты туннеля и шифра RF-буфера приходят из секрет-менеджера (`.env.rf.example`:
`EDGE_VPN_SESSION_KEY`, `EDGE_BUFFER_ENCRYPTION_KEY`), а не из кода. Вне охвата M4 и
перенесено на M5: отказоустойчивость Edge, RPO/RTO и нагрузка на WS.

### M5 — Отказоустойчивость Edge, RPO/RTO, нагрузка на WS

- **Цель.** Стабилизация: отказоустойчивость Edge и предсказуемое восстановление.
- **Задачи.** **Отказоустойчивость Edge** (ТЗ §7.12): при кратковременной потере
  связи — продолжение приёма и буферизации, авто-синхронизация после восстановления;
  недоступность отдельного Edge не роняет платформу. **Проверка RPO/RTO** буфера
  Edge (ТЗ §25.11): RPO ограничен ёмкостью/TTL буфера, восстановление доставки
  после восстановления канала. **Нагрузка на WS** — пробники на пиковый поток
  соединений/событий (ориентиры ТЗ §25.11, §25.3).
- **Тесты.** unit — поведение при исчерпании ёмкости буфера/просрочке TTL
  (backpressure, оповещение); integration — авто-синхронизация после восстановления
  канала; e2e — участие в полном наборе ТЗ §26.6 (регрессия, CP-9), нагрузочные
  пробники WS.
- **DoD.** Пройдены отказоустойчивость Edge, целевые RPO/RTO и нагрузка на WS;
  критерии приёмки (мастер §9.4, CP-9).

**Статус реализации M5.** SVC-EDGE закрывает стабилизацию CP-9 без изменения
замороженного C9. RF-буфер получил предельную ёмкость, high-watermark и
оповещения мониторинга о `edge_buffer_capacity_high_watermark`,
`edge_buffer_capacity_exhausted` и `edge_buffer_ttl_expired`
(`services/edge-gateway/src/edge-message-buffer.mjs`); при переполнении новая
запись не подтверждается и Edge сигнализирует backpressure на приём. Оркестратор
Edge возвращает измерения восстановления в `drain().recovery`
(`pending_before`, `pending_after`, `expired_skipped`, `rpo.capacity`,
`rpo.ttl_ms`, `rto_ms`) и при новом входящем сообщении после восстановления
канала автоматически синхронизирует накопленный backlog
(`services/edge-gateway/src/edge-cluster.mjs`). Нагрузка WS покрыта
детерминированным пробником mock C7 (`services/edge-gateway/src/ws-load-probe.mjs`)
и CLI `npm run probe:edge:ws` (`EDGE_WS_PROBE_CONNECTIONS`,
`EDGE_WS_PROBE_EVENTS`). Тесты: unit
`services/edge-gateway/test/unit/edge-message-buffer.test.mjs`,
`services/edge-gateway/test/unit/ws-load-probe.test.mjs`; integration
`tests/integration/edge-message-buffer-store.test.mjs` и e2e
`tests/e2e/mobile-connection-loss-cp7.test.mjs` (backlog доставляется после
восстановления без потерь/дублей, порядок сохраняется внутри Endpoint).

## 6. Точки согласования

Формулируются явно: ожидания от смежных сервисов · замораживаемый контракт ·
добавляемые межсервисные тесты (мастер §6).

### CP-7 (M4) — Edge/VPN/потеря соединения с SVC-CORE и SVC-CHAT/SVC-MOB

- **Ожидания.**
  - **SVC-CORE** (порядок/идемпотентность): ядро принимает сообщения по **C9** с
    `sequence_number` и `idempotency_key`, восстанавливает порядок в рамках Endpoint
    (ТЗ §7.10) и **дедуплицирует** после выгрузки буфера (ТЗ §11.12). Ожидание к
    **M1**: ядро готово принимать сообщения с `sequence_number`/`idempotency_key`;
  - **SVC-CHAT / SVC-MOB** (подключение через Edge): клиентские подключения РФ
    (Web Chat, Mobile API) идут через Edge Cluster/WebSocket Gateway.
- **Замораживаем.** **C9** (Edge↔App tunnel) в части сопряжения с **C1**; заморозка
  C9 (мастер §6, §9.3).
- **Тесты.** e2e **«Потеря соединения»** (буфер→восстановление→без потерь/дублей,
  сохранение порядка, ТЗ §26.6) и **«Edge Cluster»**; **contract EDGE↔CORE**
  (мастер §6, §8.4).

## 7. Стратегия тестирования

Соответствует мастер §8 (пирамида unit/integration/contract/e2e). Специфические
проверки SVC-EDGE:

- **Отсутствие потерь и дублей при разрыве/восстановлении.** После накопления в
  `edge_message_buffer` и восстановления канала все сообщения доставлены в ядро
  ровно один раз (дедуп по `idempotency_key`, ТЗ §11.12); ни одно принятое
  сообщение не потеряно (ТЗ §7.9).
- **Строгий порядок в рамках Endpoint.** Сообщения одного `endpoint_id`
  передаются в порядке приёма Edge; `sequence_number` монотонен; между разными
  Endpoint взаимный порядок не требуется (ТЗ §7.10).
- **Корректный дренаж буфера по TTL.** При приближении к пределу ёмкости —
  backpressure/оповещение; просроченные по `ttl` записи обрабатываются согласно
  стратегии (ТЗ §7.9).
- **Авто-reconnect WS без дублирующей доставки.** После временной потери связи
  соединение восстанавливается (ТЗ §11.7), уже полученные клиентом события не
  доставляются повторно.
- **RF-first не нарушается.** Первичная фиксация принятых от субъектов РФ данных —
  в RF-контуре; за рубеж данные уходят только после неё (ТЗ §7.14).
- **Contract-тесты EDGE↔CORE** — совместимость поставщика (C9) и потребителя
  (SVC-CORE) на CP-7 (мастер §8.4).

Обязательная integration-связка (ТЗ §26.4): **Backend↔WebSocket**. E2e-участие —
сценарии вех (мастер §8.2): realtime в M2, «Edge Cluster» и «Потеря соединения»
в M4.

## 8. Риски и зависимости

| Риск / зависимость | Влияние | Митигирование |
|---|---|---|
| **Порядок vs масштабирование WS vs ретраи** (ТЗ §7.10) | Дубли/перестановки сообщений | Партиционирование по `endpoint_id` (ключ, single-writer в ядре) + `sequence_number` на входе Edge + сквозной `idempotency_key`; e2e «Потеря соединения» (CP-7). |
| **Переполнение/просрочка буфера** (ТЗ §7.9) | Backpressure, риск потери при исчерпании | Предельная ёмкость и `ttl`; backpressure на приём, приоритизация, оповещение мониторинга; значения по ориентирам RPO/RTO (ТЗ §25.11). |
| **Application Cluster — SPOF** (ревью §2.3) | Простой платформы; Edge лишь буферизует | HA/реплики/multi-AZ и failover на стороне Application Cluster (ТЗ §7.12); Edge продолжает приём и буферизацию до восстановления (§7.9). |
| **Соответствие 152-ФЗ** (ТЗ §7.14) | Юридический риск | RF-first: первичная запись в РФ, отдельная БД RF-контура, минимизация/обезличивание при передаче за рубеж; согласование с SVC-DATA. |
| **RPO/RTO буфера Edge** (ТЗ §25.11) | Допустимая потеря/время восстановления | RPO ограничен ёмкостью/TTL буфера; восстановление доставки после восстановления канала; проверка на M5. |
| Зависимость от **SVC-CORE** (приёмник C9) | Блокировка CP-7 | Разработка против мока C9 до CP-7; ожидание — ядро (M1) готово к приёму с `sequence_number`/`idempotency_key`; заморозка на CP (мастер §6, §9.3). |
| Зависимость от **SVC-DATA** (схема `edge_message_buffer`, RF-БД) | Блокировка M4 | Работа против замороженной схемы мастер §4.10; RF-контур обеспечивает SVC-DATA/инфраструктура. |
| Разрыв **VPN Tunnel Service** (ТЗ §7.8) | Пауза передачи Edge→App | Контроль соединения и авто-восстановление; переход на буферизацию (§7.9); недоступность туннеля — деградируемый сценарий (ТЗ §25.4), без потери сообщений. |
