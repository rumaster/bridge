# План разработки сервиса FBP Engine (SVC-FBP)

SVC-FBP — **вынесенный движок программируемой автоматизации** (Flow-Based
Programming) платформы: исполнитель Workflow, описанных графом из Node и
Connection (ТЗ §13.4). Сервис строится как **форк проекта fbp-engine с
существенной переработкой** под мультиарендную SaaS-платформу (ТЗ §13.13):
заимствуется архитектурный подход (граф из Node/Connection, Execution Context,
пошаговое исполнение), но **не** прикладной набор узлов. Это **не «настройка»
готового движка**, а значительный форк с заменой набора узлов, удалением прямого
доступа к данным, введением мультиарендности и безопасного вычислителя выражений.
Как **вынесенный (деградируемый) сервис** (мастер §2, ТЗ §11.2, §5.4) SVC-FBP
никогда не блокирует Communication Core: при недоступности FBP Engine обмен
сообщениями продолжается (ТЗ §13.2). SVC-FBP участвует в точках согласования
**CP-4** и **CP-5** (мастер §6) и является **владельцем контракта C5** (мастер §7.1).

> Ссылки «ТЗ §…» — на техническое задание; «§…» — на мастер-план
> [`docs/plan/README.md`](../README.md); «M0…M5» — вехи (мастер §5); «CP-…» —
> точки согласования (мастер §6); «C3/C4/C5», «SVC-…» — контракты и сервисы
> (мастер §7, §2).

## 1. Назначение и границы

**Входит в SVC-FBP:**

- **исполнение Workflow**: обход графа Node/Connection, ведение Execution Context,
  пошаговое исполнение (ТЗ §13.4), маршрутизация исполнения по ветвлениям;
- **нейтральный набор узлов** коммуникационной платформы (ТЗ §13.13-п.1): вызов
  Backend API, вызов LLM, поиск в Knowledge Base, ветвление, преобразование данных
  (Transform Node), ожидание события;
- **безопасный Transform Node** (ТЗ §13.4): преобразование данных декларативным
  вычислителем выражений над whitelist-операциями, с доступом **только** к своему
  входу (`input`);
- **узел вызова Backend API** (ТЗ §13.5) — **единственный санкционированный способ
  изменять данные платформы**; формирование запроса от имени контекста
  пользователя/арендатора;
- **журнал исполнения** Workflow (ТЗ §13.9, §24.6, §22.11): диагностика,
  события узлов, ошибки;
- **неизменяемые версии** схем и **version pinning** экземпляров (ТЗ §13.10);
- **мультиарендность**: исполнение каждого экземпляра в контексте конкретной
  организации, изоляция данных между организациями (ТЗ §13.13-п.4, §22.6).

**НЕ входит в SVC-FBP (границы):**

- **прямой доступ к БД** и обход Backend API — **запрещены и удалены** из форка
  (ТЗ §13.13-п.3, §13.12, §22.3); движок не выполняет SQL и не работает с
  PostgreSQL напрямую (ТЗ §13.7); данные меняются **только** через узел вызова
  Backend API (ТЗ §13.5), с проверкой полномочий на стороне Backend;
- **инициирование Workflow самим движком или AI** — инициатором **всегда является
  Backend**, а не AI (ТЗ §6.13, §12.10); AI не вызывает FBP Engine напрямую;
- **исполнение произвольного кода** внутри узлов (`node:vm`/`isolated-vm`/
  отдельный процесс/WASM) — **запрещено** (ТЗ §13.4, §13.12);
- **транспортировка/маршрутизация сообщений** — обязанность SVC-CORE; FBP Engine
  не Message Broker (ТЗ §13.3, §6.6);
- **доступ к секретам платформы** и изменение полномочий пользователей (ТЗ §13.12).

Каноническое определение схемы БД — мастер §4.8 (владелец схемы — SVC-DATA);
каноническое определение контрактов — `packages/contracts` (мастер §7). Настоящий
план **не переопределяет** их, а детализирует участок SVC-FBP.

## 2. Технологии

| Область | Решение |
|---|---|
| Основа | **Форк проекта fbp-engine** (ТЗ §13.1, §13.13); заимствуется ядро исполнения графа (Node/Connection, Execution Context, пошаговое исполнение), прикладные узлы исходного проекта удаляются. Лицензия форка проверяется до включения кода (ТЗ §13.13). |
| Язык/среда | TypeScript; отдельный вынесенный сервис `services/fbp-engine` (мастер §3), вызывается ядром через фасад `fbp-integration` по контракту C5 с таймаутами/circuit breaker (ТЗ §11.2). |
| Модель исполнителя | **Stateless executor** (ТЗ §25.3, §13.10): исполнитель не хранит состояние экземпляра в памяти между шагами; любой узел-исполнитель может обработать любой экземпляр. |
| Состояние экземпляра | Хранится **вне исполнителя** — во внешнем хранилище через Backend (`workflow_instance_state`, мастер §4.8); это обеспечивает горизонтальное масштабирование (ТЗ §25.3). |
| Transform Node | **Декларативный безопасный вычислитель выражений** (safe expression evaluator) над whitelist операций/функций — **без** `node:vm`, `isolated-vm`, отдельного процесса и WASM (ТЗ §13.4); изоляция «по построению» (недоступ к внешнему миру = отсутствие операций в грамматике). Ограничения по времени и размеру результата; грамматика без неограниченных циклов. |
| Версионирование | **Неизменяемые (immutable) версии** схем; **version pinning** — экземпляр исполняется на зафиксированной версии, загружаемой по её идентификатору (ТЗ §13.10). |
| Доступ к данным | Только через **Backend API** (C3): чтение/изменение данных, поиск в Knowledge Base (ТЗ §13.7), схема — через Backend. Прямой доступ к БД отсутствует (ТЗ §13.12). |
| Мультиарендность | Каждый экземпляр несёт `organization_id`; все вызовы Backend API идут в контексте этой организации (ТЗ §22.6). |
| Тестирование | Jest (unit, `*.spec.ts`), Testcontainers/мок Backend API (integration Backend↔FBP Engine, ТЗ §26.4), contract- и e2e-тесты на CP (мастер §8). |

## 3. Интерфейсы и контракты

SVC-FBP — **владелец** контракта **C5** (FBP Contract, мастер §7.1) и
**совладелец** группы публичных эндпоинтов **C3.workflows** (совместно с SVC-API,
мастер §7.2). Ниже — детализация операций; **каноническое определение хранится в
`packages/contracts`** (`openapi/`), semver и заморозка — по мастер §7.4/§9.3.

### 3.1 Экспортируемые контракты

**C5 — FBP Contract (API ↔ FBP, ТЗ §13.5, мастер §7.1). SVC-FBP — владелец.**
Две составляющие:

- **Запуск Workflow (Backend → FBP).** `POST /workflows/{id}/instances` — Backend
  инициирует экземпляр Workflow (инициатор — **всегда Backend**, не AI, ТЗ §6.13),
  передавая: идентификатор конкретной **версии схемы** (version pinning, ТЗ §13.10),
  входные параметры (только необходимые данные, ТЗ §13.4-Parameters), а также
  **контекст пользователя/арендатора** (`organization_id`, идентификатор
  пользователя) для последующих вызовов Backend API. Ответ фиксирует
  `instance_id`, привязанную `version_id`, `status`.
- **Обратный вызов узла Backend API (Workflow → Backend REST).** Узел вызова
  Backend API исполняет запрос к публичному Backend API (C3) **от имени контекста
  пользователя/арендатора экземпляра** (ТЗ §13.5). Это **единственный
  санкционированный способ** читать и изменять данные платформы; Backend выполняет
  проверку полномочий, применяет бизнес-логику, меняет данные и возвращает
  результат в Execution Context (ТЗ §13.5, §13.13-п.2).

**C3.workflows (публичный REST, мастер §7.2, префикс `/api/v1`) — совместно с
SVC-API.** Эндпоинты управления Workflow (для SVC-ADMIN, ТЗ §16.7):

- `GET/POST /workflows` — список/создание Workflow организации;
- `POST /workflows/{id}/versions` — сохранение **новой неизменяемой версии** схемы
  (ТЗ §13.10); публикация новой версии не влияет на запущенные экземпляры;
- `POST /workflows/{id}/instances` — запуск экземпляра (см. C5 выше);
- `GET /workflows/{id}/instances/{iid}` — состояние/результат экземпляра;
- журнал исполнения экземпляра — чтение `workflow_execution_logs` (ТЗ §13.9,
  §24.6) для отображения истории и диагностики в SVC-ADMIN (ТЗ §16.7).

Событие realtime **`workflow.state_changed`** (C7, мастер §7.3) публикуется через
Backend при смене состояния экземпляра.

### 3.2 Потребляемые контракты

| Контракт | От кого | Назначение |
|---|---|---|
| **C3** (Backend REST) | SVC-API | **Единственный способ** читать/менять данные платформы через узел Backend API (ТЗ §13.5); поиск в Knowledge Base (ТЗ §13.7); чтение схемы — через Backend. |
| **C4** (AI Contract) | SVC-AI (через Backend) | Вызов LLM из узла Workflow (ТЗ §13.6) — опосредованно через Backend/фасад, без прямого доступа к внутренним сервисам. |
| Схема БД + миграции | SVC-DATA | таблицы §4.8 (`workflow_*`), RLS по `organization_id`; доступ — только через Backend. |

> **Инвариант границы.** SVC-FBP не имеет собственного доступа к БД (ТЗ §13.12,
> §22.3): всё чтение/запись `workflow_*` и любых данных платформы проходит через
> Backend (C3). Это прямое следствие адаптации форка (ТЗ §13.13-п.3).

## 4. Модель данных

Таблицы — по мастер §4.8 (владелец схемы **SVC-DATA**, основной потребитель
**SVC-ADMIN**; появляются в **M3**, мастер §5.1). SVC-FBP работает с ними
**только через Backend API** (прямого доступа к БД нет, ТЗ §13.12). Все таблицы
арендо-зависимы — несут `organization_id` и изолируются по нему (ТЗ §22.6).

| Таблица | Ключевые поля (акцент SVC-FBP) | Появляется |
|---|---|---|
| `workflows` | `id`, `organization_id`, `name`, `status`, `default_version_id` — «версия по умолчанию» для новых запусков переключается конфигурацией (ТЗ §13.10). | M3 |
| `workflow_versions` | `workflow_id`, `version_no`, `schema` (jsonb), `created_by`; **`UNIQUE(workflow_id, version_no)`**. **Неизменяемые (immutable)**: изменение схемы порождает новую версию, а не перезапись (ТЗ §13.10). | M3 (базово) / M4 (иммутабельность как инвариант) |
| `workflow_instances` | `workflow_id`, **`version_id`** (FK) — **version pinning**: экземпляр исполняется на зафиксированной версии (ТЗ §13.10); `status`, `started_at`, `finished_at`. | M3 (базово) / M4 (pinning как инвариант) |
| `workflow_instance_state` | `instance_id` (PK), `state` (jsonb) — **состояние вне исполнителя** для stateless-масштабирования (ТЗ §25.3); любой узел-исполнитель загружает/сохраняет состояние здесь. | M4 |
| `workflow_execution_logs` | `instance_id`, `node_id`, `event`, `data` (jsonb), `created_at` — **журнал исполнения** (ТЗ §13.9, §24.6); изоляция логов по `organization_id`. | M3 |

**Инварианты SVC-FBP:** (1) `workflow_versions` неизменяемы — новая версия вместо
перезаписи (ТЗ §13.10); (2) `workflow_instances.version_id` фиксируется при запуске
и не меняется до завершения (version pinning); (3) исполнитель не хранит состояние
между шагами — источник истины по состоянию экземпляра — `workflow_instance_state`
(ТЗ §25.3); (4) ни одна запись/чтение не выполняется в обход Backend API (ТЗ §13.12).

## 5. Поэтапный план

Каждый этап привязан к вехе (мастер §5). Для каждого: Цель · Задачи · Тесты
(unit / integration / e2e) · DoD (единый — мастер §9.4). **Ядро платформы не
зависит от FBP** (ТЗ §5.4, §13.2): до CP-4 смежные сервисы работают против мока
FBP.

### M0 — Контракт C5 и мок FBP

- **Цель.** Заморозить контракт **C5** и дать смежным сервисам мок, чтобы ядро
  разрабатывалось независимо (деградируемость, ТЗ §5.4).
- **Задачи.** Определить и зафиксировать в `packages/contracts` **C5**: запуск
  Workflow (`POST /workflows/{id}/instances` с указанием версии и контекста
  пользователя/арендатора) и обратный вызов узла Backend API; поднять **мок FBP**
  (заглушка запуска и колбэка) для фасада `fbp-integration`; каркас сервиса
  `services/fbp-engine`. Проверить лицензию fbp-engine до включения кода (ТЗ §13.13).
- **Тесты.** unit — валидация DTO C5 (запуск/колбэк), схема события
  `workflow.state_changed`; contract-заготовки API↔FBP.
- **DoD.** Контракт C5 v1 заморожен (semver), мок FBP в CI зелёный; ядро не
  зависит от реального FBP (мастер §9.4).

### M1 — Участие как мок

- **Цель.** Не блокировать вертикальный срез M1.
- **Задачи.** **Крупных задач нет.** SVC-FBP присутствует **только как мок C5**
  (мастер §5.1); поддерживать актуальность мока при уточнении контракта.
- **Тесты.** unit — совместимость мока с C5.
- **DoD.** Мок соответствует C5; сборка зелёная.

### M2 — Без крупных задач

- **Цель.** Оставаться в режиме мока до вехи программируемости (M3).
- **Задачи.** **Крупных задач по SVC-FBP в M2 нет** (мастер §5.1). При изменениях
  C4 (AI) — сверить точки будущей интеграции LLM-узла.
- **Тесты.** unit — регрессия мока C5.
- **DoD.** Контракт стабилен; мок актуален.

### M3 — Форк и переработка (ОСНОВНАЯ работа)

- **Цель.** Форкнуть fbp-engine и **переработать под платформу** (ТЗ §13.13), дав
  работающий запуск Workflow с узлом Backend API и безопасным Transform Node.
- **Задачи (адаптация форка, ТЗ §13.13):**
  1. **Форк fbp-engine** и выделение предметно-нейтрального ядра исполнения графа
     (Node/Connection, Execution Context, пошаговое исполнение).
  2. **Нейтральный набор узлов** (§13.13-п.1): вызов Backend API, вызов LLM, поиск
     в Knowledge Base, ветвление, Transform Node, ожидание события — вместо
     прикладных/доменных узлов исходного проекта.
  3. **Узел вызова Backend API** (§13.5, §13.13-п.2) — **единственный
     санкционированный способ менять данные**; вызов от имени контекста
     пользователя/арендатора; проверка полномочий — на стороне Backend.
  4. **Удаление прямого доступа к БД** и обхода Backend API (§13.13-п.3, §13.12):
     движок не выполняет SQL, работает только через C3.
  5. **Мультиарендность** (§13.13-п.4, §22.6): привязка исполнения к
     `organization_id`; запрет доступа к данным одной организации из Workflow другой.
  6. **Безопасный Transform Node** (§13.4, §13.13-п.5): декларативный вычислитель
     выражений над whitelist; валидация допустимых операций **на этапе сохранения
     схемы** (не во время исполнения); ограничения по времени/размеру результата.
  7. **Базовый журнал исполнения** (§13.9, §24.6) в `workflow_execution_logs`:
     события узлов, ошибки, диагностика.
  8. **Интеграция с редактором Workflow** (SVC-ADMIN, ТЗ §16.7): визуальное
     редактирование схем безопасным набором узлов; сохранение как новой версии.
- **Тесты.**
  - *unit:* безопасность evaluator'а Transform Node (запрет доступа к среде/сети/
    ФС/секретам/произвольному коду), маршрутизация по узлам графа, формирование
    вызова узла Backend API (контекст пользователя/арендатора), отклонение
    недопустимых операций при валидации схемы.
  - *integration:* **Backend↔FBP Engine** (ТЗ §26.4) через **мок Backend API**;
    мультиарендная изоляция экземпляров (Workflow орг. A не читает данные орг. B).
  - *e2e:* **«Workflow вызывает Backend API»** (CP-4, ТЗ §26.6: запуск→Node→
    завершение→журнал); **«Admin правит Workflow»** (CP-5).
- **DoD.** Работает запуск Workflow с узлом Backend API и Transform Node; прямой
  доступ к БД отсутствует; изоляция арендаторов и серверная валидация (мастер §9.4);
  добавлены contract- и e2e-тесты CP-4/CP-5.

**Статус реализации M3.** M3 FBP Engine завершён для CP-4/CP-5: движок исполняет
нейтральный граф, валидирует Transform Node на сохранении схемы, вызывает
Backend API как единственный write path и не имеет прямого SQL-доступа. Покрытие:
`services/fbp-engine/test/unit/{validate-workflow,nodes,transform-validate}.test.mjs`,
`services/fbp-engine/test/integration/backend-fbp.test.mjs`,
`tests/contract/c5-fbp-contract.test.mjs`,
`tests/contract/c5-fbp-node-catalog.test.mjs`,
`tests/e2e/workflow-cp4.test.mjs` и
`tests/e2e/workflow-engine-cp4-cp5.test.mjs`. C5 заморожен на CP-4 и вместе с
C3/C4 стабилизирован на CP-5 в `packages/contracts/cp4-cp5-freeze.v1.json`.
Готовность M4: базовые `workflow_*` стабильны; version pinning/stateless
масштабирование остаются следующим этапом.

### M4 — Версии, version pinning, stateless-масштабирование

- **Цель.** Обеспечить неизменяемость версий, корректный version pinning и
  горизонтальное масштабирование исполнителя.
- **Задачи.** **Неизменяемые версии** схем: изменение порождает новую версию, а не
  перезапись (ТЗ §13.10); **version pinning** — запущенный экземпляр исполняется до
  завершения на зафиксированной версии, публикация новой версии влияет только на
  последующие запуски (ТЗ §13.10). **Stateless executor** (ТЗ §25.3): вынос
  состояния экземпляра в `workflow_instance_state` (через Backend), исполнитель без
  памяти между шагами; **горизонтальное масштабирование** — любой узел-исполнитель
  обрабатывает любой экземпляр (ТЗ §25.3). Переключение «версии по умолчанию» —
  конфигурацией.
- **Тесты.**
  - *unit:* привязка версии к экземпляру, отклонение попытки перезаписать версию,
    восстановление шага из внешнего состояния.
  - *integration:* **восстановление stateless-исполнителя из состояния** (другой
    узел продолжает экземпляр по `workflow_instance_state`); совместимость pinning
    с масштабированием.
  - *e2e:* старые экземпляры завершаются на своей версии при публикации новой.
- **DoD.** Версии неизменяемы; экземпляры исполняются на своей версии; исполнитель
  масштабируется горизонтально без потери состояния (мастер §9.4).

### M5 — Нагрузка, харденинг безопасности, полнота журнала

- **Цель.** Стабильность под нагрузкой и защищённость мультиарендного исполнения.
- **Задачи.** Нагрузочные пробники и проверка **масштабирования** исполнителей
  (ориентиры ТЗ §25.11, §25.3); **харденинг безопасности Transform Node** —
  **фаззинг выражений** (попытки выхода из «песочницы»/доступа к процессу/среде
  должны отвергаться), проверка ограничений времени/размера; **полнота журнала**
  исполнения (ТЗ §13.9, §24.6): метрики Workflow (запуски, успехи, ошибки, среднее
  время, активные экземпляры — ТЗ §24.6).
- **Тесты.** unit — фаззинг грамматики evaluator'а (ни один вход не даёт побочных
  эффектов/доступа к среде); integration — деградация при недоступном Backend
  (ядро продолжает работу, ТЗ §5.4, §13.2); e2e — участие в полном наборе ТЗ §26.6
  (регрессия, CP-9).
- **DoD.** Пройдены нагрузка/масштабирование; фаззинг не выявляет обхода изоляции;
  журнал полон; критерии приёмки (мастер §9.4, CP-9).

**Статус реализации M5 (M5-99).** На интеграционном gate CP-9 SVC-FBP принят:
нагрузочный пробник исполнителей (`experiments/m5-fbp-load-probe.mjs`) в бюджете,
харденинг Transform Node подтверждён фаззингом (`docs/operations/m5-security-review.md`,
§2), участие в полном наборе §26.6 зелёное (`tests/e2e/workflow-fbp-m5-cp9.test.mjs`).
Контракт **C5** финально заморожен как `released_v1` в
`packages/contracts/cp9-freeze.v1.json` (скреплено `tests/contract/m5-gate-freeze.test.mjs`).

## 6. Точки согласования

Формулируются явно: ожидания от смежных сервисов · замораживаемый контракт ·
добавляемые межсервисные тесты (мастер §6).

### CP-4 (M3) — запуск Workflow и узел Backend API с SVC-API

- **Ожидания.** SVC-API предоставляет публичный Backend API (C3) и фасад
  `fbp-integration`, **инициирует запуск Workflow** (инициатор — Backend, не AI,
  ТЗ §6.13) и обслуживает **обратный вызов узла Backend API** с проверкой
  полномочий (ТЗ §13.5). SVC-FBP исполняет граф и меняет данные **только** через
  этот узел — **единственный санкционированный способ** (ТЗ §13.13). SVC-DATA
  поставляет `workflow_*` (мастер §5.1).
- **Замораживаем.** **C5** (FBP start + Backend API node) в версии v1.
- **Тесты.** e2e **«Workflow вызывает Backend API»** (запуск→Node→завершение→
  журнал, ТЗ §26.6); **contract API↔FBP** (мастер §8.4).

### CP-5 (M3) — визуальный редактор Workflow с SVC-ADMIN / SVC-AI(Onboarding)

- **Ожидания.** SVC-ADMIN даёт **визуальный редактор схем** (ТЗ §16.7) поверх
  безопасного набора узлов SVC-FBP; редактирование сохраняется как **новая версия**
  (ТЗ §13.10) и не влияет на запущенные экземпляры; действия редактирования пишут
  аудит (ТЗ §23.8). Совместимость с **AI Onboarding** (SVC-AI): Onboarding меняет
  конфигурацию **только через Backend API** (ТЗ §6.13, §16.8), не инициируя
  Workflow напрямую. SVC-API стабилизирует C3/C4/C5.
- **Замораживаем.** **C3 + C4 + C5** (стабилизация, мастер §6).
- **Тесты.** e2e **«Admin правит Workflow»**; совместимость с e2e «AI Onboarding
  применяет конфиг» (мастер §8.2); contract API↔FBP.

## 7. Стратегия тестирования

Соответствует мастер §8 (пирамида unit/integration/contract/e2e). Специфические
проверки SVC-FBP:

- **Безопасность Transform Node.** Попытки **выхода из «песочницы»** и доступа к
  процессу/среде/сети/ФС/секретам/системному времени/ГСЧ **должны падать** (ТЗ
  §13.4); недопустимые операции отвергаются **на этапе валидации схемы**, а не при
  исполнении; ограничения по времени и размеру результата соблюдаются; грамматика
  не допускает неограниченных циклов. На M5 — **фаззинг выражений**.
- **Идемпотентность и детерминизм исполнения.** Одинаковые вход и версия схемы дают
  одинаковый результат (Transform Node детерминирован — без доступа к времени/ГСЧ,
  ТЗ §13.4); повторный запуск не даёт скрытых побочных эффектов вне узла Backend API.
- **Version pinning.** Запущенный экземпляр исполняется по **своей** версии;
  публикация новой версии влияет только на последующие запуски (ТЗ §13.10);
  перезапись версии отклоняется (иммутабельность).
- **Мультиарендная изоляция.** Экземпляр организации A не может прочитать/изменить
  данные организации B; все вызовы Backend API идут в контексте `organization_id`
  экземпляра (ТЗ §22.6, §13.13-п.4).
- **Восстановление stateless-исполнителя.** Другой узел-исполнитель продолжает
  экземпляр из `workflow_instance_state` без потери прогресса (ТЗ §25.3).
- **Contract-тесты API↔FBP.** Consumer-driven контракт C5: запуск Workflow и
  обратный вызов узла Backend API (мастер §8.4).

Обязательная integration-связка (ТЗ §26.4): **Backend↔FBP Engine** (через мок
Backend API). E2e-участие — сценарии вех (мастер §8.2): «Workflow вызывает
Backend API» (M3, CP-4) и «Admin правит Workflow» (M3, CP-5); регрессия — CP-9.

## 8. Риски и зависимости

| Риск / зависимость | Влияние | Митигирование |
|---|---|---|
| **Масштаб форка fbp-engine** — значительный форк, а не «настройка» (ТЗ §13.13, ревью §4.9, мастер §10) | Срыв вехи M3 | Выделен **отдельный крупный этап M3**; до CP-4 ядро работает против **мока FBP**; поэтапная замена узлов и удаление прямого доступа к БД. |
| **Безопасность произвольных выражений** в мультиарендной SaaS (ТЗ §13.4) | Уязвимость (sandbox escape), утечка между арендаторами | **Декларативный safe-evaluator** без `node:vm`/`isolated-vm`/WASM; изоляция «по построению»; валидация операций при сохранении схемы; фаззинг на M5. |
| **Согласованность состояния при stateless-масштабировании** (ТЗ §25.3) | Потеря/рассинхрон прогресса экземпляра | Состояние — **вне исполнителя** в `workflow_instance_state` (через Backend); тесты восстановления другого узла-исполнителя (M4). |
| **Неизменяемость версий / version pinning** (ТЗ §13.10) | Изменение поведения запущенных экземпляров | Immutable `workflow_versions` (`UNIQUE(workflow_id, version_no)`); фиксация `version_id` при запуске; отклонение перезаписи (M4). |
| Зависимость от **SVC-API** (C3/C5, узел Backend API) | Блокировка CP-4/CP-5 | Разработка против **моков C3/C5** до CP; заморозка на CP (мастер §6, §9.3). |
| Зависимость от **SVC-DATA** (`workflow_*`, §4.8) | Блокировка M3 | Доступ к схеме — только через Backend; работа против замороженной схемы SVC-DATA (появление в M3, мастер §5.1). |
| Ошибочная инициация Workflow из AI вместо Backend (ТЗ §6.13) | Обход проверок безопасности | Инициатор — **всегда Backend**; AI меняет данные только через Backend API; contract-тест C5 фиксирует источник запуска. |
