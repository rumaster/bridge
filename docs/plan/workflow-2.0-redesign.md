### Почему D8 возник и почему не чинился

Это не разгильдяйство, а следствие сборки. `services/backend` — CommonJS с `rootDir: "src"`, а `packages/contracts` — ESM TS-исходники. Импорт исходников контракта из Backend падает на `TS6059: File is not under rootDir` плюс несовместимость ESM/CJS. Поэтому Backend **физически не мог** переиспользовать контракт и копировал правила руками — в коде это прямо задокументировано («Портирована из packages/contracts»).

Отсюда следует: пока `@bridge/contracts` не собирается в пакет, любой «единый контракт» остаётся на словах, а D1 будет возникать снова.

Отдельно: `FBP_BACKEND_API_METHODS` — это `["GET","POST","PUT","PATCH","DELETE"]`, то есть HTTP-глаголы, а не каталог вызовов. `path` — свободная строка, ни с чем не сверяется.

## Принятые решения (2026-07-15)

| № | Решение | Обоснование |
|---|---|---|
| A1 | **Модель графа — гибрид push/pull, как в образце.** `transform` и другие узлы-функции exec-портов не имеют и вычисляются лениво по требованию с мемоизацией. Дополнительно вводятся pure-узлы `variable_read` / `variable_write` и `merge` для схождения потоков | Граф короче: не надо протаскивать exec через каждое преобразование |
| A2 | **События — только контур.** Реестр событий + таблица подписок + запись/снятие при сохранении + тест-прогон. Реальный запуск по живому событию — отдельный этап | Сегодня реально публикуются два события, outbox мёртв, роутинга нет. Полный рантайм тянет за собой переписывание доставки целиком |
| A3 | **Каталог Backend API генерируется из OpenAPI, витрину курирует platform_operator в админке.** Полный список 79 операций → таблица allowlist → отдельный экран с галочками | Список едет за API и не устаревает; оператор решает, что вообще можно дёргать из схемы |
| A4 | **Ломаем формат: `schema_version` 2.0.0.** Сиды переписываем, старые `draft_schema` и `workflow_versions` дропаем миграцией | Workflow заводятся только сидом (R1), продовых схем нет — мигрировать нечего |
| A5 | **Тест — реальный прогон драфта без создания инстанса**, трасса по узлам возвращается в ответе и подсвечивается на канве | Обходит FK журнала на `workflow_instances`; тестовые прогоны не мешаются с боевыми |
| A6 | **Payload события для теста — выбор wait-event узла + редактируемый JSON** с предзаполнением примера из реестра и валидацией по payload-схеме | Иначе не проверить ветвления на разных данных |
| A7 | **Дефект D4 (401) чиним в рамках этой работы** | Иначе селектбокс вызовов и тест-прогон остаются непроверяемыми |
| A8 | **У `transform` остаётся только JS-текст.** Режим `expression` (JSON-AST по whitelist) и весь его аппарат удаляются | Режим `code` уже существовал и уже был разрешён, так что удаление `expression` ничего нового не открывает; образец устроен так же. Уносит ~700 строк AST-валидатора, продублированных дважды |
| A9 | **`@bridge/contracts` собирается в CommonJS**, Backend зависит от пакета и импортирует `@bridge/contracts/c5-workflow` | Единственный способ сделать контракт общим (см. врезку про D8). Сборка вешается на `prepare`, а не на `build`: в CI `lint` идёт раньше `build`, а типы нужны уже на линте |
| A10 | **Драфт валидируется только по форме графа**, полная проверка контракта — при копировании в рабочую версию | Драфт сохраняется автоматически при выходе из редактора: если требовать полной валидности, автосохранение будет терять недостроенную работу. Реализовано в `saveDraft` (`validateWorkflowSchemaShape`); `promoteDraft` по-прежнему требует полной валидности. Гоча, найденная при ревизии: функция была написана и задокументирована, но не вызывалась — `saveDraft` гонял полную валидацию, и решение фактически не действовало |

## Целевая модель

### Порты

```ts
PORT_TYPES = ['exec', 'string', 'number', 'boolean', 'object',
              'string_array', 'object_array', 'any']

arePortTypesCompatible(from, to):
  exec соединяется только с exec
  иначе: from === to || from === 'any' || to === 'any'
```

Ключевой принцип образца, который переносим: **порты и на фронте, и на бэкенде считает одна и та же функция** `getNodePortDefinitions(node, graph)` из `packages/contracts`. Редактор физически не может нарисовать порт, которого не будет в рантайме. Это же снимает D8 — валидация становится общей.

Инварианты валидации:
- на data-input порт заводится ровно одно ребро; на exec-input — сколько угодно;
- ребро не смешивает exec и data;
- нет циклов в exec-графе;
- типы портов совместимы.

### Каталог узлов 2.0

| Узел | exec | Data-входы | Data-выходы | Свойства |
|---|---|---|---|---|
| `wait-event` | **только выход** (источник exec) | — | `data: object` | `event_type` — селектбокс из реестра, `correlation` |
| `backend-api` | in / out | по схеме операции | по схеме ответа | `operation_id` — селектбокс из курируемого каталога |
| `knowledge-base-search` | in / out | `keys: string_array`, `tags: string_array` | `documents: object_array` | `top_k` |
| `llm` | in / out | по конфигу портов | по конфигу портов | промпт, модель |
| `branch` | in; выходы `true` / `false` | `value: any`, `right: any` | — | `operator` (истина, существует, =, !=, >, >=, <, <=), переопределение `right` |
| `transform` | **нет** (pure) | произвольные, из `config.inputs` | произвольные, из `config.outputs` | многострочный JS |
| `variable_read` | **нет** (pure) | — | `value: any` | имя переменной |
| `variable_write` | in / out (side-effect) | `value: any` | — | имя переменной |
| `merge` | входы `exec_1..exec_N`, выход | — | — | — |
| `sub_schema` | in / out | зеркалят `start`-порты субсхемы | зеркалят `end`-порты | `subSchemaSlug` |
| `start` / `end` | только в субсхемах | границы из `config.outputs` / `config.inputs` | | |

`schema.entry` **упраздняется**: точки входа — все узлы `wait-event`. В субсхемах событий нет, но `start` и `end` обязательны ровно по одному.

`bodyGraph` удаляется полностью — у `transform` и `branch` его нет ни в каком виде.

### Контракт transform

Как в образце: код оборачивается в IIFE, пользователь пишет тело и делает `return`.

```js
// в песочнице доступны: input, variables
// input — объект, ключи = имена входных портов
evaluateTransformCode(code, inputs, ctx) →
  runInSandbox(`(() => { "use strict"; ${code} })()`, { input, variables })
```

Выходы читаются путём от `{ result }`: порт с `path: "result.name"` получает `result.name`. Значение проверяется на соответствие типу порта в рантайме. Порты объявляются декларативно в `config.inputs` / `config.outputs`, а не выводятся из кода.

Песочница — три эшелона (как в образце): regex-фильтр запрещённых токенов, `vm.createContext` без Node-глобалей, таймаут V8. Существующий режим `expression` с whitelist-AST остаётся для узлов, где не нужен полный JS.

### Версии

Модель уже почти та, что нужна, — доводим до постановки:

- редактор всегда открывает **драфт**;
- автосохранение драфта при выходе из редактора и при переходе к другой схеме (сейчас есть только на unmount);
- кнопка **«Сохранить» = promote**: драфт копируется в рабочую версию;
- **при promote** ищем в схеме узлы `wait-event` и синхронизируем подписки (регистрация/разрегистрация). Драфт подписок не создаёт;
- тест гоняется **над драфтом, открытым в редакторе**.

### Этап 1. Контракт 2.0.0 — сделано

`packages/contracts/src/c5-workflow.ts` переписан по образцу `packages/schema-contract/index.mjs`: `FBP_PORT_TYPES`, `arePortTypesCompatible`, `getNodePortDefinitions(node, graph)`, `DATA_ONLY_NODE_TYPES`, `execInputPortIds` / `execOutputPortIds`, каталог узлов 2.0, `validateWorkflowGraphContract` с кодами ошибок, `canConnectPorts` для подсветки в редакторе.

Порты вычисляются функцией, а не берутся из статического списка, — иначе `merge` не мог бы зависеть от рёбер, а `transform` от конфига.

Пакетирование (решение A9):
- `packages/contracts/tsconfig.cjs.json` + `scripts/build-cjs.mjs` → `dist/cjs/c5-workflow.{js,d.ts}` плюс `dist/cjs/package.json` с `type: commonjs` (обязателен: у пакета `type: module`, иначе Node прочитал бы вывод как ESM);
- `exports["./c5-workflow"]`: `require` → dist/cjs, `import` → src (vite и tsx продолжают брать TS-исходник), `types` → dist d.ts;
- сборка повешена на `prepare` — срабатывает на `npm ci`, поэтому Dockerfile'ы менять не пришлось;
- в корневом `package.json` `packages/*` переставлены в начало списка workspaces: npm запускает скрипты в порядке массива, а раньше `apps/*` собирались раньше контрактов.

Собирается только `c5-workflow.ts`: он не имеет ни одного импорта, тогда как `c5.ts` тянет `node:fs` и `c4.ts` и потому непригоден ни для браузера, ни для CJS. Туда же переехали `TRANSFORM_DEFAULT_LIMITS`.

Валидаторы схлопнуты в вызов контракта: Backend — с 978 строк до ~150 (осталось только то, чего контракт знать не может: лимиты песочницы, форма HTTP-исключения, сбор slug'ов субсхем), движок — до ~90. Закрывает D1 и D8.

Проверено: `npm run lint` зелёный по всему монорепозиторию; Backend собирается и `require('@bridge/contracts/c5-workflow')` работает в рантайме; saas-admin собирается (vite резолвит `import` → TS); 11/11 в переписанной спеке Backend, включая регрессию D1 — узел ветвления с обеими ветками теперь сохраняется.

### Этап 3. Каталог Backend API + витрина — сделано (кроме экрана)

Каталог генерируется в `packages/contracts/src/backend-api-catalog.generated.ts` из `openapi/backend-core/openapi.json` (81 операция: operationId, method, path, path-параметры, query-параметры, наличие тела). Выкладывается статическим TS-модулем, а не читается из JSON в рантайме: его грузит браузер, где `c5.ts` с `node:fs` непригоден. Сверка `generate:check` вшита в build пакета — добавление маршрута `/api/v1` без перегенерации падает в CI, а не у оператора в редакторе.

**Узел хранит только `operation_id`**: `method` и `path` выводятся из каталога, а не дублируются в конфиге, — иначе схема разъехалась бы с API при первом переименовании маршрута, и никто бы этого не заметил. Контракт проверяет, что вызов есть в каталоге и что у каждого плейсхолдера пути есть одноимённый входной порт.

Разделение ответственности:
- **каталог** (код, из OpenAPI) — «что вообще существует»;
- **витрина** `workflow_backend_api_allowlist` (БД, курирует platform_operator) — «что разрешено дёргать из схемы».

Витрина глобальная, без `organization_id` и без RLS: она не содержит данных арендатора, читать её должен любой арендатор при валидации, а запись закрыта ролью на уровне API. Операция без строки считается запрещённой — закрыто по умолчанию. Проверка витрины идёт при каждом сохранении, а не только при выборе в редакторе: иначе операцию можно было бы закрыть, а сохранённые схемы продолжили бы её дёргать.

Эндпоинты `GET/PATCH /api/v1/workflow-backend-api-allowlist` под `@Roles("platform_operator")`. Проверено: 16/16 юнит-тестов, Backend типизируется и собирается.

**Экран курирования в админке отнесён к этапу 7** — это фронтенд, и он делается вместе с редактором.

### Этап 4. Движок 2.0

Сюда же отнесено удаление режима `expression` (решение A8) — оно неотделимо от переписывания узлов. Выяснилось, что `expression` был не только режимом transform, а **общим механизмом «проводки»**: `backend-api.body`/`query`, `branch.condition`, `llm.prompt`/`params`, `knowledge-base-search.query`, `wait-event.correlation` — всё это Transform-выражения. В 2.0 их заменяют порты, поэтому удаляются: `transform/{evaluator,operations,validate-expression}.ts`, whitelist в `packages/contracts/src/c5.ts` (`TRANSFORM_STRUCTURAL_OPERATIONS`, `TRANSFORM_FUNCTION_OPERATIONS`, `TRANSFORM_ALLOWED_OPERATIONS`), AST-лимиты из `TRANSFORM_DEFAULT_LIMITS` и тесты `transform-{evaluator,fuzz,validate}`. Остаются `code-sandbox.ts` и его лимиты.

Здесь же — синхронизация реестра `services/fbp-engine/src/nodes/registry.ts` с каталогом 2.0 (`assertRegistryMatchesCatalog` роняет движок на старте, пока этого нет).

### Этап 5. Аутентификация движка (D4) — СДЕЛАН

Решение от 2026-07-15: **сервисный токен `FBP_SERVICE_TOKEN`, опознаваемый внутри `SessionAuthGuard`**; права — от технического пользователя организации с ролью `administrator`; граница вызовов — витрина `workflow_backend_api_allowlist`, проверяемая **в рантайме**.

#### Что выяснилось при разборе (постановка D4 была неточна)

Постановка описывала D4 как «узел зовёт `backend-api-node:invoke`, а тот требует сессию». Это перестало быть правдой после решения A3:

1. **Узел не зовёт `:invoke`.** `backend-api` резолвит операцию каталога (`getBackendApiOperation`) и дёргает её `method`/`path` напрямую. У `:invoke` (принимает структурную команду §12.6) **боевых потребителей нет вообще** — только тесты (`m3-facades.spec.ts:156`). Значит защита §13.5 «роли из реальной сессии, а не из контекста» и поле `WorkflowNodeContextDto.roles` охраняют эндпоинт, которым никто не пользуется.
2. **Поверхность — весь `/api/v1`.** Раз узел ходит по произвольным маршрутам каталога, сервисный принципал должен опознаваться везде, где висит `SessionAuthGuard` (20 контроллеров), а не на одном маршруте.
3. **Витрина не была границей.** `workflow_backend_api_allowlist` проверялась только валидатором при сохранении схемы. В рантайме её никто не читал, то есть ограничением она не являлась: её обходит любая схема, попавшая в базу мимо валидатора, и любой баг валидатора.
4. **`x-actor-user-id` читается.** Вопреки постановке, заголовок разбирается `getOptionalActorUserId` в 5 контроллерах (16 мест) и попадает в аудит как актор.
5. **Роль `manager` не работала бы.** `WorkflowActionApplierService` требует `administrator` на любое действие кроме `noop`.

#### Что сделано

- **Токен опознаёт, роли разрешают.** `FBP_SERVICE_TOKEN` отвечает только на вопрос «кто ты». Права берутся из `users`/`user_roles` технического пользователя (`users.is_service`, миграция `20260715140000000`), а не из токена. Второго списка прав рядом с сессионным не появляется — расходиться нечему.
- **Гуард один.** Ветка сервисного токена живёт внутри `SessionAuthGuard`: все 20 контроллеров получают одинаковое поведение, `RolesGuard` работает поверх без изменений.
- **Сравнение токена — timing-safe**, оба значения предварительно хешируются (`timingSafeEqual` бросает на разной длине, а длина — тоже утечка). Токен не пишется в логи и не кладётся в `AuthSessionContext.token` (там заглушка).
- **`platform_operator` отбирается принудительно**, даже если роль кому-то привязали: этой ролью схема открыла бы себе в витрине что угодно, то есть сняла бы собственную границу.
- **Витрина стала границей рантайма**: гуард резолвит `method`+`path` в `operation_id` по каталогу (`resolveBackendApiOperation`, генерируется вместе с каталогом) и требует `enabled`. Маршрут вне каталога и операция без строки — запрет (закрыто по умолчанию). Людей это не касается: витрина ограничивает схемы, а не сессии.
- **Организация — только заголовком `x-organization-id`**: «организации по умолчанию» у сервисного принципала нет.
- **Клиент движка предъявляет токен** (`Authorization: Bearer`) и отказывается собираться без него: падение на старте честнее, чем безымянный 401 из чужого сервиса на каждой схеме. Переменная нужна обоим сервисам, значения обязаны совпадать.

#### Проверено (2026-07-15)

Восстановление после утраты незакоммиченной работы: уцелели миграция `20260715140000000` и правки сида, решение целиком — в этом разделе. Заново написаны экспорты `m0-seed-data.ts`, ветка гуарда, `resolveBackendApiOperation`, клиент движка и тесты.

- Юнит-тесты: 12/12 гуарда (из них 10 новых на сервисную ветку), 3 новых на HTTP-клиент движка — он до этого не был покрыт вовсе, а дефект D4 жил именно в нём. Backend 259/259 юнитов, движок 172/172.
- Пробники против живого Postgres и поднятого Backend: миграция и сид проходят, техпользователь заводится с ролью `administrator` и NULL во всех трёх идентификаторах входа. `POST /api/v1/ai/assistant:suggest` **без токена → 401, с токеном → 201** — дефект D4 закрыт. Границы держат: операция не в витрине → 403 `BACKEND_API_OPERATION_FORBIDDEN`, операция без строки → 403, без `x-organization-id` → 401 `SERVICE_ORGANIZATION_REQUIRED`, чужой токен → 401 `SESSION_INVALID` (уходит в сессионную ветку), организация без техпользователя → 401 `SERVICE_PRINCIPAL_MISSING`.

#### Границы и остатки

- Технический пользователь заводится сидом только для демо-организации. Для организаций, созданных в рантайме, его никто не создаёт — вызов вернёт `SERVICE_PRINCIPAL_MISSING`. Провижининг при создании организации — отдельная задача.
- **Ветка «маршрута нет в каталоге» в бою недостижима**: все маршруты под `SessionAuthGuard` лежат под `/api/v1` и попадают в каталог из OpenAPI, а несуществующий путь роутер Nest отвергает 404 раньше гуарда (пробник: `POST /api/v1/ai/llm/completions` → 404, не 403). Ветка остаётся страховкой на случай, когда каталог не перегенерировали после нового маршрута, и на будущий `/api/v2`: и то и другое должно быть закрыто, а не открыто.
- **Техпользователь не имеет ни email, ни Telegram-идентификаторов** (все NULL): ни один человеческий путь аутентификации не должен в него резолвиться — Telegram-вход ищет по `username`/`telegram_id`, регистрация по `email`. Войти под ним можно только сервисным токеном.
- **Аудит пишет `actor_type = 'user'`, а не `'workflow'`.** Прямые вызовы каталога идут через обычные контроллеры, а `AuditService` по умолчанию ставит `'user'` (32 места вызова). Актор при этом опознаётся — это технический пользователь с `is_service = true`, — но тип события не соответствует §22.9.
- `x-actor-user-id` — неаутентифицированный заголовок, попадающий в аудит как актор: его может подделать любой вызывающий. Дефект существовал до этой работы и здесь не чинится.

### Этап 5-bis. Узлы `llm` и `knowledge-base-search` — реальные эндпоинты

Решение владельца от 2026-07-15 по открытому вопросу: узлы должны ходить в **существующие** эндпоинты, а не в выдуманные. Оба узла брали путь из свободного `config.path` с валидацией «начинается с `/api/v1`», а дефолты `/api/v1/ai/llm/completions` и `/api/v1/ai/knowledge-base/search` в OpenAPI отсутствовали — то есть в бою оба давали 404.

#### Дефект, найденный при разборе: RAG-ассистент никогда не доходил до базы знаний

Не относится к Workflow и существовал до этой работы. `services/ai-platform/src/kb-search.ts` (`createBackendKbSearch`) зовёт Backend по `POST /knowledge:search` (контракт C3.kb, `AI_BACKEND_KB_URL` по умолчанию `http://backend:3000`). **Такого маршрута у Backend не было никогда** — `git log -S "knowledge:search" -- services/backend` пуст; Backend поднимал только CRUD документов. Воспроизведение на живом бэкенде: `POST /knowledge:search` → 404, `POST /api/v1/knowledge:search` → 404, `GET /api/v1/knowledge/documents` → 401 (для контраста — существует).

Цепочка: `runPipeline` → `searchKb` → 404 → `KbSearchError` → `catch` в `suggestAssistant` → `buildFallback` → `degraded: true, source_status: "unavailable"`. То есть `assistant:suggest` **всегда** отвечал заглушкой, а документы KB, чьи эмбеддинги Backend исправно писал в `knowledge_chunks`, не читал никто. Отказ тихий: несоответствие ловится и деградирует, а не падает.

#### Что сделано

- **Поиск живёт в Backend, а не в SVC-AI.** У SVC-AI нет ни RPC под поиск по KB, ни под completion — в `c4.ai.proto` только `SuggestAssistant`, `CreateOnboardingCommand`, `Health`. Зато Backend владеет и чанками (`knowledge_chunks`, pgvector под RLS), и моделью эмбеддингов (`KnowledgeEmbeddingService`). Гонять поиск Backend → gRPC → ai-platform → HTTP обратно в Backend за pgvector — петля за данными, которые уже под рукой. Инвариант «модель и размерность у документов и запросов совпадают» (CLAUDE.md) соблюдается по построению: обе стороны — один сервис.
- **Два маршрута поверх одного SQL**: внутренний `POST /knowledge:search` (C3.kb, вход — готовый эмбеддинг SVC-AI, вне префикса `/api/v1`, как `internal/*`) — чинит RAG-ассистента; и `POST /api/v1/knowledge/documents:search` — для узла схемы (вход — текстовые фразы и теги-предфильтр).
- **Контракт C3.kb расщеплён** на `c3-kb-payloads.ts` (без импортов, собирается в CommonJS) и `c3-kb.ts` (JSON-схемы на `node:fs`) — то же разделение и по той же причине, что `c5.ts` / `c5-workflow.ts`. Ответ Backend собирается **общей** функцией контракта: SVC-AI проверяет его по `C3_KB_SEARCH_RESPONSE_SCHEMA`, и расхождение формы не упало бы, а тихо выключило базу знаний — ровно так этот контур и был сломан.
- **Теги заведены в KB** (решение владельца): миграция `20260715160000000`, поле в DTO/сервисе/админке. В эмбеддинге не участвуют — предфильтр до векторного поиска. До этого вход `tags` узла не имел опоры в данных вообще.

#### Ошибки, пойманные пробниками (юнит-тесты их не видели)

- **Пустой список тегов вырождал фильтр.** `d.tags && '{}'` — ложь для любой строки, поэтому поиск **без тегов не находил ничего**. Пустой список обязан означать «фильтр не задан», а не «документы без тегов». Закрыто тестом.
- **Забытое экранирование двоеточия.** `@Post("documents:search")` вместо `@Post("documents\\:search")`: path-to-regexp Express 5 разбирает `:search` как **параметр**, и маршрут начинает отвечать на `/documents<что угодно>` (проверено: `/knowledgeXYZ` → 200 вместо 404). Коварство в том, что **весь прогон остаётся зелёным**: Swagger рендерит `:search` в `{search}`, поэтому Express и OpenAPI согласованно описывают неверный маршрут, и тест «publishes every actual versioned Nest route» расхождения не видит. Добавлен тест `keeps every path parameter a whole segment`: параметр всегда открывает сегмент (`/{id}`, `/{id}:start`), а приклеенный после текста (`/documents{search}`) — это забытое экранирование. Проверено, что тест краснеет на возврате бага.

#### Узел `llm`: расширение контракта C4

У SVC-AI не было RPC под сырой completion: `generate()` у провайдеров — RAG-формы (запрос + чанки → ответ с цитатами), а узлу нужен свободный промпт. Поэтому контракт C4 расширен:

- **`rpc CompleteLlm`** в `proto/ai/c4.ai.proto` + схема ответа `C4.LlmCompletionResponse`. `params` едут строкой `params_json`: значения разнотипны (число, булево, массив стоп-слов), и `map<string, string>` размазал бы приведение типов по обеим сторонам.
- **Способность `complete`** у провайдеров SVC-AI. Реальные провайдеры (openai/azure) получили её через общий `openai-compatible`. Параметры генерации проходят **белый список** (`temperature`, `top_p`, `max_tokens`, `stop`, …): `params` пишет автор схемы, и без фильтра туда можно было бы положить `model` (обойдя выбор модели платформой), `messages` (подменив промпт целиком) или `stream` (сломав разбор ответа).
- **Живёт рядом с RAG-ассистентом**, а не отдельным сервисом: делит выбор провайдера по организации (§12.9), устойчивый фасад (таймаут, предохранитель) и метрики стоимости (§24.4). Отдельный модуль завёл бы второй, неохраняемый путь к тем же провайдерам.
- **`POST /api/v1/ai/llm:complete`** в Backend под `@Roles("administrator")` — узел зовёт его от имени техпользователя схемы; границей служит витрина.
- **Деградация обязательна и размечена**: `degraded` + `fallback_reason` (`unavailable` / `timeout` / `circuit_open` / `invalid_response`). Пустой ответ модели считается отказом, а не ответом: иначе узел продолжил бы исполнение с пустой строкой и ветвление молча ушло бы не туда. Признак `degraded` вынесен в порт узла и в трассу — без него не видно, ветвилась схема по ответу модели или по заглушке.

Ещё одна ошибка, пойманная пробником: счётчики `llm_completion_*` не были заведены в `COUNTER_KEYS`, и `metrics.inc()` ронял вызов с `Unknown AI metric` — gRPC отдавал `code 13`, Backend глотал это охранником деградации и отвечал `degraded: unavailable`. **115 тестов ai-platform этого не видели.** Закрыто тестом на существование счётчиков до первого запроса.

Проверено сквозным пробником Backend → gRPC → ai-platform → провайдер: `degraded: false`, ответ валиден по `C4_AI_LLM_COMPLETION_RESPONSE_SCHEMA`, `ai_platform_llm_completion_total 1`.

### Этап 6. Тест-прогон драфта (D5) — СДЕЛАН

`POST /api/v1/workflows/:workflowId/draft:test` — движок исполняет драфт без записи в `workflow_instances`, принимает `{ node_id, event_payload }`, возвращает трассу по узлам. Закрывает D5: прежний «тестовый прогон» печатал `completed` для каждого узла в порядке массива — без ветвлений и без движка.

#### Что сделано

- **Новый RPC `TestWorkflowDraft`** в `proto/fbp/c5.fbp.proto`, а не флаг у `StartWorkflowInstance`: у прогона нет экземпляра — ни идентификатора, ни записи, ни события смены состояния, — и он возвращает трассу вместо журнала для сохранения. Флаг заставил бы половину полей ответа быть «иногда осмысленными».
- **Ничего не сохраняется**: `testWorkflowDraft` не зовёт `persistStartResult`. Это и позволяет гонять недостроенную схему — журнал исполнения ссылается на `workflow_instances` внешним ключом, а тестового инстанса нет (обходной путь из решения A5).
- **Схема берётся из `workflows.draft_schema`**, субсхемы подставляются те же и тем же способом, что в бою: тест обязан исполнять то же, что исполнит бой, иначе он не тест.
- **Прогон НЕ деградирует** — единственный вызов фасада SVC-FBP с таким поведением. Боевой старт подменяет недоступный движок заглушкой, чтобы сообщения продолжали ходить (§5.4), но заглушка со `status` здесь означала бы «схема работает», хотя её никто не исполнял. Недоступность движка → 503 `WORKFLOW_ENGINE_UNAVAILABLE`.
- **Дедлайн gRPC (29 с) держится ниже таймаута фасада (30 с)**: тогда первым срабатывает дедлайн, движок узнаёт об отмене и прекращает работу, а не жжёт вызовы в Backend после того, как ответ уже никому не нужен. Дефолт фасада в 250 мс обрубал бы любую осмысленную схему.

#### Две дыры, найденные по ходу

- **Трасса терялась при падении.** `runGraph` копил её в локальном массиве и бросал — вызывающий получал ошибку без единого шага исполнения. Именно на падении трасса и нужнее всего. Теперь она прикрепляется к ошибке неперечислимым полем (ошибка сериализуется в журнал, и трасса не должна попадать туда вторым экземпляром) и возвращается из `runWorkflow`. Вложенность разрешается в пользу внешней трассы — на успехе трасса субсхемы тоже не всплывает наверх, и падение не должно возвращать трассу другой формы, чем успех.
- **Невалидный драфт диагностировался как поломка движка.** Драфт сохраняется валидным только по форме графа (решение A10), а движок исполняет лишь полностью валидную схему и на невалидной бросает. Без проверки такой драфт доходил бы до gRPC, возвращался ошибкой, и фасад рапортовал бы «движок недоступен» — то есть врал: движок исправен, это схема не готова. Теперь Backend прогоняет ту же полную проверку контракта, что и promote, и отдаёт 400 `WORKFLOW_SCHEMA_INVALID` с точным списком.

#### Проверено

Сквозной пробник Backend → gRPC → движок на живой базе: драфт с ветвлением, `event_payload = {urgent: true}` → трасса `wait(flow) → pick(data) → check(flow) → hotText(data) → hot(flow)`; `{urgent: false}` → ветка `cold`. То есть исполнение настоящее, с ленивым вычислением pure-узлов. **Экземпляров после двух прогонов — 0.** Падающий узел → HTTP 200, `status: failed`, `node_id: hotText`, трасса `wait → pick → check → hotText✗`. Невалидный драфт → 400 `WORKFLOW_SCHEMA_INVALID`, а не 503.

Тесты: 5 интеграционных на gRPC движка (ветвление на разных нагрузках, отсутствие инстанса, `via: flow|data`, падение с трассой, требование `start_node_id`), 4 на фасад (включая обе причины 503), 2 на трассу при падении в исполнителе.

### Этап 7. Редактор на `@xyflow/react` (R6, D2, D3) — В РАБОТЕ, НЕ ЗАВЕРШЁН

`Handle` на каждый порт с цветом по типу (`portColor` из контракта), `isValidConnection` → `canConnectPorts` подсвечивает недопустимые цели во время перетаскивания, `onConnect` → общая валидация из контракта. Панель свойств: многострочный JS-редактор с подсветкой, редактор строк портов, селектбоксы operator / event_type / operation_id. Автосейв драфта, «Сохранить» = promote, подсветка трассы теста на канве.

#### Сделано

- **D3 закрыт** отдельным коммитом: write-эндпоинты субсхем (`POST`/`PATCH /workflow-subschemas`) — редактор звал их с самого начала, а контроллер имел только `GET`.
- **D2 закрыт**: `createWorkflowConnection` больше не подставляет `out`/`in` — порты обязательны и приходят с холста. Третья копия валидации из `shared/workflow.ts` удалена: он стал тонкой обёрткой над контрактом.
- **Форма графа взята из контракта**: `api/client/types.ts` ре-экспортирует `WorkflowSchema`/`WorkflowNode`/`WorkflowConnection` вместо своей копии. `entry` ушёл, `kind` обязателен. Пока форма была описана дважды, редактор мог собрать граф, который контракт отвергает, — это и был D2.
- **Логика графа — чистые функции** (`presentation/workflow/graph-ops.ts`) вне React: холст только зовёт `connectGraphPorts(graph, connection)` и кладёт результат в состояние. Проверяется без рендера (13 тестов).
- **Подсветка JS — свои ~100 строк** вместо CodeMirror: подсвечивается короткое тело функции, а не файл. Инвариант «склейка токенов побайтно равна исходнику» закрыт тестами (17): слой `<pre>` лежит под прозрачной `<textarea>`, и любой потерянный символ сдвинул бы слои.
- **Перерегистрация хэндлов** (`portSignature` + `useUpdateNodeInternals`): xyflow не замечает смену состава портов, если габариты узла те же (xyflow#394). Без этого переименование порта оставляет связь на старой координате.
- **Замещение вместо отказа**: контракт запрещает второе ребро на занятый data-вход, но перетащить связь туда — это «замени». Старое ребро снимается ДО проверки, и контракт проверяет ровно тот граф, который получится. `isValidConnection` использует ту же функцию — иначе подсветка обещала бы одно, а отпускание давало другое.
- Палитра теперь зависит от вида графа (`getNodePaletteForKind`): раньше плоский список звал добавить `start`/`end` в обычный Workflow, где контракт их отвергает.

#### Регрессия, которую нужно вернуть (спека снята с прогона)

Переписанная страница покрывает только редактирование графа и тест-прогон. Из неё **выпали четыре работавшие возможности**, у каждой был зелёный тест в `apps/saas-admin/test/m3-workflow.test.tsx` — спека целиком помечена `describe.skip` с обоснованием:

1. импорт/экспорт схемы JSON с diff-подтверждением;
2. диалог создания субсхемы и переход к её редактированию;
3. включение/отключение Workflow и выбор версии по умолчанию;
4. диагностика инстанса из истории исполнения.

Это не отказ от них — они обязаны вернуться вместе с тестами, переснятыми на новую разметку. Скип громкий намеренно: иначе регрессия влилась бы незамеченной.

#### Найдено и починено по ходу стабилизации
