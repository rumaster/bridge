# Шестая серия промптов для параллельного выполнения этапа M5

Документ отвечает на issue #150: анализирует план, фиксирует порядок выполнения и
даёт шестую серию промптов для параллельного прохождения шестого этапа. Он
продолжает первую серию
[`parallel-stage-1-prompts.md`](./parallel-stage-1-prompts.md) (этап M0), вторую
серию [`parallel-stage-2-prompts.md`](./parallel-stage-2-prompts.md) (этап M1),
третью серию [`parallel-stage-3-prompts.md`](./parallel-stage-3-prompts.md)
(этап M2), четвёртую серию
[`parallel-stage-4-prompts.md`](./parallel-stage-4-prompts.md) (этап M3) и пятую
серию [`parallel-stage-5-prompts.md`](./parallel-stage-5-prompts.md) (этап M4).

Под «шестым этапом» здесь понимается **M5 — Стабилизация и приёмка** из
[`docs/plan/README.md`](./README.md): платформа не наращивает функциональность, а
доводится до **приёмочной готовности** — полный набор e2e (ТЗ §26.6) держится
зелёным как регрессия, проверяются **нагрузка и деградация** (ТЗ §25.11, §25.2,
§25.3), **безопасность** (ТЗ §23), **RPO/RTO** и резервное копирование/восстановление
(ТЗ §25.11, §22.11), завершается **документация** (ТЗ §28), а сборка проходит
**критерии приёмки** (ТЗ §29). Этап замыкается на **единственной** точке
согласования — **CP-9** («полный набор сценариев ТЗ §26.6, приёмка §29»,
участники — **все** сервисы, замораживаются **все** контракты v1 как финально
принятые, добавляются полный e2e-набор, регрессия и нагрузочные пробники,
мастер § 6). M5 опирается на результаты M4: контракты **C8/C9/C10** заморожены на
CP-6/CP-7/CP-8 (см. gate M4-99 и `packages/contracts/cp6-cp7-freeze.v1.json`),
`broadcast_*`, `edge_message_buffer`, `notifications` и `outbox_events` готовы как
стабильная база, поэтому команды продолжают работать независимо над своей частью
стабилизации и сходятся только на CP-9.

# 1. Итоговая последовательность выполнения

## 1.1 Общая последовательность вех

1. **M0 — Контракты и каркас.** *(выполнено первой серией.)* Структура репозитория,
   CI-скелет, контракты v1, моки и базовые приложения/сервисы.
2. **M1 — Вертикальный срез «приём и ответ».** *(выполнено второй серией.)* Web Chat
   → Core → Manager Workspace → ответ клиенту; точка согласования **CP-1**.
3. **M2 — Омниканальность + realtime + AI Assistant.** *(выполнено третьей серией.)*
   Внешние адаптеры, WebSocket realtime, AI Assistant из Knowledge Base; **CP-2**,
   **CP-3**.
4. **M3 — Программируемость.** *(выполнено четвёртой серией.)* Форк FBP Engine, узел
   Backend API, безопасный Transform Node, визуальный редактор Workflow, AI
   Onboarding; **CP-4**, **CP-5**.
5. **M4 — Массовые коммуникации + Edge/ПДн.** *(выполнено пятой серией.)* Broadcast
   через ядро, RF Edge + VPN Tunnel + буфер/порядок/дедуп, Notification в Web и
   Telegram Console, Mobile API, сквозная идемпотентность и egress; **CP-6**,
   **CP-7**, **CP-8**.
6. **M5 — Стабилизация и приёмка.** *(текущий этап.)* Полный e2e-набор § 26.6 как
   регрессия, нагрузка/деградация, безопасность §23, RPO/RTO и backup/restore,
   независимое версионирование API, доступность фронтендов, документация §28 и
   приёмочные критерии §29; **CP-9**.

Критический путь шестого этапа (§ 10.1 мастер-плана: M5 не вводит новых контрактов,
а доводит всё до приёмки; единственная жёсткая зависимость — операционные
возможности БД для проб RPO/RTO и обезличивания):

```text
M4 contracts C8/C9/C10 (CP-6/CP-7/CP-8) + broadcast_*/edge_buffer/notifications/outbox заморожены
  -> SVC-DATA M5 (backup/restore + PITR, историчность configuration_history,
     обезличивание ПДн при целостном append-only аудите, проба RPO/RTO по классам данных)
  -> параллельная стабилизация всех сервисов (нагрузка, деградация, безопасность,
     доступность, версионирование) против ЗАМОРОЖЕННЫХ контрактов v1 — без новых фич
  -> M5-99 gate CP-9: полный e2e-набор § 26.6 зелёный (регрессия) + нагрузочные
     пробники + security review §23 + проба RPO/RTO + документация §28 + приёмка §29
     -> финальная заморозка всех контрактов v1 (cp9-freeze.v1.json)
```

## 1.2 Внутренний порядок M5

M5 лучше выполнять в три шага:

1. **M5-01, рекомендуемый ранний предшественник (не жёсткий блокер фич).** SVC-DATA
   даёт операционные возможности данных (§ 5.6 плана SVC-DATA): регламент и проверку
   **резервного копирования/восстановления** (PITR), целостность **историчности**
   (`configuration_history`, ТЗ §22.10), процедуру **обезличивания** ПДн (ТЗ §22.11)
   при сохранении суррогатных ссылок и **append-only** аудита, а также пробу
   **RPO/RTO** по классам данных (ТЗ §25.11). Без этих возможностей не проходят
   приёмочные проверки целостности/восстановления в gate CP-9, поэтому SVC-DATA
   стоит запускать первым. При этом остальные сервисы **не блокируются**: их
   нагрузочная/деградационная/безопасностная стабилизация идёт против уже
   замороженной схемы M4 и не ждёт M5-01.
2. **Параллельная стабилизация всех сервисов.** Каждая команда выполняет объём M5
   своего сервиса **против замороженных контрактов v1** (новые фичи запрещены):
   нагрузочные пробники по ориентирам ТЗ §25.11/§25.2/§25.3, предсказуемая
   **деградация** при отказах смежников (ТЗ §5.4, §11.2), **харденинг безопасности**
   (ТЗ §23), доступность/производительность фронтендов (ТЗ §21.7, §21.8),
   независимое версионирование API (ТЗ §11.14, §19.6) и прогон приёмочных сценариев
   (ТЗ §29). Работы делятся на три слабо связанных пула (§ 5): ядро/данные,
   вынесенные сервисы (деградация/устойчивость) и фронтенды/клиенты (приёмка).
3. **Интеграционный gate M5-99 (CP-9).** После слияния прогоняется **весь** набор
   § 26.6 как регрессия, нагрузочные пробники, security review (§23), проба
   RPO/RTO, проверяется полнота OpenAPI и версионирование, завершается документация
   (§28) и фиксируется соответствие критериям приёмки (§29). Все контракты v1
   финально замораживаются (`cp9-freeze.v1.json`).

## 1.3 Сервисы M5 (задачи есть у всех)

В отличие от M4 (замыкался на CP-6/CP-7/CP-8 и оставлял SVC-AI без задач), веха
**M5** по матрице мастер-плана (§ 5.1, столбец **M5**) даёт объём **всем
пятнадцати** сервисам: **SVC-DATA (01)**, **SVC-CORE (02)**, **SVC-IDN (03)**,
**SVC-API (04)**, **SVC-INT (05)**, **SVC-CHAT (06)**, **SVC-MWS (07)**,
**SVC-ADMIN (08)**, **SVC-AI (09)** *(на M5 снова активен — харденинг: изоляция,
мониторинг, деградация)*, **SVC-FBP (10)**, **SVC-BCAST (11)**, **SVC-NOTIF (12)**,
**SVC-EDGE (13)**, **SVC-MOB (14)** и **SVC-TGC (15)**. Нумерация задач сохраняет
**сквозное соответствие сервису из первой серии** (01 = SVC-DATA, 02 = SVC-CORE,
03 = SVC-IDN, 04 = SVC-API, 05 = SVC-INT, 06 = SVC-CHAT, 07 = SVC-MWS,
08 = SVC-ADMIN, 09 = SVC-AI, 10 = SVC-FBP, 11 = SVC-BCAST, 12 = SVC-NOTIF,
13 = SVC-EDGE, 14 = SVC-MOB, 15 = SVC-TGC).

> **Замечание о разметке разделов M5 в планах сервисов (для сопровождающих).** В
> планах SVC-DATA (01), SVC-INT (05) и SVC-CHAT (13) этап M5 размечен подзаголовком
> вида **«### 5.6 M5 …»**, а в остальных планах — коротким **«### M5 …»**. Оба
> варианта относятся к одной вехе M5 мастер-плана (§ 5). Формулировки промптов ниже
> ссылаются на соответствующий раздел каждого плана. Расхождение косметическое; при
> желании его стоит унифицировать в отдельном PR по документации.

## 1.4 О контрактах на M5: заморозка без новых версий

M5 **не вводит новых контрактов** и **не выпускает новых версий** уже
замороженных: C1/C2/C3/C7 приняты на CP-1, C2/C6/C4 — на CP-2/CP-3, C3/C4/C5 — на
CP-4/CP-5, C8 — на CP-6, C9 — на CP-7, C10 (+ `notification.created`) — на CP-8.
Задача M5 в части контрактов — **финальная приёмка v1**: полнота **OpenAPI**
(генерируется из кода и является частью поставки, ТЗ §11.14), контроль версии API
(`/api/v1`, ломающие изменения — только новой версией, ТЗ §11.8), **независимое**
версионирование Mobile API (ТЗ §19.6) и подтверждение отсутствия дрейфа
контрактов на полном contract-наборе. Итог фиксируется машинно-читаемым артефактом
`packages/contracts/cp9-freeze.v1.json` (по образцу `cp1-freeze.v1.json`,
`cp2-cp3-freeze.v1.json`, `cp4-cp5-freeze.v1.json`, `cp6-cp7-freeze.v1.json`),
помечающим все контракты как `released_v1` / `accepted`.

# 2. Правила для исполнителей шестой серии

- Каждый исполнитель берёт **ровно один** промпт из раздела 4.
- Формулировка задачи должна звучать как: «Выполнить этап **M5** плана
  `docs/plan/services/XX-...md`».
- Реализуется **только** объём M5 своего сервиса — **стабилизация**, а не новые
  фичи. Запрещено добавлять функциональность сверх того, что нужно для приёмки:
  никаких новых эндпоинтов, новых версий контрактов, новых каналов, новых узлов
  Workflow и т. п. Разрешены: нагрузочные/деградационные пробники, харденинг
  безопасности, доступность/производительность, версионирование, документация,
  тесты приёмки.
- Все работы идут **против замороженных контрактов v1** (§ 1.4). Любая
  обнаруженная несовместимость или недоопределённость контракта фиксируется как
  **blocker** с минимальным патчем и выносится в gate M5-99, а не «чинится» в обход
  версионирования.
- Бэкенд-модули ядра (CORE, API, IDN) для integration-тестов используют **реальную
  схему** SVC-DATA; вынесенные сервисы и фронтенды деградационные сценарии проверяют
  против **моков** смежников (падающий внешний API, недоступный AI/Backend/канал,
  разрыв Edge). Нагрузочные пробники — по ориентирам ТЗ §25.11/§25.2/§25.3, без
  требования промышленного стенда: достаточно воспроизводимого пробника и фиксации
  измерений.
- Соблюдаются сквозные инварианты приёмки: **изоляция арендаторов** по
  `organization_id` (RLS, ТЗ §22.6) — регрессия по всем ресурсам; **деградируемость**
  (отказ вынесенного сервиса/канала не роняет ядро, ТЗ §5.4, §11.2); **сквозной
  `idempotency_key = message_id`** и восстановление порядка по `sequence_number`
  (ТЗ §11.12, §7.10) — под нагрузкой и при сбоях; **append-only аудит** и его защита
  от изменения (ТЗ §23.8); **RF-first** размещение ПДн (ТЗ §7.14); авторитетная
  авторизация на Backend (RBAC, ТЗ §9.8).
- Код сервиса — только в его директорию (мастер § 3); контрактные артефакты и
  freeze — в `packages/contracts`; e2e/нагрузочные/визуальные сценарии — в `tests/`
  и/или сервисной test-директории; регламенты/документация — в `docs/`.
- Для каждого промпта результатом должны быть код/конфигурация/документация, тесты
  (unit + integration, а для приёмки — contract + e2e/регрессия + нагрузочная проба)
  и короткий отчёт: что сделано, какие команды проверки запущены, какие измерения
  NFR получены, какие контракты затронуты (в идеале — «не затронуты, только
  верификация»).

# 3. Критерии готовности M5

M5 считается завершённой, когда:

- **SVC-DATA** дал регламент и проверку **backup/restore** (PITR), подтвердил
  целостность **историчности** (`configuration_history` не рвётся при удалении
  конфигурации, ТЗ §22.10), реализовал **обезличивание** ПДн (необратимое стирание
  идентифицирующих данных при сохранении суррогатных ссылок, структуры истории и
  append-only аудита, ТЗ §22.11) и подтвердил **RPO/RTO** по классам данных
  (RPO≈0 для истории/ПДн/конфигурации, RPO=0 для аудита; RTO — минуты–часы, ТЗ §25.11);
- **SVC-CORE** прошёл **нагрузку/деградацию**: нагрузочные пробники приёма/маршрутизации
  (ориентиры ТЗ §25.11), предсказуемое поведение при **отказах адаптеров** (таймауты,
  ретраи, `status=failed`, без блокировки ядра), масштабирование нескольких экземпляров
  на единой модели данных (ТЗ §8.11), деградация при недоступном AI (ТЗ §8.7);
- **SVC-IDN** стабилизирован: выделены **точки расширения резервного email-входа**
  без его реализации (pluggable auth provider; `login_codes.purpose`/
  `invitations.contact_type` поддерживают `email`; ТЗ §9.6), реализованы **UX/операции
  отзыва сессий** (список активных, массовый отзыв, самоотзыв, ТЗ §16.4), выполнен
  **харденинг** (лимиты/локаут перебора, ротация секретов бота через менеджер
  секретов ТЗ §23.7, защита аудита от изменения);
- **SVC-API** обеспечил **полноту OpenAPI** (каждый эндпоинт задокументирован,
  спецификация соответствует фактическому API, ТЗ §11.14), **контроль версии API**
  (`/api/v1`, регламент ломающих изменений, мастер §7.4/§9.3) и **нагрузочную
  проверку NFR** по ориентирам ТЗ §25.2 (списки диалогов ≤ 1 с, история ≤ 2 с,
  отправка ≤ 1 с, ответ AI без LLM ≤ 500 мс и т. д.);
- **SVC-INT** подтвердил **отказоустойчивость всех каналов** и корректную
  **деградацию** при недоступности внешнего API (ядро не блокируется, недоставленное
  — в очередь/повтор), таймауты, bulkhead и circuit breaker на «падающий» канал (ТЗ
  §11.2);
- **SVC-CHAT** прошёл приёмку виджета: **доступность** (клавиатурная навигация,
  ARIA-роли, контраст, работа во встраивающем окружении), **устойчивость соединения**
  (частые reconnect и длительный разрыв → буфер Edge без потерь/дублей и с сохранением
  порядка), производительность виджета (ленивая загрузка, размер бандла, ТЗ §21.7);
- **SVC-MWS** подтвердил **производительность** рабочего места (списки ≤ 1 с, история
  ≤ 2 с, отправка ≤ 1 с, ТЗ §25.2; виртуализация длинных историй), полировку UX,
  адаптивность Desktop/Tablet (ТЗ §21.8) и доступность; приёмочные сценарии зелёные;
- **SVC-ADMIN** прошёл **приёмку** админ-сценариев, **доступность** и адаптивность,
  визуальную регрессию ключевых экранов, полировку состояний ошибок/загрузки и
  оптимизацию размеров сборки (ТЗ §21.7);
- **SVC-AI** захарденен: **изоляция арендаторов** в промптах и KB-поиске (нет утечки
  чужих документов/контекста, ТЗ §22.6), **мониторинг** качества/стоимости
  (метрики задержек, стоимости LLM, доли деградаций, health/metrics, ТЗ §24.4) и
  **graceful degradation** при недоступности LLM (ответ-заглушка, платформа
  работает без AI, ТЗ §5.4, §25.4);
- **SVC-FBP** прошёл **нагрузку/масштабирование** исполнителей и **фаззинг выражений**
  Transform Node (попытки выхода из «песочницы»/доступа к процессу/среде/сети/ФС/
  секретам/времени/ГСЧ отвергаются, ТЗ §13.4), подтвердил **полноту журнала**
  исполнения и метрик Workflow (ТЗ §13.9, §24.6);
- **SVC-BCAST** подтвердил **нагрузку** на крупные кампании (батчинг/rate limiting
  держат лимиты каналов), **устойчивость** к отказам адаптеров и **отсутствие
  дублей** при массовой доставке (согласованно со сквозным `idempotency_key`,
  корректная статистика при частичных сбоях);
- **SVC-NOTIF** дал **тонкие настройки** (гранулярность категория × канал, ТЗ §15.6),
  **устойчивость доставки** при недоступности канала (доставка через доступные,
  ретраи, деградация) и гарантированную доставку **приоритетных** уведомлений
  (`critical`/`admin`, ТЗ §15.5, §20.3);
- **SVC-EDGE** подтвердил **отказоустойчивость Edge** (при кратковременной потере
  связи — приём и буферизация, авто-синхронизация после восстановления; отказ одного
  Edge не роняет платформу, ТЗ §7.12), целевые **RPO/RTO** буфера (ТЗ §25.11) и
  **нагрузку на WS** (пиковый поток соединений/событий);
- **SVC-MOB** подтвердил **независимое версионирование** (старые клиенты не сломаны,
  ТЗ §19.6), целевую **производительность** агрегированных вызовов (ТЗ §25.2) и
  **устойчивость синхронизации** (повторные/частичные sync, восстановление после

# 5. Что запускать первым

Минимальный практичный запуск M5:

1. Выполнить **M5-01** (SVC-DATA) — ранний предшественник приёмки: без backup/restore,
   обезличивания, целостной историчности и пробы RPO/RTO не проходят приёмочные

   стартуют параллельно против замороженной схемы M4.
2. Параллельно запустить **три слабо связанных пула** стабилизации (все — против
   замороженных контрактов v1, без новых фич):
   - **Ядро и данные (нагрузка/NFR/версионирование):** **M5-02** (CORE:
     нагрузка/деградация/масштабирование), **M5-04** (API: полнота OpenAPI +
     версия + NFR §25.2), **M5-03** (IDN: точки расширения email-входа + отзыв
     сессий + харденинг). Идут против **реальной схемы** SVC-DATA.
   - **Вынесенные сервисы (деградация/устойчивость/безопасность):** **M5-05**
     (INT: отказоустойчивость каналов), **M5-09** (AI: изоляция + мониторинг +
     деградация), **M5-10** (FBP: нагрузка + фаззинг Transform Node), **M5-11**
     (BCAST: нагрузка крупных кампаний), **M5-12** (NOTIF: тонкие настройки +
     приоритеты), **M5-13** (EDGE: отказоустойчивость + RPO/RTO + нагрузка WS).
     Деградационные сценарии — против **моков** падающих смежников.
   - **Фронтенды и клиенты (приёмка/производительность/доступность):** **M5-06**
     (CHAT: доступность + устойчивость соединения), **M5-07** (MWS:
     производительность + полировка), **M5-08** (ADMIN: приёмка + доступность),
     **M5-14** (MOB: независимое версионирование + sync), **M5-15** (TGC:
     ограничения Telegram + безопасность привязки). Идут против **моков** контрактов
     до сборки живых срезов регрессии.
3. В отличие от M4, на M5 **нет сервисов без задач** — активны все пятнадцать,
