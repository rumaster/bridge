# Содержание

# 1. Общие сведения

## 1.1 Назначение документа

Настоящее техническое задание определяет требования к разработке SaaS B2B платформы MessengerBridge — сервиса для организации надёжной и бесперебойной омниканальной связи между зарубежными бизнесами и их клиентами, в первую очередь находящимися в Российской Федерации и других странах с ограничениями на использование мессенджеров.

## 1.2 Контекст и проблематика

С 2024–2026 годов в России введены блокировки и ограничения на ряд популярных мессенджеров (WhatsApp признан экстремистским, Telegram замедлен, Signal заблокирован). Зарубежные бизнесы, работающие с клиентами в РФ, теряют каналы коммуникации. Существующие решения (Wazzup, Teletype и др.) закрывают часть проблемы, но не обеспечивают полной независимости от блокировок и не предоставляют собственного защищённого канала связи.

MessengerBridge решает эту проблему через создание независимого защищённого канала (веб/мобильное приложение с VPN-туннелем) в сочетании с поддержкой всех доступных мессенджеров и умным каскадным переключением между ними.

## 1.3 Целевая аудитория продукта

Покупатель (B2B клиент платформы):

• Малый и средний зарубежный бизнес

• Имеет клиентов в РФ и других странах с ограничениями на мессенджеры

• Нуждается в надёжном, юридически чистом канале коммуникации

• Команда от 1 до 50+ менеджеров по работе с клиентами

Конечный пользователь платформы:

• Менеджер по работе с клиентами — основной пользователь интерфейса

• Администратор аккаунта — настраивает каналы, команду, ИИ-бота

• Клиент бизнеса — общается через привычный ему мессенджер или через приложение

# 2. Цели и задачи

## 2.1 Цели продукта

1. Обеспечить бесперебойную связь зарубежного бизнеса с клиентами в РФ вне зависимости от блокировок мессенджеров.

2. Предоставить единый интерфейс управления всеми каналами коммуникации.

3. Автоматизировать обработку входящих обращений с помощью ИИ-ассистента.

4. Обеспечить соответствие требованиям 152-ФЗ для защиты персональных данных клиентов.

5. Создать масштабируемый SaaS с простым онбордингом и тарифной моделью.

# 3. Функциональные требования

## 3.1 Каналы коммуникации

Платформа поддерживает следующие каналы связи с клиентами:

| Канал | Приоритет | Статус на старте | Примечания |
|---|---|---|---|
| MAX (Mail.ru) | Высокий | MVP | Основной канал для РФ, данные в РФ, 152-ФЗ OK |
| VK Мессенджер | Высокий | MVP | Российская юрисдикция, локализация OK |
| Telegram | Высокий | MVP | Требует оформления трансграничной передачи |
| WhatsApp | Средний | MVP | США юрисдикция, требует согласия клиента |
| Email | Средний | MVP | Универсальный резервный канал |
| SMS | Средний | MVP | Только короткие сообщения, без вложений |
| Веб-чат (собственный) | Высокий | MVP | Независимый канал, работает через VPN-туннель |
| Мобильное приложение | Высокий | v1.1 | iOS + Android, работает через VPN-туннель |

## 3.2 Умный каскад каналов

Система автоматически выбирает оптимальный канал для отправки сообщения по следующей логике:

• При входящем сообщении от клиента фиксируется активный канал (last_active_channel)

• При ответе менеджера система по умолчанию использует last_active_channel

• Менеджер может вручную выбрать любой доступный канал из профиля клиента

• При недоступности канала система автоматически переключается на следующий по приоритету

• Длинные сообщения (>160 символов) автоматически блокируются для отправки по SMS

• Вложения (файлы, изображения) не отправляются по SMS и Email (только ссылка)

Приоритет каскада настраивается администратором аккаунта для каждого бизнес-клиента отдельно.

## 3.3 Собственный защищённый канал (Веб/Мобильное приложение)

Независимый от внешних мессенджеров канал связи, устойчивый к блокировкам:

• Веб-чат доступен по ссылке или встраивается на сайт клиента через виджет

• Мобильное приложение для iOS и Android

• Трафик проходит через VPN-туннель с серверов в РФ, что обеспечивает доступность при блокировках

• Сквозное шифрование сообщений

• Поддержка push-уведомлений в мобильном приложении

• Клиент не устанавливает никаких дополнительных приложений для веб-чата

## 3.4 Единый интерфейс менеджера

### 3.4.1 Веб-интерфейс

• Единая лента всех входящих диалогов из всех каналов

• Фильтрация и поиск по клиентам, каналам, тегам, статусам

• Профиль клиента: все каналы, история переписки, теги, заметки

• Индикация канала для каждого сообщения (иконка мессенджера)

• Шаблоны сообщений с поддержкой переменных (имя клиента, номер заказа и т.д.)

• Статусы диалога: новый / в работе / ожидает клиента / закрыт

• Отображение онлайн-статуса менеджеров

### 3.4.2 Telegram-пульт

• Бот уведомляет менеджера о новом сообщении с указанием клиента и канала

• Менеджер отвечает реплаем (reply) на уведомление — ответ уходит клиенту в его канал

• Команды бота: /take (взять диалог), /close (закрыть диалог), /info (инфо о клиенте)

• Уведомления о новых диалогах видят все менеджеры, первый взявший получает диалог

• Ограниченный функционал по сравнению с веб-интерфейсом — для оперативных ответов

## 3.5 Управление диалогами и командой

• Новый входящий диалог виден всем менеджерам аккаунта

• Первый менеджер, нажавший «Взять», получает диалог в работу

• Каждый менеджер видит только свои активные диалоги

• История переписки с клиентом доступна менеджеру при взятии диалога

• Администратор видит все диалоги всех менеджеров

• В будущих версиях: гибкая настройка прав доступа к диалогам

## 3.6 ИИ-ассистент

### 3.6.1 Автоответчик

• Автоматически отвечает на входящие сообщения когда менеджеры не в сети

• Использует базу знаний компании (RAG) для формирования ответов

• Имеет доступ к профилю клиента (имя, история заказов, предыдущие обращения)

• При невозможности ответить — эскалирует менеджеру с уведомлением

• Администратор настраивает расписание работы ИИ (рабочие часы, выходные)

### 3.6.2 База знаний

• Текстовый редактор для ввода документов экспертизы

• Поддержка ключевых фраз для RAG-поиска

• Организация по разделам (FAQ, прайс-лист, политики, инструкции)

• Версионирование — история изменений базы знаний

• В будущих версиях: загрузка PDF/Word документов, подключение сайта

## 3.7 Рассылки

• Создание рассылки по сегменту клиентов (все / по тегу / по каналу)

• Выбор канала отправки или авто (по last_active_channel каждого клиента)

• Поддержка шаблонов с переменными

• Планирование времени отправки

• Статистика рассылки: доставлено / прочитано / ошиблись

• Ограничения: рассылки по SMS только для коротких сообщений

## 3.8 Онбординг и сопровождение

• Встроенный ИИ-ассистент онбординга в веб-интерфейсе

• Бот ведёт диалог с новым клиентом и самостоятельно выполняет настройку аккаунта

• Пошаговое подключение каналов в режиме диалога

• Интерактивные подсказки и туториалы в интерфейсе

• Бот остаётся доступен для дальнейшего сопровождения и вопросов

• База знаний онбординг-бота обновляется командой платформы

# 4. Архитектура системы

## 4.1 Общая архитектура

Платформа построена по микросервисной архитектуре с разделением на два географических кластера:

| Компонент | Расположение | Назначение |
|---|---|---|
| Primary Server Cluster | За рубежом | Основная логика, AI-сервисы, веб-интерфейс, управление |
| Russian Edge Node | РФ (Selectel / Timeweb) | Первичный сбор ПД, VPN-туннель, проксирование трафика |
| Primary Database | За рубежом | Основная БД (PostgreSQL), мультитенантность по tenant_id |
| Russian Primary DB | РФ | Первичная запись ПД граждан РФ (152-ФЗ) |
| Cache Layer | За рубежом | Redis — сессии, каскад, очереди |
| Message Queue | За рубежом | RabbitMQ / Kafka — асинхронная обработка сообщений |

## 4.2 Ключевые сервисы

• API Gateway — приём вебхуков от всех мессенджеров, нормализация в единый формат

• Router Service — определение клиента, выбор канала, управление каскадом

• Notification Service — уведомления менеджеров (Telegram-пульт, браузерные пуши)

• AI Service — RAG-поиск по базе знаний, генерация ответов, онбординг-бот

• Broadcast Service — управление рассылками и очередями отправки

• Auth Service — аутентификация, управление tenant'ами и ролями

• VPN Tunnel Service — управление защищёнными каналами через РФ-узел

## 4.3 Мультитенантность

• Единая БД с разделением всех данных по tenant_id

• Полная изоляция данных между аккаунтами на уровне запросов

• Отдельные API-ключи и webhook-эндпоинты для каждого tenant

• Логирование всех действий с привязкой к tenant_id

## 4.4 Идентификация клиентов

Связывание аккаунтов клиента в разных мессенджерах:

• Основной ключ — номер телефона (MAX, VK, WhatsApp отдают при вебхуке)

• Магическая ссылка — для Telegram (токен живёт 15 минут, хранится в Redis)

• Единая таблица clients: phone, max_chat_id, tg_id, vk_user_id, last_active_channel

• При каждом входящем сообщении обновляется last_active_channel

• Автоматический перезапуск сервисов при сбое

• Stateless-архитектура основных сервисов

• Автоскейлинг при росте нагрузки

# 6. Соответствие требованиям 152-ФЗ

## 6.1 Локализация персональных данных

В соответствии с ч. 5 ст. 18 Федерального закона № 152-ФЗ (в редакции с 1 июля 2025 года):

• Первичная запись персональных данных граждан РФ производится исключительно в базе данных, физически расположенной на территории РФ

• Российский узел платформы размещается у сертифицированного провайдера (Selectel, Timeweb или Yandex Cloud)

• Трансграничная передача данных (на зарубежный сервер) осуществляется как вторичная операция после первичной записи в РФ

• Адрес российской базы данных указывается в уведомлении Роскомнадзора

## 6.2 Обязательства платформы

• Регистрация в реестре операторов персональных данных РКН

• Публичная Политика конфиденциальности с описанием всех каналов и целей обработки

• Отдельное согласие на обработку персональных данных (не вшитое в договор)

• Уведомление РКН о трансграничной передаче данных

• Уведомление РКН об утечках в течение 24 часов

## 6.3 Обязательства клиентов платформы

Каждый бизнес-клиент при регистрации принимает условия использования, по которым обязуется:

• Получать согласие своих клиентов на обработку персональных данных

• Не передавать через платформу данные, не предусмотренные заявленными целями

• Соблюдать законодательство страны своей регистрации и страны нахождения клиентов

Платформа выступает оператором ПД в отношении данных своих бизнес-клиентов и обработчиком ПД в отношении данных конечных клиентов бизнеса. Ответственность разграничивается в договоре-оферте.

# 8. Тарифная модель

## 8.1 Принцип тарификации

Фиксированная ежемесячная подписка. Основной параметр тарификации — количество менеджеров в аккаунте. Все тарифы включают полный набор каналов и функций платформы.

## 8.2 Тарифные планы

| Тариф | Менеджеры | Особенности |
|---|---|---|
| Старт | 1–3 | Все каналы, ИИ-бот, рассылки, базовая БЗ |
| Бизнес | 4–10 | Всё из Старт + расширенная аналитика + приоритетная поддержка |
| Про | 11–30 | Всё из Бизнес + API-доступ + расширенная БЗ |
| Энтерпрайз | 31+ | Индивидуальные условия, SLA, выделенный менеджер |

Конкретные цены определяются на этапе маркетингового исследования. Предусмотрен 14-дневный бесплатный пробный период для всех тарифов.
