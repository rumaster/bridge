# 1. Введение

## 1.1 Назначение документа

Настоящий документ определяет функциональные, архитектурные и нефункциональные требования к платформе **Communication Platform with Programmable Automation and AI**.

Документ предназначен для использования:

- архитекторами;
- Backend-разработчиками;
- Frontend-разработчиками;
- разработчиками AI;
- разработчиками баз данных;
- DevOps-инженерами;
- QA-инженерами;
- техническими руководителями проекта.

Документ является основным источником требований при разработке платформы.

---

## 1.2 Область применения

Communication Platform предназначена для организации омниканальной коммуникации между организациями и их клиентами.

Платформа обеспечивает единый механизм взаимодействия независимо от используемого канала связи.

Поддерживаемые каналы включают:

- Telegram;
- MAX;
- VK;
- WhatsApp Business;
- Web Chat;
- Mobile Application;
- Email;
- SMS.

Архитектура платформы предусматривает возможность подключения дополнительных каналов без изменения существующих компонентов.

---

## 1.3 Основная задача платформы

Основной задачей платформы является обеспечение надёжной доставки сообщений между организацией и её клиентами.

Все остальные функции платформы рассматриваются как вспомогательные.

В частности:

- AI повышает удобство использования;
- Broadcast автоматизирует массовые коммуникации;
- Notification информирует пользователей платформы;
- FBP Engine обеспечивает программируемую автоматизацию.

Ни одна из перечисленных функций не должна влиять на возможность обмена сообщениями при своей недоступности.

---

# 2. Назначение платформы

Communication Platform представляет собой единую SaaS-платформу, предназначенную для построения современных коммуникационных сервисов.

Платформа предоставляет организациям единый интерфейс для работы с клиентами независимо от используемых клиентами каналов связи.

Организация взаимодействует с платформой посредством:

- административной панели;
- рабочего места менеджера;
- Telegram Console;
- Backend API.

Клиенты взаимодействуют посредством:

- Web Chat;
- мобильного приложения;
- Telegram;
- MAX;
- VK;
- WhatsApp;
- Email;
- SMS.

Все каналы коммуникации рассматриваются как транспорт доставки сообщений.

Особенности конкретных каналов полностью инкапсулируются внутри Integration Platform.

---

# 3. Цели проекта

Платформа создаётся для решения следующих задач.

## 3.1 Единая коммуникационная среда

Все сообщения независимо от канала должны обрабатываться единым Communication Core.

---

## 3.2 Омниканальность

Клиент может использовать различные каналы связи.

Менеджер работает с единой историей коммуникаций.

---

## 3.3 Независимость от поставщиков

Особенности Telegram, WhatsApp, VK, MAX и других платформ не должны влиять на архитектуру Communication Platform.

Изменения API внешних сервисов должны локализоваться исключительно внутри соответствующих Adapter.

---

## 3.4 Программируемая автоматизация

Платформа должна обеспечивать возможность изменения поведения без изменения исходного кода.

Для этого используется FBP Engine.

---

## 3.5 Использование искусственного интеллекта

AI используется исключительно как вспомогательная подсистема.

В платформе используются два независимых направления применения AI.

### AI Assistant

Используется при общении клиентов с организацией.

Основные функции:

- ответы на вопросы;
- использование базы знаний;
- генерация ответов менеджеру;
- поиск информации;
- перевод сообщений.

---

### AI Onboarding

Используется администраторами организаций.

Основные функции:

- первоначальная настройка платформы;
- помощь при подключении каналов;
- настройка автоматизации;
- изменение параметров организации;
- применение изменений посредством Backend API.

AI Onboarding не взаимодействует с клиентами организации.

---

## 3.6 Соответствие требованиям законодательства

Архитектура платформы должна обеспечивать возможность выполнения требований законодательства Российской Федерации посредством использования Edge Cluster.

Архитектура должна оставаться единой независимо от региона размещения компонентов.

# 4. Термины и определения

Настоящий раздел определяет терминологию, используемую во всех последующих разделах документа.

Все участники проекта должны использовать данные определения при проектировании, разработке, тестировании и сопровождении платформы.

При возникновении неоднозначностей определения настоящего раздела имеют приоритет.

---

## 4.1 Platform

**Communication Platform** — единая программная платформа, обеспечивающая коммуникацию между организациями и их клиентами посредством различных каналов связи.

Платформа включает серверные компоненты, пользовательские интерфейсы, интеграционные сервисы, AI-подсистемы и программируемую автоматизацию.

---

## 4.2 Tenant

Tenant — отдельная организация, использующая платформу.

Каждый Tenant обладает собственной конфигурацией, пользователями, клиентами, настройками AI, подключёнными каналами и базой знаний.

Tenant является логически изолированной областью внутри платформы.

---

## 4.3 Organization

Термины Organization и Tenant являются эквивалентными.

В пользовательской документации рекомендуется использовать термин "Организация".

В технической документации допускается использование термина Tenant.

---

## 4.4 User

User — пользователь платформы.

Пользователь взаимодействует с административной частью платформы.

Минимальные роли MVP:

- Administrator
- Manager

Архитектура должна предусматривать возможность расширения набора ролей.

---

## 4.5 Client

Client — конечный пользователь организации.

Клиент общается с организацией посредством одного или нескольких каналов связи.

Клиент не является пользователем административной части платформы.

---

## 4.6 Communication Endpoint

Communication Endpoint — конкретный способ связи клиента.

Примеры:

- Telegram Account
- WhatsApp Number
- Email Address
- Phone Number
- Web Chat Session
- Mobile Application

Один Client может иметь несколько Communication Endpoint.

---

## 4.7 Channel

Channel — тип транспортного канала коммуникации.

Примеры:

- Telegram
- MAX
- VK
- WhatsApp Business
- Web Chat
- Mobile API
- Email
- SMS

Канал не содержит бизнес-логики.

Канал отвечает исключительно за передачу сообщений.

---

## 4.8 Adapter

Adapter — компонент Integration Platform, обеспечивающий преобразование данных между внешним API канала связи и внутренней моделью платформы.

Adapter отвечает исключительно за:

- получение сообщений;
- преобразование данных;
- отправку сообщений;
- обработку особенностей внешнего API.

Adapter не содержит бизнес-логики.

Adapter не принимает решений.

Adapter не выполняет маршрутизацию.

---

## 4.9 Communication Core

Communication Core — центральная подсистема платформы.

Communication Core отвечает за:

- приём сообщений;
- маршрутизацию;
- хранение;
- обработку;
- передачу сообщений прикладным сервисам;
- взаимодействие с Integration Platform.

Communication Core является главным компонентом платформы.

---

## 4.10 Message

Message — минимальная единица коммуникации.

Каждое сообщение независимо от происхождения после обработки Adapter должно иметь единый внутренний формат.

Сообщение может содержать:

- текст;
- вложения;
- служебные данные;
- ссылки на внешние объекты.

---

## 4.11 Conversation

Conversation — логическая история взаимодействия между организацией и клиентом.

Conversation объединяет все сообщения клиента независимо от используемого канала связи.

Если клиент общается через Telegram, затем Web Chat и позже Email, все сообщения относятся к одной Conversation, если принадлежат одному Client.

Conversation является пользовательским представлением истории коммуникации.

---

## 4.12 Broadcast Campaign

Broadcast Campaign — массовая коммуникация, инициированная организацией.

Broadcast использует стандартный механизм доставки сообщений платформы.

---

## 4.13 Notification

Notification — внутреннее уведомление платформы.

Notification предназначено исключительно для пользователей платформы.

Notification не является сообщением клиента.

---

## 4.14 AI Assistant

AI Assistant — интеллектуальный помощник клиентов и менеджеров.

Основные функции:

- ответы на вопросы;
- работа с базой знаний;
- помощь менеджеру;
- поиск информации;
- генерация текста;
- перевод.

AI Assistant не изменяет конфигурацию платформы.

---

## 4.15 AI Onboarding

AI Onboarding — интеллектуальный помощник администратора организации.

Используется исключительно при настройке платформы.

Основные функции:

- подключение каналов;
- настройка организации;
- изменение конфигурации;
- применение изменений через Backend API.

AI Onboarding не взаимодействует с конечными клиентами.

---

## 4.16 FBP Engine

FBP Engine — программируемый Workflow Engine платформы.

FBP Engine используется для:

- исполнения AI Workflow;
- исполнения Automation Workflow;
- исполнения Business Workflow.

FBP Engine не является Message Broker.

FBP Engine не заменяет Communication Core.

FBP Engine выполняет только описанные схемами процессы.

---

## 4.17 Workflow

Workflow — исполняемый процесс, описанный средствами FBP Engine.

Workflow может включать:

- обращения к AI;
- вызовы Backend API;
- обработку данных;
- условия;
- циклы;
- маршрутизацию исполнения.

---

## 4.18 Knowledge Base

Knowledge Base — набор документов организации, используемый AI Assistant.

Документы индексируются посредством pgvector.

Knowledge Base не используется Communication Core напрямую.

---

## 4.19 Edge Cluster

Edge Cluster — региональный кластер платформы, предназначенный для обслуживания клиентских подключений.

Edge Cluster выполняет:

- приём подключений;
- обслуживание WebSocket;
- обслуживание Web Chat;
- обслуживание Mobile API;
- аутентификацию;
- выполнение требований законодательства РФ;
- буферизацию сообщений;
- управление VPN Tunnel Service.

Edge Cluster не содержит основной бизнес-логики платформы.

---

## 4.20 Application Cluster

Application Cluster — основной вычислительный кластер платформы.

Application Cluster содержит:

- Backend;
- AI Platform;
- FBP Engine;
- PostgreSQL;
- Broadcast;
- Notification;
- SaaS Administration;
- Manager Workspace;
- остальные серверные компоненты.

---

## 4.21 VPN Tunnel Service

VPN Tunnel Service — специализированный сервис защищённого обмена данными между Edge Cluster и Application Cluster.

VPN Tunnel Service обеспечивает прозрачную передачу сообщений между региональными кластерами.

---

## 4.22 Telegram Console

Telegram Console — дополнительный пользовательский интерфейс платформы.

Telegram Console предоставляет менеджеру возможность:

- получать уведомления;
- отвечать клиентам;
- просматривать сведения о клиентах;
- работать вне Web-интерфейса.

Telegram Console не содержит бизнес-логики.

---

## 4.23 Manager Workspace

Manager Workspace — основное рабочее место менеджеров организации.

Предоставляет единый интерфейс обработки всех коммуникаций независимо от канала связи.

---

## 4.24 SaaS Administration

SaaS Administration — административный интерфейс платформы.

Предназначен для управления организациями, пользователями, каналами связи, AI, безопасностью и конфигурацией платформы.

---

# 5. Архитектурные принципы

Архитектура Communication Platform определяется следующими принципами.

Любое проектное решение должно соответствовать данным принципам.

При возникновении противоречий предпочтение отдаётся решению, наиболее полно соответствующему настоящему разделу.

## 5.1 Communication First

Главной задачей платформы является обеспечение надёжной коммуникации.

Если архитектурное решение не повышает качество коммуникации либо не упрощает сопровождение платформы, такое решение не должно включаться в MVP.

Все дополнительные функции рассматриваются как вспомогательные.

---

## 5.2 Единая платформа

Независимо от количества каналов связи, региональных кластеров, пользовательских интерфейсов и серверных компонентов платформа должна восприниматься как единая информационная система.

Пользователь не должен знать, какие компоненты находятся в Российской Федерации, а какие — за её пределами.

---

## 5.3 Простота

При наличии нескольких технически корректных решений предпочтение отдаётся наиболее простому.

Избыточное усложнение архитектуры не допускается.

Любое усложнение должно иметь измеримое обоснование.

---

## 5.4 AI как вспомогательная подсистема

AI не является ядром платформы.

Communication Platform должна полноценно функционировать при полном отсутствии AI.

Недоступность AI не должна препятствовать:

- приёму сообщений;
- доставке сообщений;
- работе менеджеров;
- работе клиентов;
- Broadcast;
- Notification.

AI повышает удобство использования, но не является обязательным компонентом коммуникации.

---

## 5.5 Программируемость

Поведение платформы должно определяться конфигурацией, схемами автоматизации и настройками организаций, а не изменением исходного кода.

Для реализации программируемого поведения используется FBP Engine.

FBP Engine позволяет изменять:

- сценарии автоматизации;
- бизнес-процессы;
- логику AI;
- последовательность обработки данных;
- правила принятия решений.

Изменение Workflow не должно требовать перекомпиляции платформы.

---

## 5.6 Независимость каналов связи

Все каналы связи рассматриваются как транспорт доставки сообщений.

Communication Core не должен содержать зависимостей от конкретных каналов связи.

Особенности Telegram, MAX, VK, WhatsApp, Email, SMS и других платформ должны быть полностью инкапсулированы внутри соответствующих Adapter.

Добавление нового канала связи не должно требовать изменения Communication Core.

---

## 5.7 Расширяемость

Архитектура платформы должна предусматривать возможность расширения без изменения существующих компонентов.

Должна существовать возможность подключения:

- новых каналов связи;
- новых AI-моделей;
- новых Workflow;
- новых пользовательских интерфейсов;
- новых способов авторизации;
- новых внешних интеграций.

Расширение функциональности должно осуществляться посредством подключения новых компонентов, а не модификации существующих.

---

## 5.8 Независимость пользовательских интерфейсов

Все пользовательские интерфейсы работают исключительно через Backend API.

Пользовательский интерфейс не содержит бизнес-логики.

Все проверки полномочий, обработка данных и принятие решений выполняются серверной частью платформы.

---

## 5.9 Масштабируемость

Все серверные компоненты должны поддерживать горизонтальное масштабирование.

Увеличение количества экземпляров компонентов не должно требовать изменения архитектуры приложения.

Бизнес-логика должна оставаться неизменной независимо от масштаба развёртывания.

---

## 5.10 Приоритет сопровождаемости

При выборе между более сложным и более простым архитектурным решением предпочтение отдаётся тому, которое:

- проще сопровождать;
- проще тестировать;
- проще документировать;
- проще развивать.

Долгосрочная стоимость сопровождения является одним из основных критериев принятия архитектурных решений.

---

## 5.11 Архитектурная независимость AI

AI не имеет прямого доступа к внутренним компонентам платформы.

Любые изменения данных, инициированные AI, выполняются исключительно посредством Backend API.

Все действия AI должны проходить те же проверки безопасности, что и действия пользователей.

---

## 5.12 Единая модель данных

Независимо от количества каналов связи и пользовательских интерфейсов внутри платформы должна существовать единая логическая модель данных.

Все компоненты платформы работают с едиными сущностями.

Дублирование бизнес-сущностей между компонентами не допускается.

---

## 5.13 Разделение ответственности

Каждый компонент платформы должен иметь одну основную область ответственности.

Не допускается объединение нескольких независимых бизнес-функций внутри одного компонента без архитектурного обоснования.

# 6. Общая архитектура платформы

## 6.1 Общие положения

Communication Platform представляет собой модульную распределённую систему, предназначенную для организации омниканальной коммуникации между организациями и их клиентами.

Архитектура платформы разделена на независимые функциональные подсистемы, взаимодействующие посредством внутренних API и общей модели данных.

Каждая подсистема отвечает за ограниченную область ответственности и может развиваться независимо при сохранении совместимости с остальной платформой.

---

## 6.2 Логическая структура платформы

Платформа состоит из следующих основных подсистем:

- Edge Cluster;
- Application Cluster;
- Communication Core;
- Identity Platform;
- Integration Platform;
- AI Platform;
- FBP Engine;
- Broadcast Platform;
- Notification Platform;
- SaaS Administration;
- Manager Workspace;
- Web Chat;
- Mobile API.

Каждая подсистема имеет строго определённые обязанности.

---

## 6.3 Центральная роль Communication Core

Communication Core является центральным компонентом платформы.

Все входящие и исходящие сообщения проходят через Communication Core.

Ни одна прикладная подсистема не взаимодействует с внешними каналами связи напрямую.

Communication Core отвечает за:

- приём сообщений;
- маршрутизацию;
- сохранение сообщений;
- передачу сообщений прикладным сервисам;
- передачу сообщений в Integration Platform для доставки.

Communication Core не содержит логики AI.

Communication Core не зависит от конкретных каналов связи.

---

## 6.4 Прикладные подсистемы

Прикладные подсистемы используют Communication Core для решения специализированных задач.

К ним относятся:

- AI Platform;
- Broadcast Platform;
- Notification Platform;
- SaaS Administration;
- Manager Workspace.

Прикладные подсистемы не выполняют доставку сообщений самостоятельно.

Все сообщения проходят через единый механизм Communication Core.

---

## 6.5 AI Platform

AI Platform предоставляет интеллектуальные функции платформы.

В состав AI Platform входят два независимых направления:

AI Assistant

используется при взаимодействии менеджеров и клиентов.

AI Onboarding

используется администраторами организаций при настройке платформы.

Обе подсистемы используют единые сервисы AI, но имеют различные полномочия и различные сценарии использования.

---

## 6.6 FBP Engine

FBP Engine обеспечивает программируемое поведение платформы.

FBP Engine исполняет Workflow, описывающие:

- автоматизацию;
- сценарии AI;
- бизнес-процессы;
- обработку событий.

FBP Engine не принимает участие в транспортировке сообщений.

Обработка сообщений всегда остаётся обязанностью Communication Core.

---

## 6.7 Integration Platform

Integration Platform обеспечивает взаимодействие платформы со всеми внешними сервисами.

Каждый канал связи реализуется отдельным Adapter.

Adapter отвечает исключительно за преобразование данных между внешним API и внутренней моделью платформы.

Особенности внешних API полностью локализуются внутри Adapter.

---

## 6.8 Identity Platform

Identity Platform обеспечивает:

- аутентификацию пользователей;
- авторизацию;
- управление пользовательскими сессиями;
- управление ролями.

На этапе MVP используется вход посредством Telegram Bot.

Архитектура предусматривает возможность последующего подключения дополнительных механизмов аутентификации.

---

## 6.9 Broadcast Platform

Broadcast Platform предназначена для формирования массовых коммуникаций.

После формирования сообщений дальнейшая обработка полностью совпадает с обработкой обычной пользовательской переписки.

Broadcast Platform не взаимодействует напрямую с каналами связи.

---

## 6.10 Notification Platform

Notification Platform предназначена для информирования пользователей платформы о внутренних событиях.

Notification Platform не используется для коммуникации организации с её клиентами.

---

## 6.11 Пользовательские интерфейсы

Платформа предоставляет следующие пользовательские интерфейсы:

- SaaS Administration;
- Manager Workspace;
- Web Chat;
- Telegram Console;
- Mobile Application.

Все пользовательские интерфейсы используют единый Backend API.

---

## 6.12 Общая схема обработки сообщений

Жизненный цикл сообщения включает следующие этапы:

1. Получение сообщения Adapter соответствующего канала.
2. Преобразование сообщения во внутренний формат.
3. Передача сообщения в Communication Core.
4. Сохранение сообщения.
5. Определение дальнейшего маршрута обработки.
6. Передача сообщения прикладным сервисам при необходимости.
7. Формирование ответа.
8. Передача ответа в Integration Platform.
9. Преобразование ответа в формат соответствующего канала.
10. Доставка сообщения клиенту.

Независимо от канала связи последовательность обработки остаётся одинаковой.

---

## 6.13 Общая схема обработки команд AI

При использовании AI выполняется следующая последовательность:

1. Communication Core получает сообщение.
2. Backend определяет необходимость обращения к AI.
3. AI Platform получает запрос.
4. При необходимости AI использует Knowledge Base.
5. При необходимости AI инициирует Workflow в FBP Engine.
6. Workflow обращается к Backend API.
7. Backend выполняет проверки безопасности.
8. Backend изменяет данные платформы либо формирует ответ.
9. Communication Core доставляет ответ пользователю.

AI не имеет прямого доступа к базе данных.

AI не изменяет данные самостоятельно.

Все изменения проходят через Backend API.

---

## 6.14 Независимость компонентов

Каждая подсистема должна иметь возможность независимого тестирования.

Изменение одной подсистемы не должно требовать изменения остальных компонентов при сохранении публичных контрактов.

Все взаимодействия между подсистемами должны выполняться посредством документированных API и внутренних контрактов платформы.

# 7. Архитектура размещения платформы

## 7.1 Общие положения

Communication Platform проектируется как единая распределённая информационная система.

Архитектура должна обеспечивать:

- выполнение требований законодательства различных стран;
- возможность регионального размещения компонентов;
- высокую доступность;
- масштабируемость;
- прозрачность работы для пользователей.

Распределённая архитектура является особенностью инфраструктуры и не должна влиять на бизнес-логику платформы.

---

## 7.2 Общая модель размещения

Архитектура MVP предусматривает использование двух основных региональных кластеров.

**Edge Cluster (Российская Федерация)**

Предназначен для обслуживания пользователей Российской Федерации.

**Application Cluster (зарубежное размещение)**

Является основной вычислительной площадкой платформы.

Архитектура должна предусматривать возможность подключения дополнительных региональных Edge Cluster без изменения прикладной логики.

---

## 7.3 Edge Cluster

Edge Cluster является региональной точкой входа пользователей.

Основные задачи Edge Cluster:

- приём клиентских подключений;
- обслуживание WebSocket-соединений;
- обслуживание Web Chat;
- обслуживание Mobile API;
- аутентификация пользователей;
- обеспечение выполнения требований законодательства РФ;
- управление VPN Tunnel Service;
- временная буферизация сообщений;
- обеспечение высокой доступности пользовательских подключений.

Edge Cluster не содержит основной бизнес-логики платформы.

Edge Cluster не содержит AI Platform.

Edge Cluster не содержит FBP Engine.

Edge Cluster не содержит административной панели.

---

## 7.4 Application Cluster

Application Cluster является основным вычислительным центром платформы.

В состав Application Cluster входят:

- Backend API;
- Communication Core;
- Identity Platform;
- AI Platform;
- FBP Engine;
- Broadcast Platform;
- Notification Platform;
- PostgreSQL;
- pgvector;
- SaaS Administration;
- Manager Workspace;
- сервисы мониторинга;
- сервисы аналитики;
- Integration Platform.

Все вычислительные задачи выполняются в Application Cluster.

---

## 7.5 Принцип единой платформы

Независимо от региона подключения пользователь работает с одной платформой.

Организация имеет:

- одну конфигурацию;
- один набор пользователей;
- одну административную панель;
- одну модель безопасности;
- единую историю коммуникаций.

Разделение инфраструктуры не должно приводить к разделению продукта.

---

## 7.6 Работа пользователей Российской Федерации

Пользователи Российской Федерации подключаются исключительно к Edge Cluster.

Edge Cluster выполняет:

1. установление соединения;
2. идентификацию пользователя;
3. проверку полномочий;
4. приём сообщений;
5. передачу сообщений в Application Cluster.

Пользователь не взаимодействует напрямую с зарубежной инфраструктурой.

Все особенности распределённой архитектуры полностью скрыты.

---

## 7.7 Работа зарубежных пользователей

Пользователи, не требующие подключения через Edge Cluster, могут обслуживаться непосредственно Application Cluster.

Архитектура должна поддерживать оба режима работы.

Выбор режима определяется настройками инфраструктуры.

---

## 7.8 VPN Tunnel Service

VPN Tunnel Service обеспечивает защищённую связь между региональными кластерами.

Все межкластерные соединения должны использовать:

- взаимную аутентификацию;
- шифрование;
- постоянный контроль соединения;
- автоматическое восстановление после разрыва.

VPN Tunnel Service является внутренним компонентом платформы.

Он недоступен пользователям.

---

## 7.9 Буферизация сообщений

Если связь между Edge Cluster и Application Cluster временно отсутствует, Edge Cluster обязан продолжить приём сообщений.

Полученные сообщения помещаются во временное защищённое хранилище.

После восстановления соединения сообщения автоматически передаются в Communication Core.

Потеря сообщений вследствие временной недоступности канала связи не допускается.

---

## 7.10 Последовательность сообщений

При передаче накопленных сообщений должен сохраняться порядок их получения.

Communication Core должен получать сообщения в том же порядке, в котором они были приняты Edge Cluster.

---

## 7.11 Масштабирование регионов

Архитектура должна предусматривать возможность подключения дополнительных региональных Edge Cluster.

Добавление нового региона не должно требовать:

- изменения Backend API;
- изменения Communication Core;
- изменения AI Platform;
- изменения пользовательских интерфейсов.

Необходимыми являются только изменения инфраструктурной конфигурации.

---

## 7.12 Отказоустойчивость

Недоступность одного регионального кластера не должна приводить к отказу всей платформы.

При восстановлении работоспособности должна автоматически выполняться синхронизация накопленных данных.

---

# 8. Communication Core

## 8.1 Назначение

Communication Core является центральной подсистемой Communication Platform.

Все сообщения независимо от происхождения проходят через Communication Core.

Communication Core является единственной подсистемой, отвечающей за жизненный цикл сообщений.

---

## 8.2 Основные обязанности

Communication Core отвечает за:

- приём сообщений;
- регистрацию сообщений;
- маршрутизацию сообщений;
- сохранение сообщений;
- управление историей коммуникаций;
- передачу сообщений прикладным сервисам;
- передачу сообщений Integration Platform для доставки.

Communication Core не содержит AI.

Communication Core не содержит пользовательских интерфейсов.

---

## 8.3 Общая модель обработки

Каждое сообщение проходит следующие стадии:

Получение

↓

Проверка корректности

↓

Регистрация

↓

Сохранение

↓

Маршрутизация

↓

Обработка прикладными сервисами

↓

Отправка ответа

Все сообщения независимо от канала используют одинаковый жизненный цикл.

---

## 8.4 Единая модель сообщения

После обработки Adapter каждое сообщение должно иметь единый внутренний формат.

Минимально сообщение содержит:

- идентификатор сообщения;
- идентификатор организации;
- идентификатор клиента;
- идентификатор Endpoint;
- идентификатор канала;
- тип сообщения;
- содержимое;
- вложения;
- дату создания;
- служебные атрибуты.

Communication Core не должен зависеть от формата внешнего API.

---

## 8.5 Conversation

Communication Core объединяет сообщения в Conversation.

Conversation представляет собой полную историю общения организации с конкретным клиентом.

Все сообщения клиента независимо от используемого канала входят в одну Conversation.

Переключение между Telegram, Web Chat, Email или Mobile Application не создаёт новую историю общения.

---

## 8.6 Маршрутизация

Communication Core определяет дальнейшую обработку сообщения.

Сообщение может быть направлено:

- менеджеру;
- AI Assistant;
- Broadcast Platform;
- Notification Platform;
- Automation Workflow;
- внешнему сервису.

Правила маршрутизации определяются конфигурацией платформы.

---

## 8.7 Независимость от AI

Communication Core не принимает решений на основе AI.

При необходимости использования AI Communication Core передаёт сообщение AI Platform.

При недоступности AI Communication Core продолжает работу.

---

## 8.8 Независимость от каналов

Communication Core не содержит информации о Telegram, MAX, VK, WhatsApp, Email или SMS.

Communication Core работает исключительно с внутренними сущностями платформы.

Все особенности конкретного канала локализуются внутри Adapter.

---

## 8.9 Передача сообщений

После формирования ответа Communication Core передаёт сообщение в Integration Platform.

Communication Core не взаимодействует напрямую с внешними API.

---

## 8.10 Журналирование

Communication Core фиксирует все этапы жизненного цикла сообщения.

Минимально регистрируются:

- время получения;
- источник;
- маршрут обработки;
- результат обработки;
- факт доставки;
- ошибки.

Журналирование является обязательной частью платформы.

---

## 8.11 Масштабирование

Communication Core должен поддерживать запуск нескольких экземпляров.

Экземпляры должны работать с единой моделью данных.

Добавление новых экземпляров не должно изменять алгоритмы обработки сообщений.

---

## 8.12 Архитектурный принцип

Communication Core является фундаментом платформы.

Все остальные подсистемы рассматриваются как прикладные сервисы, использующие возможности Communication Core.

Ни одна подсистема не должна дублировать функции Communication Core.

# 9. Identity Platform

## 9.1 Назначение

Identity Platform обеспечивает идентификацию пользователей платформы, управление доступом и централизованную авторизацию.

Identity Platform является единственной подсистемой, отвечающей за аутентификацию пользователей и проверку их полномочий.

Ни один другой компонент платформы не должен самостоятельно реализовывать механизмы проверки прав доступа.

---

## 9.2 Область ответственности

Identity Platform отвечает за:

- аутентификацию пользователей;
- управление пользовательскими сессиями;
- управление ролями;
- проверку полномочий;
- регистрацию входов;
- отзыв активных сессий;
- аудит действий пользователей.

Identity Platform не отвечает за управление клиентами организации.

Конечные клиенты проходят идентификацию посредством соответствующих каналов связи и не являются пользователями административной части платформы.

---

## 9.3 Пользовательские роли MVP

В рамках MVP определяются две основные роли.

### Administrator

Administrator отвечает за управление организацией.

Полномочия включают:

- управление пользователями;
- подключение каналов связи;
- настройку AI;
- настройку автоматизации;
- управление Knowledge Base;
- управление Broadcast;
- настройку Notification;
- просмотр журналов аудита;
- использование AI Onboarding.

---

### Manager

Manager осуществляет ежедневную работу с клиентами.

Полномочия включают:

- обработку обращений клиентов;
- ведение переписки;
- использование AI Assistant;
- получение уведомлений;
- использование Telegram Console;
- просмотр истории коммуникаций.

Manager не имеет доступа к административной конфигурации платформы.

---

## 9.4 Архитектурная расширяемость

Архитектура должна предусматривать возможность последующего добавления новых ролей без изменения существующей модели безопасности.

Добавление новых ролей должно осуществляться посредством конфигурации и механизмов авторизации.

---

## 9.5 Способ аутентификации MVP

На этапе MVP используется аутентификация посредством Telegram Bot.

Процесс входа включает следующие этапы:

1. Пользователь вводит своё Telegram-имя.
2. Backend проверяет существование пользователя.
3. Telegram Bot отправляет одноразовый код.
4. Пользователь вводит полученный код.
5. После успешной проверки создаётся пользовательская сессия.

Одноразовый код имеет ограниченное время действия.

Повторное использование кода не допускается.

---

## 9.6 Дальнейшее развитие

Архитектура должна предусматривать возможность подключения дополнительных механизмов аутентификации без изменения пользовательских интерфейсов.

В перспективе могут быть добавлены:

- OAuth;
- OpenID Connect;
- корпоративные SSO;
- аппаратные ключи;
- двухфакторная аутентификация;
- Passkeys.

Подключение новых способов входа не должно влиять на остальную архитектуру платформы.

---

## 9.7 Пользовательская сессия

После успешной аутентификации создаётся серверная пользовательская сессия.

Сессия содержит:

- идентификатор пользователя;
- организацию;
- набор ролей;
- срок действия;
- служебные параметры безопасности.

Истечение срока действия автоматически завершает пользовательскую сессию.

---

## 9.8 Авторизация

Перед выполнением любой операции Backend обязан проверить:

- наличие активной сессии;
- принадлежность пользователя организации;
- наличие необходимых полномочий.

Все проверки выполняются серверной частью платформы.

Frontend не должен самостоятельно определять доступность операций.

---

## 9.9 Аудит безопасности

Identity Platform обязана регистрировать:

- успешные входы;
- неуспешные попытки входа;
- завершение сессий;
- смену ролей;
- изменение прав доступа;
- административные действия.

Журнал аудита является обязательной частью платформы.

---

# 10. Integration Platform

## 10.1 Назначение

Integration Platform обеспечивает взаимодействие Communication Platform со всеми внешними сервисами и каналами связи.

Integration Platform является транспортным уровнем платформы.

Она не содержит бизнес-логики и не принимает прикладных решений.

---

## 10.2 Основные задачи

Integration Platform отвечает за:

- получение сообщений;
- отправку сообщений;
- преобразование данных;
- обработку особенностей внешних API;
- управление подключениями;
- обработку ошибок взаимодействия с внешними сервисами.

---

## 10.3 Adapter

Каждый канал связи реализуется отдельным Adapter.

Adapter представляет собой независимый компонент Integration Platform.

Минимально Adapter реализует:

- получение сообщений;
- отправку сообщений;
- преобразование данных;
- обработку ошибок;
- контроль соединения.

Adapter не принимает бизнес-решений.

---

## 10.4 Поддерживаемые каналы MVP

Архитектура MVP предусматривает поддержку следующих каналов:

- Telegram;
- MAX;
- VK;
- WhatsApp Business;
- Web Chat;
- Mobile API;
- Email;
- SMS.

Добавление нового канала не должно требовать изменения остальных Adapter.

---

## 10.5 Независимость каналов

Communication Core не должен знать особенности конкретного канала связи.

После обработки Adapter каждое сообщение преобразуется в единую внутреннюю модель платформы.

Обратное преобразование выполняется перед отправкой сообщения клиенту.

---

## 10.6 Capability Model

Каждый Adapter обязан публиковать описание своих возможностей (Capabilities).

Capabilities определяют поддерживаемые функции конкретного канала.

Примеры возможностей:

- отправка текста;
- отправка изображений;
- отправка файлов;
- голосовые сообщения;
- видео;
- кнопки;
- реакции;
- индикатор набора текста;
- подтверждение прочтения;
- удаление сообщений;
- редактирование сообщений.

Communication Core принимает решения, опираясь на Capabilities Adapter, а не на название конкретного канала.

Это обеспечивает единый механизм поддержки различных платформ.

---

## 10.7 Работа с внешними API

Все обращения к внешним сервисам должны выполняться исключительно Adapter.

Другие подсистемы платформы не должны использовать API Telegram, WhatsApp, VK, MAX и других сервисов напрямую.

---

## 10.8 Обработка ошибок

При возникновении ошибок взаимодействия Adapter обязан:

- зарегистрировать ошибку;
- определить возможность повторной отправки;
- выполнить повторную попытку при необходимости;
- уведомить Communication Core о результате операции.

Обработка ошибок должна быть унифицирована независимо от используемого канала.

---

## 10.9 Масштабирование

Каждый Adapter должен поддерживать независимое горизонтальное масштабирование.

Увеличение нагрузки на один канал не должно влиять на работу остальных Adapter.

---

## 10.10 Архитектурный принцип

Integration Platform является транспортным уровнем системы.

Она обеспечивает обмен сообщениями между платформой и внешним миром.

Вся прикладная логика остаётся внутри Backend и Communication Core.

Таким образом достигается полная независимость бизнес-логики платформы от используемых каналов связи.

# 11. Backend API

## 11.1 Назначение

Backend API является единственной публичной точкой взаимодействия между пользовательскими интерфейсами, внешними интеграциями и внутренними компонентами платформы.

Любые операции чтения или изменения данных выполняются исключительно посредством Backend API.

Ни один клиентский компонент не имеет прямого доступа к базе данных.

---

## 11.2 Архитектурная модель

Backend реализуется как **модульный монолит (Modular Monolith)** на платформе **NestJS**.

Каждый функциональный модуль обладает собственной областью ответственности, внутренними интерфейсами и независимым жизненным циклом разработки.

Архитектура должна предусматривать возможность последующего выделения отдельных модулей в самостоятельные сервисы без изменения публичных контрактов API.

Такой подход обеспечивает:

- простоту разработки MVP;
- отсутствие распределённых транзакций;
- единый процесс развертывания;
- минимальную сложность сопровождения;
- возможность постепенной эволюции архитектуры.

---

## 11.3 Основные модули Backend

В состав Backend входят следующие функциональные модули:

- Communication Core;
- Identity Platform;
- Organization Management;
- User Management;
- Client Management;
- Conversation Management;
- Message Management;
- Integration Platform;
- AI Platform;
- FBP Engine Integration;
- Broadcast Platform;
- Notification Platform;
- Knowledge Base;
- Audit;
- Configuration.

Каждый модуль имеет собственный слой бизнес-логики.

---

## 11.4 Внутреннее взаимодействие модулей

Модули взаимодействуют посредством внутренних сервисных интерфейсов NestJS.

Прямой доступ одного модуля к внутренним данным другого модуля запрещён.

Каждый модуль предоставляет только документированные публичные интерфейсы.

---

## 11.5 Внешние интерфейсы

Backend предоставляет следующие категории API:

- REST API;
- WebSocket API;
- Internal Service API.

REST API используется пользовательскими интерфейсами и внешними системами.

WebSocket используется для событий реального времени.

Internal API используется исключительно внутренними компонентами платформы.

---

## 11.6 REST API

REST API является основным способом взаимодействия с платформой.

Каждый ресурс должен иметь единообразный набор операций.

Минимально поддерживаются операции:

- создание;
- получение;
- изменение;
- удаление;
- поиск;
- фильтрация;
- постраничная навигация.

Все операции должны быть идемпотентными там, где это возможно.

---

## 11.7 WebSocket API

WebSocket используется исключительно для событий реального времени.

Минимально должны поддерживаться следующие события:

- получение нового сообщения;
- изменение статуса сообщения;
- начало набора текста;
- окончание набора текста;
- изменение статуса клиента;
- получение уведомлений;
- изменение состояния Broadcast;
- изменение состояния Workflow.

Соединение должно автоматически восстанавливаться после временной потери связи.

---

## 11.8 Версионирование API

Все публичные API должны поддерживать версионирование.

Версия API указывается в URL.

Изменение существующей версии API, нарушающее обратную совместимость, не допускается.

Все несовместимые изменения публикуются только в новой версии API.

---

## 11.9 Формат данных

Все API используют JSON.

Идентификаторы объектов представлены UUID.

Дата и время передаются в формате ISO-8601 UTC.

Все текстовые данные кодируются в UTF-8.

---

## 11.10 Валидация

Все входящие запросы проходят обязательную серверную проверку.

Проверяются:

- обязательные поля;
- типы данных;
- ограничения длины;
- допустимые значения;
- принадлежность данных организации;
- права пользователя.

Недопустимые запросы не должны достигать бизнес-логики приложения.

---

## 11.11 Обработка ошибок

Все ошибки возвращаются в едином формате.

Ответ об ошибке должен содержать:

- код ошибки;
- краткое описание;
- человекочитаемое сообщение;
- идентификатор запроса;
- дополнительную диагностическую информацию (при необходимости).

Формат ошибок должен быть единым для всех модулей платформы.

---

## 11.12 Идемпотентность

Операции создания сообщений, Broadcast и других объектов должны поддерживать механизм защиты от повторной обработки.

Повторная отправка одинакового запроса не должна приводить к созданию дублирующихся данных.

---

## 11.13 Логирование

Backend обязан регистрировать:

- входящие запросы;
- исходящие ответы;
- ошибки;
- исключения;
- длительность обработки;
- идентификатор пользователя;
- организацию;
- идентификатор запроса.

Журналирование должно быть единообразным для всех модулей.

---

## 11.14 Документирование API

Все REST API документируются посредством OpenAPI (Swagger).

Документация должна генерироваться автоматически на основании исходного кода.

Каждое изменение API должно автоматически отражаться в документации.

Документация является частью поставляемого продукта.

---

# 12. AI Platform

## 12.1 Назначение

AI Platform предоставляет интеллектуальные функции платформы.

AI Platform является вспомогательной подсистемой.

Недоступность AI Platform не должна препятствовать работе Communication Platform.

Все критически важные функции платформы продолжают работать независимо от состояния AI.

---

## 12.2 Основные компоненты

AI Platform состоит из двух независимых направлений:

- AI Assistant;
- AI Onboarding.

Обе подсистемы используют общую инфраструктуру работы с языковыми моделями, но имеют различное назначение и различные полномочия.

---

## 12.3 AI Assistant

AI Assistant предназначен для помощи менеджерам и конечным клиентам.

Основные функции:

- ответы на вопросы клиентов;
- поиск информации;
- использование базы знаний;
- генерация вариантов ответов;
- перевод сообщений;
- краткое резюмирование переписки;
- помощь менеджеру при подготовке ответа.

AI Assistant не изменяет конфигурацию платформы.

AI Assistant не выполняет административные действия.

---

## 12.4 AI Onboarding

AI Onboarding предназначен исключительно для администраторов организации.

Основные функции:

- первоначальная настройка платформы;
- подключение каналов связи;
- настройка автоматизации;
- управление Knowledge Base;
- изменение параметров организации;
- помощь при конфигурировании системы.

Все изменения, инициированные AI Onboarding, выполняются исключительно через Backend API после прохождения всех проверок безопасности.

---

## 12.5 Принцип работы

AI Platform не взаимодействует с базой данных напрямую.

Последовательность обработки запроса:

1. Backend принимает запрос.
2. Backend формирует контекст.
3. AI получает только необходимый контекст.
4. AI формирует ответ или структурированную команду.
5. Backend проверяет результат.
6. Backend выполняет необходимые операции через собственную бизнес-логику.
7. Пользователь получает результат.

Таким образом, AI никогда не обладает полномочиями непосредственного изменения данных.

---

## 12.6 Структурированные ответы

При необходимости выполнения действий AI возвращает структурированный JSON-документ.

JSON содержит описание требуемой операции и её параметры.

Backend валидирует полученную структуру, проверяет полномочия пользователя и только после этого выполняет соответствующие действия.

Никакие SQL-запросы, команды или программный код, сформированные AI, не исполняются напрямую.

---

## 12.7 Knowledge Base

AI Assistant использует базу знаний организации.

Knowledge Base представляет собой набор документов, предоставленных организацией.

Документы индексируются с использованием pgvector.

AI использует поиск по смысловому сходству (semantic search) для формирования контекста ответа.

Knowledge Base является логически изолированной для каждого Tenant.

---

## 12.8 Использование FBP Engine

Все сложные сценарии работы AI реализуются посредством FBP Engine.

FBP Engine определяет:

- последовательность вызовов моделей;
- обработку результатов;
- взаимодействие с Backend API;
- использование внешних сервисов;
- маршрутизацию данных.

Изменение логики AI должно выполняться изменением Workflow, а не изменением исходного кода платформы.

---

## 12.9 Использование языковых моделей

Архитектура не зависит от конкретного поставщика LLM.

Должна существовать возможность подключения различных моделей без изменения прикладной логики платформы.

Выбор конкретной модели определяется конфигурацией организации или администратора платформы.

Поддержка нескольких моделей одновременно должна быть предусмотрена архитектурно.

---

## 12.10 Изоляция AI

AI Platform не должна иметь прямого доступа:

- к PostgreSQL;
- к внутренним сервисам;
- к файловой системе;
- к настройкам платформы;
- к пользовательским сессиям.

Все обращения выполняются только через документированные Backend API с обязательной проверкой полномочий.

Это обеспечивает предсказуемость, безопасность и возможность аудита всех действий, инициированных искусственным интеллектом.

# 13. FBP Engine

## 13.1 Назначение

FBP Engine является встроенным программируемым Workflow Engine платформы.

В основе подсистемы используется проект **fbp-engine**, адаптированный под архитектуру Communication Platform.

FBP Engine обеспечивает возможность изменения поведения платформы без изменения исходного кода Backend.

FBP Engine не является ядром платформы.

Он выполняет исключительно сценарии, инициированные Backend.

---

## 13.2 Архитектурная роль

FBP Engine располагается между прикладной логикой платформы и AI Platform.

Он используется как исполнитель бизнес-процессов, сценариев автоматизации и AI Workflow.

Communication Core никогда не зависит от FBP Engine.

При недоступности FBP Engine обмен сообщениями продолжает работать.

---

## 13.3 Основные задачи

FBP Engine используется для реализации:

- AI Workflow;
- Business Workflow;
- Automation Workflow;
- сценариев обработки событий;
- последовательностей вызова внешних сервисов;
- интеллектуальной автоматизации.

FBP Engine не используется как Message Broker.

FBP Engine не маршрутизирует сообщения.

---

## 13.4 Основные сущности

В архитектуре платформы используются следующие логические сущности FBP Engine.

### Workflow

Исполняемый процесс.

Workflow определяет последовательность выполнения операций.

---

### Node

Минимальная исполняемая единица Workflow.

Каждый Node выполняет одно действие.

Примеры:

- вызов LLM;
- обращение к Backend API;
- поиск документов;
- обработка текста;
- ветвление;
- ожидание результата.

---

### Connection

Определяет направление передачи данных между Node.

Connection образует граф исполнения Workflow.

---

### Execution Context

Набор данных, доступных во время исполнения Workflow.

Execution Context может содержать:

- параметры пользователя;
- данные организации;
- идентификаторы объектов;
- результаты предыдущих Node;
- временные вычисления.

Execution Context существует только во время выполнения Workflow.

---

### Variables

Workflow может использовать внутренние переменные.

Переменные применяются для хранения промежуточных результатов.

---

### Parameters

Workflow поддерживает входные параметры.

Backend передаёт Workflow только те данные, которые необходимы для выполнения конкретной задачи.

---

## 13.5 Интеграция с Backend

FBP Engine не изменяет данные платформы самостоятельно.

Если Workflow необходимо изменить данные платформы, выполняется следующая последовательность:

1. Workflow формирует запрос.
2. Backend API получает запрос.
3. Backend выполняет проверку полномочий.
4. Backend применяет бизнес-логику.
5. Backend изменяет данные.
6. Backend возвращает результат Workflow.

Таким образом FBP Engine не обладает административными полномочиями.

---

## 13.6 Использование AI

Workflow может использовать одну или несколько языковых моделей.

Количество моделей не ограничивается архитектурой.

FBP Engine определяет:

- последовательность обращения к моделям;
- передачу контекста;
- обработку результатов;
- объединение ответов нескольких моделей;
- дополнительные проверки.

---

## 13.7 Использование Knowledge Base

Workflow может выполнять поиск информации в базе знаний.

Поиск осуществляется посредством Backend API.

FBP Engine не взаимодействует напрямую с PostgreSQL.

Полученные документы становятся частью Execution Context.

---

## 13.8 Использование внешних сервисов

Workflow может обращаться к внешним сервисам посредством специализированных Connector.

Каждый Connector имеет собственный адаптер безопасности.

Использование внешних сервисов контролируется Backend.

---

## 13.9 Ошибки исполнения

При возникновении ошибки Workflow обязан:

- завершить выполнение;
- вернуть информацию Backend;
- сохранить диагностическую информацию;
- зарегистрировать событие аудита.

Ошибки Workflow не должны приводить к отказу Communication Core.

---

## 13.10 Версионирование Workflow

Каждая схема Workflow должна иметь собственную версию.

Новая версия Workflow не должна изменять поведение уже выполняющихся процессов.

Переключение между версиями осуществляется посредством конфигурации.

---

## 13.11 Импорт и экспорт

После MVP FBP Engine должен поддерживать:

- импорт Workflow;
- экспорт Workflow;
- импорт базы знаний;
- экспорт базы знаний.

Это позволит переносить настройки между организациями и окружениями.

---

## 13.12 Архитектурные ограничения

FBP Engine запрещается:

- выполнять SQL-запросы;
- изменять базу данных напрямую;
- обращаться к внутренним сервисам в обход Backend API;
- изменять полномочия пользователей;
- получать доступ к секретам платформы.

Все действия должны выполняться исключительно посредством документированных Backend API.

---

# 14. Broadcast Platform

## 14.1 Назначение

Broadcast Platform предназначена для организации массовых коммуникаций между организацией и её клиентами.

Broadcast является прикладной подсистемой платформы и использует Communication Core для доставки сообщений.

Broadcast Platform не взаимодействует напрямую с внешними каналами связи.

---

## 14.2 Основные возможности

Broadcast Platform должна обеспечивать:

- создание кампаний;
- выбор получателей;
- подготовку сообщений;
- персонализацию;
- планирование времени отправки;
- запуск кампаний;
- контроль выполнения;
- получение статистики.

---

## 14.3 Архитектурный принцип

Broadcast Platform не содержит собственной системы доставки сообщений.

После формирования сообщения оно передаётся Communication Core.

Дальнейшая обработка полностью совпадает с обработкой обычной пользовательской переписки.

Это обеспечивает единый механизм доставки сообщений независимо от источника их возникновения.

---

## 14.4 Получатели

Получатели Broadcast определяются фильтрами.

Минимально должны поддерживаться фильтры по:

- организации;
- тегам;
- каналам связи;
- пользовательским сегментам;
- произвольным условиям.

Архитектура должна предусматривать возможность добавления новых критериев отбора.

---

## 14.5 Персонализация

Перед отправкой сообщение может быть персонализировано.

Персонализация выполняется Backend до передачи сообщения Communication Core.

Персонализация может использовать данные клиента и организации.

---

## 14.6 Ограничение скорости

Broadcast Platform должна поддерживать управление скоростью отправки сообщений.

Параметры ограничения определяются:

- возможностями конкретного канала;
- политиками организации;
- инфраструктурными ограничениями.

---

## 14.7 Планирование

Broadcast может запускаться:

- немедленно;
- по расписанию;
- по событию;
- посредством Workflow.

---

## 14.8 Контроль выполнения

Для каждой кампании должна отображаться информация о состоянии выполнения.

Минимально фиксируются:

- количество подготовленных сообщений;
- количество отправленных сообщений;
- количество доставленных сообщений;
- количество ошибок;
- время выполнения.

---

## 14.9 Повторная отправка

При временных ошибках доставки должна поддерживаться повторная отправка сообщений.

Количество попыток определяется настройками платформы.

---

## 14.10 Независимость каналов

Broadcast Platform не зависит от Telegram, WhatsApp, Email, SMS и других платформ.

Все особенности конкретных каналов полностью инкапсулируются внутри Integration Platform.

Broadcast работает исключительно с внутренней моделью сообщений.

---

# 15. Notification Platform

## 15.1 Назначение

Notification Platform предназначена для информирования пользователей платформы о внутренних событиях.

Notification не используется для общения организации с её клиентами.

---

## 15.2 Источники уведомлений

Уведомления могут формироваться:

- Backend;
- Communication Core;
- Broadcast Platform;
- AI Platform;
- Workflow;
- системой безопасности;
- административными сервисами.

---

## 15.3 Получатели уведомлений

Получателями являются исключительно пользователи платформы.

Минимально:

- Administrator;
- Manager.

Конечные клиенты уведомления Notification Platform не получают.

---

## 15.4 Каналы доставки уведомлений

Архитектура должна поддерживать доставку уведомлений посредством:

- Web Interface;
- Telegram Console;
- электронной почты;
- Push-уведомлений.

Перечень поддерживаемых каналов может расширяться.

---

## 15.5 Категории уведомлений

Минимально поддерживаются:

- информационные;
- предупреждения;
- ошибки;
- критические события;
- административные сообщения.

---

## 15.6 Управление уведомлениями

Пользователь должен иметь возможность управлять настройками получения уведомлений.

Настройки определяются индивидуально для каждого пользователя.

---

## 15.7 Архитектурный принцип

Notification Platform не содержит бизнес-логики коммуникации.

Она предназначена исключительно для информирования пользователей платформы о происходящих событиях.

# 16. SaaS Administration

## 16.1 Назначение

SaaS Administration является основным административным интерфейсом платформы.

Через SaaS Administration администраторы организаций выполняют настройку платформы, управление пользователями, каналами связи, AI, автоматизацией и другими компонентами системы.

SaaS Administration является единственным интерфейсом управления конфигурацией организации.

---

## 16.2 Основные функции

Административная панель должна обеспечивать:

- управление организацией;
- управление пользователями;
- управление ролями;
- подключение каналов связи;
- настройку Integration Platform;
- настройку AI Assistant;
- настройку AI Onboarding;
- управление Knowledge Base;
- управление Workflow;
- управление Broadcast;
- просмотр журналов аудита;
- просмотр системных журналов;
- настройку Notification;
- управление параметрами безопасности.

---

## 16.3 Управление организацией

Administrator может изменять:

- название организации;
- описание;
- часовой пояс;
- язык интерфейса;
- параметры AI;
- ограничения использования платформы;
- настройки каналов связи.

Все изменения выполняются через Backend API.

---

## 16.4 Управление пользователями

Администратор может:

- создавать пользователей;
- блокировать пользователей;
- изменять роли;
- отзывать активные сессии;
- изменять параметры доступа.

Удаление пользователей должно выполняться в соответствии с политикой хранения данных платформы.

---

## 16.5 Управление каналами связи

Каждый подключённый канал отображается как отдельная конфигурационная сущность.

Для каждого канала должны отображаться:

- состояние подключения;
- дата последней проверки;
- используемые возможности (Capabilities);
- журнал ошибок;
- параметры подключения.

Подключение нового канала не требует изменения пользовательского интерфейса.

---

## 16.6 Управление Knowledge Base

Administrator должен иметь возможность:

- загружать документы;
- удалять документы;
- обновлять документы;
- переиндексировать базу знаний;
- просматривать состояние индексации.

Knowledge Base используется исключительно AI Platform.

---

## 16.7 Управление Workflow

Все Workflow отображаются в отдельном разделе административной панели.

Administrator может:

- включать Workflow;
- отключать Workflow;
- выбирать активную версию;
- просматривать историю исполнения;
- просматривать диагностическую информацию.

Редактирование Workflow в MVP не предусматривается.

---

## 16.8 AI Onboarding

Администратор может использовать AI Onboarding для настройки платформы.

AI Onboarding работает в виде диалогового помощника.

После получения подтверждения пользователя AI формирует структурированный запрос к Backend API.

Backend выполняет проверку полномочий и применяет изменения.

---

## 16.9 Архитектурный принцип

SaaS Administration не содержит бизнес-логики.

Все операции выполняются посредством Backend API.

Frontend отвечает исключительно за отображение данных и взаимодействие с пользователем.

---

# 17. Manager Workspace

## 17.1 Назначение

Manager Workspace является основным рабочим местом сотрудников организации.

Все ежедневные операции по взаимодействию с клиентами выполняются через данный интерфейс.

Manager Workspace предоставляет единый интерфейс независимо от канала, используемого клиентом.

---

## 17.2 Основные функции

Manager Workspace должен обеспечивать:

- просмотр очереди обращений;
- поиск клиентов;
- просмотр истории коммуникаций;
- ведение переписки;
- просмотр карточки клиента;
- работу с вложениями;
- использование AI Assistant;
- получение уведомлений;
- запуск Broadcast (при наличии полномочий);
- просмотр истории действий.

---

## 17.3 Единая история коммуникаций

Для каждого клиента отображается единая Conversation.

История сообщений объединяет все поддерживаемые каналы связи.

Менеджер не должен переключаться между различными интерфейсами в зависимости от канала клиента.

---

## 17.4 Карточка клиента

Карточка клиента отображает:

- основные сведения;
- список Communication Endpoint;
- историю коммуникаций;
- активные обращения;
- пользовательские заметки;
- теги;
- историю изменений.

Карточка клиента является логическим представлением данных Backend.

---

## 17.5 Работа с сообщениями

Менеджер может:

- отправлять сообщения;
- получать сообщения;
- просматривать вложения;
- отвечать клиенту;
- пересылать сообщения;
- использовать шаблоны ответов.

После отправки сообщение передаётся Communication Core.

---

## 17.6 Использование AI Assistant

AI Assistant предоставляет менеджеру:

- рекомендации по ответу;
- краткое содержание длинной переписки;
- поиск информации в базе знаний;
- перевод сообщений;
- исправление текста;
- генерацию вариантов ответа.

Менеджер самостоятельно принимает решение об использовании предложений AI.

---

## 17.7 Работа в реальном времени

Manager Workspace использует WebSocket.

Без обновления страницы должны отображаться:

- новые сообщения;
- изменение статусов;
- уведомления;
- изменение очереди обращений.

---

## 17.8 Архитектурный принцип

Manager Workspace является эталонным интерфейсом работы менеджеров.

Все остальные пользовательские интерфейсы должны использовать те же Backend API и ту же бизнес-логику.

---

# 18. Web Chat

## 18.1 Назначение

Web Chat является встроенным клиентским интерфейсом Communication Platform.

Он предназначен для общения конечных пользователей с организацией через веб-браузер.

---

## 18.2 Архитектурная роль

Web Chat рассматривается как один из Communication Endpoint.

С точки зрения Communication Core Web Chat не отличается от Telegram, WhatsApp, MAX или любого другого канала связи.

---

## 18.3 Reference Client

Web Chat является эталонной реализацией клиентского интерфейса платформы.

Все новые возможности платформы в первую очередь должны поддерживаться Web Chat.

Другие клиентские приложения могут реализовывать только поддерживаемое ими подмножество функций.

---

## 18.4 Основные функции

Web Chat должен обеспечивать:

- подключение клиента;
- отправку сообщений;
- получение сообщений;
- работу с вложениями;
- отображение истории переписки;
- отображение статуса соединения;
- отображение статуса доставки сообщений;
- работу в реальном времени.

---

## 18.5 Работа с AI

Если организацией разрешено использование AI Assistant, Web Chat должен обеспечивать возможность общения клиента с AI.

AI взаимодействует с клиентом посредством стандартного механизма Communication Core.

Специального режима общения с AI не существует.

---

## 18.6 Авторизация клиента

Архитектура должна поддерживать как анонимный режим работы, так и идентифицированных пользователей.

Конкретная модель авторизации определяется настройками организации.

---

## 18.7 Работа через Edge Cluster

При размещении клиента в Российской Федерации Web Chat подключается к Edge Cluster.

Edge Cluster обеспечивает обслуживание соединения и передачу сообщений в Application Cluster посредством VPN Tunnel Service.

Для клиента данный процесс полностью прозрачен.

---

## 18.8 Архитектурный принцип

Web Chat не содержит бизнес-логики.

Вся обработка сообщений выполняется Backend и Communication Core.

Web Chat отвечает исключительно за пользовательский интерфейс и взаимодействие с Backend API.

# 19. Mobile API

## 19.1 Назначение

Mobile API предназначен для взаимодействия мобильных приложений с Backend платформы.

Mobile API использует те же бизнес-процессы и модели данных, что и Web-интерфейсы.

Создание отдельной серверной логики для мобильных приложений не допускается.

---

## 19.2 Архитектурный принцип

Mobile API является специализированным представлением Backend API.

Вся бизнес-логика остаётся общей для:

- Web Chat;
- Manager Workspace;
- SaaS Administration;
- Mobile Application.

Это обеспечивает единое поведение платформы независимо от используемого клиентского приложения.

---

## 19.3 Основные функции

Mobile API предоставляет:

- аутентификацию;
- получение списка Conversation;
- получение истории сообщений;
- отправку сообщений;
- работу с вложениями;
- получение уведомлений;
- получение статусов сообщений;
- работу с AI Assistant;
- синхронизацию данных.

---

## 19.4 Работа в реальном времени

Mobile API должен поддерживать получение событий посредством WebSocket.

При невозможности использования постоянного соединения допускается использование Push Notification совместно с последующей синхронизацией данных.

---

## 19.5 Работа через Edge Cluster

При использовании инфраструктуры Российской Федерации мобильное приложение подключается к Edge Cluster.

Все дальнейшее взаимодействие осуществляется через VPN Tunnel Service и Communication Core.

---

## 19.6 Версионирование

Mobile API должен иметь независимое версионирование.

Изменения API не должны нарушать работу ранее опубликованных мобильных приложений.

---

# 20. Telegram Console

## 20.1 Назначение

Telegram Console является дополнительным пользовательским интерфейсом платформы.

Основная задача Telegram Console — предоставить менеджеру возможность оперативной работы без открытия Web-интерфейса.

Telegram Console не заменяет Manager Workspace.

Она предназначена для выполнения наиболее востребованных операций.

---

## 20.2 Основные сценарии использования

Telegram Console используется для:

- получения уведомлений;
- просмотра новых обращений;
- быстрого ответа клиенту;
- просмотра информации о клиенте;
- получения рекомендаций AI;
- получения ссылок на соответствующие разделы Manager Workspace.

---

## 20.3 Получение уведомлений

При возникновении важных событий Backend может отправлять уведомления менеджеру через Telegram Bot.

Примеры уведомлений:

- новое обращение клиента;
- новое сообщение;
- критическое уведомление;
- ошибка Broadcast;
- завершение Workflow;
- административные сообщения.

Перечень уведомлений определяется настройками пользователя.

---

## 20.4 Ответ клиенту

Менеджер может ответить клиенту непосредственно из Telegram Console.

Последовательность обработки ответа полностью совпадает с обычной перепиской:

1. сообщение получает Backend;
2. сообщение проходит проверки безопасности;
3. сообщение поступает в Communication Core;
4. Communication Core передаёт сообщение соответствующему Adapter;
5. сообщение доставляется клиенту.

Telegram Console не взаимодействует с каналами связи напрямую.

---

## 20.5 Просмотр информации о клиенте

Telegram Console должна обеспечивать быстрый просмотр:

- имени клиента;
- используемого канала;
- краткой истории переписки;
- количества непрочитанных сообщений;
- текущего статуса обращения.

Полная карточка клиента доступна только в Manager Workspace.

---

## 20.6 Использование AI

Менеджер может запросить рекомендации AI непосредственно из Telegram Console.

AI может предоставить:

- краткое содержание диалога;
- рекомендуемый ответ;
- поиск информации в базе знаний;
- перевод сообщения.

Применение рекомендаций AI всегда выполняется менеджером вручную.

---

## 20.7 Ограничения Telegram Console

Telegram Console не предназначена для выполнения административных операций.

Через Telegram Console запрещается:

- управление пользователями;
- изменение настроек организации;
- изменение Workflow;
- изменение параметров безопасности;
- управление каналами связи.

Все административные операции выполняются исключительно через SaaS Administration.

---

## 20.8 Архитектурный принцип

Telegram Console является альтернативным пользовательским интерфейсом.

Она использует те же Backend API, что и остальные приложения платформы.

Никакой отдельной бизнес-логики для Telegram Console не существует.

---

# 21. Frontend

## 21.1 Общие положения

Все пользовательские интерфейсы платформы реализуются с использованием **React** и **Vite**.

Frontend отвечает исключительно за представление данных и взаимодействие с пользователем.

Вся бизнес-логика располагается в Backend.

---

## 21.2 Состав Frontend

Frontend платформы включает следующие независимые приложения:

- SaaS Administration;
- Manager Workspace;
- Web Chat.

Архитектура должна предусматривать возможность подключения новых приложений без изменения Backend.

---

## 21.3 Общая компонентная библиотека

Все интерфейсы используют единую библиотеку компонентов.

Переиспользуемыми должны быть:

- элементы форм;
- таблицы;
- карточки;
- модальные окна;
- элементы навигации;
- средства отображения сообщений;
- уведомления;
- компоненты работы с файлами.

Дублирование компонентов между приложениями не допускается.

---

## 21.4 Архитектура приложений

Каждое приложение должно иметь модульную структуру.

Основные слои:

- Presentation;
- API Client;
- State Management;
- Routing;
- Shared Components.

Бизнес-логика внутри Frontend не размещается.

---

## 21.5 Работа с Backend

Frontend взаимодействует исключительно посредством Backend API.

Запрещается:

- прямой доступ к PostgreSQL;
- выполнение SQL-запросов;
- хранение бизнес-логики;
- принятие решений о правах доступа.

Все проверки выполняются Backend.

---

## 21.6 Работа в реальном времени

Все пользовательские интерфейсы используют WebSocket для получения событий.

При поступлении новых сообщений пользовательский интерфейс обновляется автоматически.

Обновление страницы не требуется.

---

## 21.7 Производительность

Frontend должен обеспечивать:

- ленивую загрузку модулей;
- оптимизацию размеров сборки;
- повторное использование компонентов;
- минимизацию количества сетевых запросов.

---

## 21.8 Адаптивность

Минимально должны поддерживаться:

- Desktop;
- Tablet.

Архитектура должна предусматривать возможность дальнейшей адаптации интерфейсов для мобильных браузеров.

---

## 21.9 Архитектурный принцип

Все Frontend-приложения являются клиентами единой платформы.

Они не содержат собственной бизнес-логики и используют одинаковые Backend API.

Это обеспечивает единое поведение платформы независимо от используемого пользовательского интерфейса.

# 23. Безопасность

## 23.1 Общие положения

Безопасность платформы должна соответствовать современным требованиям к корпоративным SaaS-системам.

Все архитектурные решения должны приниматься с учётом принципа Security by Design.

---

## 23.2 Основные принципы

При проектировании платформы используются следующие принципы:

- минимально необходимые полномочия;
- разделение ответственности;
- защита данных при передаче;
- защита данных при хранении;
- аудит действий;
- обязательная аутентификация пользователей;
- серверная проверка полномочий.

---

## 23.3 Передача данных

Все соединения должны использовать TLS.

Передача данных между Edge Cluster и Application Cluster осуществляется через защищённый VPN Tunnel Service с взаимной аутентификацией.

---

## 23.4 Управление доступом

Доступ определяется совокупностью:

- роли пользователя;
- принадлежности организации;
- типа операции;
- состояния объекта.

Frontend не участвует в принятии решений о предоставлении доступа.

---

## 23.5 Защита API

Backend обязан реализовать:

- проверку токенов доступа;
- защиту от повторной отправки запросов;
- ограничение частоты запросов (Rate Limiting);
- защиту от массового перебора;
- серверную валидацию всех входящих данных.

---

## 23.6 Защита AI

AI Platform должна работать в режиме ограниченных полномочий.

AI запрещается:

- выполнять произвольный код;
- выполнять SQL-запросы;
- получать доступ к внутренним сервисам;
- изменять данные напрямую;
- использовать секреты платформы.

Все действия AI проходят через Backend API.

---

## 23.7 Управление секретами

Пароли, ключи API, токены и иные секреты не должны храниться в исходном коде приложения.

Использование централизованного механизма управления секретами является обязательным.

---

## 23.8 Аудит безопасности

Должны регистрироваться:

- входы пользователей;
- ошибки аутентификации;
- административные действия;
- изменение ролей;
- изменение конфигурации;
- обращения AI к Backend API;
- выполнение Workflow.

Журнал аудита должен быть защищён от изменения пользователями.

---

## 23.9 Соответствие законодательству

Архитектура должна обеспечивать возможность соблюдения требований законодательства Российской Федерации в части обработки персональных данных.

При использовании зарубежного кластера взаимодействие между региональными площадками осуществляется посредством VPN Tunnel Service.

Конкретная модель обработки персональных данных определяется политикой эксплуатации платформы и требованиями законодательства на момент внедрения.

# 24. Мониторинг и журналирование

## 24.1 Назначение

Платформа должна обеспечивать централизованный сбор информации о состоянии всех компонентов.

Мониторинг является обязательной частью архитектуры.

---

## 24.2 Логирование

Все серверные компоненты используют единый формат журналирования.

Минимально регистрируются:

- время;
- компонент;
- уровень сообщения;
- идентификатор запроса;
- пользователь;
- организация;
- описание события.

---

## 24.3 Метрики

Для каждого компонента должны собираться метрики производительности.

Минимально:

- количество запросов;
- среднее время обработки;
- количество ошибок;
- использование памяти;
- использование процессора;
- количество активных соединений;
- длина очередей.

---

## 24.4 Health Check

Каждый серверный компонент предоставляет endpoint проверки работоспособности.

Health Check используется системой оркестрации и мониторинга.

---

## 24.5 Трассировка запросов

Каждый внешний запрос получает уникальный идентификатор.

Идентификатор сохраняется на протяжении всего жизненного цикла обработки запроса.

Это позволяет отслеживать прохождение запроса через все компоненты платформы.

---

## 24.6 Мониторинг Workflow

Для каждого Workflow отображаются:

- количество запусков;
- успешные выполнения;
- ошибки;
- среднее время исполнения;
- активные экземпляры.

---

## 24.7 Мониторинг AI

Должны отображаться:

- количество запросов к AI;
- используемые модели;
- время ответа;
- ошибки;
- стоимость использования (при наличии внешних LLM).

---

## 24.8 Архитектурный принцип

Средства мониторинга не должны влиять на бизнес-логику платформы.

Их отключение не должно приводить к отказу основных функций Communication Platform.

# 25. Нефункциональные требования

## 25.1 Общие положения

Настоящий раздел определяет требования к качественным характеристикам Communication Platform.

Нефункциональные требования являются обязательными для всех компонентов системы независимо от их назначения.

---

## 25.2 Производительность

Архитектура платформы должна обеспечивать обработку пользовательских операций без заметных задержек.

При нормальной нагрузке время ответа Backend API должно соответствовать следующим требованиям:

| Операция | Целевое время |
|-----------|---------------:|
| Авторизация | ≤ 1 сек |
| Получение списка диалогов | ≤ 1 сек |
| Получение истории сообщений | ≤ 2 сек |
| Отправка сообщения | ≤ 1 сек |
| Создание Broadcast | ≤ 3 сек |
| Ответ AI (без учёта времени LLM) | ≤ 500 мс |
| Получение уведомлений | ≤ 1 сек |

Время ответа внешних LLM в данные показатели не входит.

---

## 25.3 Масштабируемость

Архитектура должна поддерживать горизонтальное масштабирование следующих компонентов:

- Backend API;
- Communication Core;
- Adapter;
- WebSocket Gateway;
- AI Platform;
- FBP Engine.

Добавление новых экземпляров компонентов не должно требовать изменения прикладной логики.

---

## 25.4 Отказоустойчивость

Кратковременная недоступность одного из компонентов не должна приводить к полной остановке платформы.

Особенно это касается:

- AI Platform;
- FBP Engine;
- отдельных Adapter;
- VPN Tunnel Service.

Communication Core должен продолжать обработку сообщений даже при деградации вспомогательных сервисов.

---

## 25.5 Доступность

Архитектура должна предусматривать возможность достижения высокой доступности посредством стандартных средств оркестрации контейнеров.

Конкретные SLA определяются эксплуатационной документацией.

---

## 25.6 Сопровождаемость

Кодовая база должна быть организована таким образом, чтобы:

- каждый модуль имел ограниченную область ответственности;
- изменения были локализованы;
- тестирование выполнялось независимо;
- документация автоматически обновлялась при изменении API.

---

## 25.7 Расширяемость

Добавление нового канала связи, нового Workflow, новой AI-модели или нового пользовательского интерфейса не должно требовать изменения архитектуры платформы.

---

## 25.8 Переносимость

Платформа должна поддерживать развёртывание в любом Kubernetes-совместимом окружении.

Использование инфраструктурно-зависимых решений должно быть минимизировано.

---

## 25.9 Контейнеризация

Все серверные компоненты должны поставляться в виде OCI/Docker-совместимых контейнеров.

Каждый компонент должен иметь независимый Dockerfile.

---

## 25.10 Конфигурирование

Все параметры окружения должны храниться во внешней конфигурации.

Изменение конфигурации не должно требовать изменения исходного кода.

Все компоненты платформы должны сопровождаться автоматизированными тестами.

Проект должен содержать следующие категории тестов:

- Unit Tests;
- Integration Tests;
- End-to-End Tests.

---

## 26.3 Unit Tests

# Приложение Б. Размещение зарубежного кластера

| Критерий | Европа (например, Германия, Нидерланды, Финляндия) | СНГ (например, Казахстан, Армения) |
|----------|-----------------------------------------------------|------------------------------------|
| Задержка для пользователей РФ | Средняя | Минимальная |
| Соответствие европейским стандартам защиты данных | Высокое | Зависит от страны |
| Доступность облачной инфраструктуры | Максимальная | Ограниченная |
| Выбор провайдеров | Очень широкий | Ограниченный |
| Интеграция с международными сервисами | Наиболее удобна | Может быть ограничена |
| Стоимость эксплуатации | Выше | Ниже |
| Юридическая устойчивость | Выше для международного SaaS | Может зависеть от локального законодательства |
| Масштабирование | Практически без ограничений | Ограничено рынком инфраструктуры |

**Рекомендуемый вариант:** размещение основного **Application Cluster** в одной из стран Европейского союза с развитой облачной инфраструктурой. Это обеспечивает максимальную совместимость с международными сервисами, высокую доступность оборудования и лучшую перспективу масштабирования глобального SaaS. При необходимости работа с пользователями Российской Федерации осуществляется через **Edge Cluster** и **VPN Tunnel Service**, что соответствует принятой архитектурной модели.
