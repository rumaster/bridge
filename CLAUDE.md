# CLAUDE.md — рабочие принципы для этого репозитория

## Спецификация не является истиной в последней инстанции

Документы в `docs/` (в т.ч. ТЗ `docs/MessengerBridge_TZ.md`) — это проектные намерения, а **не** непогрешимый источник правды. Спецификации могут содержать ошибки, устаревать или расходиться с обоснованными продуктовыми/инженерными решениями.

Правила:

- Если код и спецификация конфликтуют — не «подгоняй» решение под спецификацию молча. Прими обоснованное решение и **обнови спецификацию**, чтобы она соответствовала реализации.
- Любое сознательное отклонение от ТЗ фиксируй прямо в затронутом разделе ТЗ как пометку «Ревизия (дата)» с краткой причиной и владельцем решения.
- Не считай формулировку ТЗ блокирующим ограничением; при необходимости меняй ТЗ вместе с кодом в том же изменении.

## Knowledge Base (редизайн 2026-07-14, ревизия 2026-07-15)

- Документы KB — это текстовые инструкции для AI Assistant: **название**, **контент**, **список ключевых (поисковых) фраз** (по одной на строку) и **теги** (по одному на строку). Загрузки файлов и статусов индексации нет.
- **Теги (добавлены 2026-07-15)** — грубый предфильтр «в каком разделе знаний искать» под узел «Поиск в Knowledge Base» контракта Workflow 2.0. В эмбеддинге **не участвуют**: тег сужает множество документов ДО векторного поиска и не влияет на расстояния внутри него. Смешивать их с семантикой нельзя.
- Поиск живёт в Backend, а не в SVC-AI: два маршрута поверх одного pgvector-запроса — внутренний `POST /knowledge:search` (контракт C3.kb, вход — готовый эмбеддинг от SVC-AI, вне префикса `/api/v1`) и `POST /api/v1/knowledge/documents:search` для узла схемы (вход — текстовые фразы и теги, вектор считает Backend).
- Эмбеддинг считается **по каждой ключевой фразе**, а не по контенту, — **при сохранении** (создание/изменение) в `services/backend` (модуль `knowledge-base`), и пишется в `knowledge_chunks` (pgvector, `vector(1536)`): одна фраза → одна строка, где `embedding` — вектор фразы, `content` — контент документа (уходит в промпт), `metadata.source` — сама фраза. Документ без фраз чанков не имеет и не находится. Образец — публичный репозиторий `rumaster/fbp-engine` («Экспертиза»).
- **Инвариант**: модель эмбеддингов и размерность (1536) у Backend (документы) и ai-platform (запросы) должны совпадать. Держи `EMBEDDING_PROVIDER` / `LLM_EMBEDDING_MODEL_NAME` (и ключи провайдера) синхронными у обоих сервисов. При отсутствии провайдера обе стороны используют один и тот же детерминированный фолбэк-эмбеддинг.

## Деплой на стенды (ручные GitHub Actions)

Стенды раскатываются **покомпонентно и вручную** — двумя `workflow_dispatch`-экшенами
(вкладка Actions, кнопка «Run workflow»). Автодеплоя по push нет намеренно: что и когда
едет на стенд, решает человек.

| Экшен | Файл | Зачем |
|---|---|---|
| **Deploy (ручной)** | `.github/workflows/deploy.yml` | Пересобрать и перезапустить выбранные сервисы |
| **Миграции БД (ручной)** | `.github/workflows/migrate.yml` | Прогнать миграции схемы (отдельно от кода) |

### Как это устроено

Образы собираются **на раннере GitHub**, пушатся в **GHCR**, стенд их только **тянет**.
Сборка на стенде запрещена: RF edge — ~908 МБ RAM, `npm ci`+`vite build` там уходят в
OOM (предыдущий edge-хост так и умер). Поэтому `remote-deploy.sh` вызывает
`up -d --no-build` — если образ не подтянулся, деплой честно падает, а не пытается
собрать его на месте.

У **каждого образа свой тег** `BRIDGE_TAG_<IMAGE>`, который деплой прописывает в
env-файл стенда (`.env` / `.env.rf`). Это и есть источник правды о задеплоенных
версиях: сервисы могут жить на разных версиях (в этом и смысл покомпонентного
деплоя), а ручной `docker compose up -d` на стенде поднимет ровно то же самое.
Без тега (локальная разработка) образ резолвится в `:local`, и обычный
`docker compose up --build` работает как раньше.

Стенд после деплоя стоит на **detached HEAD** ровно того коммита, который задеплоен, —
`git log -1` на стенде отвечает на вопрос «что тут сейчас едет».

### Компоненты

Список стендов и компонентов — в **`deploy/components.json`** (единственный источник
правды; workflow читает его). Добавляешь сервис — правишь этот файл, а не YAML.

- **app** (Application Cluster, `85.120.252.39`): `backend`, `ai-platform`,
  `integration-platform`, `broadcast-platform`, `notification-platform`, `mobile-api`,
  `fbp-engine`, `saas-admin`, `manager-workspace`, `web-chat`, `c7-ws`, `edge-vpn-app`,
  `awg-server`, `telegram-console`
- **edge-rf** (RF Edge, 152-ФЗ, `51.21.218.232`): `edge-gateway`, `web-chat`,
  `awg-client`, `mail-provision`

`components` принимает список через запятую (`backend,web-chat`) или `all`.

### Как пользоваться

1. Actions → **Deploy (ручной)** → Run workflow.
2. `target` — стенд, `components` — что реально менялось, `ref` — ветка/тег/SHA
   (пусто = ветка запуска), `dry_run` — только показать план.
3. План (сервисы, образы, профили, теги) виден в Summary джобы.

Порядок с миграциями — обычный: **аддитивная миграция → деплой кода**. Для
несовместимых изменений схемы разноси на два шага (expand/contract), иначе
между миграцией и деплоем стенд полежит.

### Грабли, о которых надо знать

- **Общий образ ≠ общий сервис.** Один образ шарят несколько сервисов:
  `edge-gateway` ← `c7-ws`, `edge-vpn-app` (app) и `edge-gateway` (edge-rf);
  `awg` ← `awg-server`, `awg-client`; `db-tools` ← `migrate`, `seed`, `migrate-rf`.
  Деплой одного двигает общий `BRIDGE_TAG_*`, и соседний сервис подхватит ту же
  версию при следующем `up -d`. Workflow предупреждает об этом в Summary — если
  менялся общий код, деплойте их вместе.
- **`mail-provision` на edge-rf сейчас поднят standalone** (контейнер
  `bridge-mail-provision`), а не через compose-профиль `mail` — обход OOM. Деплой
  этого компонента поднимет второй контейнер и подерётся за порт 3300. Сперва
  погасите standalone: `docker rm -f bridge-mail-provision`. Техдолг.
- **`down` откатывает ровно одну миграцию** (`node-pg-migrate` берёт `count=1` для
  `down`; для `up` — все). Требует вписать имя стенда в `confirm_down`.
- **`main` в этом репозитории — не мейнлайн.** Разработка идёт в
  `issue-1-17113a10fe0c`; `main` заморожен на старом коммите. Деплоить надо из
  ветки разработки.

### Подготовка стенда (если поднимаете новый)

Рабочая копия должна быть обычным git-чекаутом, где проходит
`git fetch origin <sha> && git checkout --detach FETCH_HEAD`, а env-файл лежит рядом
и **gitignored** (переживает чекаут). Нужны секреты репозитория:

| Секрет | Что |
|---|---|
| `DEPLOY_SSH_KEY` | Приватный ed25519-ключ деплоя (публичный — в `authorized_keys` стенда) |
| `APP_HOST` / `RF_HOST` | Адреса стендов |
| `APP_SSH_KNOWN_HOSTS` / `RF_SSH_KNOWN_HOSTS` | Публичные ключи хостов (`StrictHostKeyChecking=yes`, без TOFU) |

GHCR-доступ стенду не выдаётся заранее: workflow делает `docker login` эфемерным
`GITHUB_TOKEN` этого запуска (токен уходит **через stdin**, не через argv — иначе
светился бы в `ps`) и `docker logout` в конце.

## Контракт API

- OpenAPI бэкенда генерируется из кода: `packages/contracts/openapi/backend-core/openapi.json`.
- Клиент `packages/api-client` генерируется из этого JSON (`npm run generate`), синхронность проверяется `generate:check`.
- Замороженный гейт CP-9 (`packages/contracts/cp9-svc-api-acceptance.v1.json`) фиксирует `generated_operation_count` / `generated_path_count`. При добавлении/удалении маршрутов `/api/v1` обновляй эти счётчики и добавляй запись в `x-revisions`.
